= About Loki log store
include::_attributes/common-attributes.adoc[]
:context: about-loki-log-store

[role="_abstract"]
Loki is an optional component of OpenShift Logging that provides local log storage for short-term troubleshooting. Loki is a horizontally scalable, highly available log aggregation system that uses Kubernetes labels to organize and query logs.

[id="what-loki-is_{context}"]
== What Loki is

Loki is a log aggregation system inspired by Prometheus. Unlike traditional logging systems that index the full contents of every log line, Loki indexes only a small set of metadata labels extracted from Kubernetes resources. The actual log content is compressed and stored in object storage such as Amazon S3, Google Cloud Storage, or Azure Blob Storage.

This label-based indexing approach makes Loki:

* **Cost-effective**: Small index size reduces storage and query costs
* **Horizontally scalable**: Add more ingesters or queriers as log volume grows
* **Kubernetes-native**: Uses Kubernetes labels you already have for pod, namespace, and container selection

[id="how-loki-uses-kubernetes-labels_{context}"]
== How Loki uses Kubernetes labels

Loki organizes logs into **streams**, where each stream is identified by a unique set of Kubernetes labels. When Vector sends logs to Loki, it automatically extracts labels from Kubernetes metadata:

* **kubernetes_namespace_name**: The namespace where the pod runs
* **kubernetes_pod_name**: The name of the pod
* **kubernetes_container_name**: The container within the pod
* **kubernetes_host**: The node where the pod runs
* **log_type**: Whether the log is application, infrastructure, or audit

For infrastructure logs from systemd, Loki also extracts:

* **systemd_unit**: The systemd unit that generated the log (for example, `kubelet.service`)

These Kubernetes labels enable you to select and filter logs exactly as you would select pods with `kubectl`. For example, you can query:

* All logs from a specific namespace
* Logs from a particular pod
* All application logs across all namespaces
* Infrastructure logs from the kubelet service on specific nodes

[id="loki-streams-and-labels_{context}"]
== Streams and labels

Loki stores logs as **streams**. Each unique combination of labels creates a separate stream. For example:

* One stream for application logs from `pod-1` in `namespace-a`
* A different stream for application logs from `pod-2` in `namespace-a`
* Another stream for infrastructure logs from `kubelet.service` on `node-1`

When you query Loki using LogQL (Loki's query language), you first select streams by their labels, then filter the log content within those streams. This two-step process mirrors how Kubernetes works: select resources by labels, then examine their content.

[id="how-loki-works_{context}"]
== How Loki works

The Loki data flow:

1. **Collection**: Vector collects logs and extracts Kubernetes labels
2. **Ingestion**: Loki's distributor receives logs and forwards them to ingesters
3. **Temporary storage**: Ingesters hold logs in memory temporarily
4. **Compression and storage**: Ingesters compress logs into chunks and store them in object storage
5. **Indexing**: Only the labels (metadata) are indexed—not the log content
6. **Querying**: When you query, Loki uses the index to find relevant streams, then decompresses chunks to return matching log lines

[id="short-term-storage-design_{context}"]
== Short-term storage design

The OpenShift Logging configuration of Loki is designed for short-term log storage and fast troubleshooting, not long-term archival.

Key characteristics:

* **30-day maximum retention**: The default OpenShift configuration retains logs for up to 30 days
* **Optimized for recent queries**: Performance is best when querying recent logs (last few hours or days)
* **Short-term troubleshooting**: Ideal for debugging current issues, not historical analysis

[IMPORTANT]
====
For long-term storage, compliance archives, or queries spanning more than 30 days, forward logs to an external log management platform in addition to or instead of using Loki.
====

[id="loki-components_{context}"]
== Loki components

When you deploy Loki in OpenShift using the LokiStack custom resource, you deploy several components:

Distributor:: Receives logs from Vector and forwards them to ingesters

Ingester:: Temporarily holds logs in memory, then compresses and stores them as chunks in object storage

Querier:: Fetches data from the index and object storage to answer queries

Query Frontend:: Processes and optimizes queries before sending them to queriers

Ruler (optional):: Evaluates alerting and recording rules on log data

The Loki Operator manages these components and their scaling based on your LokiStack configuration.

[id="querying-loki_{context}"]
== Querying Loki with LogQL

Loki uses LogQL, a query language inspired by PromQL (Prometheus Query Language). LogQL queries have two parts:

1. **Label selection**: Use Kubernetes labels to select streams
2. **Content filtering**: Filter log lines by content within selected streams

Example queries:

* Select all application logs from namespace `my-app`:
+
[source,logql]
----
{log_type="application", kubernetes_namespace_name="my-app"}
----

* Find errors in a specific pod:
+
[source,logql]
----
{kubernetes_namespace_name="my-app", kubernetes_pod_name="web-1"} |= "error"
----

* Query infrastructure logs from kubelet:
+
[source,logql]
----
{log_type="infrastructure", systemd_unit="kubelet.service"}
----

You can query Loki through the OpenShift web console (if you have the Cluster Observability Operator installed), Grafana, or the Loki API directly.
