[role="_abstract"]
OpenShift Logging supports three common deployment scenarios based on which components you install. Each scenario provides different capabilities for log collection, storage, and visualization.

[id="scenario-components-overview_{context}"]
== Scenario components overview

OpenShift Logging uses a modular architecture where you choose which components to deploy:

[cols="3,2,5",options="header"]
|===
|Component |Required? |Function

|Vector collector
|Yes
|Collects logs from all pods and forwards to destinations

|Loki log store
|No
|Stores logs locally for short-term querying (30 days max)

|Cluster Observability Operator
|No
|Provides UI visualization in OpenShift web console
|===

The three most common deployment patterns combine these components in different ways.

[id="scenario-1-vector-only_{context}"]
== Scenario 1: Vector only (forward-only deployment)

**Components**: Vector collector

**What this scenario provides**:

* Log collection from all pods, containers, and infrastructure
* Log forwarding to external log management platforms
* No local log storage in the cluster
* Transform and filter logs before forwarding

**Common configurations**:

* Forward all logs to Amazon CloudWatch
* Send logs to an existing Splunk deployment
* Route logs to Kafka topics for further processing
* Forward to multiple destinations simultaneously (for example, CloudWatch and S3)

**What you manage**:

* One operator: Red Hat OpenShift Logging Operator
* One custom resource: `ClusterLogForwarder` to configure Vector
* No object storage setup in your cluster
* External log platform storage and retention policies

In this scenario, your cluster does not store logs locally. All log data leaves the cluster and goes to external systems. You query and visualize logs using those external platforms (Splunk UI, CloudWatch Logs Insights, Grafana connected to external Loki, and so on).

[id="scenario-2-vector-loki_{context}"]
== Scenario 2: Vector + Loki

**Components**: Vector collector + Loki log store

**What this scenario provides**:

* Log collection from all pods, containers, and infrastructure
* Local log storage in Loki for up to 30 days
* Query logs with LogQL using external tools (Grafana, Loki CLI)
* Optional forwarding to external systems in addition to local storage

**Common configurations**:

* Store logs in Loki for troubleshooting + forward to CloudWatch for compliance
* Local queries for recent issues using Grafana
* Keep 30 days local, forward everything to long-term archive
* Short-term operational visibility without external tool dependencies

**What you manage**:

* Two operators: Red Hat OpenShift Logging Operator and Loki Operator
* Two custom resources: `ClusterLogForwarder` and `LokiStack`
* Object storage backend for Loki (Amazon S3, Google Cloud Storage, Azure Blob, or compatible)
* Loki retention policies (up to 30 days)

In this scenario, logs are stored both locally (in Loki) and optionally forwarded externally. You query local logs using external tools that understand the Loki API, such as Grafana. The OpenShift web console does not have log querying capabilities unless you also install the Cluster Observability Operator.

[id="scenario-3-vector-loki-coo_{context}"]
== Scenario 3: Vector + Loki + COO (full observability stack)

**Components**: Vector collector + Loki log store + Cluster Observability Operator

**What this scenario provides**:

* Log collection from all pods, containers, and infrastructure
* Local log storage in Loki for up to 30 days
* Query logs directly in the OpenShift web console
* Correlate logs with metrics and distributed traces
* Multi-tenant monitoring per namespace
* Optional forwarding to external systems

**Common configurations**:

* Complete observability in OpenShift console
* Log/metric/trace correlation for troubleshooting
* Platform teams providing observability-as-a-service to application teams
* Namespace-scoped log queries for multi-tenant clusters

**What you manage**:

* Three operators: Red Hat OpenShift Logging Operator, Loki Operator, and Cluster Observability Operator
* Multiple custom resources: `ClusterLogForwarder`, `LokiStack`, `UIPlugin`, and optionally `MonitoringStack`
* Object storage backend for Loki
* Console UI plugin configurations
* Multi-tenant monitoring stack configurations (if used)

In this scenario, the OpenShift web console becomes your primary interface for log queries. A "Logs" tab appears where you can write LogQL queries, filter by namespace or pod, and correlate log data with metrics and traces without leaving the browser.

[id="choosing-your-scenario_{context}"]
== Determining which scenario fits your needs

The choice between these scenarios depends on several factors:

* **Need for local log queries**: If you never query logs locally and always use an external platform, Scenario 1 may be sufficient.
* **Console integration requirements**: If you want to query logs without leaving the OpenShift web console, you need Scenario 3.
* **Object storage availability**: Scenarios 2 and 3 require an object storage backend (S3-compatible storage). If setting up object storage is not feasible, Scenario 1 is your only option.
* **Signal correlation needs**: If troubleshooting requires correlating logs with metrics and traces, Scenario 3 provides built-in correlation in the console.
* **Multi-tenancy**: If you manage a cluster with multiple teams needing namespace-scoped observability, Scenario 3 provides the necessary isolation and customization.

For detailed guidance on choosing a scenario, including resource requirements, cost implications, and decision criteria, see the Plan section.
