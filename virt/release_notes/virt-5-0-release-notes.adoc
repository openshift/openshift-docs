// Installation and update

//CNV-67900
Boot source image support for heterogeneous clusters is generally available::
+
After you enable the `enableMultiArchBootImageImport` feature gate, {VirtProductName} creates architecture-specific boot sources for each supported architecture, such as `rhel9-amd64` and `rhel9-arm64`. You can also specify the architecture for standalone data volumes and virtual machines. For more information, see xref:../../virt/storage/virt-boot-source-image-heterogeneous-clusters.adoc#virt-boot-source-image-heterogeneous-clusters[Heterogeneous cluster support].
+
link:https://issues.redhat.com/browse/CNV-67900[CNV-67900]

//CNV-81291
The `virt-platform-autopilot` controller is generally available::
+
The `virt-platform-autopilot` controller lowers deployment complexity by automatically enforcing configuration best practices across {VirtProductName} and adjacent Operators, such as the Kube Descheduler Operator and Cluster Observability Operator. It simplifies initial setup and maintains safe, optimal settings for swap readiness, load-aware balancing, and enhanced cluster observability to help ensure long-term stability across version upgrades.
+
link:https://issues.redhat.com/browse/CNV-81291[CNV-81291]

Self-service Technical Supportability Review::

You can use the self-service Technical Supportability Review (TSR) on the Red{nbsp}Hat Customer Portal to validate your cluster configuration against Red{nbsp}Hat common practices. The TSR performs hundreds of checks across the {product-title} platform, including {VirtProductName}, and coverage is continually expanding.

For more information, see link:https://access.redhat.com/support/cases/#/analyze[Technical Supportability Review with AI tool] and link:https://access.redhat.com/solutions/7141255[Red{nbsp}Hat Technical Supportability Review with AI: Proactive AI-Driven Cluster Assessments for {product-title}].

The `virt-platform-autopilot` controller replaces the `wasp-agent` component::

== Deprecated features

The `HotplugVolume` feature gate is deprecated::

The `HotplugVolume` feature gate, which allows you to add storage without restarting your VM, is deprecated and will be removed in a future release. This feature gate will be replaced by `DeclarativeHotplugVolumes`.
+
[NOTE]
====
`DeclarativeHotplugVolumes` does not support hot plugging ephemeral volumes. Ephemeral volumes are hot plugged to a VMI and do not persist in the owner VM. Existing ephemeral volumes that are hot plugged are automatically detached after you switch to the `DeclarativeHotplugVolumes` feature gate.
====
+
link:https://issues.redhat.com/browse/CNV-73301[CNV-73301]

//CNV-98500
The `pc-q35-rhel7.x.0` and `pc-q35-rhel8.x.0` machine types are deprecated::
+
The `pc-q35-rhel7.x.0` and `pc-q35-rhel8.x.0` machine types have been deprecated since {VirtProductName} 4.13. They will be removed in a future release as part of the move to Red{nbsp}Hat Enterprise Linux (RHEL) 10 user space. Update your virtual machines (VMs) to the `pc-q35-rhel9.x.0` machine type. Updating the machine type requires a VM restart, so plan for downtime.
+
link:https://issues.redhat.com/browse/CNV-98500[CNV-98500]

[id="virt-5-0-bug-fixes_{context}"]
== Fixed issues

Detached disks are no longer deleted together with the original virtual machine::
+
Before this update, when you detached a disk from a virtual machine (VM), the `DataVolume` object retained a stale owner reference to the original VM. As a consequence, if you deleted the original VM, garbage collection deleted the `DataVolume` object and its underlying persistent volume claim (PVC). This caused data loss even when the disk was attached to a different VM. With this release, {VirtProductName} updates the owner reference when you detach a disk, so the `DataVolume` object no longer references the original VM. As a result, a detached disk and its PVC are preserved when you delete the VM that the disk was originally attached to.
+
link:https://redhat.atlassian.net/browse/CNV-71659[CNV-71659]

Node labels remain after uninstalling {VirtProductName}::
Uninstalling {VirtProductName} does not remove the `feature.node.kubevirt.io` node labels that {VirtProductName} creates. As a consequence, nodes can still appear as if they are configured for virtualization workloads.
+
To work around this problem, manually remove the `feature.node.kubevirt.io` labels from affected nodes after you uninstall {VirtProductName}.
+
link:https://issues.redhat.com/browse/CNV-38543[CNV-38543]

//CNV-61066: The underlying bug, CNV-79378, is open and targeted at CNV v5.1.0.
[id="virt-4-22-ki-virtualization_{context}"]
Live migration fails when VM names exceed 47 characters::
Live migration fails if a virtual machine name exceeds 47 characters. As a consequence, you cannot live migrate VMs with longer names.
+
To work around this problem, use VM names that are 47 characters or fewer when you create VMs that you plan to live migrate.
+
link:https://issues.redhat.com/browse/CNV-61066[CNV-61066]

//CNV-68996
Duplicate boot sources remain after you enable multi-architecture boot image import::
If you enable the `spec.featureGates.enableMultiArchBootImageImport` feature gate after boot sources are imported, {VirtProductName} recreates the boot source import resources by using architecture-suffixed names. The names depend on the architectures that the cluster supports, for example `fedora-amd64`, `fedora-arm64`, and `fedora-s390x`. The earlier resources, which have no architecture suffix, remain in the `openshift-virtualization-os-images` namespace. As a consequence, duplicate boot sources are displayed in the web console and in the CLI. Storage usage can also increase, because the extra persistent volume claims (PVCs) and volume snapshots are still present.
+
To work around this problem, delete the leftover boot source resources. First, identify the active `DataSource` objects, which are the objects that resolve to the PVC or volume snapshot that you want to keep. Then, delete the stale `DataSource` objects and the PVCs and volume snapshots that they reference. As a result, only the architecture-suffixed boot sources remain.
+
link:https://issues.redhat.com/browse/CNV-68996[CNV-68996]
