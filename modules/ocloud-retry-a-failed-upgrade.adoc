= Retry a failed upgrade

[role="_abstract"]
You can retry a failed upgrade by reverting the `ProvisioningRequest` custom resource to the original `ClusterTemplate` version, waiting for the cluster to stabilize, and then re-triggering the upgrade. The retry procedure differs between single-node image-based upgrades and multi-node ClusterVersion upgrades.

.Prerequisites

* The `UpgradeCompleted` condition on the `ProvisioningRequest` CR shows `reason: Failed` or `reason: TimedOut`.

.Procedure

For single-node image-based upgrades:

. Wait for the automatic rollback to complete. The IBGU plan includes `AbortOnFailure` actions that handle rollback and cleanup automatically. The `UpgradeCompleted` condition shows `reason: Failed` with details in the message.

. Revert the `ProvisioningRequest` CR to the original `ClusterTemplate` version by running the following command:
+
[source,terminal]
----
$ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateName":"<template_name>","templateVersion":"<original_version>"}}'
----
+
where:
+
--
`<uuid>`:: Specifies the UUID of the `ProvisioningRequest` CR for the target cluster.
`<template_name>`:: Specifies the template name, such as `sno-ran-du`.
`<original_version>`:: Specifies the original `ClusterTemplate` version, such as `v4-Y-Z-1`.
--

. Wait for the `ProvisioningRequest` CR to return to `provisioningPhase: fulfilled`.

. Re-trigger the upgrade by updating the `ProvisioningRequest` CR to the target `ClusterTemplate` version again by running the following command:
+
[source,terminal]
----
$ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateName":"<template_name>","templateVersion":"<target_version>"}}'
----
+
where:
+
--
`<target_version>`:: Specifies the new `ClusterTemplate` version for the target release.
--

For multi-node ClusterVersion upgrades:

. Investigate the spoke cluster to determine the root cause of the failure. Check the `UpgradeCompleted` condition message for details, which may include Cluster Version Operator (CVO) conditions.

. If the cluster is still on the original version and ready to retry:
+
.. Revert the `ProvisioningRequest` CR to the original `ClusterTemplate` version using the same `oc patch` command shown above.
.. Wait for `provisioningPhase: fulfilled`.
.. Update the `ProvisioningRequest` CR to the target `ClusterTemplate` version again to reattempt the upgrade.

. If the administrator completed the upgrade to the target version outside of the O-Cloud Manager:
+
.. Add or update a `ManagedCluster` label through the `ProvisioningRequest` `clusterInstanceParameters` to trigger reconciliation:
+
[source,terminal]
----
$ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateParameters":{"clusterInstanceParameters":{"extraLabels":{"ManagedCluster":{"upgrade-reconcile":"true"}}}}}}'
----
+
The O-Cloud Manager detects the new cluster version and transitions the `ProvisioningRequest` CR to `provisioningPhase: fulfilled`.

.Verification

* Verify that the upgrade retry succeeds by monitoring the `UpgradeCompleted` condition by running the following command:
+
[source,terminal]
----
$ oc get provisioningrequests.clcm.openshift.io <uuid> \
  -o jsonpath='{.status.conditions[?(@.type=="UpgradeCompleted")]}'
----
+
A `reason: Completed` with `status: "True"` indicates the upgrade succeeded.
