= Configuring the HardwareConfig CR for a Telecom Grandmaster clock on Intel Granite Rapids-D hardware

[role="_abstract"]
Configuring an Intel Granite Rapids-D (GNR-D) Telecom Grandmaster (T-GM) deployment requires that you create a `HardwareConfig` custom resource (CR) in addition to the `PtpConfig` CR.
The `HardwareConfig` CR defines the hardware parameters for the deployment, including GNSS initialization and the relationships between the hardware cards in the server.
The `HardwareConfig` CR references named hardware profiles through the `hardwareSpecificDefinitions` field, which provide predefined configuration for specific hardware so that you do not set each parameter manually.
You can adjust holdover thresholds, GNSS source settings, and DPLL parameters in the `HardwareConfig` CR without requiring kernel or firmware upgrades.

.Prerequisites

* You have installed the {product-title} CLI (`oc`).
* You have logged in as a user with `cluster-admin` privileges.
* You have installed the PTP Operator.
* You have applied a `PtpConfig` custom resource (CR) for Telecom Grandmaster configuration on Intel Granite Rapids-D hardware, as described in "Configuring linuxptp services as a Telecom Grandmaster clock on Intel Granite Rapids-D hardware". The `relatedPtpProfileName` value in the `HardwareConfig` CR must match the profile name in that `PtpConfig` CR.
* You have Dell PowerEdge XR8720t hardware with a NAC adapter and 2 Carter Flat NICs installed.
* You have connected a GNSS antenna to the NAC adapter with clear sky view.

.Procedure

. Create a `HardwareConfig` custom resource (CR) YAML file named `hardwareconfig-tgm.yaml` with the following content:
+
[source,yaml,subs="attributes+"]
----
apiVersion: ptp.openshift.io/v2alpha1
kind: HardwareConfig
metadata:
  name: gnrd-tgm
  namespace: openshift-ptp
spec:
  profile:
    name: gnrd-tgm
    clockType: T-GM
    clockChain:
      structure:
        - name: nac
          hardwareSpecificDefinitions: dell/XR8720t
          dpll:
            holdoverParameters:
              maxInSpecOffset: 100
              localMaxHoldoverOffset: 1500
              localHoldoverTimeout: 14400
        - name: cf1
          hardwareSpecificDefinitions: intel/e830
          dpll:
            networkInterface: enp108s0f0np0
        - name: cf2
          hardwareSpecificDefinitions: intel/e830
          dpll:
            networkInterface: enp110s0f0np0
      behavior:
        sources:
          - name: GNSS
            sourceType: gnss
            subsystem: nac
            gnssConfig:
              init:
                antennaVoltage: true
                constellations:
                  - GPS
                  - Galileo
                survey:
                  observationTime: 86400
                  accuracy: 1
  relatedPtpProfileName: grandmaster
----
+
where:
+
--
`structure`:: Lists each timing subsystem in the clock chain. For each entry, set `name`, the `hardwareSpecificDefinitions` behavior profile for the hardware, and the `dpll` parameters. Use `dell/XR8720t` for the onboard NAC subsystem and `intel/e830` for each Carter Flat card.
`networkInterface`:: Specifies the Carter Flat interface for the subsystem. The example values `enp108s0f0np0` and `enp110s0f0np0` are the {op-system-base} 10 names. Replace them with your Carter Flat interface names. Add or remove Carter Flat entries to match the number of expansion cards.
`maxInSpecOffset`:: Specifies the holdover specification threshold in nanoseconds. When the offset exceeds this threshold, the DPLL enters FREERUN. The default value is `100`.
`localMaxHoldoverOffset`:: Specifies the maximum offset during holdover in nanoseconds. The default value is `1500`.
`localHoldoverTimeout`:: Specifies the holdover timeout duration in seconds. The default value is `14400`, which assumes a DPLL oscillator that can maintain time for 4 hours. Set this value based on your hardware. For hardware with an 8-hour oscillator, set this value to `28800`.
`sources`:: Lists the timing sources for the clock chain. For a T-GM, define a GNSS source with `sourceType: gnss` and set `subsystem` to the name of the subsystem that receives the GNSS signal, for example, `nac`.
`antennaVoltage`:: Enables antenna voltage control on the GNSS antenna port. The default value is `true`. Set this value to `true` if you use an active GNSS antenna that requires DC bias power and supports health monitoring. Set this value to `false` if you use a passive antenna.
`constellations`:: Lists the GNSS constellations to enable. Specify one or more of `GPS`, `Galileo`, `GLONASS`, `BeiDou`, and `SBAS`. If you omit this field, the default is `GPS`. For a Telecom Grandmaster deployment, enable `GPS` and `Galileo`, as shown in the example.
`observationTime`:: Specifies the survey mode observation time in seconds. The default value is `86400` (24 hours).
`accuracy`:: Specifies the survey mode accuracy threshold in meters. The recommended value is `1` (1 meter). If you omit the `survey` configuration, no survey runs.
`relatedPtpProfileName`:: Specifies the profile name that must match the profile name in your `PtpConfig` CR, for example, `grandmaster`.
--
+
[NOTE]
====
For the Dell PowerEdge XR8720t platform, the GNSS receiver serial port is detected automatically.
Do not set a serial device in the `HardwareConfig` CR.
When you use the `HardwareConfig` mechanism, the `ts2phc.nmea_serialport` value in the `ts2phcConf` field of the `PtpConfig` CR is ignored.
The software detects the serial device and injects it into `ts2phc` automatically.
====

. Apply the `HardwareConfig` CR:
+
[source,terminal]
----
$ oc apply -f hardwareconfig-tgm.yaml
----
+
.Example output
[source,terminal]
----
hardwareconfig.ptp.openshift.io/gnrd-tgm created
----

. Verify that the `HardwareConfig` CR is created:
+
[source,terminal]
----
$ oc get hardwareconfig -n openshift-ptp
----
+
.Example output
[source,terminal]
----
NAME                      AGE
gnrd-tgm                  10s
----

.Verification

. Check the `linuxptp-daemon` pod logs to verify that the daemon loaded and applied the profile:
+
[source,terminal]
----
$ oc logs -n openshift-ptp -l app=linuxptp-daemon -c linuxptp-daemon-container | grep -iE "load profiles|Successfully applied profile"
----
+
Confirm that the output contains `load profiles` and `Successfully applied profile`, which indicate that the daemon loaded the `PtpConfig` profile and applied the `HardwareConfig` CR.

. Verify that the applied `HardwareConfig` CR references the correct `PtpConfig` profile:
+
[source,terminal]
----
$ oc get hardwareconfig -n openshift-ptp -o yaml | grep relatedPtpProfileName
----
+
Confirm that `relatedPtpProfileName` matches the profile name in your `PtpConfig` CR, for example, `grandmaster`.

. Verify that the holdover parameters are applied to the DPLL:
+
[source,terminal]
----
$ oc get hardwareconfig -n openshift-ptp -o yaml | grep -A 5 holdover
----
+
Confirm that the `holdoverParameters` values, such as `maxInSpecOffset`, `localMaxHoldoverOffset`, and `localHoldoverTimeout`, match the values you configured.

. Verify that the GNSS source parameters are applied:
+
[source,terminal]
----
$ oc get hardwareconfig -n openshift-ptp -o yaml | grep -A 8 gnssConfig
----
+
.Example output
[source,yaml]
----
gnssConfig:
  init:
    antennaVoltage: true
    constellations:
      - GPS
      - Galileo
    survey:
      observationTime: 86400
      accuracy: 1
----
+
Confirm that `antennaVoltage`, `constellations`, and the `survey` values match the values you configured.

. Verify that the T-GM reports Clock Class 6 by querying the PTP metrics:
+
[NOTE]
====
The `cloud-event-proxy` container exposes the PTP metrics endpoint only when the PTP fast event notifications publisher is enabled. For more information, see "Configuring the PTP fast event notifications publisher".
====
+
[source,terminal]
----
$ oc exec -it <linuxptp-daemon> -n openshift-ptp -c cloud-event-proxy -- curl -s 127.0.0.1:9091/metrics | grep openshift_ptp_clock_class
----
+
Replace `<linuxptp-daemon>` with the name of the `linuxptp-daemon` pod on your T-GM node.
+
.Example output
[source,terminal]
----
openshift_ptp_clock_class{node="compute-1.example.com",process="ptp4l"} 6
----
+
A clock class value of `6` indicates that the T-GM is locked to the GNSS time source and traceable to a Primary Reference Time Clock (PRTC).
