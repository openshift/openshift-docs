= Understanding the HTTP add-on

[role="_abstract"]
You can scale a workload on HTTP traffic by installing the HTTP add-on with the Custom Metrics Autoscaler Operator. The add-on supplies the request counts that the autoscaler uses, because an HTTP request is not stored in a queue that a scaler can query.

The add-on has three components:

* An interceptor proxy that receives requests, matches them to a workload, and counts them. While a workload scales up from zero replicas, the interceptor can hold a request until a pod is ready.
* A scaler that aggregates those counts and reports them to the Custom Metrics Autoscaler Operator.
* An operator that manages `InterceptorRoute` resources (`http.keda.sh/v1beta1`).

You create an `InterceptorRoute` resource to select the backend service and the scaling metric. You then create a `ScaledObject` resource that uses the `external-push` trigger. The Custom Metrics Autoscaler Operator creates a horizontal pod autoscaler (HPA) from that scaled object. You can create only one scaled object for a workload, and you cannot use a scaled object and an HPA that you created yourself on the same workload.

An HTTP request follows this path:

. A client sends a request to an {product-title} route. The route forwards the request to the interceptor proxy service, `keda-add-ons-http-interceptor-proxy`, in the `{cma-namespace}` namespace.
. The interceptor matches the request host, path, and headers to an `InterceptorRoute` resource, counts the request, and forwards it to the target service. If the workload has no ready pods, the interceptor holds the request until a pod is ready or a timeout expires.
. The scaler polls the interceptor pods and computes the concurrency and request-rate metrics for each route.
. The Custom Metrics Autoscaler Operator reads those metrics and updates the HPA, which changes the replica count of the workload.

The interceptor must read the HTTP host, path, and headers. Configure the {product-title} route with edge or re-encrypt TLS termination. Passthrough termination does not give the interceptor the request metadata it needs to route and count traffic.

By default, the interceptor connects to a ready pod IP instead of the service cluster IP. That path bypasses service network policy, session affinity, and topology-aware routing. To send traffic through the service, set the interceptor environment variable `KEDA_HTTP_DIRECT_POD_ROUTING` to `false` when you enable the add-on.

For a gRPC backend, or an HTTP/2 backend that does not use TLS, set `appProtocol: kubernetes.io/h2c` on the service port. The interceptor then connects to that backend with HTTP/2 and without TLS.
