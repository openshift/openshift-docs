= Factors affecting throughput

[role="_abstract"]
While Scanner V4 resources constrain throughput, other factors affect the number of VMs that a specific {product-title-short} deployment supports.

Consider the following factors:

* VM scan interval: The system measures throughput in VM scans per unit of time, and therefore scan interval, a configuration parameter of `roxagent`, directly impacts the number of VMs that {product-title-short} can handle. The figures in the earlier table use a scan interval of 4 hours, the default setting. A scan interval of 2 hours would result in halved numbers of VMs, and an interval of 8 hours would result in doubled numbers of VMs.

* VM index report rate limiter: A rate limiter protects {product-title-short} against excessive load, rejecting index reports sent by VMs when their rate exceeds the maximum value. If you see administration events indicating that VM index reports are being rate limited and you have increased system resources, adjust the rate limit by using the `ROX_VM_INDEX_REPORT_RATE_LIMIT` environment variable. The rate limiter allows bursts according to the `ROX_VM_INDEX_REPORT_BUCKET_CAPACITY` environment variable, which you can increase to allow larger bursts if the Central pod has enough available memory. For more information, see "Advanced virtual machine scanning configuration" in "Scanning virtual machines".

* Number of packages installed in each VM: Increased numbers of packages result in increased scan times, and therefore reduce throughput.

* Vulnerabilities in installed packages: Greater numbers of overall vulnerabilities found in VMs result in longer scan times, reducing throughput.

* Other workloads: While {product-title-short} processes VMs, {product-title-short} components keep processing the rest of the usual workloads. These components include Scanner V4, and therefore such workloads reduce the VM scanning throughput.
+
To account for these factors and their variability, the suggested capacity for each deployment type includes a headroom of at least 100%. Therefore, even if the processing time doubles due to an increased number of packages or vulnerabilities, {product-title-short} can handle the specified number of VMs.
