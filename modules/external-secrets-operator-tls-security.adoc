= Transport Layer Security profile support

[role="_abstract"]
The {external-secrets-operator} can use the cluster-wide Transport Layer Security (TLS) security profile for secure connections. Using the profile keeps TLS settings consistent with your cluster security policy.

The profile comes from the `apiserver.config.openshift.io/cluster` `APIServer` custom resource (CR). When you enforce the profile, the {external-secrets-operator} applies the profile to the following components:

* The secure serving endpoints of the {external-secrets-operator} for metrics and the webhook
* The `external-secrets`, `external-secrets-webhook`, and `external-secrets-cert-controller` operand `Deployments`
* The `bitwarden-sdk-server` operand `Deployment`, when you enable it

The {external-secrets-operator} injects operand container arguments derived from the resolved profile:

* `--tls-min-version=<version>`
* `--tls-ciphers=<cipher_list>`, which the {external-secrets-operator} omits when the minimum TLS version is 1.3, such as with the `Modern` profile

[id="external-secrets-operator-tls-adherence_{context}"]
== Transport Layer Security adherence

The `spec.tlsAdherence` field on the `APIServer` CR controls whether the {external-secrets-operator} uses the cluster TLS security profile. The {external-secrets-operator} uses the profile only when you set the field to `StrictAllComponents`. This value requires cluster-wide adherence. If you leave `spec.tlsAdherence` unset or set it to `LegacyAdheringComponentsOnly`, the {external-secrets-operator} and the operand use default TLS settings.

When the TLS security profile or the adherence policy changes, the {external-secrets-operator} shuts down and restarts. The restart reloads the new settings and reconciles operand `Deployments`.

For the `Old`, `Intermediate`, `Modern`, and `Custom` profile types and control-plane configuration details, see "Configuring TLS security profiles".
