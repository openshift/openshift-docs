= Nested SPIRE configuration

[role="_abstract"]
When you configure nested {spiffe-full} Runtime Environment (SPIRE) use the following fields and status conditions.

You can configure the `spire` plugin under `spec.upstreamAuthority`. You can set only one of `certManager`, `vault`, or `spire`.

The following table explains the nested server fields.

[cols="2,5",options="header"]
|===
|Field |Description

|`serverAddress`
|Required. Enter the DNS hostname of the parent gRPC endpoint. Maximum length is 253 characters. Do not include a scheme, a port, or a path.

|`serverPort`
|Optional. Set the TCP port of the parent gRPC endpoint. The default is `443`. Valid values are `1` through `65535`.

|`trustBundleSecret`
|Required. Enter the name of a secret in the Operator namespace. The secret has the key `bundle.crt` with X.509 root certificates in Privacy-Enhanced Mail (PEM) format.
|===

The following table explains the parent server fields.

[cols="2,5",options="header"]
|===
|Field |Description

|`managedRoute`
|Optional. Set `"true"` to create passthrough route `spire-server-grpc`. Set `"false"` when you expose the endpoint yourself. The default is `"false"`. The value is a string.

|`nodeAttestor.externalK8sPSAT.clusters[].name`
|Enter the name of a nested cluster. The name matches `ZeroTrustWorkloadIdentityManager.spec.clusterName` from the nested cluster. The Operator reads secret `nested-spire-<name>-kubeconfig`, key `kubeconfig`. The list accepts at most 100 unique names.
|===

The route host is `grpc.<cluster_name>.<trust_domain>` from the parent cluster name and trust domain. External clients use port `443`.

On the nested cluster, {zero-trust-full} adds the `spire-agent-upstream` sidecar to the `spire-server` pod.

On the parent cluster, {zero-trust-full} creates two `ClusterStaticEntry` objects for each nested cluster:

*Node alias: For example, `nested-spire-<cluster_name>-node-alias`.

*Nested server entry: For example, `nested-spire-<cluster_name>-downstream`. The nested server entry lets the nested server request an intermediate certificate authority (CA).

The class name on both entries is `zero-trust-workload-identity-manager-spire`. Do not edit the `ClusterStaticEntry` objects. {zero-trust-full} reconciles them.

The following table explains status conditions.

[cols="2,5",options="header"]
|===
|Condition |Meaning

|`UpstreamAgentAvailable`
|Nested server custom resource (CR). The sidecar in `spire-server-0` is ready and `trustBundleSecret` exists. Reasons include `Ready`, `UpstreamAgentNotReady`, and `TrustBundleMissing`.

|`ManagedGRPCRouteAvailable`
|Parent server CR, only when `managedRoute` is `"true"`. The route matches the expected spec. Reasons include `RouteAdmitted`, `RouteNotAdmitted`, and `RouteCreationFailed`.

|`DownstreamClustersValid`
|Parent server CR. Each cluster has a non-empty `kubeconfig` key, and both `ClusterStaticEntry` objects match the needed configuration. The check does not prove that SPIRE applied the entries. `DownstreamClustersValid` includes the following statuses: `Ready`, `KubeConfigMissing`, `KubeConfigInvalid`, `ClusterNameConflict`, `EntryReconcileFailed`, and `ResourceConflict`.
|===
