= mirrorSourcePolicy field: Controlling fallback to source registry

[role="_abstract"]
The `mirrorSourcePolicy` field in ImageDigestMirrorSet and ImageTagMirrorSet custom resources controls whether CRI-O can contact the original source registry as a fallback after all configured mirrors fail. This field is critical for air-gapped deployments where network policy must prevent any contact with external registries. Understanding the policy options and their implications is essential for designing resilient mirror configurations that respect network isolation requirements.

== mirrorSourcePolicy values

The `mirrorSourcePolicy` field accepts two values:

|===
|Policy Value |Behavior |Use Case

|`AllowContactingSource` (default)
|After all configured mirrors fail to provide an image, CRI-O attempts to pull the image directly from the original source registry. This allows fallback to external registries even if all mirrors are unavailable.
|Hybrid deployments where the cluster has occasional internet connectivity or where maintaining all images in mirrors is not practical. If mirrors fail, external source registries are available as a last resort.

|`NeverContactSource`
|CRI-O never contacts the original source registry, even after all configured mirrors fail. If all mirrors fail, the image pull fails immediately without attempting the source.
|Air-gapped and restricted environments where network policy strictly isolates the cluster from external networks. Required for compliance requirements that mandate zero contact with external registries.

|===

== Fallback sequence with AllowContactingSource

When `mirrorSourcePolicy: AllowContactingSource` is configured, CRI-O follows this fallback sequence:

1. Attempt to pull the image manifest from the primary mirror
2. If the primary mirror fails with a transient error, attempt the secondary mirror
3. If the secondary mirror fails, attempt the tertiary mirror
4. If all mirrors have been tried and failed, attempt the original source registry
5. If the source registry succeeds, the image pull completes
6. If the source registry also fails, the image pull fails

This multi-tier fallback provides resilience across mirrors and ultimately allows external source registries as a safety net.

== Fallback sequence with NeverContactSource

When `mirrorSourcePolicy: NeverContactSource` is configured, CRI-O follows this fallback sequence:

1. Attempt to pull the image manifest from the primary mirror
2. If the primary mirror fails with a transient error, attempt the secondary mirror
3. If the secondary mirror fails, attempt the tertiary mirror
4. If all mirrors have been tried and failed, the image pull fails immediately
5. No attempt is made to contact the original source registry

With this policy, the mirrors must contain all images the cluster needs. If an image is not available in any configured mirror, the pull fails.

== Use cases for AllowContactingSource

AllowContactingSource is appropriate for:

* **Hybrid deployments**: Clusters with mixed internal and external connectivity. For example, clusters in a corporate network with firewall access to some external registries.
* **Disaster recovery scenarios**: Clusters that normally rely on local mirrors but can temporarily use external sources if all mirrors fail during emergencies.
* **Development/test environments**: Non-production clusters where strict image availability guarantees are not required.
* **Migration periods**: Temporarily allowing external source contact while transitioning from single-mirror to multi-mirror architecture.
* **Image pull fallback for missing images**: When administrative processes have not yet synced all required images to mirrors, external source fallback prevents cluster-wide pull failures.

Example configuration for hybrid deployment:

[source,yaml]
----
apiVersion: config.openshift.io/v1
kind: ImageDigestMirrorSet
metadata:
  name: hybrid-mirrors
spec:
  imageDigestMirrors:
  - source: registry.redhat.io
    mirrors:
    - internal-quay.example.com          # Primary: internal mirror
    - backup-mirror.example.com          # Secondary: backup internal mirror
    mirrorSourcePolicy: AllowContactingSource  # Fallback to registry.redhat.io if needed
----

With this configuration, the cluster can pull directly from `registry.redhat.io` if both internal mirrors fail.

== Use cases for NeverContactSource

NeverContactSource is required for:

* **Air-gapped clusters**: Clusters in completely isolated networks with no external connectivity. Network policy prevents any outbound connections.
* **Regulatory compliance**: Deployments in regulated environments (finance, healthcare, government) where accessing external registries violates compliance policies.
* **Restricted networks**: Military, government, or enterprise environments where external internet access is explicitly forbidden.
* **Security policies**: Organizations that require explicit network isolation to prevent data exfiltration or unauthorized external communication.

Example configuration for air-gapped cluster:

[source,yaml]
----
apiVersion: config.openshift.io/v1
kind: ImageDigestMirrorSet
metadata:
  name: airgapped-mirrors
spec:
  imageDigestMirrors:
  - source: registry.redhat.io
    mirrors:
    - local-quay.cluster.local          # Primary: local mirror on cluster
    - quay-backup.data-center.local     # Secondary: backup in isolated network
    - quay-dr.disaster-recovery.local   # Tertiary: disaster recovery location
    mirrorSourcePolicy: NeverContactSource  # Enforce zero external contact
----

With this configuration, the cluster cannot pull directly from `registry.redhat.io` even if all mirrors fail.

== Planning mirror coverage with NeverContactSource

When using `NeverContactSource`, mirror coverage becomes critical. The cluster cannot fall back to external sources if mirrors are incomplete.

To plan mirror coverage:

. **Inventory all images**: Document all container images the cluster needs:
  - OpenShift core images (etcd, API server, controllers)
  - Operator images (all operators deployed on the cluster)
  - Application images (workload deployments)
  - Build images (build pipelines if BuildConfig or build-oriented operators are used)

. **Verify mirror population**: Ensure all images from step 1 exist in at least one configured mirror:
  - Use `oc-mirror` tool to sync images from source registries to mirrors
  - Verify digests match between source and mirrors (no image corruption during sync)
  - Test pull operations from each mirror to confirm accessibility

. **Plan for updates**: When updating operators or applications, ensure the new image versions are synchronized to mirrors before upgrading:
  - Update mirrors first
  - Then update the cluster (operators, deployments)
  - This prevents upgrade blockers due to missing images

. **Document mirror relationships**: Maintain documentation of which images are mirrored where, so administrators understand fallback coverage.

## Implications of NeverContactSource failures

With `NeverContactSource` configured, image pull failures have significant consequences:

* **Pull failures are permanent**: If an image is not in any configured mirror, the pull fails permanently (no external fallback)
* **Workload deployment failures**: Pods cannot start if their image is missing from mirrors
* **Operator installation failures**: Operator images must be available in mirrors before installing the operator
* **Cluster upgrade blockers**: If an updated component image is not in mirrors, the upgrade cannot complete
* **On-call escalation**: Image pull failures require manual synchronization of missing images to mirrors (production incident)

These implications make thorough mirror coverage planning essential when using `NeverContactSource`.

## Interaction with ICSP (deprecated)

ImageContentSourcePolicy (ICSP) is deprecated but still functional in OpenShift 4.20 and later.

ICSP does not support the `mirrorSourcePolicy` field. When ICSP is used:

* **Default behavior**: ICSP behaves like `AllowContactingSource` (always falls back to source registry after mirrors fail)
* **No control**: There is no way to prevent source contact with ICSP
* **Migration recommendation**: For air-gapped clusters that currently use ICSP, migrate to IDMS/ITMS with `mirrorSourcePolicy: NeverContactSource` to enforce network isolation

Example ICSP (does not support policy control):

[source,yaml]
----
apiVersion: v1
kind: ImageContentSourcePolicy
metadata:
  name: registry-mirror
spec:
  repositoryDigestMirrors:
  - mirrors:
    - quay.example.com
    source: registry.redhat.io
----

To achieve the same behavior with explicit `NeverContactSource` control, migrate to IDMS:

[source,yaml]
----
apiVersion: config.openshift.io/v1
kind: ImageDigestMirrorSet
metadata:
  name: registry-mirror
spec:
  imageDigestMirrors:
  - source: registry.redhat.io
    mirrors:
    - quay.example.com
    mirrorSourcePolicy: NeverContactSource
----

## Verifying mirrorSourcePolicy enforcement

To verify that your configured policy is enforced:

. **For AllowContactingSource**, disable all mirrors and verify that external source fallback works:
+
[source,terminal]
----
$ oc debug node/<test-node>
sh-4.4# iptables -I OUTPUT -d quay.example.com -j DROP
sh-4.4# crictl pull registry.redhat.io/ubi9/ubi-minimal:latest
----
+
With `AllowContactingSource`, the pull should succeed by contacting the external source. With `NeverContactSource`, the pull should fail.

. **For NeverContactSource**, disable all mirrors and verify that external source is not contacted:
+
[source,terminal]
----
$ oc debug node/<test-node>
sh-4.4# iptables -I OUTPUT -d registry.redhat.io -j DROP
sh-4.4# iptables -I OUTPUT -d quay.example.com -j DROP
sh-4.4# crictl pull registry.redhat.io/ubi9/ubi-minimal:latest
----
+
The pull should fail because both mirrors and source are unreachable, confirming that NeverContactSource is enforced (no attempt to contact external source).

## Recommendations

* **Development clusters**: Use `AllowContactingSource` for flexibility during development
* **Production disconnected clusters**: Use `NeverContactSource` to enforce network isolation and prevent accidental external communication
* **Hybrid production clusters**: Use `AllowContactingSource` for maximum resilience, combined with network policies that prevent actual external traffic as an additional security layer
* **Compliance-sensitive environments**: Always use `NeverContactSource` with comprehensive mirror coverage to meet regulatory requirements
