[id="kueue-workload-readiness-timeouts_{context}"]
= Workload readiness timeouts and retries

[role="_abstract"]
Readiness timeouts control how long {kueue-name} waits for pods to reach a ready state during startup or recovery. You can adjust these timeouts to accommodate tasks such as image pulls and worker initialization.

One set of readiness timeouts applies across the whole cluster. You cannot set different timeouts for individual namespaces or workloads.

Choose timeouts that cover the expected startup and recovery times. A short timeout can trigger eviction before pods reach a ready state. A long timeout can delay other workloads that need the reserved quota.

[id="kueue-start-and-recovery-timeouts_{context}"]
== Start and recovery timeouts

The start timeout begins when {kueue-name} admits a workload. The workload must reach the `PodsReady=True` condition before the timeout expires. A pod in the `Running` phase alone does not make the workload ready.

The recovery timeout applies when one or more pods in a workload are no longer ready. For example, a pod might fail while its replacement waits to start.

The recovery timeout begins when the `PodsReady` condition changes to `False` with the `WaitForRecovery` reason. Disabling the recovery timeout does not disable the start timeout.

[id="kueue-workload-retries_{context}"]
== Workload retries

When a readiness timeout expires, {kueue-name} checks the retry limit. A retry is an attempt to admit a workload after a readiness timeout.

If retries remain or you omit the limit, {kueue-name} evicts the workload with the `PodsReadyTimeout` reason. If no retries remain, {kueue-name} deactivates the workload.
