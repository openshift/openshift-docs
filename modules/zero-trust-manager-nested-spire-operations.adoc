= Nested SPIRE Day 2 behavior

[role="_abstract"]
After you put the certificate authority (CA) chain in place, nested servers can keep issuing identities while the parent server is unavailable, until their intermediate CA expires. Readiness conditions report Kubernetes reconciliation.

A nested server keeps issuing from its cached intermediate CA until that CA expires. The agent sidecar retries attestation until the parent server is reachable again. CA renewal then resumes without a configuration change.

While the parent server restarts after a cluster-list change, existing nested servers also keep issuing from their cached CAs.

*Limits of status conditions*

The `DownstreamClustersValid` condition checks `kubeconfig` secrets and registration objects.

The `UpstreamAgentAvailable` condition checks the sidecar and the trust bundle secret. The `ManagedGRPCRouteAvailable` condition checks that the cluster admitted the route.

Use {spiffe-full} Runtime Environment (SPIRE) Controller Manager logs for registration failures and SPIRE server logs for CA failures.

If a generated `ClusterStaticEntry` is missing, {zero-trust-full} recreates it on the next reconcile. Until both entries exist, the server cannot obtain a new intermediate CA.

*Upgrade order*

First, upgrade the root cluster. Do not run an agent that is newer than the parent server. You can run an agent that is at most one minor version older.

You can omit the new nested SPIRE fields. The `spec.managedRoute` field defaults to `"false"`, so an upgrade does not expose the gRPC endpoint.

To add a nested cluster, repeat the credential, registration, trust bundle, and nested server procedures for the new cluster. Batch several additions in one CR update when you want a single parent server restart.
