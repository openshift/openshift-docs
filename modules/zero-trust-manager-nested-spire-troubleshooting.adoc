= Troubleshooting nested SPIRE

[role="_abstract"]
Use {spiffe-full} Runtime Environment (SPIRE) server logs and `SpireServer` status conditions to isolate nested SPIRE failures. Readiness conditions report local Kubernetes state. You can see certificate authority (CA) signing in the server log.

You can check the SPIRE server logs by running the following command:

[source,terminal]
----
$ oc logs pod/spire-server-0 -c spire-server -n zero-trust-workload-identity-manager | grep "X509 CA"
----

The following table explains the errors, their causes, and what to do.

[cols="2,2,3",options="header"]
|===
|Symptom or error |Likely cause |What to do

|`self_signed=true` after you set `spec.upstreamAuthority.spire`
|The current CA is still the previous CA
|Wait for the next rotation. To switch during a maintenance window, re-initialize the datastore. See "Re-initializing the SPIFFE Runtime Environment (SPIRE) server datastore".

|`too many intermediates for path length constraint`
|External root CA path length is too short
|This error applies when the root CA comes from an external public key infrastructure (PKI). Reissue the external root CA with a path length that covers every intermediate tier in the longest chain. A SPIRE self-signed root does not use an external path length.

|`no X.509 bundle found for trust domain`
|Trust domain mismatch
|Set the same `spec.trustDomain` on every cluster in the hierarchy.

|`not configured for cluster`
|The cluster name is not registered on the parent server
|Set `spec.nodeAttestor.externalK8sPSAT.clusters[].name` to the `spec.clusterName` value from the nested cluster.

|`ClusterNameConflict`
|The nested cluster name matches the parent `spec.clusterName`
|Use a nested cluster name that differs from the `spec.clusterName` value on the parent cluster.

|Attestation fails and the namespace differs
|The parent allow list uses the parent namespace
|Install {zero-trust-full} in the same namespace on every cluster.

|`Unauthorized`, `Forbidden`, or `token not authenticated`
|A `TokenReview` error means the nested cluster API rejected the parent credentials
|Point secret `nested-spire-<cluster_name>-kubeconfig` at the API server of the cluster named `<cluster_name>`. Confirm the `ServiceAccount` has `create` on `tokenreviews`, `get` on `nodes`, and `get` on `pods` in the Operator namespace. Confirm the secret data key is `kubeconfig` and the value is not empty. Read `DownstreamClustersValid`. The message names the cluster and the secret.

|`certificate contains no URI SAN`
|The route does not use passthrough TLS
|Confirm that the route `spire-server-grpc` uses passthrough termination. A router certificate has DNS subject alternative names. It does not have a SPIFFE URI Subject Alternative Name (SAN).

|`EOF`, `connection refused`, or `context deadline exceeded`
|The nested server cannot reach the parent gRPC endpoint
|Confirm DNS for the route host resolves to the parent cluster ingress. Confirm the nested SPIRE server can open TCP to `serverAddress` on `serverPort`.

|The parent server cannot reach a nested API
|The network path to the nested API server is blocked
|Confirm the parent SPIRE server can open TCP to each nested cluster API server.

|`spire-agent-upstream` in `CrashLoopBackOff`
|Sidecar configuration or connectivity
|Check `UpstreamAgentAvailable` and the `spire-agent-upstream` container logs.

|Pod stuck in `ContainerCreating` or `FailedMount`
|The pod cannot mount a referenced secret
|If `spire-server-0` reports `FailedMount`, recreate the missing `kubeconfig` secret or `trustBundleSecret` in the Operator namespace.

|TLS handshake error after a pod is recreated
|`trustBundleSecret` holds a stale root CA
|Update `bundle.crt` before you reschedule the pod. A container restart in the same pod can still succeed.
|===
