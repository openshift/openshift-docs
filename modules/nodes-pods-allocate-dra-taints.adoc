= About device taints and tolerations

// Taken from https://kubernetes.io/docs/concepts/scheduling-eviction/dynamic-resource-allocation/#terminology
[role="_abstract"]
You can use device taints and tolerations with Dynamic Resource Allocation (DRA) to let drivers and administrtors keep pods off of specific devices or evict pods already using the devices.

An administrator can taint devices by creating a `DeviceTaintRule` object that adds a taint to any device that matches the specified device selector. The device selector can be the name of a device class, DRA driver, pool, or a specific device. You can then apply matching tolerations for specific workloads through a resource claim. 

Taints can also be published directly by a DRA driver in a resource slice. Consult the documentation of a DRA driver to learn whether the driver uses taints and what their keys and values are.

For example, you can use a device taint rule to reserve devices for specialized workloads. Or, if a device is not working or is off-line for maintenance, you can prevent new pods from being scheduled on the device and remove any existing pods from the device.

The following example device taint rule taints all devices controlled by the `dra.example.com` driver. 

[source,yaml]
----
apiVersion: resource.k8s.io/v1
kind: DeviceTaintRule
metadata:
  name: example
spec:
  deviceSelector:
    driver: dra.example.com
  taint:
    key: dra.example.com/unhealthy
    value: Broken
    effect: NoExecute
    tolerationSeconds: 300
----

where:

`spec.deviceSelector` specifies how to identify the devices that the taint applies to. Use the following options:

* `driver`. Specifies all the devices controlled by the specified DRA driver are tainted.
* `deviceClass`. Specifies that all the devices configured under this specific device class are tainted. You can specify a `deviceclass` and specific `driver` to avoid ambiguity.
* `pool`. Specifies that all the devices configured under a specific DRA driver node resource pool are tainted. You can specify a `pool` and specific `driver` to avoid ambiguity.
* `device` Specifies that an exact device is tainted.  You can specify a `device`, `pool`, and specific `driver` to avoid ambiguity. 

`spec.taint.key` specifies the key of the key/value pair for the taint.
`spec.taint.value` specifies the value of the key/value pair for the taint.
`spec.taint.effect` specifies the effect of the taint. Use one of the following options:

* `NoSchedule` blocks new workloads from being added to the device, but leaves existing workloads in place
* `NoExecute` blocks new workloads from being added to the device and removes existing workloads. You can use the `tolerationSeconds` parameter with the `NoExecute` parameter to indicate how long a workload can remain bound to a device before being evicted.
* `None` is ignored by the scheduler. New workloads can be added to the device and existing workloads remain.

The following resource claim contains a toleration for the taint created with the previous device taint rule example. In this example, any associated workload remains on the device for 300 seconds before termination.

[source,yaml]
----
apiVersion: resource.k8s.io/v1
kind: ResourceClaim
metadata:
  name: resilient-workload-claim
  namespace: default
spec:
  resourceClassName: example-device-class
  tolerations:
    - key: "dra.example.com/unhealthy"
      operator: "Equal"
      value: "Broken"
      effect: "NoExecute"
      tolerationSeconds: 300 
----
