[id="rn-ocp-release-note-bare-metal-hardware-fixed-issues_{context}"]
== Bare Metal Hardware Provisioning

* Before this update, the `baremetal` cluster Operator did not set its `Progressing` status condition to `True` during cluster upgrades. As a consequence, the Cluster Version Operator (CVO) waited for the Operator without receiving proper progress signals, and upgrade monitoring tests failed. With this release, the `baremetal` Operator correctly reports `Progressing=True` during version changes. As a result, cluster upgrades proceed with accurate Operator status reporting. (link:https://redhat.atlassian.net/browse/OCPBUGS-66101[OCPBUGS-66101])

* Before this update, when the bare-metal host (BMH) `spec.online` parameter was set to `False`, the Bare Metal Operator (BMO) forced the `ironic` service to issue a power-off command to the node at the end of inspection, after the ramdisk had been ejected. As a consequence, the node operating system lost access to the boot media during shutdown, and filesystem corruption errors were visible on the BMH console. With this release, the node is powered off after inspection, while cleaning up the ramdisk, before ejecting Redfish virtual media. As a result, the host does not lose access to the boot media. (link:https://redhat.atlassian.net/browse/OCPBUGS-66156[OCPBUGS-66156])

* Before this update, the Bare Metal Operator (BMO) `getChecksum()` function accepted non-empty checksums for {oci-first-no-rt} images. As a consequence, OCI image provisioning failed. With this release, a check in the `getChecksum()` function rejects non-empty user-provided checksums for OCI images. As a result, OCI image provisioning does not fail. (link:https://redhat.atlassian.net/browse/OCPBUGS-84305[OCPBUGS-84305])

* Before this update, when managing a high volume of `BareMetalHost` resources on a single multicluster engine instance, the Bare Metal Operator (BMO) issued excessive requests to the Provisioner API during reconciliation. As a consequence, VirtualMedia injection and node reconciliation were noticeably slower at this scale. With this release, the BMO reconciliation loop is optimized to issue fewer requests to the Provisioner API. As a result, responsiveness improves when managing large numbers of `BareMetalHost` resources. (link:https://redhat.atlassian.net/browse/OCPBUGS-85527[OCPBUGS-85527])

* Before this update, when servicing a bare-metal host (BMH), the `service_disable_ramdisk` parameter remained set to `False` even if all servicing steps were performed out-of-band. As a result, the BMH underwent an unnecessary reboot. With this release, the `ironic` service code has been modified to automatically set `service_disable_ramdisk` to `True` when all servicing steps are out-of-band. (link:https://redhat.atlassian.net/browse/OCPBUGS-85528[OCPBUGS-85528])

* Before this update, the `ironic-agent` container image was missing the `iproute` package at runtime, which provides the `ip` command required for network configuration. As a consequence, the Ironic Python Agent (IPA) failed to heartbeat to the `ironic` service during bare-metal node cleaning, and node cleaning operations timed out. With this release, the `ironic-agent` container image build process is updated to retain required packages such as `iproute` and `psmisc`. As a result, IPA completes network configuration successfully and bare-metal node cleaning operations complete without timing out. (link:https://redhat.atlassian.net/browse/OCPBUGS-94115[OCPBUGS-94115])

* Before this update, bare-metal nodes provisioned through virtual media failed to boot the inspection image because of incorrect kernel arguments in the provisioning ISO. As a consequence, soft lockups occurred on some hardware, for example, Fujitsu PRIMERGY M8, because the `{{console=ttyS0}}` parameter lacked baud rate and parity settings. The `{{ip=dhcp}}` parameter was missing, which prevented network acquisition during early boot. With this release, the provisioning ISO includes the `{{ip=dhcp}}` parameter and specifies the full serial console configuration. As a result, bare-metal Installer-provisioned installations complete without manual intervention. (link:https://redhat.atlassian.net/browse/OCPBUGS-98696[OCPBUGS-98696])

* Before this update, the Bare Metal Operator (BMO) did not set the `IRONIC_INSECURE` function. As a consequence, bare-metal host (BMH) provisioning failed. With this release, the BMO correctly sets the `IRONIC_INSECURE` function. As a result, BMH provisioning succeeds. (link:https://redhat.atlassian.net/browse/OCPBUGS-111889[OCPBUGS-111889])

[id="rn-ocp-release-note-cloud-compute-fixed-issues_{context}"]
== Cloud Compute

* Before this update, the `AWSMachine` controller was requeuing machine instances before confirming the presence of tags. As a consequence, duplicate {aws-first} EC2 instances were created. With this release, the `AWSMachine` controller verifies tags before requeuing instances. As a result, duplicate EC2 instances are not created. (link:https://redhat.atlassian.net/browse/OCPBUGS-62985[OCPBUGS-62985])

* Before this update, if an OpenStack cloud provider lacked the optional Standard Attributes Tag extension, the Machine API Provider for OpenStack (MAPO) attempted to apply port tags during network port creation. As a consequence, provisioning failed. With this release, MAPO checks whether the `standard-attr-tag` extension is available before applying tags. If unsupported, MAPO skips tag assignment or returns an error prompting you to remove explicit configurations. As a result, machine provisioning completes successfully. (link:https://redhat.atlassian.net/browse/OCPBUGS-77061[OCPBUGS-77061])

== etcd

* Before this update, an upgrade with a control plane `MachineConfig` might have caused quorum loss. As a consequence, the upgrade caused prolonged API and etcd downtime, leading to service interruption. With this release, the `cluster-etcd-operator` keeps guard pods that prevent a `MachineConfig` object from draining the node. As a result, etcd maintains quorum during upgrades.  (link:https://redhat.atlassian.net/browse/OCPBUGS-66334[OCPBUGS-66334])

[id="rn-ocp-release-note-Helm-fixed-issues_{context}"]
== Helm

* Before this update, installing a Helm chart by using the Chart URL option in the {product-title} web console with an {oci-first} URL that included a version number, for example, `oci://registry-1.docker.io/bitnamicharts/nginx:22.6.12` failed with an error indicating that the chart was not available or could not be found. As a consequence, users could not install Helm charts from OCI registries when specifying the version number directly in the URL. With this release, the Helm chart installation process correctly handles OCI URLs that include version numbers. As a result, users can now successfully install Helm charts from OCI registries by providing the complete URL with the version number in the web console Chart URL field.

[id="rn-ocp-release-note-hosted-control-planes-fixed-issues_{context}"]
== Hosted Control Planes

* Before this update, KubeVirt-based `NodePool` resources incorrectly reported `ClusterNetworkCIDRConflict` errors because the controller flagged OVN-Kubernetes internal overlay IP addresses as conflicting with the cluster network. With this release, Classless Inter-Domain Routing (CIDR) conflict detection is triggered only when all the non-link local addresses for the machine fall within the cluster network. As a result, when external addresses exist, in-network addresses are correctly treated as expected container network interface (CNI) internal IP addresses, which prevents false positive conflict reports. (link:https://redhat.atlassian.net/browse/OCPBUGS-84269[OCPBUGS-84269])

* Before this update, applying resource overrides to containers without pre-existing resource requests caused a nil map panic and crash loop. With this release, a nil guard is added to the `applyRequestsOverrides` function in the Control Plane Operator (CPO) before calling `maps.Copy` on the `Resources.Requests` parameter.  As a result, resource request overrides are successfully applied regardless of pre-existing requests. (link:https://redhat.atlassian.net/browse/OCPBUGS-93785[OCPBUGS-93785])

* Before this update, the Konnectivity proxy-server in the `kube-apiserver` deployment was not configured with the `--cluster-ca-cert` flag. As a consequence, a reachable client could establish a connection to the Konnectivity proxy-server without a valid client certificate signed by the hosted cluster Konnectivity certification authority (CA). With this release, the `--cluster-ca-cert` flag is added to the `konnectivity-server` container arguments in the `kube-apiserver` deployment manifest. As a result, unauthenticated connections are prevented because the proxy-server requires and validates client certificates signed by the hosted cluster Konnectivity CA. (link:https://redhat.atlassian.net/browse/OCPBUGS-99014[OCPBUGS-99014])

[id="rn-ocp-release-note-monitoring-fixed-issues_{context}"]
== Monitoring

* Before this update, when Prometheus compacted time series data, it attempted to enable direct I/O on files that were already open. Some file systems, such as {ibm-title} Storage Scale, do not support this operation. As a consequence, compaction failed with a `cannot enable Direct IO: invalid argument` error, Prometheus could not write chunks to disk, and memory usage in Prometheus pods increased until the pods hit their memory limits and restarted or affected other workloads on the node. With this release, Prometheus detects when a file system does not support direct I/O on open files and handles the condition gracefully. As a result, Prometheus writes chunks to disk and completes compaction successfully on these storage back ends. (link:https://redhat.atlassian.net/browse/OCPBUGS-92191[OCPBUGS-92191])

* Before this update, the Cluster Monitoring Operator (CMO) checked only the `openshift-config/pull-secret` for the `cloud.openshift.com` authentication token used by the telemeter client. As a consequence, on platforms where this secret did not contain the token, such as the {azure-first} Red Hat OpenShift {hcp}, the telemeter client was not deployed, which prevented cluster registration in {cluster-manager-first}. With this release, the CMO falls back to `kube-system/global-pull-secret` if the token is not found in the primary secret. As a result, the telemeter client is deployed correctly. (link:https://redhat.atlassian.net/browse/OCPBUGS-98450[OCPBUGS-98450])

* Before this update, Alertmanager crashed because the `tzdata` package was missing in the {product-title} base images, This issue caused the absence of the `/usr/share/zoneinfo` directory. As a consequence, Alertmanager pods failed to start, which made time-based alerts inaccessible for the time zones. With this release, the `tzdata` package has been reinstated in {product-title} images. As a result, Alertmanager does not crash on startup when location fields are present in the `active_interval` or `mute_interval` entries. (link:https://redhat.atlassian.net/browse/OCPBUGS-99435[OCPBUGS-99435])

* Before this update, containers in the `openshift-monitoring` namespace ran with writable root filesystems because `readOnlyRootFilesystem: true` was not enabled in their security contexts. As a consequence, customer compliance scans flagged these containers as security policy violations. With this release, monitoring components enable read-only root filesystems with dedicated `emptyDir` volumes for paths requiring write access. As a result, monitoring containers meet compliance requirements for read-only root filesystems. (link:https://redhat.atlassian.net/browse/OCPBUGS-105389[OCPBUGS-105389])

* Before this update, Fibre Channel adapters reported incomplete data. As a consequence, the node_exporter failed to run. With this release, guards are added to ignore incomplete data. (link:https://redhat.atlassian.net/browse/OCPBUGS-112719[OCPBUGS-112719])

[id="rn-ocp-release-note-node-tuning-operator-fixed-issues_{context}"]
== Node Tuning Operator

* Before this update, a failure to update the `PerformanceProfile` status due to a temporarily unavailable API server during an upgrade or under network load could leave the profile in a `Degraded` condition. As a consequence, the degraded condition might stop and never resolve, even after the cluster returned to a healthy state, because the Operator did not retry until the next reconcile event. With this release, the Operator schedules a retry of the status update until it succeeds, retrying approximately every 30 seconds. As a result, the stopped degraded status is temporary and resolves automatically during the next retry. (link:https://issues.redhat.com/browse/OCPBUGS-62277[OCPBUGS-62277])

* Before this update, the Node Tuning Operator (NTO) reconciliation used the rate-limited work queue for all event enqueues. As a consequence, node-tuning configuration was delayed for cluster notes greater than 100. With this release, the NTO reconciliation loop uses the rate-limited work queue only for failures instead of all event enqueues. As a result, node-tuning configuration for cluster nodes greater than 100 is not delayed. (link:https://issues.redhat.com/browse/OCPBUGS-112279[OCPBUGS-112279])

* Before this update, the short description for the `info` command in the Performance Profile Creator (PPC) tool was not updated after the cluster inspection was moved. As a consequence, inconsistencies between the parent help and the information help occurred when you ran the PPC tool. With this release, the short description for the `info` command in the PPC tool is updated to match the current CLI. As a result, the help inconsistencies do not occur when you run the tool.  (link:https://issues.redhat.com/browse/OCPBUGS-114144[OCPBUGS-114144])

* Before this update, you were required to enable timer migration to prevent TCP and other leftover timers from interfering with latency-sensitive workloads. As a consequence, this migration increased latency for high-resolution timers and disrupted benchmarks such as the `cyclictest` tool. With this release, the improved timer wheel logic in {op-system-base-full} 10 allows you to disable timer migration. As a result, both polling and high-resolution timer latency-sensitive workloads run without interruption from leftover timers. (link:https://issues.redhat.com/browse/OCPBUGS-114934[OCPBUGS-114934])

(link:https://redhat.atlassian.net/browse/OCPBUGS-84534[OCPBUGS-84534])

[id="rn-ocp-release-note-storage-fixed-issues_{context}"]
== Storage

* Before this update, when using zonal deployments of vSphere with {product-title}, if a data center was missing from the vCenter section of the infrastructure configuration, the cluster became degraded without any warnings or errors logged by the vSphere platform detector. As a consequence, the CSI driver was unable to find virtual machines in the zone that was missed in the vCenter section. With this release, the vSphere platform detector validates that all data centers used in failure domains are also specified in the vCenter section. As a result, configuration errors are detected and reported, preventing cluster degradation. (link:https://redhat.atlassian.net/browse/OCPBUGS-56274[OCPBUGS-56274])

* Before this update, when an UltraSSD_LRS Azure Disk volume snapshot was deleted in {product-title} before the snapshot completed in Azure, and the delete operation failed in Azure, the `VolumeSnapshotContent` resource became stuck in a `Deleting` or `Terminating` state. As a consequence, the resource remained indefinitely in this state until the `openshift-cluster-csi-drivers/azure-disk-csi-driver-controller` pods were manually restarted. With this release, the Azure Disk CSI driver correctly reconciles with the Azure backend when deleting snapshots. As a result, terminating `VolumeSnapshotContent` objects are removed without requiring a restart of the CSI driver controller pods. (link:https://redhat.atlassian.net/browse/OCPBUGS-77492[OCPBUGS-77492])

* Before this update, a regression in the Azure Disk CSI driver caused the `ManagedBy` field on Azure disks to remain set after a node was deleted, preventing disk detachment. As a consequence, when a disk was assigned to another node while waiting for `ControllerUnpublish` to finish, the operation became stuck indefinitely, and the disk could not be detached for several hours. With this release, the Azure Disk CSI driver correctly clears the `ManagedBy` field during the unpublish operation. As a result, disks detach properly when nodes are deleted or volumes are moved between nodes. (link:https://redhat.atlassian.net/browse/OCPBUGS-78197[OCPBUGS-78197])

* Before this update, when the CSI driver `CreateVolumeGroupSnapshot` operation was called repeatedly, the host-path CSI driver did not return complete responses consistently. As a consequence, volume group snapshot creation operations could fail intermittently, particularly in test scenarios. With this release, the host-path CSI driver correctly returns complete responses for all `CreateVolumeGroupSnapshot` calls. As a result, volume group snapshot operations complete reliably. (link:https://redhat.atlassian.net/browse/OCPBUGS-78576[OCPBUGS-78576])

* Before this update, the vSphere Problem Detector Operator incorrectly reported missing privileges for compute clusters on newly deployed {product-title} clusters, even when vCenter permissions were configured identically to older clusters. As a consequence, warning events were logged indicating missing privileges such as `Resource.AssignVMToPool`, `VApp.AssignResourcePool`, `VApp.Import`, and `VirtualMachine.Config.AddNewDisk`, despite the service account having the required permissions. With this release, the vSphere Problem Detector Operator correctly validates vCenter permissions across all cluster deployments. As a result, false positive warnings are no longer generated on newly deployed clusters. (link:https://redhat.atlassian.net/browse/OCPBUGS-79057[OCPBUGS-79057])

* With this release, end-to-end test automation has been added to validate that storage components no longer generate self-signed certificates. As a result, the feature is properly tested in automated test suites. (link:https://redhat.atlassian.net/browse/OCPBUGS-84247[OCPBUGS-84247])

* Before this update, CSI driver configuration tests did not skip execution when the `ClusterCSIDriver` resource state was set to `Removed`. As a consequence, tests that attempted to configure CSI drivers timed out waiting for the storage operator to become progressing, resulting in test failures with messages such as "Failed to wait for operator Progressing=True". With this release, CSI driver configuration tests correctly detect when a `ClusterCSIDriver` is in the `Removed` state and skip execution. As a result, tests no longer fail when CSI drivers are intentionally removed. (link:https://redhat.atlassian.net/browse/OCPBUGS-84809[OCPBUGS-84809])

* Before this update, the SELinux warning controller of the Kubernetes Controller Manager performed `O(V * P^2)` operations during every Prometheus metrics scrape, where V is the number of volumes and P is the number of pods per volume. As a consequence, on large clusters with hundreds of nodes and attached volumes, the KCM leader `/metrics` endpoint took over 12 seconds to respond, exceeding the 5-second Prometheus scrape timeout and causing `KubeControllerManagerDown` alerts to fire. With this release, the SELinux warning controller is optimized to reduce computational overhead during metrics collection. As a result, metrics scraping completes within the timeout period, and cluster monitoring operates correctly on large production clusters. (link:https://redhat.atlassian.net/browse/OCPBUGS-85410[OCPBUGS-85410])

* Before this update, the Manila CSI driver node plugin crashed immediately on startup if the NFS CSI plugin socket was not available, with no retry logic for connection errors. As a consequence, after node disruptions, the Manila CSI driver accumulated excessive container restarts, causing CI invariant test failures. With this release, the Manila CSI driver retries connection attempts when the NFS plugin socket is temporarily unavailable, and the Operator deployment includes an init container to ensure proper startup ordering. As a result, the driver starts reliably after node reboots without excessive restarts. (link:https://redhat.atlassian.net/browse/OCPBUGS-85457[OCPBUGS-85457])

* Before this update, the `smb-csi-driver-controller` pod had a total memory request of 230 MiB across its seven containers, but a hardcoded memory limit of only 200 MiB on the `csi-driver` container. As a consequence, the pod was deployed in an over-committed state where minimum requirements exceeded maximum allowed usage, triggering constant `KubePodMemoryUsageLimitHigh` alerts. With this release, the pod-level memory limit has been increased to accommodate all sidecar containers introduced in {product-title} 4.20. As a result, monitoring alerts no longer fire for this pod. (link:https://redhat.atlassian.net/browse/OCPBUGS-86023[OCPBUGS-86023])

* Before this update, when the `ClusterCSIDriver` management state of the AWS EBS CSI driver was set to `Unmanaged`, the static resources controller continued to reconcile and revert user-modified fields in the `CSIDriver` resource. As a consequence, manual changes to fields such as `nodeAllocatableUpdatePeriodSeconds` were immediately overwritten by the Operator. With this release, the static resources controller skips reconciliation when the management state is `Unmanaged`. As a result, administrators can modify CSI driver configuration without Operator interference when the driver is in unmanaged mode. (link:https://redhat.atlassian.net/browse/OCPBUGS-86504[OCPBUGS-86504])

* Before this update, when failure domains were removed from the vSphere infrastructure specification, the vSphere Problem Detector logged warning messages indicating "failure domain labels missing from node" even though the nodes and failure domains were correctly configured. As a consequence, misleading warnings appeared in the logs during valid failure domain reconfiguration. With this release, the vSphere Problem Detector correctly handles failure domain removal without generating false warnings. As a result, no spurious warnings are logged when administrators remove failure domains from the platform specification. (link:https://redhat.atlassian.net/browse/OCPBUGS-87906[OCPBUGS-87906])

* Before this update, all containers in the `gcp-pd-csi-driver-controller` deployment ran as the root user (UID 0). As a consequence, the deployment did not follow security best practices for running containers as non-root users. With this release, security constraints have been applied to run all CSI driver controller containers as non-root users with additional hardening including read-only root filesystems and dropped capabilities. As a result, the GCP Persistent Disk CSI driver controller adheres to OpenShift Container Platform security standards. (link:https://redhat.atlassian.net/browse/OCPBUGS-88299[OCPBUGS-88299])

* Before this update, the CSI snapshot controller fired `SnapshotContentObjectDeleteError` warning events when it attempted to delete a `VolumeSnapshotContent` resource that had already been removed. As a consequence, misleading error events appeared during concurrent snapshot deletions or bulk deletion scenarios, even though the final deletion was successful. With this release, the snapshot controller suppresses error events when the resource is already deleted (NotFound error). == Virtualization

* Before this update, the Hosted Cluster Config Operator (HCCO) machine controller included all CAPI machine internal IP addresses in EndpointSlice endpoints without filtering, including link-local addresses such as `169.254.0.2` and `fe80::*`. Because Kubernetes 1.33 added validation that rejects link-local addresses in EndpointSlice endpoints, the HCCO failed to create or update EndpointSlice endpoints for 'kubevirt` guest cluster `LoadBalancer` shadow services on the management cluster. As a consequence, user-created `LoadBalancer` services in hosted clusters deployed with the `kubevirt` provider did not contain EndpointSlice endpoints or backends, which caused connection attempts from the management cluster to fail with "Connection refused" errors. With this release, the HCCO filters out link-local addresses from machine addresses before creating EndpointSlice endpoints. As a result, EndpointSlice endpoints are created successfully for all shadow services, and `LoadBalancer` services in `kubevirt`-based hosted clusters can be accessed from pods on the management cluster. (link:https://redhat.atlassian.net/browse/OCPBUGS-83604[OCPBUGS-83604])
