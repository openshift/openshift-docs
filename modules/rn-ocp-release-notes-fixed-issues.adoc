[id="rn-ocp-release-note-bare-metal-hardware-fixed-issues_{context}"]
== Bare Metal Hardware Provisioning

* Before this update, the `baremetal` cluster Operator did not set its `Progressing` status condition to `True` during cluster upgrades. As a consequence, the Cluster Version Operator (CVO) waited for the Operator without receiving proper progress signals, and upgrade monitoring tests failed. With this release, the `baremetal` Operator correctly reports `Progressing=True` during version changes. As a result, cluster upgrades proceed with accurate Operator status reporting. (link:https://redhat.atlassian.net/browse/OCPBUGS-66101[OCPBUGS-66101])

* Before this update, when the bare-metal host (BMH) `spec.online` parameter was set to `False`, the Bare Metal Operator (BMO) forced the `ironic` service to issue a power-off command to the node at the end of inspection, after the ram disk was ejected. As a consequence, the node operating system lost access to the boot media during shutdown, and filesystem corruption errors were visible on the BMH console. With this release, the node is powered off after inspection, while cleaning up the ram disk, before ejecting Redfish virtual media. As a result, the host does not lose access to the boot media. (link:https://redhat.atlassian.net/browse/OCPBUGS-66156[OCPBUGS-66156])

* Before this update, the Bare Metal Operator (BMO) `getChecksum()` function accepted non-empty checksums for {oci-first-no-rt} images. As a consequence, OCI image provisioning failed. With this release, a check in the `getChecksum()` function rejects non-empty user-provided checksums for OCI images. As a result, OCI image provisioning does not fail. (link:https://redhat.atlassian.net/browse/OCPBUGS-84305[OCPBUGS-84305])

* Before this update, when managing a high volume of `BareMetalHost` resources on a single multicluster engine instance, the Bare Metal Operator (BMO) issued excessive requests to the Provisioner API during reconciliation. As a consequence, VirtualMedia injection and node reconciliation were noticeably slower at this scale. With this release, the BMO reconciliation loop is optimized to issue fewer requests to the Provisioner API. As a result, responsiveness improves when managing large numbers of `BareMetalHost` resources. (link:https://redhat.atlassian.net/browse/OCPBUGS-85527[OCPBUGS-85527])

* Before this update, when servicing a bare-metal host (BMH), the `service_disable_ramdisk` parameter remained set to `False` even if all servicing steps were performed out-of-band. As a result, the BMH underwent an unnecessary reboot. With this release, the `ironic` service code is modified to automatically set `service_disable_ramdisk` to `True` when all servicing steps are out-of-band. (link:https://redhat.atlassian.net/browse/OCPBUGS-85528[OCPBUGS-85528])

* Before this update, the `ironic-agent` container image was missing the `iproute` package at runtime, which provides the `ip` command required for network configuration. As a consequence, the Ironic Python Agent (IPA) failed to heartbeat to the `ironic` service during bare-metal node cleaning, and node cleaning operations timed out. With this release, the `ironic-agent` container image build process is updated to retain required packages such as `iproute` and `psmisc`. As a result, IPA completes network configuration successfully and bare-metal node cleaning operations complete without timing out. (link:https://redhat.atlassian.net/browse/OCPBUGS-94115[OCPBUGS-94115])

* Before this update, bare-metal nodes provisioned through virtual media failed to boot the inspection image because of incorrect kernel arguments in the provisioning ISO. As a consequence, soft lockups occurred on some hardware, for example, Fujitsu PRIMERGY M8, because the `{{console=ttyS0}}` parameter lacked baud rate and parity settings. The `{{ip=dhcp}}` parameter was missing, which prevented network acquisition during early boot. With this release, the provisioning ISO includes the `{{ip=dhcp}}` parameter and specifies the full serial console configuration. As a result, bare-metal Installer-provisioned installations complete without manual intervention. (link:https://redhat.atlassian.net/browse/OCPBUGS-98696[OCPBUGS-98696])

* Before this update, the Bare Metal Operator (BMO) did not set the `IRONIC_INSECURE` function. As a consequence, bare-metal host (BMH) provisioning failed. With this release, the BMO correctly sets the `IRONIC_INSECURE` function. As a result, BMH provisioning succeeds. (link:https://redhat.atlassian.net/browse/OCPBUGS-111889[OCPBUGS-111889])

[id="rn-ocp-release-note-cloud-compute-fixed-issues_{context}"]
== Cloud Compute

* Before this update, the `AWSMachine` controller was requeuing machine instances before confirming the presence of tags. As a consequence, duplicate {aws-first} EC2 instances were created. With this release, the `AWSMachine` controller verifies tags before requeuing instances. As a result, duplicate EC2 instances are not created. (link:https://redhat.atlassian.net/browse/OCPBUGS-62985[OCPBUGS-62985])

* Before this update, if an OpenStack cloud provider lacked the optional Standard Attributes Tag extension, the Machine API Provider for OpenStack (MAPO) attempted to apply port tags during network port creation. As a consequence, provisioning failed. With this release, MAPO checks whether the `standard-attr-tag` extension is available before applying tags. If unsupported, MAPO skips tag assignment or returns an error prompting you to remove explicit configurations. As a result, machine provisioning completes successfully. (link:https://redhat.atlassian.net/browse/OCPBUGS-77061[OCPBUGS-77061])

As a consequence, unnecessary log messages were generated. With this update, the Operator recognizes externally managed secrets and skips unnecessary reconciliation. (link:https://redhat.atlassian.net/browse/OCPBUGS-33994[OCPBUGS-33994])

== etcd

* Before this update, an upgrade with a control plane `MachineConfig` might have caused quorum loss. As a consequence, the upgrade caused prolonged API and etcd downtime, leading to service interruption. With this release, the `cluster-etcd-operator` keeps guard pods that prevent a `MachineConfig` object from draining the node. As a result, etcd maintains quorum during upgrades. (link:https://redhat.atlassian.net/browse/OCPBUGS-66334[OCPBUGS-66334])

[id="rn-ocp-release-note-Helm-fixed-issues_{context}"]
== Helm

* Before this update, installing a Helm chart by using the Chart URL option in the {product-title} web console with an {oci-first} URL that included a version number, for example, `oci://registry-1.docker.io/bitnamicharts/nginx:22.6.12` failed with an error indicating that the chart was not available or could not be found. As a consequence, users could not install Helm charts from OCI registries when specifying the version number directly in the URL. With this release, the Helm chart installation process correctly handles OCI URLs that include version numbers. As a result, users can now successfully install Helm charts from OCI registries by providing the complete URL with the version number in the web console Chart URL field.

[id="rn-ocp-release-note-hosted-control-planes-fixed-issues_{context}"]
== Hosted Control Planes

* Before this update, KubeVirt-based `NodePool` resources incorrectly reported `ClusterNetworkCIDRConflict` errors because the controller flagged OVN-Kubernetes internal overlay IP addresses as conflicting with the cluster network. With this release, Classless Inter-Domain Routing (CIDR) conflict detection is triggered only when all the non-link local addresses for the machine fall within the cluster network. As a result, when external addresses exist, in-network addresses are correctly treated as expected container network interface (CNI) internal IP addresses, which prevents false positive conflict reports. (link:https://redhat.atlassian.net/browse/OCPBUGS-84269[OCPBUGS-84269])

* Before this update, applying resource overrides to containers without pre-existing resource requests caused a nil map panic and crash loop. With this release, a nil guard is added to the `applyRequestsOverrides` function in the Control Plane Operator (CPO) before calling `maps.Copy` on the `Resources.Requests` parameter. As a result, resource request overrides are successfully applied regardless of pre-existing requests. (link:https://redhat.atlassian.net/browse/OCPBUGS-93785[OCPBUGS-93785])

* Before this update, the Konnectivity proxy-server in the `kube-apiserver` deployment was not configured with the `--cluster-ca-cert` flag. As a consequence, a reachable client could establish a connection to the Konnectivity proxy-server without a valid client certificate signed by the hosted cluster Konnectivity certification authority (CA). With this release, the `--cluster-ca-cert` flag is added to the `konnectivity-server` container arguments in the `kube-apiserver` deployment manifest. As a result, unauthenticated connections are prevented because the proxy-server requires and validates client certificates signed by the hosted cluster Konnectivity CA. (link:https://redhat.atlassian.net/browse/OCPBUGS-99014[OCPBUGS-99014])

[id="rn-ocp-release-note-monitoring-fixed-issues_{context}"]
== Monitoring

* Before this update, when Prometheus compacted time series data, it attempted to enable direct I/O on files that were already open. Some file systems, such as {ibm-title} Storage Scale, do not support this operation. As a consequence, compaction failed with a `cannot enable Direct IO: invalid argument` error, Prometheus could not write chunks to disk, and memory usage in Prometheus pods increased until the pods hit their memory limits and restarted or affected other workloads on the node. With this release, Prometheus detects when a file system does not support direct I/O on open files and handles the condition gracefully. As a result, Prometheus writes chunks to disk and completes compaction successfully on these storage back ends. (link:https://redhat.atlassian.net/browse/OCPBUGS-92191[OCPBUGS-92191])

* Before this update, the Cluster Monitoring Operator (CMO) checked only the `openshift-config/pull-secret` for the `cloud.openshift.com` authentication token used by the telemeter client. As a consequence, on platforms where this secret did not contain the token, such as the {azure-first} Red Hat OpenShift {hcp}, the telemeter client was not deployed, which prevented cluster registration in {cluster-manager-first}. With this release, the CMO falls back to `kube-system/global-pull-secret` if the token is not found in the primary secret. As a result, the telemeter client is deployed correctly. (link:https://redhat.atlassian.net/browse/OCPBUGS-98450[OCPBUGS-98450])

* Before this update, Alertmanager crashed because the `tzdata` package was missing in the {product-title} base images, This issue caused the absence of the `/usr/share/zoneinfo` directory. As a consequence, Alertmanager pods failed to start, which made time-based alerts inaccessible for the time zones. With this release, the `tzdata` package is reinstated in {product-title} images. As a result, Alertmanager does not crash on startup when location fields are present in the `active_interval` or `mute_interval` entries. (link:https://redhat.atlassian.net/browse/OCPBUGS-99435[OCPBUGS-99435])

* Before this update, containers in the `openshift-monitoring` namespace ran with writable root filesystems because `readOnlyRootFilesystem: true` was not enabled in their security contexts. As a consequence, customer compliance scans flagged these containers as security policy violations. With this release, monitoring components enable read-only root filesystems with dedicated `emptyDir` volumes for paths requiring write access. As a result, monitoring containers meet compliance requirements for read-only root filesystems. (link:https://redhat.atlassian.net/browse/OCPBUGS-105389[OCPBUGS-105389])

* Before this update, Fibre Channel adapters reported incomplete data. As a consequence, the node_exporter failed to run. With this release, guards are added to ignore incomplete data. (link:https://redhat.atlassian.net/browse/OCPBUGS-112719[OCPBUGS-112719])

[id="rn-ocp-release-note-node-fixed-issues_{context}"]
== Node

* Before this update, when control plane nodes rebooted during resiliency testing, Tuned pods running on worker nodes occasionally lost connectivity to the Kubernetes API server and entered a degraded state with errors such as "rpc error: code = Unavailable desc = keepalive ping failed to receive ACK within timeout" and "dial tcp 172.22.0.1:443: i/o timeout". As a consequence, `PerformanceProfile` resources showed a Degraded status with `ComponentCreationFailed`, and the only recovery method was to manually restart the affected Tuned pod. With this release, Tuned pods handle temporary API server connectivity loss more gracefully and automatically recover when connectivity is restored. As a result, `PerformanceProfile` resources remain healthy during control plane node reboots, and manual intervention is no longer required. (link:https://redhat.atlassian.net/browse/OCPBUGS-62277[OCPBUGS-62277])

* Before this update, the upstream pod in-place resize scheduler-focused test expected a second test pod to remain in `Pending` phase when the first pod consumed all available CPU resources, but the scheduler incorrectly allowed the second pod to enter `Running` phase. As a consequence, the test failed consistently with the error "Expected pod 'testpod2' to be in phase Pending, but got phase: Running". With this release, the scheduler correctly enforces resource constraints during in-place resize operations. As a result, the test passes reliably and pods are scheduled according to available node resources. (link:https://redhat.atlassian.net/browse/OCPBUGS-63132[OCPBUGS-63132])

* Before this update, when the `config-operator` restarted or experienced temporary API server connectivity issues, the `config-drift-monitor` emitted `ConfigDriftMonitorStopped` and `RemoveSigtermProtection` events repeatedly for each Tuned resource during recovery. As a consequence, the pathological events test failed in serial-techpreview jobs, reporting that these events occurred more than 20 times. With this release, the `config-drift-monitor` reduces event noise during restart and recovery scenarios. As a result, pathological event tests pass reliably in serial-techpreview jobs. (link:https://redhat.atlassian.net/browse/OCPBUGS-63307[OCPBUGS-63307])

* Before this update, when the kubelet calculated resource capacity during pod resize operations with the `InPlacePodVerticalScaling` feature gate enabled, it incorrectly computed the used CPU value as an extremely large number instead of the actual value. As a consequence, pod resize requests failed with "OutOfcpu" errors even when sufficient CPU capacity was available on the node. With this release, the kubelet correctly calculates used CPU during resize operations. As a result, in-place pod vertical scaling requests succeed when the node has sufficient CPU resources. (link:https://redhat.atlassian.net/browse/OCPBUGS-64847[OCPBUGS-64847])

* Before this update, when `AutoSizingReserved` option was enabled by default for all topologies including {hcp}, the feature dynamically increased system-reserved memory based on node size, which significantly reduced allocatable memory on the small instance types, for example, m5.large and m5.xlarge used in {hcp} worker nodes. As a consequence, platform pods such as monitoring, DNS, networking, and registry could not be scheduled on {hcp} worker nodes due to insufficient allocatable memory, causing cluster Operators to degrade and e2e tests to fail. With this release, `AutoSizingReserved` option is disabled for {hcp} worker nodes (`ControlPlaneTopology=External`). As a result, {hcp} e2e tests pass and {hcp} worker nodes have sufficient allocatable memory for all platform pods to schedule successfully. (link:https://redhat.atlassian.net/browse/OCPBUGS-79502[OCPBUGS-79502])

* Before this update, when scheduling pods that request PCI devices on systems with very large Non-uniform Memory Access (NUMA) topologies (for example, NVIDIA GB200 systems with 34 NUMA nodes), the kubelet TopologyManager never finished computing topology hints because of combinatorial explosion in hint generation. As a consequence, pods requesting GPU, InfiniBand, or Non-Volatile Memory Express (NVMe) devices remained indefinitely in `Pending` state, and KubeVirt VirtualMachineInstances using `hostDevices` never transitioned to Running. With this release, the TopologyManager hint generation algorithm is optimized to compute hints in bounded time even on systems with many NUMA nodes. As a result, pods and VMs requesting PCI host devices start successfully on large NUMA systems such as GB200-class hardware. (link:https://redhat.atlassian.net/browse/OCPBUGS-83502[OCPBUGS-83502])

* Before this update, {product-title} switched to RHEL 10 as the default base operating system, but the `runc` OCI runtime binary was not included in the RHCOS 10 image. As a consequence, all CI jobs configured to use `runc` as the OCI runtime failed during bootstrap because CRI-O could not find the `runc` executable in `$PATH`, preventing container runtime initialization. With this release, the CI infrastructure for runc-based jobs is updated to ensure the runc binary is available in RHCOS 10 environments. As a result, runc-based CI jobs bootstrap successfully and complete without runtime errors. (link:https://redhat.atlassian.net/browse/OCPBUGS-89267[OCPBUGS-89267])

* Before this update, the Kubelet LimitedSwap Drop-in Configuration test case (TC6) for Container-Native Virtualization (CNV) failed during kubelet restart via `oc debug node`, which degraded worker nodes and left system configuration artifacts (`system_compressible` and `reserved-cpu-test` remnants). As a consequence, subsequent tests in the `disruptive-longrunning` suite needed significantly more time to complete, and the entire test suite timed out. With this release, the test properly cleans up node configuration and ensures kubelet restarts successfully without degrading the node. As a result, `disruptive-longrunning` test suites complete within the expected time without timeout failures. (link:https://redhat.atlassian.net/browse/OCPBUGS-90507[OCPBUGS-90507])

* Before this update, the `CRIOCredentialProviderConfig` custom resource definition (CRD) immediately set `v1` as the storage version when first introduced. As a consequence, clusters that upgraded to a version containing this CRD could not safely roll back to earlier versions because the storage version change was not gradual. With this release, the CRD follows the rollback-safe versioning pattern and does not immediately change the storage version upon introduction. As a result, cluster administrators can safely roll back upgrades without encountering CRD storage version incompatibilities. (link:https://redhat.atlassian.net/browse/OCPBUGS-94869[OCPBUGS-94869])

* Before this update, the upstream Kubernetes test for Dynamic Resource Allocation (DRA) extended resources deployed a DRA driver and sample device plugin on separate nodes, and the test infrastructure exhibited flakiness when the driver setup interacted with the device plugin. As a consequence, the test failed approximately 53% of the time in the serial suite with errors such as "endpoint not found in cache for a registered resource: example.com/resource". With this release, the test is skipped in the general serial lane, matching the upstream approach of testing DRA in a dedicated lane where the driver setup is more reliable. As a result, the serial suite no longer experiences frequent failures from this flaky DRA test infrastructure. (link:https://redhat.atlassian.net/browse/OCPBUGS-99058[OCPBUGS-99058])

* Before this update, the CPU Partitioning conformance test enumerated all `openshift-*` namespaces and expected them to have the `workload.openshift.io/allowed:management` annotation, but did not exclude ephemeral `openshift-debug-*` namespaces created by `oc debug node/` commands in parallel `SecurityPenetration` tests. As a consequence, when `SecurityPenetration` tests ran concurrently with the CPU Partitioning test, the CPU Partitioning test failed because debug namespaces lacked the management annotation. With this release, the test excludes `openshift-debug-*` namespaces from the annotation check. As a result, the CPU Partitioning test passes reliably even when `SecurityPenetration` tests run in parallel. (link:https://redhat.atlassian.net/browse/OCPBUGS-100392[OCPBUGS-100392])

* Before this update, when creating approximately 100 pods concurrently on the same node with each pod mounting the same OCI image as an Image volume, CRI-O acquired a write lock for every mount operation through the containers/storage layer. As a consequence, even though the image layer was already present on the node, all mount operations serialized behind a single lock, causing pod startup time to increase by approximately 80% compared to using EmptyDir volumes. With this release, CRI-O optimizes the image volume mount path to avoid unnecessary lock contention when mounting already-present image layers. As a result, mounting the same image across many pods on a node no longer significantly degrades pod startup performance. (link:https://redhat.atlassian.net/browse/OCPBUGS-108950[OCPBUGS-108950])

* Before this update, the Node Tuning Operator performed unconditional status updates for all tuned resources during every sync event, resulting in O(N²) PUT requests with strict client-side rate limiting (QPS=5, Burst=10). As a consequence, on large clusters with many tuned resources (for example, 150+ nodes with 43 tuned CRs), the Operator experienced severe reconciliation delays of up to 17 minutes, leaving newly scaled nodes unusable until their profiles were generated. With this release, the Operator only updates tuned resource status when changes occur and increases client-side QPS limits to 50. As a result, reconciliation completes promptly even on large-scale clusters, and node scale-out operations proceed without extended delays. (link:https://redhat.atlassian.net/browse/OCPBUGS-112279[OCPBUGS-112279])

* Before this update, the Performance Profile Creator `info` command help text documented the pre-4.20 `--info=log` and `--info=json` flag values and was inconsistent with the current CLI implementation. As a consequence, users and documentation authors were confused because the help text contradicted the actual working flags (`--text` and `--json`). With this release, the help text for the `info` command is updated to accurately reflect the current CLI, documenting the `info` subcommand and its `--text` and `--json` flags. As a result, the help text is consistent with the actual CLI behavior. (link:https://redhat.atlassian.net/browse/OCPBUGS-114144[OCPBUGS-114144])

* Before this update, the Node Tuning Operator enabled `timer.migration` on all kernel versions to prevent TCP and other timers from interfering with latency-sensitive workloads. As a consequence, high-resolution timers lost their high-resolution properties when migrated to other CPUs, which negatively impacted `cyclictest` and similar benchmarks. With this release, `timer.migration` is automatically disabled on RHEL 10 kernels, which implement a new timer wheel logic that provides good behavior for both polling and timer latency-sensitive workloads without requiring timer migration. As a result, both polling and high-resolution timer workloads achieve better latency on RHEL 10-based systems. (link:https://redhat.atlassian.net/browse/OCPBUGS-114934[OCPBUGS-114934])

== Pod Autoscaler

* Before this update, by default, the Vertical Pod Autoscaler (VPA) Operator required a control plane node for running workloads. As a consequence, it caused issues in single-node deployments. With this release, the Operator is updated to support deployment without control plane node requirements. As a result, the VPA Operator functions correctly in single-node configurations. == Virtualization

* Before this update, the Hosted Cluster Config Operator (HCCO) machine controller included all CAPI machine internal IP addresses in EndpointSlice endpoints without filtering, including link-local addresses such as `169.254.0.2` and `fe80::*`. Because Kubernetes 1.33 added validation that rejects link-local addresses in EndpointSlice endpoints, the HCCO failed to create or update EndpointSlice endpoints for 'kubevirt` guest cluster `LoadBalancer` shadow services on the management cluster. As a consequence, user-created `LoadBalancer` services in hosted clusters deployed with the `kubevirt` provider did not contain EndpointSlice endpoints or backends, which caused connection attempts from the management cluster to fail with "Connection refused" errors. With this release, the HCCO filters out link-local addresses from machine addresses before creating EndpointSlice endpoints. As a result, EndpointSlice endpoints are created successfully for all shadow services, and `LoadBalancer` services in `kubevirt`-based hosted clusters can be accessed from pods on the management cluster. (link:https://redhat.atlassian.net/browse/OCPBUGS-83604[OCPBUGS-83604])
