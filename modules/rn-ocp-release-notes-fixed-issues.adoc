== API Server and Authentication

* Before this update, the OAuth server login page displayed OKD branding instead of OpenShift branding. As a consequence, users saw incorrect branding on the login page. With this update, the Operator binary is built with the correct branding configuration. As a result, the OAuth server login page displays OpenShift branding as expected. (link:https://issues.redhat.com/browse/OCPBUGS-69977[OCPBUGS-69977])

* Before this update, LDAP group sync using the RFC 2307 schema failed with a "Filter Compile Error" when `groupUIDAttribute` was set to `dn`. As a consequence, users could not sync LDAP groups despite following the documented configuration. With this update, filter validation is skipped for group queries that use `dn` as the group UID attribute. As a result, LDAP group sync with the RFC 2307 schema completes successfully. (link:https://issues.redhat.com/browse/OCPBUGS-78768[OCPBUGS-78768])

[id="rn-ocp-release-note-bare-metal-hardware-fixed-issues_{context}"]
== Bare Metal Hardware Provisioning

* Before this update, the `baremetal` cluster Operator did not set its `Progressing` status condition to `True` during cluster upgrades. As a consequence, the Cluster Version Operator (CVO) waited for the Operator without receiving proper progress signals, and upgrade monitoring tests failed. With this release, the `baremetal` Operator correctly reports `Progressing=True` during version changes. As a result, cluster upgrades proceed with accurate Operator status reporting. (link:https://redhat.atlassian.net/browse/OCPBUGS-66101[OCPBUGS-66101])

* Before this update, when the bare-metal host (BMH) `spec.online` parameter was set to `False`, the Bare Metal Operator (BMO) forced the `ironic` service to issue a power-off command to the node at the end of inspection, after the RAM disk was ejected. As a consequence, the node operating system lost access to the boot media during shutdown, and filesystem corruption errors were visible on the BMH console. With this release, the node is powered off after inspection, while cleaning up the RAM disk, before ejecting Redfish virtual media. As a result, the host does not lose access to the boot media. (link:https://redhat.atlassian.net/browse/OCPBUGS-66156[OCPBUGS-66156])

* Before this update, the Bare Metal Operator (BMO) `getChecksum()` function accepted non-empty checksums for {oci-first-no-rt} images. As a consequence, OCI image provisioning failed. With this release, a check in the `getChecksum()` function rejects non-empty user-provided checksums for OCI images. As a result, OCI image provisioning does not fail. (link:https://redhat.atlassian.net/browse/OCPBUGS-84305[OCPBUGS-84305])

* Before this update, when managing a high volume of `BareMetalHost` resources on a single multicluster engine instance, the Bare Metal Operator (BMO) issued excessive requests to the Provisioner API during reconciliation. As a consequence, VirtualMedia injection and node reconciliation were noticeably slower at this scale. With this release, the BMO reconciliation loop is optimized to issue fewer requests to the Provisioner API. As a result, responsiveness improves when managing large numbers of `BareMetalHost` resources. (link:https://redhat.atlassian.net/browse/OCPBUGS-85527[OCPBUGS-85527])

* Before this update, when servicing a bare-metal host (BMH), the `service_disable_ramdisk` parameter remained set to `False` even if all servicing steps were performed out-of-band. As a result, the BMH underwent an unnecessary reboot. With this release, the `ironic` service code is modified to automatically set `service_disable_ramdisk` to `True` when all servicing steps are out-of-band. (link:https://redhat.atlassian.net/browse/OCPBUGS-85528[OCPBUGS-85528])

* Before this update, the `ironic-agent` container image was missing the `iproute` package at runtime, which provides the `ip` command required for network configuration. As a consequence, the Ironic Python Agent (IPA) failed to heartbeat to the `ironic` service during bare-metal node cleaning, and node cleaning operations timed out. With this release, the `ironic-agent` container image build process is updated to retain required packages such as `iproute` and `psmisc`. As a result, IPA completes network configuration successfully and bare-metal node cleaning operations complete without timing out. (link:https://redhat.atlassian.net/browse/OCPBUGS-94115[OCPBUGS-94115])

* Before this update, bare-metal nodes provisioned through virtual media failed to boot the inspection image because of incorrect kernel arguments in the provisioning ISO. As a consequence, soft lockups occurred on some hardware, for example, Fujitsu PRIMERGY M8, because the `{{console=ttyS0}}` parameter lacked baud rate and parity settings. The `{{ip=dhcp}}` parameter was missing, which prevented network acquisition during early boot. With this release, the provisioning ISO includes the `{{ip=dhcp}}` parameter and specifies the full serial console configuration. As a result, bare-metal Installer-provisioned installations complete without manual intervention. (link:https://redhat.atlassian.net/browse/OCPBUGS-98696[OCPBUGS-98696])

* Before this update, the Bare Metal Operator (BMO) did not set the `IRONIC_INSECURE` function. As a consequence, bare-metal host (BMH) provisioning failed. With this release, the BMO correctly sets the `IRONIC_INSECURE` function. As a result, BMH provisioning succeeds. (link:https://redhat.atlassian.net/browse/OCPBUGS-111889[OCPBUGS-111889])

== Cloud Compute

* Before this update, the `AWSMachine` controller was requeuing machine instances before confirming the presence of tags. As a consequence, duplicate {aws-first} EC2 instances were created. With this release, the `AWSMachine` controller verifies tags before requeuing instances. As a result, duplicate EC2 instances are not created. (link:https://redhat.atlassian.net/browse/OCPBUGS-62985[OCPBUGS-62985])

* Before this update, if an OpenStack cloud provider lacked the optional Standard Attributes Tag extension, the Machine API Provider for OpenStack (MAPO) attempted to apply port tags during network port creation. As a consequence, provisioning failed. With this release, MAPO checks whether the `standard-attr-tag` extension is available before applying tags. If unsupported, MAPO skips tag assignment or returns an error prompting you to remove explicit configurations. As a result, machine provisioning completes successfully. (link:https://redhat.atlassian.net/browse/OCPBUGS-77061[OCPBUGS-77061])

[id="rn-ocp-release-note-hosted-control-planes-fixed-issues_{context}"]
== Hosted Control Planes

* Before this update, KubeVirt-based `NodePool` resources incorrectly reported `ClusterNetworkCIDRConflict` errors because the controller flagged OVN-Kubernetes internal overlay IP addresses as conflicting with the cluster network. With this release, Classless Inter-Domain Routing (CIDR) conflict detection is triggered only when all the non-link local addresses for the machine fall within the cluster network. As a result, when external addresses exist, in-network addresses are correctly treated as expected container network interface (CNI) internal IP addresses, which prevents false positive conflict reports. (link:https://redhat.atlassian.net/browse/OCPBUGS-84269[OCPBUGS-84269])

* Before this update, applying resource overrides to containers without pre-existing resource requests caused a nil map panic and crash loop. With this release, a nil guard is added to the `applyRequestsOverrides` function in the Control Plane Operator (CPO) before calling `maps.Copy` on the `Resources.Requests` parameter. As a result, resource request overrides are successfully applied regardless of pre-existing requests. (link:https://redhat.atlassian.net/browse/OCPBUGS-93785[OCPBUGS-93785])

* Before this update, the Konnectivity proxy-server in the `kube-apiserver` deployment was not configured with the `--cluster-ca-cert` flag. As a consequence, a reachable client could establish a connection to the Konnectivity proxy-server without a valid client certificate signed by the hosted cluster Konnectivity certification authority (CA). With this release, the `--cluster-ca-cert` flag is added to the `konnectivity-server` container arguments in the `kube-apiserver` deployment manifest. As a result, unauthenticated connections are prevented because the proxy-server requires and validates client certificates signed by the hosted cluster Konnectivity CA. (link:https://redhat.atlassian.net/browse/OCPBUGS-99014[OCPBUGS-99014])

[id="rn-ocp-release-note-installer-fixed-issues_{context}"]
== Installer

* Before this update, when you configured networking with the `agent-tui` parameter during an Assisted Installer workflow, the `NetworkManager` keyfiles created in that session were not automatically passed to the CoreOS installation program. As a consequence, the installation program could not identify the keyfiles as manually created configurations and the network configurations set up through the `agent-tui` parameter during installation did not persist into the installed operating system. This issue caused nodes to have missing or incorrect network settings after the cluster was deployed. With this release, the agent detects manually-created `NetworkManager` keyfiles by comparing their modification times against the agent-tui start time (derived from the birth time of the `/var/log/agent` parameter). When these keyfiles are found, the `--copy-network` command is automatically appended to the CoreOS installation program arguments, which ensures the configurations are passed on to the installed system. (link:https://redhat.atlassian.net/browse/OCPBUGS-63472[OCPBUGS-63472])

* Before this update, older versions of Software Development Kit (SDK) for Virtual Private Cloud (VPC) could not parse a VPC with new security group rule types, such as `any`, that were introduced by {ibm-cloud-title}. As a consequence, the installation program could not successfully set up a new VPC or use an existing VPC with such a protocol type. With this release, the SDK for VPC is updated to a version that supports parsing the new types. As a result, the installation process can create or use a VPC with the new security group rule types. (link:https://redhat.atlassian.net/browse/OCPBUGS-78429[OCPBUGS-78429])

* Before this update, the installation program created inbound {aws-first} security group rules for a TCP port range historically used for Open Virtual Network (OVN) northbound and southbound database traffic between control plane and compute nodes. These rules used inconsistent port numbers across {product-title} versions, with some versions creating rules for ports `6441-6442` instead of the correct `6641-6642`. As a consequence, clusters exposed unnecessary and inconsistently numbered inbound security group rules. These rules no longer reflected how OVN-Kubernetes (OVN-K) communicates the northbound and southbound databases that run locally on each node and communicate over UNIX domain sockets rather than TCP. With this release, the installation program does not create the security group rules for these OVN database ports on {aws-short}. As a result, newly installed {aws-short} clusters no longer include the unused, inconsistently numbered inbound security group rules. (link:https://issues.redhat.com/browse/OCPBUGS-79536[OCPBUGS-79536])

* Before this update, during an appliance-based no-registry installation, the `watch-iri-tls-certs.path` and `reconfigure-local-registry-iri-tls.sh` files that reconfigure the local registry when Internal Release Image (IRI) TLS certificates are generated by Assisted Service were not included in the bootstrap ignition. The files were only present in the installation ignition, so they never ran at the correct time. As a consequence, the appliance registry on the rendezvous host continued serving with its initial self-signed certificates after the IRI TLS certificate was created. Other nodes could not pull images from the registry over api-int, causing the installation to fail. With this release, the `watch-iri-tls-certs.path` unit and `reconfigure-local-registry-iri-tls.service` are included in the bootstrap ignition so the appliance registry is reconfigured with the correct IRI TLS certificate as soon as Assisted Service generates it. As a result, other nodes can pull images from the registry during installation and the installation completes successfully. (link:https://issues.redhat.com/browse/OCPBUGS-81505[OCPBUGS-81505])

* Before this update, the Internal Release Image (IRI) registry, which serves the release image payload to cluster nodes, had its backing store mounted read-only but lacked enforcement at the application layer. As a consequence, any attempt to push an image to the IRI registry at `api-int.<baseDomain>:22625` returned an `HTTP 500 Internal Server Error`, with no indication that the registry was intentionally read-only. With this release, the `REGISTRY_STORAGE_MAINTENANCE_READONLY` environment variable is set on the IRI registry service. As result, an `HTTP 405 Method Not Allowed` message is returned on write attempts. (link:https://issues.redhat.com/browse/OCPBUGS-82974[OCPBUGS-82974])

* Before this update, when destroying a cluster installed in the {aws-first} China `cn-north-1` (Beijing) region, the installation program did not search the `cn-northwest-1` region for tagged Route 53 resources. As a consequence, Route 53 hosted zones and associated records were not deleted during cluster destruction. This issue resulted in leaked resources in the {aws-short} China partition that required manual cleanup. With this release, the installation program correctly creates a tag client for the `cn-northwest-1` region when destroying a cluster from the `cn-north-1` region to discover all cluster-owned Route 53 resources. As a result, Route 53 hosted zones are properly discovered and deleted during cluster destruction in the {aws-short} China `cn-north-1` region. (link:https://redhat.atlassian.net/browse/OCPBUGS-85352[OCPBUGS-85352])

* Before this update, on {gcp-first} clusters, values specified in `defaultMachinePlatform` were not applied to individual machine pools during cluster installation. As a consequence, settings such as `osDisk.diskType` were ignored, and control plane nodes used default values instead of the specified configuration. With this release, the installation program correctly applies `defaultMachinePlatform` settings to all machine pools. As a result, {gcp-short} machine configurations use the specified platform defaults. (link:https://redhat.atlassian.net/browse/OCPBUGS-88303[OCPBUGS-88303])

* Before this update, when removing a cluster, an error querying or deleting a Cloud Native Storage (CNS) volume prevented the installation program from processing remaining volumes. As a consequence, storage resources were not deleted. With this release, the installation program processes the remaining volumes across vCenters after individual errors and reports any cleanup failures. As a result, orphaned storage resources are prevented. (link:https://redhat.atlassian.net/browse/OCPBUGS-92792[OCPBUGS-92792])

* Before this update, the installation program used a 30-second timeout when retrieving marketplace images. As a consequence, installation could fail with `context deadline exceeded` errors during `GetMarketplaceImage` operations. With this release, the installation program increases the timeout for retrieving marketplace images to five minutes. As a result, the installation program can successfully retrieve marketplace images. (link:https://redhat.atlassian.net/browse/OCPBUGS-113641[OCPBUGS-113641])

[id="rn-ocp-release-note-kube-api-server-fixed-issues_{context}"]
== Kube API Server

* Before this update, the `kube-apiserver-check-endpoints` container generated a TLS certificate for the `check-endpoint` service on port `17697` with a validity of only one second. As a consequence, the certificate expired almost immediately after generation, which differed from earlier {product-title} versions where the certificate was valid for one month. With this release, the `kube-apiserver-check-endpoints` container generates certificates with an appropriate validity period. As a result, the `check-endpoint` service certificate remains valid for the expected duration, consistent with earlier releases. (link:https://redhat.atlassian.net/browse/OCPBUGS-62792[OCPBUGS-62792])

* Before this update, clusters installed with a custom service account issuer included both the custom issuer and the default issuer during the first 24 hours. As a consequence, service account tokens included two audiences, preventing some applications from deploying unless the audience was explicitly specified. With this release, only the custom issuer is present when configured during installation. As a result, service account tokens contain a single audience, and some applications can deploy immediately. (link:https://redhat.atlassian.net/browse/OCPBUGS-76588[OCPBUGS-76588])

* Before this update, certificate files for the Kube API server were not flushed to disk immediately after being written, and data could remain in memory without being persisted to storage. As a consequence, on {sno} clusters, an ungraceful shutdown could cause all Kube API server certificates to be lost, leaving the cluster unable to start. With this release, certificate writes are flushed to disk before any earlier data is removed, ensuring crash durability. As a result, {sno} clusters that experience an unexpected shutdown no longer risk losing their Kube API server certificates. (link:https://redhat.atlassian.net/browse/OCPBUGS-84258[OCPBUGS-84258])

* Before this update, when deploying STS clusters through Hive or ACM with manual credentials mode, the `kube-apiserver` Operator ignored the custom service account issuer from the Authentication CR during the first revision. As a consequence, the `kube-apiserver` used the default issuer at startup and then rolled out with the correct issuer after bootstrap, which raced against token expiry and caused installation timeouts. With this update, the Operator falls back to discovering the service account issuer from the rendered input manifests. As a result, STS cluster installations using Hive or ACM no longer experience timeouts caused by a service account issuer mismatch. (link:https://issues.redhat.com/browse/OCPBUGS-86057[OCPBUGS-86057])

* Before this update, the `kube-apiserver-to-kubelet-signer` CA certificate refresh interval was incorrectly set to 30 days despite having a 365-day validity period. As a consequence, the CA was regenerated monthly, triggering unnecessary `kube-apiserver` rollouts. With this update, the refresh interval is set to 292 days, which is 80% of the validity period, consistent with other signers. As a result, the CA is no longer regenerated prematurely and unnecessary rollouts no longer occur. (link:https://issues.redhat.com/browse/OCPBUGS-86699[OCPBUGS-86699])

* Before this update, the Go OpenSSL Federal Information Processing Standards (FIPS) provider could potentially overwhelm `libcrypto` library with concurrent requests. As a consequence, processes could hit the `maxThreads` limit of 10,000 and crash. With this release, the Go OpenSSL FIPS provider is updated to limit concurrent requests to the `libcrypto` library to four times the number of CPUs, buffering requests as lightweight Go routines. As a result, processes avoid the `maxThreads` limit and do not crash. (link:https://redhat.atlassian.net/browse/OCPBUGS-99552[OCPBUGS-99552])

== Kube Scheduler

* Before this update, the `kube-scheduler` Cluster Operator briefly reported a `Degraded=True` status during cluster upgrades due to transient node not-ready events and static pod restarts. With this update, a 10-minute stabilization period is applied to the `NodeControllerDegraded`, `StaticPodsDegraded`, and `GuardControllerDegraded` conditions. As a result, the `kube-scheduler` Cluster Operator no longer falsely reports a degraded status during upgrades. (link:https://issues.redhat.com/browse/OCPBUGS-38663[OCPBUGS-38663])

== Machine Config Operator

* Before this update, when nodes used a locally stored RHEL CoreOS image and the image was garbage collected by Kubernetes, applying an extension to the node caused the machine config pool to become degraded. As a consequence, node updates failed with an error indicating that the image reference could not be resolved. With this release, the Machine Config Operator properly handles locally stored images that might be garbage collected. As a result, machine config pools no longer become degraded in this scenario. (link:https://redhat.atlassian.net/browse/OCPBUGS-57473[OCPBUGS-57473])

* Before this update, when Image Mode was enabled in a machine config pool and the `MachineOSConfig` resource was deleted before the operating system image was fully applied to all nodes, the machine config pool became degraded. As a consequence, nodes failed to update with manifest unknown errors because the operating system image was garbage collected from the internal registry. With this release, the Machine Config Operator prevents premature garbage collection of operating system images during rollouts. As a result, machine config pools no longer become degraded when `MachineOSConfig` resources are deleted during image application. (link:https://redhat.atlassian.net/browse/OCPBUGS-59197[OCPBUGS-59197])

* Before this update, the Machine Config Operator used inconsistent cryptographic implementations (`OpenPGP` versus `gpgme`) across different components. As a consequence, build environments without the `gpgme-devel` package experienced compilation failures. With this release, all Machine Config Operator components use the `gpgme` implementation consistently. As a result, builds complete successfully and align with industry-standard container tools. (link:https://redhat.atlassian.net/browse/OCPBUGS-63750[OCPBUGS-63750])

* Before this update, the `machine-config` `ClusterOperator` did not reference cluster-scoped RBAC resources in its `relatedObjects` field. As a consequence, the `oc adm inspect clusteroperator/machine-config` command did not collect `ClusterRole` and `ClusterRoleBinding` resources needed for debugging. With this release, the `ClusterOperator` includes all relevant cluster-scoped resources in its `relatedObjects` field. As a result, must-gather and inspect commands collect complete debugging information. (link:https://redhat.atlassian.net/browse/OCPBUGS-65504[OCPBUGS-65504])

* Before this update, when an extension package installation failed but did not return an error code, the machine config pool reported success even though the packages were not installed on the node. As a consequence, users believed the installation was successful when the expected packages were missing. With this release, the Machine Config Daemon verifies that expected packages are installed and degrades the machine config pool if verification fails. As a result, package installation failures are accurately reported to users. (link:https://redhat.atlassian.net/browse/OCPBUGS-65645[OCPBUGS-65645])

* Before this update, when a `MachineOSBuild` image was deleted from the registry and a `MachineConfig` was reapplied, a new `MachineOSBuild` was triggered unnecessarily instead of reusing the existing build. As a consequence, unnecessary image rebuilds occurred, slowing down machine config updates. With this release, the Machine Config Operator correctly identifies and reuses existing builds when the configuration has not changed. As a result, machine config updates proceed directly without unnecessary image rebuilds. (link:https://redhat.atlassian.net/browse/OCPBUGS-68350[OCPBUGS-68350])

* Before this update, when a `PinnedImageSet` resource specified a large number of container images to pin, the image synchronization process did not complete and appeared to get stuck. As a consequence, not all specified images were pinned to nodes as requested. With this release, the pinned image synchronization logic is improved to handle large image sets. As a result, all images in a `PinnedImageSet` are successfully synchronized to nodes. (link:https://redhat.atlassian.net/browse/OCPBUGS-77140[OCPBUGS-77140])

* Before this update, when applying the DISA STIG compliance profile, the `usbguard` service was not properly enabled on nodes even after installing the extension. As a consequence, compliance scans failed for the `service-usbguard-enabled` rule. With this release, the Machine Config Operator correctly enables the `usbguard` service when the extension is installed. As a result, nodes pass DISA STIG compliance scans. (link:https://redhat.atlassian.net/browse/OCPBUGS-78524[OCPBUGS-78524])

* Before this update, control plane nodes were labeled with `node-role.kubernetes.io/control-plane` but still had the legacy `node-role.kubernetes.io/master` taint. As a consequence, the node labeling and tainting were inconsistent. With this release, the Machine Config Operator applies the `node-role.kubernetes.io/control-plane` taint to align with the updated node labels. As a result, control plane node taints are consistent with their labels. (link:https://redhat.atlassian.net/browse/OCPBUGS-82139[OCPBUGS-82139])

* Before this update, the Machine Config Operator updated {aws-first} AMI allowlists through automated processes. As a consequence, new {aws-short} regions and instance types were supported. With this release, the AMI allowlist is updated. As a result, additional {aws-first} AMI IDs are recognized and supported. (link:https://redhat.atlassian.net/browse/OCPBUGS-83539[OCPBUGS-83539])

* Before this update, during a cluster upgrade that changed the `baseOSExtensionsContainerImage` and `osImageURL` fields, two separate rendered `MachineConfig` resources were created sequentially instead of one. As a consequence, the upgrade process created unnecessary intermediate configurations. With this release, the Machine Config Controller creates a single rendered `MachineConfig` during upgrades. * Before this update, a race condition between the {op-system-first} CPU hotplug `udev` rule and the Node Tuning Operator service that offlines the CPUs defined in the performance profile brought some offlined CPUs back online.
As a consequence, when you applied a `PerformanceProfile` that offlined CPUs from more than one NUMA node, only a subset of the specified CPUs remained offline after the node booted.
With this release, the race condition is resolved.
As a result, all CPUs listed in the `offlined` field of the performance profile remain offline after the node boots. (link:https://issues.redhat.com/browse/OCPBUGS-128909[OCPBUGS-128909])

* Before this update, the NUMA Resources Operator did not validate the image that you set in the `spec.imageSpec` field of the `NUMAResourcesScheduler` custom resource (CR).
As a consequence, because this CR is cluster-scoped and the scheduler runs with high privileges, a user with write access to the CR could run an arbitrary container image with scheduler privileges.
With this release, the NUMA Resources Operator validates the scheduler image by default and accepts only digest-based image references, such as `registry.redhat.io/openshift4/noderesourcetopology-scheduler-rhel9@sha256:<digest>`.
The digest must match one of the trusted scheduler images that are embedded in the Operator for the current release stream, or the latest image from the previous release stream.
As a result, if you specify an image that does not meet these requirements, the `NUMAResourcesScheduler` resource enters a `Degraded` state with the reason `InvalidSchedulerImage`. (link:https://issues.redhat.com/browse/OCPBUGS-94176[OCPBUGS-94176])
+
[IMPORTANT]
====
If you set a custom image in the `spec.imageSpec` field of the `NUMAResourcesScheduler` CR, for example, a tag-based reference, the resource enters a `Degraded` state after you upgrade to this release.
====
+
--
To restore the scheduler, perform one of the following actions:

* Update the `spec.imageSpec` field to reference the scheduler image by its `sha256` digest instead of a tag, and make sure that the image you are using is in the current production stream.
* Add the digest of your custom image to the trusted list by setting the `SCHEDULER_IMAGE_DIGESTS` environment variable in the Operator subscription.
* Disable validation by setting the `SCHEDULER_IMAGE_VALIDATION` environment variable to `false` in the Operator subscription.
Disabling validation removes this security protection; disable it only when required.

For more information about the NUMA Resources Operator and the `NUMAResourcesScheduler` CR, see xref:../scalability_and_performance/cnf-numa-aware-scheduling.adoc#cnf-numa-aware-scheduling[Scheduling NUMA-aware workloads].

* Before this update, the Hosted Cluster Config Operator (HCCO) machine controller included all CAPI machine internal IP addresses in EndpointSlice endpoints without filtering, including link-local addresses such as `169.254.0.2` and `fe80::*`. Because Kubernetes 1.33 added validation that rejects link-local addresses in EndpointSlice endpoints, the HCCO failed to create or update EndpointSlice endpoints for `kubevirt` guest cluster `LoadBalancer` shadow services on the management cluster. As a consequence, user-created `LoadBalancer` services in hosted clusters deployed with the `kubevirt` provider did not contain EndpointSlice endpoints or backends, which caused connection attempts from the management cluster to fail with "Connection refused" errors. With this release, the HCCO filters out link-local addresses from machine addresses before creating EndpointSlice endpoints. As a result, EndpointSlice endpoints are created successfully for all shadow services, and `LoadBalancer` services in `kubevirt`-based hosted clusters can be accessed from pods on the management cluster.
