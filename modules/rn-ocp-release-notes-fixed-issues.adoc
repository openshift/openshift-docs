[id="rn-ocp-release-note-bare-metal-hardware-fixed-issues_{context}"]
== Bare Metal Hardware Provisioning

* Before this update, the `baremetal` cluster Operator did not set its `Progressing` status condition to `True` during cluster upgrades. As a consequence, the Cluster Version Operator (CVO) waited for the Operator without receiving proper progress signals, and upgrade monitoring tests failed. With this release, the `baremetal` Operator correctly reports `Progressing=True` during version changes. As a result, cluster upgrades proceed with accurate Operator status reporting. (link:https://redhat.atlassian.net/browse/OCPBUGS-66101[OCPBUGS-66101])

* Before this update, when the bare-metal host (BMH) `spec.online` parameter was set to `False`, the Bare Metal Operator (BMO) forced the `ironic` service to issue a power-off command to the node at the end of inspection, after the RAM disk was ejected. As a consequence, the node operating system lost access to the boot media during shutdown, and filesystem corruption errors were visible on the BMH console. With this release, the node is powered off after inspection, while cleaning up the RAM disk, before ejecting Redfish virtual media. As a result, the host does not lose access to the boot media. (link:https://redhat.atlassian.net/browse/OCPBUGS-66156[OCPBUGS-66156])

* Before this update, the Bare Metal Operator (BMO) `getChecksum()` function accepted non-empty checksums for {oci-first-no-rt} images. As a consequence, OCI image provisioning failed. With this release, a check in the `getChecksum()` function rejects non-empty user-provided checksums for OCI images. As a result, OCI image provisioning does not fail. (link:https://redhat.atlassian.net/browse/OCPBUGS-84305[OCPBUGS-84305])

* Before this update, when managing a high volume of `BareMetalHost` resources on a single multicluster engine instance, the Bare Metal Operator (BMO) issued excessive requests to the Provisioner API during reconciliation. As a consequence, VirtualMedia injection and node reconciliation were noticeably slower at this scale. With this release, the BMO reconciliation loop is optimized to issue fewer requests to the Provisioner API. As a result, responsiveness improves when managing large numbers of `BareMetalHost` resources. (link:https://redhat.atlassian.net/browse/OCPBUGS-85527[OCPBUGS-85527])

* Before this update, when servicing a bare-metal host (BMH), the `service_disable_ramdisk` parameter remained set to `False` even if all servicing steps were performed out-of-band. As a result, the BMH underwent an unnecessary reboot. With this release, the `ironic` service code is modified to automatically set `service_disable_ramdisk` to `True` when all servicing steps are out-of-band. (link:https://redhat.atlassian.net/browse/OCPBUGS-85528[OCPBUGS-85528])

* Before this update, the `ironic-agent` container image was missing the `iproute` package at runtime, which provides the `ip` command required for network configuration. As a consequence, the Ironic Python Agent (IPA) failed to heartbeat to the `ironic` service during bare-metal node cleaning, and node cleaning operations timed out. With this release, the `ironic-agent` container image build process is updated to retain required packages such as `iproute` and `psmisc`. As a result, IPA completes network configuration successfully and bare-metal node cleaning operations complete without timing out. (link:https://redhat.atlassian.net/browse/OCPBUGS-94115[OCPBUGS-94115])

* Before this update, bare-metal nodes provisioned through virtual media failed to boot the inspection image because of incorrect kernel arguments in the provisioning ISO. As a consequence, soft lockups occurred on some hardware, for example, Fujitsu PRIMERGY M8, because the `{{console=ttyS0}}` parameter lacked baud rate and parity settings. The `{{ip=dhcp}}` parameter was missing, which prevented network acquisition during early boot. With this release, the provisioning ISO includes the `{{ip=dhcp}}` parameter and specifies the full serial console configuration. As a result, bare-metal Installer-provisioned installations complete without manual intervention. (link:https://redhat.atlassian.net/browse/OCPBUGS-98696[OCPBUGS-98696])

* Before this update, the Bare Metal Operator (BMO) did not set the `IRONIC_INSECURE` function. As a consequence, bare-metal host (BMH) provisioning failed. With this release, the BMO correctly sets the `IRONIC_INSECURE` function. As a result, BMH provisioning succeeds. (link:https://redhat.atlassian.net/browse/OCPBUGS-111889[OCPBUGS-111889])

[id="rn-ocp-release-note-cloud-compute-fixed-issues_{context}"]
== Cloud Compute

* Before this update, the `AWSMachine` controller was requeuing machine instances before confirming the presence of tags. As a consequence, duplicate {aws-first} EC2 instances were created. With this release, the `AWSMachine` controller verifies tags before requeuing instances. As a result, duplicate EC2 instances are not created. (link:https://redhat.atlassian.net/browse/OCPBUGS-62985[OCPBUGS-62985])

* Before this update, if an OpenStack cloud provider lacked the optional Standard Attributes Tag extension, the Machine API Provider for OpenStack (MAPO) attempted to apply port tags during network port creation. As a consequence, provisioning failed. With this release, MAPO checks whether the `standard-attr-tag` extension is available before applying tags. If unsupported, MAPO skips tag assignment or returns an error prompting you to remove explicit configurations. As a result, machine provisioning completes successfully. (link:https://redhat.atlassian.net/browse/OCPBUGS-77061[OCPBUGS-77061])

== etcd

* Before this update, an upgrade with a control plane `MachineConfig` might have caused quorum loss. As a consequence, the upgrade caused prolonged API and etcd downtime, leading to service interruption. With this release, the `cluster-etcd-operator` keeps guard pods that prevent a `MachineConfig` object from draining the node. As a result, etcd maintains quorum during upgrades. (link:https://redhat.atlassian.net/browse/OCPBUGS-66334[OCPBUGS-66334])

[id="rn-ocp-release-note-Helm-fixed-issues_{context}"]
== Helm

* Before this update, installing a Helm chart by using the Chart URL option in the {product-title} web console with an {oci-first} URL that included a version number, for example, `oci://registry-1.docker.io/bitnamicharts/nginx:22.6.12` failed with an error indicating that the chart was not available or could not be found. As a consequence, users could not install Helm charts from OCI registries when specifying the version number directly in the URL. With this release, the Helm chart installation process correctly handles OCI URLs that include version numbers. As a result, users can successfully install Helm charts from OCI registries by providing the complete URL with the version number in the web console Chart URL field.

[id="rn-ocp-release-note-hosted-control-planes-fixed-issues_{context}"]
== Hosted Control Planes

* Before this update, KubeVirt-based `NodePool` resources incorrectly reported `ClusterNetworkCIDRConflict` errors because the controller flagged OVN-Kubernetes internal overlay IP addresses as conflicting with the cluster network. With this release, Classless Inter-Domain Routing (CIDR) conflict detection is triggered only when all the non-link local addresses for the machine fall within the cluster network. As a result, when external addresses exist, in-network addresses are correctly treated as expected container network interface (CNI) internal IP addresses, which prevents false positive conflict reports. (link:https://redhat.atlassian.net/browse/OCPBUGS-84269[OCPBUGS-84269])

* Before this update, applying resource overrides to containers without pre-existing resource requests caused a nil map panic and crash loop. With this release, a nil guard is added to the `applyRequestsOverrides` function in the Control Plane Operator (CPO) before calling `maps.Copy` on the `Resources.Requests` parameter. As a result, resource request overrides are successfully applied regardless of pre-existing requests. (link:https://redhat.atlassian.net/browse/OCPBUGS-93785[OCPBUGS-93785])

* Before this update, the Konnectivity proxy-server in the `kube-apiserver` deployment was not configured with the `--cluster-ca-cert` flag. As a consequence, a reachable client could establish a connection to the Konnectivity proxy-server without a valid client certificate signed by the hosted cluster Konnectivity certification authority (CA). With this release, the `--cluster-ca-cert` flag is added to the `konnectivity-server` container arguments in the `kube-apiserver` deployment manifest. As a result, unauthenticated connections are prevented because the proxy-server requires and validates client certificates signed by the hosted cluster Konnectivity CA. (link:https://redhat.atlassian.net/browse/OCPBUGS-99014[OCPBUGS-99014])

[id="rn-ocp-release-note-monitoring-fixed-issues_{context}"]
== Monitoring

* Before this update, when Prometheus compacted time series data, it attempted to enable direct I/O on files that were already open. Some file systems, such as {ibm-title} Storage Scale, do not support this operation. As a consequence, compaction failed with a `cannot enable Direct IO: invalid argument` error, Prometheus could not write chunks to disk, and memory usage in Prometheus pods increased until the pods hit their memory limits and restarted or affected other workloads on the node. With this release, Prometheus detects when a file system does not support direct I/O on open files and handles the condition gracefully. As a result, Prometheus writes chunks to disk and completes compaction successfully on these storage back ends. (link:https://redhat.atlassian.net/browse/OCPBUGS-92191[OCPBUGS-92191])

* Before this update, the Cluster Monitoring Operator (CMO) checked only the `openshift-config/pull-secret` for the `cloud.openshift.com` authentication token used by the telemeter client. As a consequence, on platforms where this secret did not contain the token, such as the {azure-first} Red Hat OpenShift {hcp}, the telemeter client was not deployed, which prevented cluster registration in {cluster-manager-first}. With this release, the CMO falls back to `kube-system/global-pull-secret` if the token is not found in the primary secret. As a result, the telemeter client is deployed correctly. (link:https://redhat.atlassian.net/browse/OCPBUGS-98450[OCPBUGS-98450])

* Before this update, Alertmanager crashed because the `tzdata` package was missing in the {product-title} base images, This issue caused the absence of the `/usr/share/zoneinfo` directory. As a consequence, Alertmanager pods failed to start, which made time-based alerts inaccessible for the time zones. With this release, the `tzdata` package is reinstated in {product-title} images. As a result, Alertmanager does not crash on startup when location fields are present in the `active_interval` or `mute_interval` entries. (link:https://redhat.atlassian.net/browse/OCPBUGS-99435[OCPBUGS-99435])

* Before this update, containers in the `openshift-monitoring` namespace ran with writable root filesystems because `readOnlyRootFilesystem: true` was not enabled in their security contexts. As a consequence, customer compliance scans flagged these containers as security policy violations. With this release, monitoring components enable read-only root filesystems with dedicated `emptyDir` volumes for paths requiring write access. As a result, monitoring containers meet compliance requirements for read-only root filesystems. (link:https://redhat.atlassian.net/browse/OCPBUGS-105389[OCPBUGS-105389])

* Before this update, Fibre Channel adapters reported incomplete data. As a consequence, the node_exporter failed to run. With this release, guards are added to ignore incomplete data. (link:https://redhat.atlassian.net/browse/OCPBUGS-112719[OCPBUGS-112719])

[id="rn-ocp-release-note-networking-fixed-issues_{context}"]
== Networking

* Before this update, the `CredentialsRequest` manifests for the ingress capability on {ibm-cloud-title} and {ibm-power-server-title} did not include the `include.release.openshift.io` annotations that the corresponding manifests for other providers included. As a consequence, the `oc adm release extract --credentials-requests --included` command excluded these `CredentialsRequest` manifests, so installations that used manually managed credentials did not receive a credentials request for ingress. Without valid credentials, the Ingress Operator could not create the `\*.apps` DNS record so the Operator reported a degraded `DNSReady=False` status, which caused installation to fail. With this update, the `CredentialsRequest` manifests for {ibm-cloud-title} and {ibm-power-server-title} include the missing `include.release.openshift.io annotations`. As a result, the `oc adm release extract --credentials-requests --included` command extracts the ingress `CredentialsRequest` manifests correctly, and installations on {ibm-cloud-title} and {ibm-power-server-title} that use manually managed credentials no longer fail because of missing ingress credentials. (link:https://issues.redhat.com/browse/OCPBUGS-36723[OCPBUGS-36723])

* Before this update, the `Wildcard` policy of an Ingress Controller prevented new routes from reusing previous hostnames until an administrator restarted the router. As a consequence, affected routes reported a `HostAlreadyClaimed` error. With this release, the Ingress Controller allows new routes to reuse previous hostnames immediately when the `Wildcard` policy is active. As a result, administrators can update hostnames seamlessly without restarting the router. (link:https://redhat.atlassian.net/browse/OCPBUGS-49738[OCPBUGS-49738])

* Before this update, clicking *Create Ingress* on the web console *Search* page, after searching for Ingress resources, redirected users to a `404: Page Not Found` error instead of the Ingress creation form. As a consequence, users could not create an Ingress resource directly from the *Search* page and had to go to the creation form through another part of the console. With this update, the *Create Ingress* button on the *Search* page links to the correct URL. As a result, clicking *Create Ingress* from the *Search* page opens the Ingress creation form as expected. (link:https://issues.redhat.com/browse/OCPBUGS-54248[OCPBUGS-54248])

* Before this update, when an Ingress Controller used an AWS Network Load Balancer (NLB), the default HAProxy tunnel timeout of `1` hour was longer than the NLB default idle timeout of `350` seconds. As a consequence, the NLB silently evicted the flow-tracking entry of the connection after `350` seconds of inactivity without notifying any endpoint. With this update, the Ingress Operator sets a shorter default tunnel timeout when an Ingress Controller uses an NLB, so that HAProxy closes idle connections before the NLB evicts them. As a result, clients that use an NLB-backed route receive a clean connection close instead of a TCP reset when a connection is idle. (link:https://issues.redhat.com/browse/OCPBUGS-54702[OCPBUGS-54702])

* Before this update, on a single-stack IPv4 cluster where the Ingress Controller used the `PROXY` protocol behind a dual-stack load balancer, HAProxy always assumed client source addresses were IPv4 and never enclosed them in brackets in the `Forwarded` header. As a consequence, requests from IPv6 clients produced a `Forwarded` header with an unbracketed IPv6 address, which does not conform to RFC 7239 and could cause applications to fail to parse the client address. With this update, HAProxy checks the IP family of the source address for each request and adds brackets around IPv6 addresses regardless of the configured stack mode of the cluster. As a result, the Ingress Controller produces a correctly formatted `Forwarded` header for both IPv4 and IPv6 client addresses. (link:https://issues.redhat.com/browse/OCPBUGS-62267[OCPBUGS-62267])

* Before this update, AWS Network Load Balancers (NLBs) had native client IP preservation enabled by default on their target groups. As a consequence, hairpin connection failures occurred when a pod connected to an internal NLB route that returned traffic to a router pod on the same node. Because native client IP preservation preserved the original client IP, asymmetric routing occurred and caused the connection to time out. This issue primarily impacted Red Hat OpenShift Service on AWS (ROSA) private deployments and custom internal NLB setups. With this update, a protocol field is added to the AWS NLB configuration parameters in the `IngressController` API. New NLB Ingress Controllers default to `PROXY`, which disables native client IP preservation and enables `PROXY` protocol version 2. Existing Ingress Controllers are not modified during an upgrade. Additionally, an informational alert notifies administrators to explicitly configure the protocol field when upgrading a cluster. (link:https://issues.redhat.com/browse/OCPBUGS-63219[OCPBUGS-63219])

* Before this update, when a `br-ex` interface was created by using the default mechanism, `LLDP` settings from the underlying interface were not preserved on the bridge. As a consequence, there was no way to enable `LLDP` on `br-ex` without making unsupported changes, such as applying a `NodeNetworkConfigurationPolicy` (NNCP) directly to the underlying interface after installation. Because the capture logic of NMState could match the transient NetworkManager connection profiles that `configure-ovs.sh` manages for `br-ex`, this unsupported approach risked overwriting those profiles with invalid configuration. This situation corrupted the network setup of the node and causing some nodes to lose network connectivity on the next reboot. With this update, `LLDP` settings from the underlying interface are persisted on `br-ex` when it is created. As a result, `LLDP` can be enabled for the interface underlying `br-ex` in a supported fashion. (link:https://issues.redhat.com/browse/OCPBUGS-63650[OCPBUGS-63650])

* Before this update, the {product-title} Router performed synchronous and sequential `SubjectAccessReview` (SAR) API calls to validate each externally-managed certificate for a route during startup. As a consequence for a cluster with a high amount of external certificate routes, the kubelet killed any router pod that exceeded the `120` second startup probe timeout value. With this update, an SAR caching mechanism, `sarCache`, and a semaphore throttles concurrent SAR API calls in the router. This process happens alongside any increasing route status that has a writer-lease concurrency. As a result, the initialization time of an {product-title} Router is reduced. This change allows thousands of routes with external certificates to load within the startup probe window and prevents router pods from entering a `CrashLoopBackOff` loop. (link:https://issues.redhat.com/browse/OCPBUGS-77056[OCPBUGS-77056])

* Before this update, the NMState console plugin did not properly handle empty node selections when creating a `NodeNetworkConfigurationPolicy` (NNCP) resource. As a consequence, if no nodes were selected in the *Nodes* configuration step of the wizard, clicking the *Next* button on the policy name step caused the web console to display an error message: `Something wrong happened: n is not iterable`, which prevented policy creation. With this update, the console plugin correctly processes empty node selections during wizard navigation. As a result, you can successfully browse the wizard and create NNCP resources through the web console without encountering the error. (link:https://issues.redhat.com/browse/OCPBUGS-77435[OCPBUGS-77435])

* Before this update, the Cluster DNS Operator considered a node `schedulable` if any one of its taints was tolerated, instead of requiring that all of the taints for a node be tolerated. As a consequence, on a node with more than one taint, the Operator could mark the node as `schedulable` even though one or more of its other taints were not tolerated. With this update, the Cluster DNS Operator checks that all of the taints of a node are tolerated before considering the node `schedulable`. As a result, nodes with multiple taints are marked `schedulable` only when every taint on the node is tolerated. (link:https://issues.redhat.com/browse/OCPBUGS-77532[OCPBUGS-77532])

* Before this update, the `nodeSelector` field description for the `NodeNetworkConfigurationPolicy` (NNCP) custom resource, as shown by `oc explain nncp.spec.nodeSelector`, referenced the general Kubernetes node selector documentation and did not clarify that only simple key-value equality matching was supported. As a consequence, users could reasonably expect that constructs such as `matchLabels` and `matchExpressions` worked in an NNCP `nodeSelector`, but the policy was rejected when they tried to use them. With this update, the `nodeSelector` field description clarifies that only direct key-value pair matching is available and that `matchLabels` and `matchExpressions` are not supported. As a result, `oc explain nncp.spec.nodeSelector` accurately describes the supported `nodeSelector` syntax for NNCP resources. (link:https://issues.redhat.com/browse/OCPBUGS-78801[OCPBUGS-78801])

* Before this update, OVN-Kubernetes used the `vm.kubevirt.io/name` label to identify `virt-launcher` pods during live migration status checks. As a consequence, when many virtual machines in the same namespace had the same `spec.template.spec.hostname` value, they shared the same label value on their `virt-launcher` pods. This caused the third and next VMs to fail to start with the error `Failed to discover live migration status: unexpected live migration state at pods`, as OVN-Kubernetes incorrectly identified pods from other VMs. With this update, OVN-Kubernetes correctly identifies `virt-launcher` pods when multiple VMs share the same hostname. As a result, virtual machines start successfully regardless of whether other VMs in the namespace use the same hostname value. (link:https://issues.redhat.com/browse/OCPBUGS-79408[OCPBUGS-79408])

* Before this update, the installation program created inbound {aws-first} security group rules for a TCP port range historically used for Open Virtual Network (OVN) northbound and southbound database traffic between control plane and compute nodes. These rules used inconsistent port numbers across {product-title} versions, with some versions creating rules for ports `6441-6442` instead of the correct `6641-6642`. As a consequence, clusters exposed unnecessary and inconsistently numbered inbound security group rules. These rules no longer reflected how OVN-Kubernetes (OVN-K) communicates the northbound and southbound databases that run locally on each node and communicate over UNIX domain sockets rather than TCP. With this release, the installation program no longer creates the security group rules for these OVN database ports on {aws-short}. As a result, newly installed {aws-short} clusters no longer include the unused, inconsistently numbered inbound security group rules. (link:https://issues.redhat.com/browse/OCPBUGS-79536[OCPBUGS-79536])

* Before this update, the *Create UserDefinedNetwork* form in the web console did not trim leading or trailing whitespace from a subnet Classless Inter-Domain Routing (CIDR) value before submitting it. As a consequence, if you pasted a CIDR value that included extraneous whitespace, for example from a copy-paste operation, the form displayed the error `Invalid value: "string": CIDR is invalid for the spec.layer2.subnets field`, even though the CIDR value itself was valid. With this update, the form trims whitespace from the CIDR input before validation. As a result, users can paste a CIDR value with extra leading or trailing whitespace without triggering a validation error. (link:https://issues.redhat.com/browse/OCPBUGS-81271[OCPBUGS-81271])

* Before this update, when a pod of a virtual machine instance on a localnet OVN-Kubernetes secondary network was deleted, OVN-Kubernetes might not remove the logical switch port from the OVN northbound database. As a consequence, an orphaned logical switch port for the deleted pod remained on the localnet logical switch alongside the correct logical switch port for the replacement pod, both sharing the same MAC address, which caused network connectivity issues for the virtual machine. With this update, OVN-Kubernetes correctly removes the logical switch port for the deleted pod in this scenario. As a result, no duplicate logical switch port remains after a virtual machine pod is deleted and recreated on a localnet secondary network, and connectivity is not impacted. (link:https://issues.redhat.com/browse/OCPBUGS-81326[OCPBUGS-81326])

* Before this update, when you used the FRR-K8s daemon to learn Border Gateway Protocol (BGP) routes from a network fabric in an environment where a high number of pods were created and deleted, learned BGP routes might get uninstalled from the cluster. This issue affected BGP configurations managed by either the `RouteAdvertisements` feature or the MetalLB Operator, causing traffic that relied on those routes to fail. With this update, FRR is upgraded from version 8 to version 10. As a result, learned BGP routes remain properly installed in the routing table, resolving the traffic failures caused by dropped routes. (link:https://issues.redhat.com/browse/OCPBUGS-84304[OCPBUGS-84304])

* Before this update, the `istio-proxy` container in the `Gateway API` gateway pod and the discovery container in the `istiod` pod, both in the `openshift-ingress` namespace, did not set `terminationMessagePolicy` to `FallbackToLogsOnError`. As a consequence, these containers did not follow the platform-wide pod policy for termination message handling, which meant less diagnostic information was available from container logs when either container terminated with an error. With this update, both containers set `terminationMessagePolicy=FallbackToLogsOnError`. As a result, container logs are used as the termination message when these containers exit with an error and no termination message file is written, improving diagnosing of Gateway API failures. (link:https://issues.redhat.com/browse/OCPBUGS-84491[OCPBUGS-84491])

* Before this update, one or more containers in the `openshift-ovn-kubernetes` namespace did not set `terminationMessagePolicy` to `FallbackToLogsOnError`. As a consequence, these containers did not follow the platform-wide pod policy for termination message handling, which meant less diagnostic information was available from container logs when a container terminated with an error. With this update, the affected containers in the `openshift-ovn-kubernetes` namespace set `terminationMessagePolicy=FallbackToLogsOnError`. As a result, container logs are used as the termination message when these containers exit with an error and no termination message file was written, improving ability to diagnose OVN-Kubernetes failures. (link:https://issues.redhat.com/browse/OCPBUGS-84519[OCPBUGS-84519])

* Before this update, the DNS Operator treated a difference between the desired and up-to-date pod counts of its managed `DaemonSets` as evidence of an ongoing rollout. As a consequence, when a cluster scaled up, the desired pod count increased before DNS pods were running on the new nodes, causing the Operator to report `Progressing=True` even though no DNS version or configuration change was underway. With this update, the DNS Operator additionally verifies that a `DaemonSet` is actively rolling out by checking its observed generation and comparing its up-to-date pod count with its currently scheduled pod count. As a result, cluster scale-up alone no longer causes the DNS Operator to report `Progressing=True`, while actual DNS rollouts continue to be reported correctly. (link:https://issues.redhat.com/browse/OCPBUGS-86009[OCPBUGS-86009])
