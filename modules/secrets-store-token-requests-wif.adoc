= Understanding token requests for Workload Identity Federation

[role="_abstract"]
You can configure the {secrets-store-operator} to use Workload Identity Federation (WIF) with cloud provider secret stores by customizing the service account token audience. This enables secure, credential-free authentication to external secret management systems across multiple cloud providers.

Workload Identity Federation allows your {product-title} workloads to access cloud provider services without storing long-lived credentials. Instead, the {secrets-store-operator} uses short-lived service account tokens with a specified audience to authenticate to external secret stores.

The `tokenRequests` parameter in the `Driver` custom resource enables you to configure the audience for projected service account tokens. This parameter is essential for multi-cloud deployments and environments that require specific token audiences for authentication.

== Workload Identity Federation support

The {secrets-store-operator} supports Workload Identity Federation with the following cloud providers and secret management systems:

* *AWS Secrets Manager*: Use AWS Identity and Access Management (IAM) roles for service accounts (IRSA) to authenticate to AWS Secrets Manager without storing AWS credentials.

* *Azure Key Vault*: Use Azure Active Directory Workload Identity to authenticate to Azure Key Vault with pod-managed identities.

* *Google Secret Manager*: Use Workload Identity for Google Kubernetes Engine (GKE) to authenticate to Google Secret Manager with service account impersonation.

* *HashiCorp Vault*: Use Vault's Kubernetes authentication method to authenticate with service account tokens.

== Benefits of Workload Identity Federation

Configuring token requests for Workload Identity Federation provides the following benefits:

* *Enhanced security*: Eliminates the need to store long-lived cloud provider credentials in your cluster, reducing the risk of credential exposure.

* *Simplified credential management*: Removes the operational burden of rotating and managing cloud provider credentials.

* *Fine-grained access control*: Enables precise control over which workloads can access specific secrets through cloud provider IAM policies.

* *Multi-cloud flexibility*: Supports consistent authentication patterns across different cloud providers and secret management systems.

* *Compliance and auditing*: Provides better audit trails through cloud provider IAM logs, showing which workloads accessed which secrets.

== Token audience customization

The `tokenRequests.audience` parameter allows you to specify the audience claim in the projected service account token. Different cloud providers require different audience values:

* AWS IRSA typically requires an audience matching the OIDC provider URL
* Azure Workload Identity requires `api://AzureADTokenExchange`
* Google Workload Identity uses the default service account token audience
* HashiCorp Vault can be configured with custom audience values

Configuring the correct audience ensures that the service account token is accepted by the external secret management system's authentication mechanism.
