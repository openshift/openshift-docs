= Why fencing might not occur

[role="_abstract"]
In a two-node {product-title} cluster with fencing (TNF), several distinct conditions can each prevent Pacemaker from fencing a failed control plane node. Identifying which condition applies determines whether you resolve a configuration issue or follow a different recovery procedure. Use the commands in "Manually verifying fencing status" to gather the evidence referenced in this table, or the `fencing_validator` script, whose exit codes map to the first three scenarios below.

.Reasons fencing might not occur
[cols="2,3,3", options="header"]
|===
| Scenario | How to confirm | Resolution

| Fencing is disabled cluster-wide.
| `pcs property show stonith-enabled` returns `false`. The `fencing_validator` script returns exit code `20`.
| Confirm that no maintenance window is active, then re-enable fencing with `sudo pcs property set stonith-enabled=true`.

| A fencing device failed to start.
| `pcs stonith status` shows the device `Stopped`, often with a `Failed Resource Actions` entry. The `fencing_validator` script returns exit code `20`.
| The Baseboard Management Controller (BMC) endpoint is usually unreachable or the credentials are wrong. See xref:../installing_tnf/install-post-tnf.adoc#troubleshooting-fencing-credential-updates_install-post-tnf[Troubleshooting fencing credential updates] to distinguish a connectivity failure from an authentication failure.

| A cluster daemon is not running.
| `systemctl status corosync pacemaker pcsd` shows `corosync`, `pacemaker`, or `pcsd` is not `active (running)`. The `fencing_validator` script returns exit code `22`.
| Restart the affected daemon, for example `sudo systemctl restart pacemaker`. Pacemaker cannot evaluate fencing or quorum on a node where these daemons are down.

| The control plane nodes lost corosync quorum.
| `pcs quorum status` reports `Quorate: No`. The `fencing_validator` script does not detect this case directly, because it checks etcd quorum, not corosync quorum.
| Both control plane nodes likely lost power or network connectivity at the same time, so the surviving node does not have enough votes to fence its peer unilaterally. See xref:../installing_tnf/install-post-tnf.adoc#installation-manual-recovering-when-auto-recovery-is-unavail_install-post-tnf[Manually recovering from a disruption event when automated recovery is unavailable] to restore corosync quorum.

| Fencing already completed.
| `pcs stonith history show` lists a recent fence event for the node in question.
| Fencing worked as expected. If the cluster has not recovered yet, proceed to the recovery scenario that matches your situation instead of investigating fencing further.

| The failed resource has not been detected yet.
| `pcs status` still shows the resource `Started` on the node you expect to have failed.
| Pacemaker has not run its next monitor interval yet, or the failure is at a layer Pacemaker does not monitor, for example an application-level fault with no corresponding resource agent. Wait for the next monitor interval, or confirm the failure manually, before assuming fencing should have triggered.
|===
