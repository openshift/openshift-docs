= Reserve OVS-DPDK CPUs with a performance profile

[role="_abstract"]
Create or update a `PerformanceProfile` custom resource (CR) that reserves CPUs for OVS-DPDK by setting `spec.cpu.ovsDpdk`. You can optionally add the load-balancing annotation in the same CR; see _Disable load balancing on OVS-DPDK CPUs_ for when that extra hardening is useful.

.Prerequisites

* You have access to the cluster as a user with the `cluster-admin` role.
* You have installed the OpenShift CLI (`oc`).
* You have identified the CPU topology and NUMA locality of the OVS-DPDK NICs on the target nodes.
* Workload partitioning is enabled at install time by setting `CPUPartitioningAllNodes`, or the `kubelet` CPU Manager `strict-cpu-reservation` policy option is configured on the target nodes. The performance profile populates the workload partitioning CPU sets.
* You understand that this feature is Technology Preview.

.Procedure

. Optional: Inspect CPU and NUMA topology on a target node to identify which CPUs to assign to OVS-DPDK. Choose CPUs on the same NUMA node as the OVS-DPDK NIC for lowest latency:
+
[source,terminal]
----
$ oc debug node/<node_name> -- chroot /host lscpu -e
----
+
Review the `SOCKET` and `NUMA` columns to identify which CPUs belong to each NUMA node. Then check which NUMA node the OVS-DPDK NIC is on:
+
[source,terminal]
----
$ oc debug node/<node_name> -- chroot /host bash -c 'cat /sys/class/net/<interface_name>/device/numa_node'
----
+
Select `ovsDpdk` CPUs from the same NUMA node as the NIC. For example, if the NIC is on NUMA node 1 and CPUs 1,3,5,7 are on NUMA node 1, you might set `ovsDpdk: "3"` or `ovsDpdk: "3,5"` from that set.

. Generate a base performance profile by using the Performance Profile Creator (PPC) tool with a must-gather from your cluster:

.. Collect a must-gather from the cluster:
+
[source,terminal]
----
$ oc adm must-gather
----

.. Generate the base profile by running the PPC tool:
+
[source,terminal,subs="attributes+"]
----
$ podman run --entrypoint performance-profile-creator \
  -v <path_to_must_gather>:/must-gather:z \
  registry.redhat.io/openshift4/ose-cluster-node-tuning-rhel9-operator:v{product-version} \
  --must-gather-dir-path /must-gather \
  --mcp-name=<mcp_name> \
  --reserved-cpu-count=<reserved_count> \
  --rt-kernel=true \
  --split-reserved-cpus-across-numa=false \
  --power-consumption-mode=ultra-low-latency \
  > my-performance-profile.yaml
----
+
Replace `<mcp_name>` with the name of the machine config pool for the target nodes. For {sno}, use `--mcp-name=master`.
+
For more information about PPC arguments, see "Running the Performance Profile Creator using Podman".

. Edit the generated profile to add `spec.cpu.ovsDpdk` and optionally add the load-balancing annotation. Move the CPUs you want to assign to OVS-DPDK from the `isolated` set to the new `ovsDpdk` field. Ensure that the `reserved`, `ovsDpdk`, and `isolated` sets do not overlap.
+
.Example performance profile with OVS-DPDK CPUs
[source,yaml]
----
apiVersion: performance.openshift.io/v2
kind: PerformanceProfile
metadata:
  name: ovs-dpdk-isolation
  annotations:
    performance.openshift.io/cpu-load-balancing-ovs-dpdk: "disable"
spec:
  cpu:
    reserved: "0-1"
    ovsDpdk: "2-3"
    isolated: "4-7"
  machineConfigPoolSelector:
    pools.operator.machineconfiguration.openshift.io/worker: ""
  nodeSelector:
    node-role.kubernetes.io/worker: ""
----
+
where:

* `performance.openshift.io/cpu-load-balancing-ovs-dpdk: "disable"` is optional. Set it only when you need stronger scheduler isolation for PMD threads. Omit the annotation for the base reservation. For why and when to use this annotation, see _Disable load balancing on OVS-DPDK CPUs_.
* `spec.cpu.reserved` lists CPUs for operating system and platform components.
* `spec.cpu.ovsDpdk` lists CPUs reserved for OVS-DPDK PMD threads. Do not reuse this set for unrelated DPDK applications. The PPC tool does not generate this field. You must add it manually.
* `spec.cpu.isolated` lists CPUs for `Guaranteed` application pods.
* `spec.machineConfigPoolSelector` matches the machine config pool for the target nodes.
* `spec.nodeSelector` matches the node role for the target nodes. On single-node {product-title}, use `node-role.kubernetes.io/master: ""` and set `machineConfigPoolSelector` to `pools.operator.machineconfiguration.openshift.io/master: ""`.

. Apply the performance profile:
+
[source,terminal]
----
$ oc apply -f my-performance-profile.yaml
----

. Wait for the Machine Config Operator to apply the configuration and for the target nodes to reboot. Confirm that the relevant machine config pool has finished updating:
+
[source,terminal]
----
$ oc get mcp
----
+
The pool that matches your profile selector must show `UPDATED=True` and `UPDATING=False`.

.Verification

. Verify that the performance profile is available:
+
[source,terminal]
----
$ oc get performanceprofile ovs-dpdk-isolation -o yaml
----
+
Confirm that the `Available` condition is `True`. If the profile is `Degraded` with reason `OvsDpdkCPUsPrerequisiteNotMet`, enable workload partitioning or `strict-cpu-reservation` and reapply the profile.

. Start a debug session on a node that matches the performance profile:
+
[source,terminal]
----
$ oc debug node/<node_name>
----

. Set `/host` as the root directory for the debug shell:
+
[source,terminal]
----
# chroot /host
----

. Verify that kernel boot parameters include the OVS-DPDK CPUs:
+
[source,terminal]
----
# cat /proc/cmdline
----
+
Confirm the following:

* `isolcpus` includes the union of `isolated` and `ovsDpdk` CPUs.
* `nohz_full` and `rcu_nocbs` include the `ovsDpdk` CPUs.
* `systemd.cpu_affinity` does not include the `ovsDpdk` CPUs.

. Verify that `kubelet` reserved system CPUs are the union of `reserved` and `ovsDpdk`. Run the following command from a separate terminal or after exiting the debug session:
+
[source,terminal]
----
$ oc get --raw "/api/v1/nodes/<node_name>/proxy/configz" | \
  python3 -c 'import sys,json; print(json.load(sys.stdin)["kubeletconfig"]["reservedSystemCPUs"])'
----
+
The reported set must equal `reserved` ∪ `ovsDpdk`. For example, with `reserved: "0-2"` and `ovsDpdk: "3"`, the output is `0-3`.

. Verify that IRQ balancing excludes the OVS-DPDK CPUs:
+
[source,terminal]
----
# grep -E "^IRQBALANCE_BANNED_CPUS=" /etc/sysconfig/irqbalance
----
+
Confirm that `IRQBALANCE_BANNED_CPUS` includes a hex mask that covers the `ovsDpdk` CPUs. For example, `ovsDpdk: "3"` (CPU 3) produces `IRQBALANCE_BANNED_CPUS=8`. The mask value is not zero-padded.

. Verify that the default SMP affinity mask excludes the OVS-DPDK CPUs:
+
[source,terminal]
----
# cat /proc/irq/default_smp_affinity
----
+
The mask must clear the bits for `ovsDpdk` CPUs. For example, with `ovsDpdk: "3"` on an 8-CPU node, the output is `f7`.

. Verify that the OVS-DPDK configuration script is present:
+
[source,terminal]
----
# stat /usr/local/bin/ovs-dpdk-cpus-configure.sh
----

. Verify the OVS-DPDK cgroup hierarchy and CPU assignment:
+
[source,terminal]
----
# cat /sys/fs/cgroup/ovs.slice/ovs-vswitchd.service/ovsdpdk.slice/cgroup.type
# cat /sys/fs/cgroup/ovs.slice/ovs-vswitchd.service/ovsdpdk.slice/cpuset.cpus.exclusive
# cat /sys/fs/cgroup/ovs.slice/ovs-vswitchd.service/ovsdpdk.slice/cpuset.cpus.partition
----
+
Confirm the following:

* `cgroup.type` is `threaded`.
* `cpuset.cpus.exclusive` matches the `spec.cpu.ovsDpdk` value.
* `cpuset.cpus.partition` is `isolated` when `performance.openshift.io/cpu-load-balancing-ovs-dpdk` is set to `disable`, or `member` when the annotation is omitted or set to `enable`.
+
When the annotation is set to `disable`, the `ovsDpdk` CPUs are also excluded from kernel scheduling domains. That exclusion must remain in place for the life of the reservation and must not change when unrelated `Guaranteed` pods start or stop on the node.
+
The `IRQBALANCE_BANNED_CPUS` and `default_smp_affinity` settings for `ovsDpdk` CPUs are also persistent. They are not affected when `Guaranteed` pods with the `irq-load-balancing.crio.io: "disable"` annotation start or stop on the node. CRI-O IRQ hooks do not clear or override the `ovsDpdk` IRQ isolation.

[NOTE]
====
These checks confirm that the platform configuration for OVS-DPDK CPU isolation is in place. Measuring OVS-DPDK dataplane throughput and packet loss requires your OVS-DPDK application test environment.
