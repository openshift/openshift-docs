= Removing a cluster from nested SPIRE

[role="_abstract"]
You must remove a cluster from nested before you delete its registration on the parent server. {zero-trust-full} deletes its resources except the `kubeconfig` secret and the trust bundle secret.

[IMPORTANT]
====
* If you remove the cluster entry while the sidecar is still running, attestation fails and certificate authority (CA) renewal stops. The nested server continues to issue identities until the cached intermediate CA expires.

* If you clear `spec.upstreamAuthority.spire` but leave the cluster entry, the parent server keeps the stale attestation configuration and registration entries.
====

Workload certificates that you already issued stay valid until they expire. After the current intermediate CA expires, the nested server signs new certificates with its own CA. To return the nested server to the hierarchy, restore the configuration. The {spiffe-full} Runtime Environment (SPIRE) rebuilds the chain at the next CA rotation.

.Prerequisites

* You have `cluster-admin` access to the nested cluster and to its parent cluster.
* If you are removing a mid-tier server, you already detached every cluster that obtains its intermediate CA from that server.

.Procedure

. On the nested cluster, export the `SpireServer` custom resource (CR) by running the following command:
+
[source,terminal]
----
$ oc get spireserver cluster -o yaml > SpireServer-nested.yaml
----

. Remove `spec.upstreamAuthority.spire` from the exported file.
+
If `upstreamAuthority` has no other plugin, remove the whole `upstreamAuthority` field.

. Apply the file by running the following command:
+
[source,terminal]
----
$ oc apply -f SpireServer-nested.yaml
----

. Confirm that the sidecar is removed by running the following command:
+
[source,terminal]
----
$ oc get pod spire-server-0 -n zero-trust-workload-identity-manager -o jsonpath='{range .status.containerStatuses[*]}{.name}{"\n"}{end}'
----

. On the parent cluster, remove the `name` entry for the nested cluster from `spec.nodeAttestor.externalK8sPSAT.clusters` and apply the `SpireServer` CR.
+
The parent SPIRE server restarts. Its other nested servers keep issuing from their cached CAs.

. Optional: if the parent server of the cluster you are removing no longer needs an external gRPC endpoint, set `spec.managedRoute` to `"false"` and apply the CR.
+
{zero-trust-full} removes the `ManagedGRPCRouteAvailable` condition but does not delete the route.

. Optional: delete the route by running the following command:
+
[source,terminal]
----
$ oc delete route spire-server-grpc -n zero-trust-workload-identity-manager
----

. Optional: on the parent cluster, delete the `kubeconfig` secret by running the following command:
+
[source,terminal]
----
$ oc delete secret nested-spire-cluster01-kubeconfig -n zero-trust-workload-identity-manager
----

. Optional: on the nested cluster, delete the trust bundle secret by running the following command:
+
[source,terminal]
----
$ oc delete secret spire-trust-bundle -n zero-trust-workload-identity-manager
----
+
Replace the secret names if needed.
