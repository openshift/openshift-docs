= Understanding the performance impact of secret rotation

[role="_abstract"]
The {secrets-store-operator} uses the `RequiresRepublish` flag to dynamically control whether mounted secrets need to be republished to pods. Understanding how this flag works helps you optimize cluster performance by reducing unnecessary kubelet operations.

The `RequiresRepublish` flag determines whether the kubelet needs to call the CSI driver's `NodePublishVolume` operation to update secret content in pod volumes. This flag is automatically set based on your rotation configuration:

* *When rotation is enabled*: The `RequiresRepublish` flag is set to `true`, which instructs the kubelet to periodically call the CSI driver to check for secret updates from the external store. This ensures that rotated secrets are reflected in your pods.

* *When rotation is disabled*: The `RequiresRepublish` flag is set to `false`, which prevents the kubelet from making unnecessary CSI driver calls. This reduces performance overhead and improves cluster efficiency.

== Performance considerations

In large-scale deployments, the performance impact of secret rotation can be significant:

* *High-volume environments*: Clusters managing hundreds of secrets across many pods can experience reduced transaction costs and improved performance with optimized rotation settings.

* *Polling overhead*: Frequent polling of external secret stores generates API calls to cloud providers (such as Azure Key Vault, AWS Secrets Manager, or Google Secret Manager), which can result in high transaction costs.

* *Kubelet operations*: Each `NodePublishVolume` call consumes cluster resources. Disabling rotation for secrets that change infrequently eliminates these unnecessary operations.

* *Network traffic*: Reducing polling frequency decreases network traffic between your cluster and external secret management systems.

== Best practices for rotation configuration

Consider the following guidelines when configuring secret rotation:

* *Assess secret change frequency*: For secrets that change infrequently, consider longer polling intervals or disabling rotation entirely.

* *Balance security and cost*: Set polling intervals that meet your security requirements while minimizing operational costs. For example, a 5-minute polling interval might be appropriate for moderately sensitive secrets, while highly sensitive secrets might require more frequent polling.

* *Monitor transaction costs*: Track API usage and costs for your external secret management system to identify opportunities for optimization.

* *Test rotation behavior*: Verify that your polling interval provides acceptable secret freshness for your applications before deploying to production.
