= Fencing credential management

[role="_abstract"]
You must provide Baseboard Management Controller (BMC) connection details for each control plane node in a two-node {product-title} cluster with fencing. Pacemaker stores the Redfish API endpoint, username, and password information in the fencing configuration.

When a node becomes unresponsive and fails its health checks, Pacemaker connects to the BMC of a node by using the stored credentials to power off or isolate the node.
This isolation prevents the unresponsive node from continuing to serve requests while the remaining node manages the cluster.

In earlier versions of {product-title}, Pacemaker identified fencing credentials only by hostname. When a hostname was changed after initial cluster installation through DNS reconfiguration or system renaming, the fencing mechanism could not locate the correct credentials.
Because of this, Pacemaker could not access the BMC for that node, and if the node became unresponsive, Pacemaker could not fence it, risking data corruption and cluster unavailability.

Additionally, updating credentials across the cluster required manual configuration changes that were complex and error-prone.
You had to manually verify and reconfigure credentials, leaving room for inconsistencies.

You can now identify fencing credentials by MAC address instead of, or in addition to, hostname in the `install-config.yaml` file. MAC addresses are stable hardware identifiers that do not change when the hostname is modified after installation. To use MAC-based identification, specify the `macAddress` field instead of `hostname` in the fencing credentials section of the `install-config.yaml` file. The MAC address must belong to an OS-visible, non-loopback network interface on the target control plane node (for example, the boot NIC), not the BMC management interface. You must provide at least one of `hostname` or `macAddress` for each credential entry. If both are specified, `hostname` takes precedence.
