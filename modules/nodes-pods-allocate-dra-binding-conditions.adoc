= About DRA device binding conditions

[role="_abstract"]
When working with Dynamic Resource Allocation (DRA), you can improve scheduling reliability by using device binding conditions to allow the scheduler to delay pod scheduling until specific external resources, such as fabric-attached GPUs or reprogrammable FPGAs, are confirmed to be ready.

For example, you can use device binding to Ensure that High-Performance Computing (HPC) workloads that require specialized network-attached devices are scheduled only on nodes where these devices are pre-attached and ready for use. Or you could ensure that storage devices are ready for your storage-intensive applications before scheduling the workloads.

To configure device binding conditions, use your third-party DRA driver to publish the following fields in the device section of a resource slice:

* `bindingConditions`, which is a list of conditions that must be `True` in the `.status.conditions` field of the associated resource claim before the Pod can be bound. These conditions typically represent readiness signals, such as `DeviceAttached` or `DeviceInitialized`.
* `bindingFailureConditions`, which is a list of condition types that, if set to `True` in `status.conditions` field of the associated resource claim, indicate a failure state. If any of these conditions is `True`, the scheduler reschedules the pod to a different device.
* `bindsToNode`, which sets a node selector inside the resource claim that external controllers can use to perform node-specific operations such as device attachment or preparation. If set to `True`, the scheduler records the selected node name in the `status.allocation.nodeSelector` field of the resource claim. This does not affect the Pod's spec.nodeSelector. Instead, 

All condition types listed in the `bindingConditions` and `bindingFailureConditions` fields are evaluated from the `status.conditions` field of a resource claim. External controllers are responsible for updating these conditions using standard Kubernetes condition semantics, such as `type`, `status`, `reason`, `message`, or `lastTransitionTime`.

The scheduler waits up to 600 seconds (default) for all `bindingConditions` to become True. If the timeout is reached or any `bindingFailureConditions` is `True`, the scheduler clears the allocation and reschedules the pod. A cluster administration can configure this timeout duration by editing the kube-scheduler configuration file.

apiVersion: v1
kind: ConfigMap
metadata:
  name: "secondary-scheduler-config"
  namespace: "aa"
data:
  "config.yaml": |
    apiVersion: kubescheduler.config.k8s.io/v1
    kind: KubeSchedulerConfiguration
    profiles:
    - schedulerName: default-scheduler
      pluginConfig:
      - name: DynamicResources
        args:
          apiVersion: kubescheduler.config.k8s.io/v1
          kind: DynamicResourcesArgs
          bindingTimeout: 60s
