= Upgrade clusters with the Provisioning API

[role="_abstract"]
You can trigger a cluster upgrade through the Provisioning REST API by sending an update request with a new `templateVersion` that references a `ClusterTemplate` CR configured for the target release. This method is used by SMO frameworks and external automation systems that manage cluster upgrades programmatically.

.Prerequisites

* You authenticated to the O-Cloud Manager REST API and set the `MY_TOKEN` environment variable.
* The cluster is fully provisioned with `provisioningPhase: fulfilled`.
* A new `ClusterTemplate` CR version configured for the target {product-title} release exists on the hub cluster.

.Procedure

. Get the O-Cloud Manager API hostname by running the following command:
+
[source,terminal]
----
$ export API_HOST=$(oc get routes -n oran-o2ims -o jsonpath='{.items[0].spec.host}')
----

. Set the Provisioning API base URL by running the following command:
+
[source,terminal]
----
$ export PROV_URL="https://${API_HOST}/o2ims-infrastructureProvisioning/v1"
----

. Retrieve the current provisioning request by running the following command:
+
[source,terminal]
----
$ curl -ks -H "Authorization: Bearer ${MY_TOKEN}" \
  "${PROV_URL}/provisioningRequests/<uuid>" | jq > current-request.json
----
+
where:
+
`<uuid>`:: Specifies the UUID of the provisioning request for the target cluster.

. Modify the `current-request.json` file to update the `templateVersion` field to the new release version. The following example upgrades from version `v4-Y-Z-1` to `v4-Y-Z+1-1`:
+
[source,json]
----
{
  "provisioningRequestId": "<uuid>",
  "templateName": "sno-ran-du",
  "templateVersion": "v4-Y-Z+1-1",
  "templateParameters": {
    "nodeClusterName": "sno1",
    "oCloudSiteId": "site-east-1",
    "clusterInstanceParameters": {
      "clusterName": "sno1",
      "nodes": [ ... ]
    },
    "policyTemplateParameters": { ... }
  }
}
----
+
* The `templateVersion` value must match the version of the new `ClusterTemplate` CR prepared for the target release.
* All other fields remain unchanged unless the new template requires different parameter values.
+
[NOTE]
====
The PUT request replaces the entire provisioning request. Retrieve the current state first, then send the complete modified payload. Do not send partial updates.
====

. Send the updated provisioning request by running the following command:
+
[source,terminal]
----
$ curl -ks -X PUT \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${MY_TOKEN}" \
  "${PROV_URL}/provisioningRequests/<uuid>" \
  -d @current-request.json | jq
----

.Verification

* Query the provisioning request status and verify that the upgrade completes by running the following command:
+
[source,terminal]
----
$ curl -ks -H "Authorization: Bearer ${MY_TOKEN}" \
  "${PROV_URL}/provisioningRequests/<uuid>" | jq -r '.status.provisioningStatus.provisioningPhase'
----
+
The `provisioningPhase` transitions from `progressing` to `fulfilled` when the upgrade completes successfully.
