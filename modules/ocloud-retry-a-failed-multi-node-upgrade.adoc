= Retry a failed multi-node cluster upgrade

[role="_abstract"]
When a standard platform upgrade fails on a multi-node {product-title} cluster, the recovery path depends on the failure reason reported in the `UpgradeCompleted` condition. Input errors can be corrected in place, while timeout failures require investigating the spoke cluster and determining whether to retry or reconcile a manually completed upgrade.

.Prerequisites

* The `UpgradeCompleted` condition on the `ProvisioningRequest` CR shows `reason: PreconditionChecksFailed`, `reason: Failed`, or `reason: TimedOut`.
* You have access to the spoke cluster for investigation if the failure reason is `TimedOut`.

.Procedure

. Check the `UpgradeCompleted` condition to determine the failure type by running the following command:
+
[source,terminal]
----
$ oc get provisioningrequests.clcm.openshift.io <uuid> \
  -o jsonpath='{.status.conditions[?(@.type=="UpgradeCompleted")]}'
----
+
where:
+
`<uuid>`:: Specifies the UUID of the `ProvisioningRequest` CR for the target cluster.

. If the `reason` is `PreconditionChecksFailed` or `Failed`, fix the input error directly:
+
The upgrade was not started or was rejected because a precondition was not met, such as a schema validation failure, version mismatch, or invalid `ClusterVersion` configuration. Patch the `ProvisioningRequest` CR with corrected `upgradeParameters` values or fix the referenced `ClusterTemplate` CR. The O-Cloud Manager re-evaluates the upgrade automatically after the change is detected.

. If the `reason` is `TimedOut`, investigate the spoke cluster to determine the root cause. Check the `UpgradeCompleted` condition `message` for details, which might include Cluster Version Operator conditions such as `Failing` or `Upgradeable=False`.

. Resolve the root cause on the spoke cluster, such as fixing a degraded Operator or clearing a misconfigured policy.

. Revert the `ProvisioningRequest` CR to the original `ClusterTemplate` version by running the following command:
+
[source,terminal]
----
$ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateName":"<template_name>","templateVersion":"<original_version>"}}'
----
+
where:
+
--
`<template_name>`:: Specifies the template name, such as `std-ran-du`.
`<original_version>`:: Specifies the original `ClusterTemplate` version, such as `v4-Y-Z-1`.
--

. Wait for the `ProvisioningRequest` CR to return to `provisioningPhase: fulfilled`.

. Re-trigger the upgrade by updating the `ProvisioningRequest` CR to the target `ClusterTemplate` CR version by running the following command:
+
[source,terminal]
----
$ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateName":"<template_name>","templateVersion":"<target_version>"}}'
----
+
where:
+
`<target_version>`:: Specifies the new `ClusterTemplate` CR version for the target release.
+
[NOTE]
====
If the administrator completed the upgrade to the target version outside of the O-Cloud Manager, you can skip the revert and re-trigger steps. Instead, add or update a `ManagedCluster` label through the `ProvisioningRequest` `clusterInstanceParameters` to trigger reconciliation:

[source,terminal]
----
$ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateParameters":{"clusterInstanceParameters":{"extraLabels":{"ManagedCluster":{"upgrade-reconcile":"true"}}}}}}'
----

The O-Cloud Manager detects that the spoke cluster is already running the target version and transitions the `ProvisioningRequest` CR to `provisioningPhase: fulfilled`.
====

.Verification

* Verify that the upgrade completed successfully by running the following command:
+
[source,terminal]
----
$ oc get provisioningrequests.clcm.openshift.io <uuid>
----
+
.Example output
[source,terminal]
----
NAME                                   DISPLAYNAME   AGE    PROVISIONPHASE   PROVISIONDETAILS
123e4567-e89b-12d3-a456-426614174000                 300m   fulfilled        Upgrade to version 4.22.0 completed
----
