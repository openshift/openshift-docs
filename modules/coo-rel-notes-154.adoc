[id="cluster-observability-operator-1-5-4-fixed-issues_{context}"]
== Fixed issues

Operator no longer panics when an `ObservabilityInstaller` resource has an empty specification::

Before this update, when you created an `ObservabilityInstaller` resource with an empty specification, such as `spec: {}`, the `capabilities` field was unset, and the controller did not check for this before it read the tracing storage configuration. As a consequence, the controller panicked with a nil pointer dereference and entered a repeating panic and recovery loop, and no components were deployed.
+
With this release, the controller handles an empty specification and treats the capabilities as disabled. As a result, the resource is created successfully, tracing remains disabled by default, and the controller no longer panics.
+
link:https://issues.redhat.com/browse/COO-1257[COO-1257]

Korrel8r correlates alerts from the user-workload monitoring Alertmanager::

Before this update, when user-workload monitoring was enabled with a separate Alertmanager instance, the `korrel8r.yaml` configuration that the operator generated contained only the platform Alertmanager in the `alert` domain. As a consequence, the troubleshooting panel could not correlate alerts that originated from the user-workload Alertmanager.
+
With this release, the operator adds a second `alert` domain entry for the user-workload monitoring Alertmanager. As a result, the troubleshooting panel correlates alerts from both the platform and the user-workload Alertmanager instances.
+
link:https://issues.redhat.com/browse/COO-1312[COO-1312]

Log entries remain legible when the browser page is zoomed in::

Before this update, the *Logs* view in the {ocp-product-title} web console did not recalculate row heights or line spacing for the *Message* column when you zoomed in on the browser page. As a consequence, the text scaled up while the row height stayed fixed, so log lines overlapped vertically and rows were clipped, which made the log content illegible.
+
With this release, the *Logs* table recalculates row heights and text container bounds when the zoom level changes. As a result, log messages wrap correctly and remain readable at any zoom level.
+
link:https://issues.redhat.com/browse/COO-2519[COO-2519]

Perses instances use the Red{nbsp}Hat build of Perses by default::

Before this update, the Perses Operator that {coo-full} deploys used an upstream Perses image as its default base image. As a consequence, Perses instances that did not explicitly set an image in the custom resource used an upstream image instead of the supported build, and you had to set the image manually on every Perses custom resource.
+
With this release, {coo-full} passes the Red{nbsp}Hat Perses image to the Perses Operator as the default base image. As a result, Perses instances use the supported Red{nbsp}Hat build without additional configuration.
+
link:https://issues.redhat.com/browse/COO-2633[COO-2633]

== Known issues

These are the known issues in {coo-full} 1.5.4:

Incorrect base image prevents CVE fixes in {coo-full} 1.5.4::

{coo-full} 1.5.4 was inadvertently released by using Red{nbsp}Hat Enterprise Linux (RHEL) 9.7 base images. Because RHEL 9.7 is deprecated and no longer receives security updates, the CVE fixes intended for this release were not applied.
+
As a workaround, upgrade directly to {coo-full} 1.5.5, which resolves this issue by using the supported RHEL 9.8 base images.
