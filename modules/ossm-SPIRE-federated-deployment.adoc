= Federated SPIRE across clusters

[role="_abstract"]

When workloads across multiple clusters need to communicate securely, federate SPIRE servers to establish trust relationships. This enables workloads to verify each other's identities across clusters without direct network connectivity.

== How SPIRE federation works

SPIRE federation establishes trust between SPIRE servers in different trust domains. A _trust domain_ is a boundary within which SPIRE issues and manages SPIFFE identities (similar to a PKI realm or certificate authority's scope).

Each cluster operates its own SPIRE server with a unique trust domain identifier. Through federation, these servers exchange _trust bundles_: collections of public keys needed to verify SPIFFE identities issued by other clusters.

When a workload on Cluster A needs to communicate with a workload on Cluster B:

. Both workloads obtain SPIFFE identities from their SPIRE servers.
. The SPIFFE identities include the trust domain of the issuing cluster.
. Each cluster's SPIRE server provides the trust bundle from the other cluster.
. Workloads use these bundles to verify the authenticity of identities from federated trust domains.

== Use cases for federation

Deploy federated SPIRE when your application architecture spans many clusters:

* **Different microservices across clusters**: Each cluster hosts different services that need to communicate with each other.
For example, a payment service on Cluster A needs to securely call an inventory service on Cluster B.
* **High availability and disaster recovery**: The same applications run on many clusters for redundancy.
Federated SPIRE enables these replicas to verify each other's identities and share workloads across sites.
* **Hybrid deployments**: A combination of both patterns, where some services are unique to specific clusters while others are replicated for availability.
