= Federated SPIRE deployment

[role="_abstract"]
A federated SPIRE deployment enables workloads across many {ocp-short-name} clusters to establish trust and verify each other's identities.
Federation creates trust relationships between SPIRE servers in different clusters, allowing secure cross-cluster communication in multi-cluster mesh environments.

== How SPIRE federation works

SPIRE federation establishes trust between SPIRE servers in different trust domains.
Each cluster operates its own SPIRE server with a unique trust domain identifier.
Through federation, these servers exchange trust bundles that contain the public keys needed to verify SPIFFE identities issued by other clusters.

When a workload on Cluster A needs to communicate with a workload on Cluster B:

. Both workloads obtain SPIFFE identities from their SPIRE servers.
. The SPIFFE identities include the trust domain of the issuing cluster.
. Each cluster's SPIRE server provides the federation bundle from the other cluster.
. Workloads use these bundles to verify the authenticity of identities from federated trust domains.

== Trust domains in federation

A trust domain is a boundary within which SPIRE issues and manages SPIFFE identities.
In federated deployments, each cluster has its own trust domain, typically matching the cluster's ingress domain.
Trust domain names must be unique across all federated clusters.

For example:
* Cluster A trust domain: `cluster-a.example.com`
* Cluster B trust domain: `cluster-b.example.com`

When workloads communicate across clusters, they can verify that identities come from authorized trust domains based on the federation configuration.

== Use cases for federation

Deploy federated SPIRE when:

* Your service mesh spans many {ocp-short-name} clusters.
* Workloads on different clusters need to communicate securely using mutual TLS.
* You want to verify the identity and origin of cross-cluster traffic.
* You need to enforce zero-trust principles across cluster boundaries.

Federated SPIRE deployments require more configuration and ongoing management compared to single cluster deployments.
Only use federation when your architecture requires cross-cluster workload communication.
