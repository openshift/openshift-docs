= Traditional Argo CD architecture

[role="_abstract"]
Traditional Argo CD architecture uses a centralized control plane to manage applications across one or more clusters. All Argo CD components run on a single hub cluster, and the hub establishes direct connections to managed clusters for deployment operations.

*Traditional architecture components*

Traditional Argo CD consists of the following core components:

* *Application controller* - Continuously monitors applications and reconciles the desired state from Git with the actual state on clusters.
* *Repo server* - Clones Git repositories, renders manifests, and caches repository contents.
* *API server* - Provides the REST API and serves the web console.
* *Redis* - Caches repository data and provides message queuing for the application controller.
* *ApplicationSet controller* - Generates multiple applications from templates and generators.
* *Notifications controller* - Sends notifications about application events to configured destinations.

*How traditional architecture works*

In traditional Argo CD:

. The application controller polls Git repositories at regular intervals to detect changes
. When changes are detected, the repo server renders the manifests using Helm, Kustomize, or plain YAML
. The application controller compares the rendered manifests with resources on the target cluster
. If differences exist, the controller applies the changes to the cluster using the Kubernetes API
. The controller uses cluster credentials stored as Kubernetes secrets to authenticate with remote clusters

*Traditional architecture benefits*

Traditional architecture provides:

* *Simplicity* - All components run on a single cluster, simplifying deployment and operations.
* *Full feature support* - Supports all Argo CD features without limitations.
* *Direct control* - The hub has direct access to managed clusters for real-time synchronization.
* *Mature and stable* - The traditional architecture is the upstream Argo CD standard with the most extensive testing and community support.

*Traditional architecture limitations*

Traditional architecture has constraints when:

* *Network access* - Managed clusters must be network-accessible from the hub cluster. Firewalls or isolated networks can block connections.
* *Scale limits* - A single control plane has practical limits managing hundreds of clusters or thousands of applications.
* *Resource consumption* - The hub cluster must have sufficient resources to reconcile all applications across all managed clusters.
* *Hub dependency* - Managed clusters cannot reconcile applications if the hub cluster is unavailable.

*When to use traditional architecture*

Choose traditional Argo CD architecture when:

* Managing applications on a single cluster or a small number of clusters
* All managed clusters are network-reachable from the hub cluster
* You need the full feature set and upstream compatibility
* Your deployment is under 50 clusters with fewer than 1000 total applications
* Your hub cluster has sufficient resources to handle reconciliation for all managed clusters
