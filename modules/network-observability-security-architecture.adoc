= Network Observability security architecture

[role="_abstract"]
The Network Observability Operator uses multiple components that communicate across different namespaces to collect, process, and display network flow data. Understanding the security architecture helps you configure appropriate network policies and security hardening measures.

== Components and security boundaries

The Network Observability Operator consists of the following components:

Network Observability Operator::
Runs in the `openshift-netobserv-operator` namespace. This component manages the deployment and configuration of all other Network Observability components. It requires egress access to the API server and ingress access for webhooks and metrics.

eBPF agents::
Run as a DaemonSet on each node to capture network flow data. The agents communicate with the FlowLogs Pipeline (FLP) to send collected flow data. This communication can be secured by using TLS or mutual TLS.

FlowLogs Pipeline (FLP)::
Runs in the `netobserv` namespace (configurable). This component receives flow data from the eBPF agents, enriches it with Kubernetes metadata, and forwards it to storage backends such as Loki or exports it to external systems.

Console plugin::
Runs in the `netobserv` namespace and provides the web console interface for viewing network flow data. It requires access to query the storage backend and serve content to the OpenShift Console.

== Network traffic flows

Understanding the network traffic flows between components helps you configure minimal network policies:

Agent to FLP::
eBPF agents send flow data to the FLP over gRPC. This connection can be secured with TLS or mTLS. The default configuration uses automatic TLS with OpenShift service CA annotations.

FLP to Loki::
If using Loki as the storage backend, FLP sends enriched flow data to Loki over HTTP or HTTPS.

FLP to Kafka::
If using Kafka as a buffer, FLP sends flow data to Kafka brokers.

Console plugin to Loki::
The console plugin queries Loki directly to retrieve and display flow data in the web console.

Console plugin to OpenShift Console::
The OpenShift Console loads the Network Observability plugin to display the network flow visualization interface.

Operator to API server::
The operator communicates with the Kubernetes API server to manage resources, watch for configuration changes, and perform reconciliation.

All components to DNS::
All components require access to DNS for service discovery and name resolution.

== Security model

The Network Observability security model uses the following mechanisms:

Network policies::
Control ingress and egress traffic for components. The operator can deploy network policies automatically by using the FlowCollector custom resource, or you can create custom policies manually.

Runtime network policy deployment::
The operator deploys a network policy for its own namespace at runtime. This is controlled by the `DEPLOY_OPERATOR_NETWORK_POLICY` environment variable in the Cluster Service Version, which defaults to `true`.

Transport Layer Security (TLS)::
Secure communications between eBPF agents and the FlowLogs Pipeline by using TLS or mutual TLS. The default configuration uses automatic TLS with zero configuration required.

Pod Security Standards::
Network Observability components follow OpenShift pod security standards and use Security Context Constraints (SCCs) appropriately.

Service accounts::
Each component uses dedicated service accounts with minimal required permissions following the principle of least privilege.
