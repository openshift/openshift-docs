= How layer-level mirror fallback works when a mirror cannot serve a layer

[role="_abstract"]
In OpenShift 4.20 and later, CRI-O on Linux nodes implements per-layer mirror fallback, allowing automatic failover to secondary image mirrors when a primary mirror cannot provide a specific layer. This layer-level granularity differs from the previous whole-registry fallback behavior and enables clusters to overcome deadlock scenarios where a reachable but degraded primary mirror would previously block all image pulls.

== What is layer-level mirror fallback

Layer-level mirror fallback is the automatic process of attempting to retrieve an image layer from a secondary mirror when the primary mirror encounters an error while downloading that specific layer.

Container images consist of two components:

* **Image manifest**: Metadata describing the image structure, layer digests, and configuration
* **Image layers**: The actual file content for each layer (compressed tar archives)

In previous OpenShift releases, if the primary mirror failed to serve the entire image (manifest or any layer), the cluster would mark the entire mirror as failed and only then attempt the next mirror. This whole-registry approach caused deadlock scenarios when a primary mirror was reachable but degraded.

In OpenShift 4.20 and later, CRI-O attempts to download each layer independently from the mirrors list in declared order:

1. CRI-O attempts to fetch the manifest from the primary mirror
2. If the manifest is unavailable, CRI-O tries the secondary mirror
3. Once a manifest is obtained (from any mirror), CRI-O begins downloading layers
4. For each layer, CRI-O attempts the primary mirror first
5. If the primary mirror fails for that layer with a transient error, CRI-O immediately retries with the secondary mirror
6. If the secondary mirror fails, CRI-O tries the tertiary mirror
7. The process continues until the layer is obtained or all mirrors are exhausted

This per-layer independence means that a single image pull can source layers from multiple mirrors.

== Manifest retrieval and layer download stages

The fallback behavior differs depending on which stage of the pull process encounters an error.

=== Manifest retrieval stage

When CRI-O attempts to download the image manifest:

* **Attempt from primary mirror**: CRI-O first requests the manifest from the primary mirror
* **Primary failure**: If the primary mirror returns a transient error (404, 502, 503, 429, timeout), CRI-O proceeds to the secondary mirror
* **Secondary mirror**: CRI-O requests the manifest from the secondary mirror
* **Success or next mirror**: If the secondary mirror provides the manifest, layer downloading begins from that manifest. If the secondary fails, CRI-O tries the tertiary mirror
* **Authentication failures**: If the primary mirror returns an authentication error (401, 403), CRI-O does not attempt fallback and the pull fails immediately

If the manifest is obtained from a secondary mirror, subsequent layer downloads still prefer the primary mirror. This allows scenarios where the manifest comes from Mirror B but layers are served by Mirror A.

=== Layer download stage

Once the manifest is obtained, CRI-O downloads each layer:

* **Attempt from primary mirror**: For each layer, CRI-O first attempts download from the primary mirror
* **Primary failure**: If the primary mirror fails with a transient error during layer download, CRI-O immediately retries that specific layer with the secondary mirror
* **Layer-specific fallback**: The failure applies only to that layer; other layers continue attempting from the primary mirror
* **Complete success or all mirrors exhausted**: The layer download succeeds when any mirror provides it, or fails if all mirrors return errors or authentication failures

The layer-specific nature of the fallback means that a single image pull can successfully combine layers from multiple mirrors without marking any mirror as completely failed.

== Error conditions that trigger fallback

The following HTTP status codes and error conditions trigger layer-level fallback to the next mirror:

* **HTTP 404 (Not Found)**: Layer does not exist in the primary mirror; attempt secondary mirror
* **HTTP 502 (Bad Gateway)**: Primary mirror gateway or upstream service error; attempt secondary mirror
* **HTTP 503 (Service Unavailable)**: Primary mirror temporarily unavailable; attempt secondary mirror
* **HTTP 429 (Too Many Requests)**: Rate limit exceeded on primary mirror; attempt secondary mirror
* **Connection timeout**: Network latency or connectivity issue with primary mirror; attempt secondary mirror
* **Connection reset**: Unexpected connection termination; attempt secondary mirror
* **Backend storage error**: Registry backend failure (e.g., corrupted layers); attempt secondary mirror

The following error conditions do NOT trigger fallback:

* **HTTP 401 (Unauthorized)**: Authentication failure; pull fails immediately (do not attempt other mirrors for security reasons)
* **HTTP 403 (Forbidden)**: Authorization failure; pull fails immediately (do not attempt other mirrors)
* **Partial layer download with connection drop during transfer**: Retry the same mirror before attempting fallback; do not immediately try secondary mirror

== Comparison: Manifest versus layer fallback scope

Fallback behavior depends on which component of the image pull is affected:

* **Manifest failure**: Fallback to next mirror for the entire manifest; layer downloads then begin from the mirror that provided the manifest or from the primary mirror for subsequent layers
* **Layer download failure**: Fallback to next mirror for that specific layer only; manifest remains valid and other layers continue downloading from the original mirror

This separation allows a single image pull to efficiently use the closest mirror for some components while falling back to distant mirrors only for layers that are unavailable locally.

== Mirror ordering and fallback sequence

The order of mirrors in the IDMS or ITMS `mirrors:` array directly determines the fallback sequence.

Example IDMS configuration:

[source,yaml]
----
spec:
  imageDigestMirrors:
  - source: registry.redhat.io
    mirrors:
    - quay.example.com                    # Primary mirror - tried first
    - mirror.backup.example.com           # Secondary mirror - tried if primary fails
    - mirror.disaster-recovery.example.com # Tertiary mirror - tried if secondary fails
----

CRI-O attempts mirrors in this exact order:
1. First mirror in the list (primary)
2. Second mirror in the list (secondary)
3. Third mirror in the list (tertiary)
4. If `mirrorSourcePolicy: AllowContactingSource`, attempt the original source registry

== Role of mirrorSourcePolicy in fallback

The `mirrorSourcePolicy` field controls whether CRI-O attempts to fall back to the original source registry after all configured mirrors fail.

* **`AllowContactingSource` (default)**: After all mirrors fail, CRI-O attempts to pull the image directly from the source registry. This mode is useful for hybrid deployments where the cluster has occasional external connectivity.
* **`NeverContactSource`**: CRI-O does not contact the source registry, even after all mirrors fail. This mode is required for air-gapped clusters where network policy prevents source contact.

The `mirrorSourcePolicy` field does not affect fallback between mirrors themselves—that always occurs when transient errors are encountered.

== Platform distinction: Linux CRI-O vs. Windows containerd

Layer-level mirror fallback behavior is specific to Linux nodes running CRI-O.

Windows nodes running containerd maintain the previous whole-registry fallback behavior:

* Containerd does not implement per-layer fallback
* Windows nodes fall back to the next mirror only when the entire image pull fails
* If you manage a mixed Linux/Windows cluster, be aware that Windows nodes have different fallback semantics

This platform distinction is important for cluster administrators managing image pull reliability across heterogeneous node types.

== Example: Layer-level fallback in action

Consider a practical scenario where an ODF operator attempts to pull an image with three layers:

1. **Base OS layer** (500 MB)
2. **Application dependencies layer** (200 MB)
3. **ODF-specific layer** (100 MB)

Configuration:

* Primary mirror: `quay.example.com`
* Secondary mirror: `mirror-backup.example.com`

Pull sequence:

1. CRI-O fetches the manifest from `quay.example.com` — success
2. CRI-O starts downloading base OS layer from `quay.example.com` — success (500 MB downloaded)
3. CRI-O downloads application dependencies layer from `quay.example.com` — success (200 MB downloaded)
4. CRI-O attempts to download ODF-specific layer from `quay.example.com` — fails with HTTP 502
5. CRI-O immediately retries the ODF-specific layer from `mirror-backup.example.com` — success (100 MB downloaded)
6. Image pull completes; ODF operator can proceed

The entire image was successfully pulled even though the primary mirror failed for one layer. The pull combined layers from both mirrors without marking the primary mirror as failed.

== Benefits of layer-level fallback

Layer-level fallback provides several benefits over whole-registry fallback:

* **Resilience to transient failures**: A temporary issue with the primary mirror for a single layer does not affect the availability of other layers or the operator's ability to pull images
* **Faster recovery**: Immediate per-layer fallback is faster than waiting for whole-registry failure detection and recovery
* **Better multi-mirror utilization**: Secondary mirrors are not just backups; they actively participate in image pulling when primary mirrors have issues
* **Reduced deadlock scenarios**: Interconnected mirror architectures no longer create deadlock situations
* **Improved uptime**: Clusters with multiple mirrors achieve higher availability because any healthy mirror can serve any layer
