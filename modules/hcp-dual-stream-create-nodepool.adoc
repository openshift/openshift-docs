= Creating a NodePool with a specific {op-system} major version

[role="_abstract"]
Pinning the {op-system} stream at creation time gives you control over the operating system version running on your compute nodes and prevents unexpected stream transitions during future {product-title} upgrades.

You can create a `NodePool` resource that runs {op-system-base} 9 or {op-system-base} 10 worker nodes by setting the `spec.osImageStream` field in the `NodePool` manifest.

If you do not set `spec.osImageStream` field, the `NodePool` resource uses the version-derived default: `rhel-9` on {product-title} releases before 5.0, and `rhel-10` on {product-title} 5.0 and later.

[IMPORTANT]
====
If you change the `spec.osImageStream.name` field on an existing `NodePool`, you trigger a rolling node replacement. All nodes in the pool are reprovisioned by using the new {op-system} boot image. This results in temporary capacity reduction during the rollout.

Changing `spec.osImageStream.name` from `rhel-10` to `rhel-9` on an existing `NodePool` is not supported. The API rejects the change with the following error:

----
OS stream downgrade from rhel-10 to rhel-9 is not allowed; create a new NodePool instead
----

Instead, create a `NodePool` resource with `spec.osImageStream.name: rhel-9` and migrate workloads to the new pool.
====

.Prerequisites

* An {product-title} 5.0 or later cluster running {hcp} is available.
* For {op-system-base} 10 `NodePool` resources on {product-title} 4.x, the `TechPreviewNoUpgrade` feature set is enabled on the cluster. Enabling `TechPreviewNoUpgrade` is a one-way change.
* The `oc` CLI is installed and configured to access the `HostedCluster` namespace.
* You have reviewed the xref:../hosted_control_planes/hcp-dual-stream.adoc#hcp-dual-stream-arch_hcp-dual-stream[supported architectures and platform boot images] to confirm that {op-system-base} 10 is available for your target platform and architecture.
* No `ContainerRuntimeConfig` resources in the cluster set `defaultRuntime: runc` for workloads that you intend to run on {op-system-base} 10 nodes. For more information, see "Container runtime compatibility for {op-system-base} 10 node pools".

.Procedure

. Create a `NodePool` manifest file, for example `nodepool.yaml`, with `spec.osImageStream.name` field set to the target {op-system} stream.

** For {op-system-base} 10, create a manifest file as shown in the following example:
+
[source,yaml]
----
apiVersion: hypershift.openshift.io/v1beta1
kind: NodePool
metadata:
  name: <nodepool_name>
  namespace: <namespace_name>
spec:
  clusterName: <cluster_name>
  replicas: <replica_count>
  osImageStream:
    name: rhel-10
  platform:
    type: AWS
    aws:
      instanceType: m5.xlarge
----
+
* Replace `<nodepool_name>` with the name for the `NodePool` resource.
* Replace `<cluster_name>` with the name of the `HostedCluster` resource that this `NodePool` resource belongs to.
* Replace `<replica_count>` with the number of compute nodes to provision.
* Replace `<namespace_name> with the namespace for the `NodePool` resource. The conventional namespace for `NodePool` resources in {hcp} is `clusters`, but `NodePool` resources can reside in other namespaces.

** For {op-system-base} 9, create a manifest file as shown in the following example:
+
[source,yaml]
----
apiVersion: hypershift.openshift.io/v1beta1
kind: NodePool
metadata:
  name: <nodepool_name>
  namespace: <namespace_name>
spec:
  clusterName: <cluster_name>
  replicas: <replica_count>
  osImageStream:
    name: rhel-9
  platform:
    type: AWS
    aws:
      instanceType: m5.xlarge
----
+
* Replace `<nodepool_name>` with the name for the `NodePool` resource.
* Replace `<cluster_name>` with the name of the `HostedCluster` resource that this `NodePool` resource belongs to.
* Replace `<replica_count>` with the number of compute nodes to provision.
* Replace `<namespace_name> with the namespace for the `NodePool` resource. The conventional namespace for `NodePool` resources in {hcp} is `clusters`, but `NodePool` resources can reside in other namespaces.

. Apply the `NodePool` manifest by entering the following command:
+
[source,terminal]
----
$ oc apply -f nodepool.yaml
----

. Monitor the `NodePool` resource until the nodes reach `Ready` status by entering the following command:
+
[source,terminal]
----
$ oc get nodepool <nodepool_name> -n <namespace> -w
----
+
Node provisioning typically takes 5–15 minutes depending on platform. If the `NodePool` resource does not reach a ready state within 30 minutes, check events by entering `oc describe nodepool <nodepool_name> -n <namespace>`.

. Verify that `status.osImageStream` reflects the intended stream:
+
[source,terminal]
----
$ oc get nodepool <nodepool_name> -n <namespace> -o jsonpath='{.status.osImageStream}'
----
+
The following example shows expected output for {op-system-base} 10:
+
[source,terminal]
----
rhel-10
----

.Verification

* Confirm that the `NodePool` nodes are running and that the status shows the correct {op-system} stream:
+
[source,terminal]
----
$ oc get nodepool <nodepool_name> -n <namespace>
----
+
The `READY` column shows `True` when all nodes in the pool are available.
+
[NOTE]
====
The `spec.osImageStream` field cannot be removed from a `NodePool` spec after it has been set. If you need to use a different stream, you must create a new `NodePool` resource.
====
