= How virtualized control planes work

[role="_abstract"]
A virtualized control plane deployment involves two distinct clusters:

Hosting cluster:: An existing {product-title} cluster running {VirtProductName} that hosts the control plane VMs.
A single hosting cluster can support multiple target clusters by running each cluster's control plane VMs in separate namespaces.

Target cluster:: The {product-title} cluster whose control plane nodes run as VMs on the hosting cluster.
The target cluster's worker nodes run on separate infrastructure, either physical servers or VMs on different hosts.

KubeVirt Redfish runs on the hosting cluster and exposes the control plane VMs through standard Redfish API endpoints.
This enables standard installation workflows such as Agent-based Installer or {ztp-first} to treat the VMs the same as physical servers with baseboard management controllers (BMCs).

[NOTE]
====
Virtualized control planes differ from {hcp-capital}.
With virtualized control planes, the control plane runs as VMs with hypervisor-level isolation.
With {hcp-capital}, the control plane runs as pods with container-level isolation.
====
