= Cluster-level overcommit using the Cluster Resource Override Operator

[role="_abstract"]
You can use the Cluster Resource Override Operator to control the level of overcommit and manage container density across all the nodes in your cluster. The Operator, which is an admission webhook, controls how nodes in specific projects can exceed defined memory and CPU limits.

// Paragraph taken from 3.11 docs and modified. 
// https://docs.openshift.com/container-platform/3.11/admin_guide/overcommit.html#configuring-masters-for-overcommitment
The Operator modifies the ratio between the requests and limits that are set on developer containers. In conjunction with a per-project limit range that specifies limits and defaults, you can achieve the desired level of overcommit.

You must install the Cluster Resource Override Operator by using the {product-title} console or CLI as shown in the following sections. After you deploy the Cluster Resource Override Operator, the Operator modifies all new pods in specific namespaces. The Operator does not edit pods that already exist.

You can set different ratios for one project, or for pods in that project that have specific labels, by creating a `ResourceOverride` object. A matching `ResourceOverride` object replaces the cluster-wide ratios for that pod. Unset fields on the matching object are not copied from the `ClusterResourceOverride` object. Pods that do not match a `ResourceOverride` object continue to use the `ClusterResourceOverride` object named `cluster`. Clusters that use only the cluster-wide object do not need to change. For more information, see "Project-level overcommit using the Cluster Resource Override Operator".

During the installation, you create a `ClusterResourceOverride` custom resource (CR), where you set the level of overcommit, as shown in the following example:

[source,yaml]
----
apiVersion: operator.autoscaling.openshift.io/v1
kind: ClusterResourceOverride
metadata:
    name: cluster
spec:
  podResourceOverride:
    spec:
      memoryRequestToLimitPercent: 50
      cpuRequestToLimitPercent: 25
      limitCPUToMemoryPercent: 200
# ...
----
where:

--
`metadata.name`:: Specifies a name for the object. The name must be `cluster`.
`spec.podResourceOverride.spec.memoryRequestToLimitPercent`:: If a container memory limit has been specified or defaulted, the memory request is overridden to this percentage of the limit, between 1-100. The default is 50.
`spec.podResourceOverride.spec.cpuRequestToLimitPercent`:: If a container CPU limit has been specified or defaulted, the CPU request is overridden to this percentage of the limit, between 1-100. The default is 25.
`spec.podResourceOverride.spec.limitCPUToMemoryPercent`:: If a container memory limit has been specified or defaulted, the CPU limit is overridden to a percentage of the memory limit, if specified. Scaling 1Gi of RAM at 100 percent is equal to 1 CPU core. This is processed before overriding the CPU request (if configured). The default is 200.
--

[NOTE]
====
The `memoryRequestToLimitPercent`, `cpuRequestToLimitPercent`, and `limitCPUToMemoryPercent` fields have no effect if limits have not been set on containers. Create a `LimitRange` object with default limits for each project or configure limits in `Pod` specs for those fields to apply.

The `cpuRequestToRequestPercent` field uses the original CPU request. It applies when no CPU limit is set. Use it for workloads that set a CPU request and omit a CPU limit, including charts that were sized for another processor architecture, without editing the workload manifests.
====

When configured, you can enable overrides on a per-project basis by applying the following label to the `Namespace` object for each project where you want the overrides to apply. The same label is required for a `ResourceOverride` object in that project. For example, you can omit the label so that infrastructure components are not subject to the overrides.

[source,yaml]
----
apiVersion: v1
kind: Namespace
metadata:

# ...

  labels:
    clusterresourceoverrides.admission.autoscaling.openshift.io/enabled: "true"

# ...
----

The Operator watches for the `ClusterResourceOverride` CR and ensures that the `ClusterResourceOverride` admission webhook is installed into the same namespace as the operator.

// Examples take from: https://github.com/openshift/cluster-resource-override-admission-operator?tab=readme-ov-file#test-pod-resource-override
For example, a pod has the following resource limits:

[source,yaml]
----
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  namespace: my-namespace
# ...
spec:
  containers:
    - name: hello-openshift
      image: openshift/hello-openshift
      resources:
        limits:
          memory: "512Mi"
          cpu: "2000m"
# ...
----

The Cluster Resource Override Operator intercepts the original pod request, then overrides the resources according to the configuration set in the `ClusterResourceOverride` object.

[source,yaml]
----
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  namespace: my-namespace
# ...
spec:
  containers:
  - image: openshift/hello-openshift
    name: hello-openshift
    resources:
      limits:
        cpu: "1"
        memory: 512Mi
      requests:
        cpu: 250m
        memory: 256Mi
# ...
----
where:

--
`spec.containers.resources.limits.cpu`:: Specifies that the CPU limit has been overridden to `1` because the `limitCPUToMemoryPercent` parameter is set to `200` in the `ClusterResourceOverride` object. As such, 200% of the memory limit, 512Mi in CPU terms, is 1 CPU core.
`spec.containers.resources.requests.cpu`:: Specifies that the CPU request is now `250m` because `cpuRequestToLimitPercent` is set to `25` in the `ClusterResourceOverride` object. As such, 25% of the 1 CPU core is 250m.
--

You can set `cpuRequestToRequestPercent` when you want the CPU request to be a percentage of the original CPU request. The following `ClusterResourceOverride` object sets only that field:

[source,yaml]
----
apiVersion: operator.autoscaling.openshift.io/v1
kind: ClusterResourceOverride
metadata:
    name: cluster
spec:
  podResourceOverride:
    spec:
      cpuRequestToRequestPercent: 50
# ...
----
where:

--
`spec.podResourceOverride.spec.cpuRequestToRequestPercent`:: If a container CPU request has been specified or defaulted, the CPU request is overridden to this percentage of the original CPU request, between 1-100. Omit this field to leave request-relative CPU override disabled. This field has no default. A CPU limit is not required. This field is processed after the other overrides and uses the original CPU request.
--

For example, a pod has a CPU request of `200m` and no CPU limit:

[source,yaml]
----
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  namespace: my-namespace
# ...
spec:
  containers:
    - name: hello-openshift
      image: openshift/hello-openshift
      resources:
        requests:
          cpu: "200m"
# ...
----

The Cluster Resource Override Operator intercepts the original pod request, then overrides the CPU request to `100m`, which is 50 percent of the original `200m` request.

[source,yaml]
----
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  namespace: my-namespace
# ...
spec:
  containers:
  - image: openshift/hello-openshift
    name: hello-openshift
    resources:
      requests:
        cpu: 100m
# ...
----
where:

--
`spec.containers.resources.requests.cpu`:: Specifies that the CPU request is `100m` because `cpuRequestToRequestPercent` is set to `50` and the original CPU request was `200m`.
--

If `cpuRequestToRequestPercent` and `cpuRequestToLimitPercent` are both set, `cpuRequestToRequestPercent` is applied last. It uses the original CPU request and replaces the request that was computed from `cpuRequestToLimitPercent`.
