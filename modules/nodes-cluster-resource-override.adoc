= About configuring overcommit by using the Cluster Resource Override Operator

[role="_abstract"]
You can use the Cluster Resource Override Operator to control the level of overcommit and manage container density across all the nodes in your cluster. The Operator, which is an admission webhook, controls how nodes in specific projects can exceed defined memory and CPU limits.

// Paragraph taken from 3.11 docs and modified. 
// https://docs.openshift.com/container-platform/3.11/admin_guide/overcommit.html#configuring-masters-for-overcommitment
The Operator modifies the ratio between the requests and limits that are set on developer containers. In conjunction with a per-project limit range that specifies limits and defaults, you can achieve the desired level of overcommit.

You must install the Cluster Resource Override Operator by using the {product-title} console or CLI as shown in the following sections. After you deploy the Cluster Resource Override Operator, the Operator modifies all new pods in specific namespaces. The Operator does not edit pods that existed before you deployed the Operator.

The Operator supports two approaches for applying overcommit policies:

* **Single-profile mode**: A single `ClusterResourceOverride` CR named `cluster` applies to all opted-in namespaces with the `clusterresourceoverrides.admission.autoscaling.openshift.io/enabled: "true"` label.

* **Multi-profile mode**: Create multiple named `ClusterResourceOverride` CRs and assign each to specific namespaces using `ClusterResourceOverrideBinding` objects. This allows different namespaces to use different overcommit ratios based on their workload characteristics, for example production or development.

You create at least one `ClusterResourceOverride` custom resource (CR), where you set the level of overcommit, as shown in the following example. For more information, see "Configuring multi-profile mode overcommit" or "Configuring single-profile mode overcommit".

[NOTE]
====
The Cluster Resource Override Operator overrides have no effect if limits have not been set on containers. Create a `LimitRange` object with default limits per individual project or configure limits in `Pod` specs for the overrides to apply.
====

The Operator watches for the `ClusterResourceOverride` CR and ensures that the `ClusterResourceOverride` admission webhook is installed into the same namespace as the operator.

// Examples take from: https://github.com/openshift/cluster-resource-override-admission-operator?tab=readme-ov-file#test-pod-resource-override
For example, a pod has the following resources limits:

[source,yaml]
----
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  namespace: my-namespace
# ...
spec:
  containers:
    - name: hello-openshift
      image: openshift/hello-openshift
      resources:
        limits:
          memory: "512Mi"
          cpu: "2000m"
# ...
----

Then, you create the `ClusterResourceOverride` object:

[source,yaml]
----
apiVersion: operator.autoscaling.openshift.io/v1
kind: ClusterResourceOverride
metadata:
    name: cluster
spec:
  podResourceOverride:
    spec:
      memoryRequestToLimitPercent: 50
      cpuRequestToLimitPercent: 25
      limitCPUToMemoryPercent: 200
----

The Cluster Resource Override Operator intercepts the original pod request, then overrides the resources according to the configuration set in the `ClusterResourceOverride` object.

[source,yaml]
----
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  namespace: my-namespace
# ...
spec:
  containers:
  - image: openshift/hello-openshift
    name: hello-openshift
    resources:
      limits:
        cpu: "1"
        memory: 512Mi
      requests:
        cpu: 250m
        memory: 256Mi
# ...
----

In this example, the `limits.cpu` parameter shows that the CPU limit has been overridden to `1` because the `limitCPUToMemoryPercent` parameter is set to `200` in the `ClusterResourceOverride` object. As such, 200% of the memory limit, 512Mi in CPU terms, is 1 CPU core.  

The `memory.cpu` parameter shows that the CPU request is now `250m` because the `cpuRequestToLimit` is set to `25` in the `ClusterResourceOverride` object. As such, 25% of the 1 CPU core is 250m.

Scaling CPU requests relative to existing requests::
You can use the `RequestRelative` CPU override strategy to reduce CPU requests as a percentage of the existing request value, independent of whether a CPU limit is set. This is useful for Helm charts that define CPU requests without corresponding limits, or for architecture-specific optimization.
+
The traditional `LimitRelative` strategy computes the new CPU request as a percentage of the CPU limit. However, this approach has limitations:
+
--
* Helm charts often define CPU requests without CPU limits
* Containers without CPU limits are not affected by `LimitRelative` overrides
* Different architectures may require different request scaling
--
+
The `RequestRelative` strategy overcomes these limitations by scaling the request value itself.
+
For more information on how to use the `RequestRelative` CPU override strategy, see "Configuring multi-profile mode overcommit" or "Configuring single-profile mode overcommit".
