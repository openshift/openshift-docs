= Metrics that carry custom labels

[role="_abstract"]
A `TelemetryPolicy` CR labels the metrics that the {prodname} components emit. It leaves the `istio_*` metrics unchanged. Two components consume the labels.

The Limitador component of {prodname} counters carry the complete label set.

.Limitador metrics that carry custom labels
[cols="1,2",options="header"]
|===
| Metric | Description

| `authorized_calls`
| Requests that a rate limit check allowed

| `limited_calls`
| Requests that a rate limit check rejected

| `authorized_hits`
| Hits counted against a limit, which for a `TokenRateLimitPolicy` CR is the token consumption

| `report_calls`
| Calls to the Limitador `Report` method, which a `TokenRateLimitPolicy` CR uses to report token usage after the response
|===

Each series also carries the `limitador_namespace` label, which identifies the targeted route in the form `_<route_namespace>_/_<route_name>_`.

The Authorino Operator receives the same labels on every route that carries an `AuthPolicy` CR, and applies them to its own per-`AuthConfig` metrics. Authorino serves these metrics on the `/server-metrics` endpoint rather than on the `/metrics` endpoint. The following metrics carry every label except the labels that derive from the `auth.*` attributes:

* `auth_server_authconfig_total`
* `auth_server_authconfig_response_status`
* `auth_server_authconfig_duration_seconds`
* `auth_server_evaluator_*`

Authorino exports the `auth_server_evaluator_*` metrics only for evaluators that set the `metrics` field to `true`, or when Authorino runs with deep metrics enabled.

An `auth.*` label reaches Limitador but never Authorino, because the two components resolve the expression against data of a different shape. The `wasm-shim` module resolves the copy for Limitador against the flattened dynamic metadata that an `AuthPolicy` CR exports, where a `TokenReview` identity is `auth.identity.username`. Authorino resolves its own copy against its internal authorization JSON, where the same identity is `auth.identity.user.username`.

The expressions given are the expressions that Limitador requires. Authorino evaluates each request at several points in its pipeline and logs a `failed to evaluate CEL expression` error with the reason `no such key: username` at each of them. These errors are expected and have no effect on the Limitador labels.

Writing the label in the form that Authorino expects is not a workaround, because the `wasm-shim` module then cannot resolve it and the route stops producing Limitador metrics. Write `auth.*` labels for Limitador, and treat their absence from the Authorino metrics as expected.

For the labels that Authorino does apply, a single metric can hold series that have different label sets. Authorino allocates one counter for each distinct label combination and never reclaims them. Thus, a renamed or removed label leaves its earlier series in place. Aggregate such a metric with an explicit `sum by (...)` clause rather than summing the metric as a whole, and note that a high-cardinality expression costs storage twice, both in Limitador and in Authorino.
