The {otel} 3.11.6 release resolves the following Common Vulnerabilities and Exposures (CVEs):

Zstd decompression no longer stops the Collector::
Before this update, the Zstandard (zstd) decompression logic in the Go `klauspost/compress` library mishandled an integer value, which left stale internal state in the decoder. As a consequence, a remote attacker could send a crafted zstd-compressed stream to the Collector, causing an out-of-bounds read and an unhandled panic that stopped the Collector. With this update, the library handles the integer value correctly, so the decoder no longer retains stale internal state or performs the out-of-bounds read. As a result, the Collector no longer stops when it decodes a crafted zstd-compressed payload.
+
link:https://access.redhat.com/security/cve/cve-2026-116591[CVE-2026-116591]

The {otel} 3.11.5 release resolves the following Common Vulnerabilities and Exposures (CVEs):

Go certificate verification no longer trusts certificates from compromised intermediate CAs::
Before this update, the certificate verification process in the Go `crypto/x509` package did not block trust in intermediate certificates associated with a compromised certificate authority (CA). As a consequence, a remote attacker could present a certificate that one of these intermediate authorities signed and impersonate a legitimate server during a secure connection. The attacker could then conduct a man-in-the-middle (MitM) attack to intercept or alter confidential communications. With this update, the Go `crypto/x509` package rejects the known untrusted intermediate certificates during certificate verification. As a result, Collector components that use the Go certificate verification process no longer trust certificates that are signed by the affected intermediate CAs. Connections to servers that present such certificates fail.
+
link:https://access.redhat.com/security/cve/cve-2026-111943[CVE-2026-111943]

The {otel} 3.11.4 release incorporates updated base images that resolve the following Common Vulnerabilities and Exposures (CVEs):

Removed intermediate CA certificates with weak private keys::
Before this update, the system certificate authority (CA) store in Red Hat products included root CA certificates that signed intermediate CA certificates with weak private keys. As a consequence, a man-in-the-middle attacker could issue certificates for arbitrary hostnames. A TLS client using the system CA store could treat these certificates as trusted, potentially causing the client to connect to malicious sites. With this update, the vulnerable CA certificates are removed from the system CA store. As a result, clients no longer trust certificates signed by these compromised intermediate CAs.
+
link:https://access.redhat.com/security/cve/cve-2026-114406[CVE-2026-114406]

The {otel} 3.11.3 release resolves these Common Vulnerabilities and Exposures (CVEs):

Apache Thrift Go services are no longer vulnerable to DoS via empty network frames::
Before this update, Apache Thrift Go services were vulnerable to a denial of service (DoS) attack when processing specially crafted network frames with zero payload bytes. When the transport received these empty frames, it recursively called its read function rather than iterating in a loop, which exhausted the execution stack. As a consequence, this stack exhaustion caused an unrecoverable error that terminated the entire process. With this update, Apache Thrift handles empty frame payloads correctly. As a result, Go services are no longer vulnerable to DoS attacks via specially crafted network frames.
+
link:https://access.redhat.com/security/cve/cve-2026-83663/[CVE-2026-83663]
+
link:https://redhat.atlassian.net/browse/TRACING-6873[TRACING-6873]

Apache Thrift Go library is no longer vulnerable to DoS via malformed compressed data::
Before this update, the Apache Thrift Go library incorrectly handled decompression when a remote attacker sent specially crafted, highly compressed data to an affected service. As a consequence, the data amplification exhausted system resources and caused the service to become unavailable. With this update, Apache Thrift correctly handles decompression of compressed data. As a result, the Go library is no longer vulnerable to denial of service (DoS) attacks via malformed compressed frames.
+
link:https://access.redhat.com/security/cve/cve-2026-94637/[CVE-2026-94637]
+
link:https://redhat.atlassian.net/browse/TRACING-6879[TRACING-6879]

The {otel} 3.11.2 release resolves these Common Vulnerabilities and Exposures (CVEs):

`golang.org/x/mod/sumdb` verifies module content against the transparency log::
Before this update, `golang.org/x/mod/sumdb`, the Go module checksum verification package, could be compromised when a malicious Go checksum database (GOSUMDB) served module content not recorded in the transparency log. As a consequence, a coordinated Go proxy (GOPROXY) and GOSUMDB could deliver malicious module content to clients without detection, potentially enabling a supply chain compromise. With this update, the package verifies module content against the transparency log. As a result, clients can detect and reject malicious content served by a coordinated proxy and GOSUMDB.
+
link:https://access.redhat.com/security/cve/cve-2026-56864[CVE-2026-56864]
+
link:https://redhat.atlassian.net/browse/TRACING-6792[TRACING-6792]

`golang.org/x/mod/sumdb/tlog` validates sumdb tiles::
Before this update, `golang.org/x/mod/sumdb/tlog`, the Go module transparency log package, could not detect forged sumdb tiles. As a consequence, a malicious Go proxy (GOPROXY) could forge tiles and bypass integrity checks. This could serve malicious module content to the local Go module cache without detection. Users could unknowingly incorporate compromised modules. With this update, the package validates sumdb tiles. As a result, forged tiles are detected and rejected, preventing malicious content from reaching the module cache.
+
link:https://access.redhat.com/security/cve/cve-2026-56865[CVE-2026-56865]
+
link:https://redhat.atlassian.net/browse/TRACING-6793[TRACING-6793]

gRPC-Go servers no longer fail when receiving fragmented HTTP/2 DATA frames::
Before this update, an unauthenticated remote attacker could exhaust process memory by sending millions of fragmented HTTP/2 DATA frames. As a consequence, each fragmented frame was stored as a separate message, consuming disproportionate heap memory and leading to a runtime panic or out-of-memory termination, which caused a denial of service (DoS). With this update, the gRPC-Go library properly handles fragmented HTTP/2 frames. As a result, servers no longer exhaust memory or crash when receiving fragmented DATA frames.
+
link:https://access.redhat.com/security/cve/cve-2026-84304[CVE-2026-84304]
+
link:https://redhat.atlassian.net/browse/TRACING-6883[TRACING-6883]
+
link:https://redhat.atlassian.net/browse/TRACING-6884[TRACING-6884]

gRPC-Go servers no longer fail when receiving malformed RPC requests::
Before this update, servers created with the `xds.NewGRPCServer()` constructor could be exploited by a remote client sending a malformed remote procedure call (RPC) request lacking required headers. As a consequence, this caused an index-out-of-bounds panic that terminated the entire server process, resulting in a denial of service (DoS). In some deployments, unauthenticated clients could trigger this attack. With this update, gRPC-Go, the Go implementation of gRPC, validates headers in RPC requests. As a result, servers no longer fail when receiving malformed RPC requests.
+
link:https://access.redhat.com/security/cve/cve-2026-84445[CVE-2026-84445]

link:https://redhat.atlassian.net/browse/TRACING-6819[TRACING-6819]

The {otel} 3.11.1 release fixes this issue:

TargetAllocator endpoint uses FQDN to work behind HTTP proxy::
Before this update, the Collector used a bare service name (`+http://<name>-targetallocator:80+`) to contact the Target Allocator. When the cluster was behind a corporate HTTP proxy, the bare hostname did not match the standard `NO_PROXY=.svc` entry, causing the request to route through the proxy instead of reaching the service directly. As a consequence, the proxy returned an HTML authentication page instead of the expected JSON response, breaking the metrics scraping pipeline. With this release, the Target Allocator endpoint uses the fully qualified domain name (FQDN) (`+http://<name>-targetallocator.<namespace>.svc:80+`). As a result, the endpoint matches the standard `NO_PROXY=.svc` pattern, and the Collector reaches the Target Allocator directly without routing through the proxy.
+
link:https://redhat.atlassian.net/browse/TRACING-6784[TRACING-6784]

The {otel} 3.11.0 release fixes these issues:

`Instrumentation` CR status fields are updated automatically::
Before this update, when creating or updating an `Instrumentation` custom resource (CR), the `.status.observedGeneration` and `.status.conditions` fields were not updated because the {OTelOperator} lacked a reconciliation controller for `Instrumentation` CRs. In this release, the Operator continuously reconciles `Instrumentation` CRs and populates these status fields upon creation or update without requiring an Operator restart.
+
link:https://issues.redhat.com/browse/TRACING-6412[TRACING-6412]

Automatic RBAC of the Operator includes `PersistentVolume` and `PersistentVolumeClaim` resources::
Before this update, the automatic Role-Based Access Control (RBAC) feature of the {OTelOperator} did not include the required permissions for `PersistentVolume` and `PersistentVolumeClaim` resources. As a consequence, the Kubernetes Cluster Receiver failed with RBAC errors. With this update, the Operator automatically grants the required permissions for these resources. As a result, the Kubernetes Cluster Receiver works correctly with the automatic RBAC feature.
+
link:https://redhat.atlassian.net/browse/TRACING-6381[TRACING-6381]

Denial of service vulnerability fixed in Apache Thrift::
Before this update, Apache Thrift improperly handled highly compressed data, leading to a data amplification flaw. Consequently, a remote attacker could send specially crafted, highly compressed data, causing the component to fail during data expansion, which resulted in resource exhaustion and a denial of service (DoS). With this update, Apache Thrift properly manages data expansion for compressed payloads, preventing resource exhaustion and maintaining system availability.
+
link:https://access.redhat.com/security/cve/CVE-2026-48586[CVE-2026-48586]

Denial of service vulnerability fixed in Apache Thrift language bindings::
Before this update, an integer overflow or wraparound vulnerability existed in Apache Thrift bindings for C++, `c_glib`, Go, `netstd`, Delphi, and Haxe. Consequently, a remote attacker could send specially crafted input to trigger the flaw, causing affected services to become unavailable and impacting system reliability. With this update, Apache Thrift language bindings correctly handle input values to prevent integer overflows and wraparound conditions, ensuring service availability and system stability.
+
link:https://access.redhat.com/security/cve/CVE-2026-55969[CVE-2026-55969]

The {otel} 3.9.3 release fixes the following issues:

TOCTOU race condition in `libcap` `cap_set_file()` function is fixed::
Before this update, the `cap_set_file()` function in the Linux `libcap` library contained a time-of-check to time-of-use (TOCTOU) race condition. A local unprivileged user with write access to a parent directory could exploit this vulnerability to redirect file capability updates to an attacker-controlled file. This flaw allowed an attacker to inject capabilities into or strip capabilities from unintended executables, leading to privilege escalation. With this update, the race condition in `cap_set_file()` is fixed. As a result, file capability updates are applied to the intended target files, and the vulnerability is no longer exploitable.
+
link:https://access.redhat.com/security/cve/CVE-2026-4878[CVE-2026-4878]

Integer overflow vulnerability in Apache Thrift TFramedTransport Go implementation is fixed::
Before this update, the Apache Thrift TFramedTransport Go language implementation contained an integer overflow or wraparound vulnerability. An attacker could exploit this flaw to cause unexpected behavior or resource exhaustion, leading to a denial of service. With this update, the integer overflow issue is fixed. As a result, TFramedTransport correctly handles integer values, and the vulnerability is no longer exploitable.
+
link:https://access.redhat.com/security/cve/CVE-2026-41602[CVE-2026-41602]

Denial-of-service vulnerability in Go `crypto/x509` and `crypto/tls` packages is fixed::
Before this update, the Go standard library packages `crypto/x509` and `crypto/tls` did not properly limit the number of intermediate certificates processed during certificate chain building. An attacker could provide an excessive number of intermediate certificates, causing uncontrolled resource consumption. This flaw could cause a denial-of-service (DoS) condition, making the affected system or application unavailable to legitimate users. With this update, the number of intermediate certificates processed during certificate chain building is properly limited. As a result, the packages handle certificate chains efficiently, and the vulnerability is no longer exploitable.
+
link:https://access.redhat.com/security/cve/CVE-2026-32280[CVE-2026-32280]

TLS 1.3 connection deadlock vulnerability is fixed::
Before this update, if one side of a TLS 1.3 connection sent multiple key update messages post-handshake in a single record, the connection could deadlock. This deadlock caused uncontrolled consumption of resources and could lead to a denial of service. With this update, TLS 1.3 connections correctly handle multiple key update messages in a single record. As a result, connections no longer deadlock, and the vulnerability is no longer exploitable.
+
link:https://access.redhat.com/security/cve/CVE-2026-32283[CVE-2026-32283]

IPC API vulnerability in `systemd` manager is fixed::
Before this update, the system and service manager `systemd` contained a flaw that an unprivileged user could exploit by making an Inter-Process Communication (IPC) API call with spurious data. In version 249 or earlier, this flaw could lead to stack overwriting with attacker-controlled content, potentially enabling arbitrary code execution or privilege escalation. In version 250 or later, this flaw caused the `systemd` manager to assert and stop responding, resulting in a denial of service (DoS). With this update, the `systemd` manager correctly validates IPC API calls. As a result, the vulnerability is no longer exploitable.
+
link:https://access.redhat.com/security/cve/CVE-2026-29111[CVE-2026-29111]
