= Defining the virtual machine workload in the mesh

[role="_abstract"]

A `WorkloadGroup` resource describes the identity, labels, and network of the virtual machines that join the mesh. It is the equivalent of a `Deployment` resource for workloads that do not run as pods. The control plane uses it to issue certificates to the proxy running on a virtual machine and to include the workload in service discovery.

The `WorkloadGroup` resource is also where you override the proxy settings that differ on a virtual machine, through the `proxy.istio.io/config` annotation. The `istioctl x workload entry configure` command reads the annotation and merges its values into the configuration files that it generates for the virtual machine, so you do not have to edit the generated files afterwards.

The following examples use the `external-vm` namespace and a workload named `vm-app`. Substitute names that suit your environment.

.Procedure

. Create a namespace for the virtual machine workload by running the following command:
+
[source,terminal]
----
$ oc create namespace external-vm
----

. Create a service account that represents the identity of the virtual machine by running the following command:
+
[source,terminal]
----
$ oc create serviceaccount vm-app -n external-vm
----

. Create a `WorkloadGroup` resource named `workloadgroup.yaml` similar to the following example:
+
[source,yaml]
----
apiVersion: networking.istio.io/v1
kind: WorkloadGroup
metadata:
  name: vm-app
  namespace: external-vm
  annotations:
    proxy.istio.io/config: | # <1>
      binaryPath: /usr/bin/envoy # <2>
      discoveryAddress: istiod.istio-system.svc.<ingress_domain>:443 # <3>
      proxyMetadata:
        CA_ADDR: istiod.istio-system.svc.<ingress_domain>:443 # <4>
spec:
  metadata:
    labels:
      app: vm-app # <5>
  template:
    serviceAccount: vm-app # <6>
    network: vm-network # <7>
----
<1> The proxy configuration overrides for the virtual machine. The `istioctl x workload entry configure` command merges these values into the generated `mesh.yaml` and `cluster.env` files. Replace `<ingress_domain>` with the cluster ingress domain.
<2> The path to the Envoy binary. The `istio-proxy` RPM installs Envoy at `/usr/bin/envoy`, whereas the default value points to `/usr/local/bin/envoy`, which the RPM does not create.
<3> The address that the proxy connects to for its xDS configuration. The default value, `istiod.istio-system.svc:15012`, resolves only inside the cluster, so set it to the hostname of the route that exposes the control plane, on port 443.
<4> The address that the proxy sends certificate signing requests to. The proxy uses a separate connection for certificate signing, which does not read the `discoveryAddress` field, so the route hostname must be set a second time here. Without this value, the proxy cannot obtain a workload certificate.
<5> The labels that identify the workload running on the virtual machine. Services and policies select the workload through these labels, in the same way that they select workloads running in pods.
<6> The service account whose identity the virtual machine assumes. The control plane issues certificates for this identity.
<7> The network that the virtual machine belongs to. This value must differ from the `spec.values.global.network` value in the `Istio` resource so that traffic between the virtual machine and in-cluster workloads passes through the east-west gateway.

. Apply the `WorkloadGroup` resource by running the following command:
+
[source,terminal]
----
$ oc apply -f workloadgroup.yaml
----

.Verification

. Verify that the workload group exists by running the following command:
+
[source,terminal]
----
$ oc get workloadgroup vm-app -n external-vm
----
