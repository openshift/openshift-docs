= Skip-version upgrades with the RevisionBased strategy and IstioRevisionTag

[role="_abstract"]
For more efficient upgrades that minimize workload disruption, you can upgrade sidecar mode deployments two versions at a time with the `RevisionBased` update strategy and `IstioRevisionTag`.

[#how-skipping-a-version-works_{context}]
== How skipping a version works

You skip one Operator minor version and upgrade directly from _n_ to _n+2_. For example, you can upgrade directly from {SMProductShortName} 3.3 to 3.5, which requires only one workload restart instead of multiple restarts at each intermediate version.

During the upgrade process, both the old and new control plane versions operate concurrently.
Existing proxies remain attached to the old version until you restart the workloads.

[#requirements-and-considerations_{context}]
== Supported configurations and guidelines

Review the supported configurations and operational guidelines before upgrading with the skip-version method:     

* *Sidecar mode required.* Ambient mode still requires sequential minor version upgrades.

* *`RevisionBased` strategy required.* The `InPlace` update strategy still requires upgrading one minor version at a time.

* *No workload changes during upgrade.* Wait until the upgrade is complete before modifying the mesh topology.

* *Single version skip only.* You can skip only one minor version at a time. To skip more versions, repeat the complete upgrade procedure for each version skip.

* *Best practice: Longer grace period for validation.* Consider increasing the `inactiveRevisionDeletionGracePeriodSeconds` parameter in the `Istio` resource to validate the new version before the process removes the old revision. The default grace period (30 seconds) for deleting inactive revisions might not provide enough time for extended validation.

* *Release notes for the skipped version.* Read the release notes for the skipped version to understand the full range of changes and features resulting from the upgrade.

* *Compatible version of OpenShift Container Platform.* Review the versions of OpenShift that support your target version of Service Mesh. Refer to the OpenShift Operator Life Cycles web page.

* *Correct Gateway API version.* Check the minimum Gateway API version for both your current and target Istio versions to determine if you need to update the API. 
+
Refer to the Kubernetes Gateway API page for your version of Istio. Use the following URL (replacing _<version>_ with your Istio version):
+
[source,terminal,subs="+quotes"]
----
https://istio.io/v__<version>__/docs/tasks/traffic-management/ingress/gateway-api/
----
+
The page displays the compatible Gateway API version in the custom resource definition (CRD) installation command. If the Gateway API version increases between your current and target Istio versions, you must update the Gateway API CRDs before or during the Istio upgrade.

* *Rolling back an upgrade.* To roll back a skip-version upgrade (in case of issues), revert the operands only: the control plane, data plane, and container network interface (CNI) plugin. The Operator cannot be downgraded.

[#limitations_{context}]
== Limitations

* In Istio 1.27 and earlier, Kubernetes Gateway API gateways can remain on the old revision after upgrading the control plane, causing the gateway to stop serving traffic. 
+
Workaround:
+
Update the Gateway resource to trigger reconciliation by the new revision. For example, add an annotation:
+
[source,terminal,subs="+quotes"]
----
$ oc annotate gateway __<gateway-name>__ -n __<namespace>__ --overwrite nudge="$(date +%s)"
----

* When upgrading from Service Mesh versions earlier than 3.4, gateways can experience a brief outage (approximately 50 seconds) while the new revision initializes. Service Mesh 3.4 fixed this issue.

* During the upgrade while both revisions run, the control planes repeatedly overwrite each other's status updates for Kubernetes Gateway API objects until the process removes the old revision.
