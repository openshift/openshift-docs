= Example `PinnedImageSet` configurations

[role="_abstract"]
The following examples show common `PinnedImageSet` configurations for targeting machine config pools, disconnected environments, and large image lists.

[IMPORTANT]
====
Image references in a `PinnedImageSet` must use an immutable digest in the form `<registry>/<repository>@sha256:<digest>`. Tag references such as `:latest` are not supported. You can resolve a digest by running `skopeo inspect docker://<image>:<tag> | grep Digest` or `podman manifest inspect <image>:<tag>`.
====

== Pinning images to the worker pool

The following example pins images to nodes in the `worker` machine config pool:

[source,yaml]
----
apiVersion: machineconfiguration.openshift.io/v1
kind: PinnedImageSet
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
  name: worker-pinned-images
spec:
  pinnedImages:
  - name: quay.io/openshift-release-dev/ocp-release@sha256:513cf1028aa1a021fa73d0601427a0fbcf6d212b88aaf9d76d4e4841a061e44e
  - name: registry.access.redhat.com/ubi9/ubi@sha256:16e9e43d99e181463513cc84a514859b1abb9460f1c4d9e208da4b4e51cd5cc3
----

== Pinning images to the control plane pool

On clusters where application or operational images must be available on control plane nodes, including single-node {product-title} (SNO) clusters that use only the `master` machine config pool, target the `master` role:

[source,yaml]
----
apiVersion: machineconfiguration.openshift.io/v1
kind: PinnedImageSet
metadata:
  labels:
    machineconfiguration.openshift.io/role: master
  name: master-pinned-images
spec:
  pinnedImages:
  - name: registry.access.redhat.com/ubi9/ubi@sha256:16e9e43d99e181463513cc84a514859b1abb9460f1c4d9e208da4b4e51cd5cc3
----

[NOTE]
====
If you omit `metadata.labels`, the Machine Config Operator (MCO) attempts to pin the images to all machine config pools. For predictable targeting, set `machineconfiguration.openshift.io/role` to the pool you intend to update.
====

== Pinning different image sets to multiple pools

Create a separate `PinnedImageSet` object for each machine config pool that requires a different image list. The following example shows one set for workers and one set for a custom pool named `infra`:

[source,yaml]
----
apiVersion: machineconfiguration.openshift.io/v1
kind: PinnedImageSet
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
  name: worker-app-pinned-images
spec:
  pinnedImages:
  - name: registry.example.com/team/app@sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
  - name: registry.example.com/team/sidecar@sha256:bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb
----

[source,yaml]
----
apiVersion: machineconfiguration.openshift.io/v1
kind: PinnedImageSet
metadata:
  labels:
    machineconfiguration.openshift.io/role: infra
  name: infra-pinned-images
spec:
  pinnedImages:
  - name: registry.example.com/observability/agent@sha256:cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc
----

The `infra` example assumes that you already created a custom machine config pool whose `spec.machineConfigSelector` matches the `machineconfiguration.openshift.io/role: infra` label. For more information, see the documentation for creating a custom machine config pool.

== Pinning images from a disconnected mirror registry

In a disconnected or air-gapped environment, pin images from your mirrored registry by digest so that nodes do not need access to external registries:

[source,yaml]
----
apiVersion: machineconfiguration.openshift.io/v1
kind: PinnedImageSet
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
  name: mirror-pinned-images
spec:
  pinnedImages:
  - name: mirror.example.com/openshift4/ose-cli@sha256:dddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddddd
  - name: mirror.example.com/ubi9/ubi-minimal@sha256:eeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeee
----

Before you create the object, verify that each node can inspect the mirrored image:

[source,terminal]
----
$ oc debug node/<node_name> -- chroot /host podman manifest inspect mirror.example.com/ubi9/ubi-minimal@sha256:<digest>
----

== Pinning a large set of images

A single `PinnedImageSet` can include up to 500 image digests. Use large lists carefully:

* Confirm that each affected node has enough free disk space. The MCO checks available storage before pulling images and reports an error if space is insufficient.
* Expect longer pull times on control plane nodes, where image pulls are more heavily throttled than on worker nodes.
* Monitor progress and failures in the `MachineConfigNode` status for each node.

.Example truncated large image list
[source,yaml]
----
apiVersion: machineconfiguration.openshift.io/v1
kind: PinnedImageSet
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
  name: large-preload-pinned-images
spec:
  pinnedImages:
  - name: quay.io/openshift-release-dev/ocp-release@sha256:513cf1028aa1a021fa73d0601427a0fbcf6d212b88aaf9d76d4e4841a061e44e
  - name: quay.io/openshift-release-dev/ocp-release@sha256:61eae2d261e54d1b8a0e05f6b5326228b00468364563745eed88460af04f909b
  # ...
  # Add additional digest-pinned images, up to a maximum of 500 entries.
----

After you create or update a `PinnedImageSet`, confirm that the set is associated with the target nodes:

[source,terminal]
----
$ oc get machineconfignode <node_name> -o jsonpath='{.status.pinnedImageSets}{"\n"}'
----

.Example successful association
[source,terminal]
----
[{"currentGeneration":1,"desiredGeneration":1,"name":"worker-app-pinned-images"}]
----

If the association is missing, verify that the `machineconfiguration.openshift.io/role` label matches an existing machine config pool and that the node is a member of that pool.

== Sharing base images across pools

Create a shared base `PinnedImageSet` and separate workload-specific sets. Label each set for the pools that need those images. The following example shows a base set for workers and an application set for the same pool; create additional labeled sets for other pools as needed.

[source,yaml]
----
apiVersion: machineconfiguration.openshift.io/v1
kind: PinnedImageSet
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
  name: worker-base-images
spec:
  pinnedImages:
  - name: registry.access.redhat.com/ubi9/ubi-minimal@sha256:eeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeeee
----

[source,yaml]
----
apiVersion: machineconfiguration.openshift.io/v1
kind: PinnedImageSet
metadata:
  labels:
    machineconfiguration.openshift.io/role: worker
  name: worker-app-images
spec:
  pinnedImages:
  - name: registry.example.com/team/app@sha256:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
----

Both sets apply to the `worker` pool. Custom pools, such as `infra`, can reuse the same pattern with a different `machineconfiguration.openshift.io/role` label.
