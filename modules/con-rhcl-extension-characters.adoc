= Extension characteristics

[role="_abstract"]
Your extensions connect to the {prodname} Operator over a network. Each extension owns a single policy `Kind` that cooperates with the {prodname} Operator, exchanging topology queries and data bindings over gRPC by using the Extension SDK.

On startup, the extension connects to the {prodname} Operator, proves its identity and claims the policy `Kind` it manages. Then your reconciler runs for every instance of your extension custom resource definition (CRD) exactly as a `controller-runtime` reconciler would, with one extra argument, a `KuadrantCtx`, that has the extension methods.

Every extension does the following actions:

* Defines a custom resource definition (CRD) whose `spec` carries a target, so that instances attach to Gateway API resources.
* Runs as a separate controller process that reconciles instances of that CRD.
* Claims a single policy `Kind` at handshake, which the {prodname} Operator authorizes through RBAC.

Depending on what you are building, an extension can also do any of the following things:

* Query the {prodname} topology by sending common expression language (CEL) expressions to the Operator, and re-reconcile whenever the result changes.
* Create and manage {prodname} policies such as `AuthPolicy` objects, Gateway API resources such as `HTTPRoute` objects, and ordinary Kubernetes resources.
* Publish data bindings: CEL expressions that the Authorino and Limitador components evaluate for each request, rather than values resolved at reconciliation time.
* Define a pipeline of actions that the data plane runs on request and response traffic, including calls out to your own gRPC service.

The {prodname} Operator maintains an in-memory graph of Gateway API resources and `Kuadrant` policies. This is the topology. Your extension can query it with CEL expressions to discover relationships and extract configuration. This lets you build context-aware extensions that adapt to cluster state instead of requiring configuration to be duplicated in multiple places.

The controller might also read and interact with other resources in the cluster topology. Extensions have the following characteristics:

* The Kubernetes `ServiceAccount` object that the extension workload runs as is the extension identity. The extension presents a token for that `ServiceAccount` object at handshake. The Operator verifies the token and derives the identity from the token. The Operator does not just trust a name that the extension asserts.

* Ownership with role-based access (RBAC): Which policy kind an extension can claim is an authorization decision. The extension `ServiceAccount` object is granted permission to `register` a specific policy kind through an ordinary `Role` and `ClusterRole` binding. The Operator checks that permission at handshake. There is no separate credential to generate or distribute.

* Authentication maintained: Extensions hold an authenticated session while connected. All calls after the first authentication ride on that session. The single gRPC endpoint is a `Service` object that every extension connects to. Built-in extensions and standalone extensions use the same endpoint and the same handshake; they differ only in where their token comes from.
