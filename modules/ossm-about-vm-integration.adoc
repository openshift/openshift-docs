= About adding virtual machines to the mesh

[role="_abstract"]

A workload that runs on a virtual machine or a physical host, instead of in a pod, can join the mesh and be referenced as an internal service. The way the workload joins the mesh depends on whether {VirtProductName} manages the virtual machine and on how the network of the machine is configured.

[id="ossm-vm-internal-service_{context}"]
== Referencing an external workload as an internal service

Depending on the use case, an external workload is referenced either through a `Service` or through a `ServiceEntry` resource:

* A `Service` resource can select external workloads and in-cluster pods at the same time, so a hostname such as `app.prod.svc.cluster.local` resolves to endpoints in both places. This is useful for migrating an application from a virtual machine to the cluster, where pods are added to an existing service and the virtual machine is removed when the migration is complete.

* A `ServiceEntry` resource publishes an external workload under a dedicated hostname, such as `db.prod.vm`, when the workload does not belong to an in-cluster service.

In both cases, {istio} manages traffic, security, and observability for the hostname.

[id="ossm-vm-managed-by-virtualization_{context}"]
== Virtual machines managed by {VirtProductName}

A virtual machine that uses the masquerade or passt network binding shares the network namespace of its `virt-launcher` pod. Whenever the use case allows one of these bindings, rely on the sidecar injection that {VirtProductName} supports: the sidecar injected into the `virt-launcher` pod handles the traffic of the virtual machine, and the guest operating system requires no proxy and no mesh configuration. For more information, see link:https://docs.redhat.com/en/documentation/openshift_container_platform/latest/html/virtualization/networking#virt-connecting-vm-to-service-mesh[Connecting a virtual machine to a service mesh].

A virtual machine that uses any other network binding, for example a bridge binding, sends traffic that the injected proxy does not intercept. Such a virtual machine can join the mesh by running the `istio-proxy` RPM in the guest operating system, as described in this section.

[id="ossm-vm-outside-cluster_{context}"]
== Other virtual machines and physical hosts

Virtual machines that {VirtProductName} does not manage, and physical hosts, join the mesh in the same way: the `istio-proxy` service runs in the operating system of the machine. The proxy connects to the control plane and obtains a workload identity, and the workload becomes a member of the mesh, with mutual TLS, observability, and traffic management applied to its traffic.

[id="ossm-vm-ambient-mode_{context}"]
== Ambient mode

{SMProductName} does not support extending ambient mode to machines outside the cluster.
