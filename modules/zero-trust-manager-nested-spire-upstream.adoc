= Configuring the upstream cluster

[role="_abstract"]
Expose the upstream SPIRE server gRPC endpoint and register the downstream cluster. {zero-trust-full} creates a passthrough Route, mounts the downstream kubeconfig, and creates the registration entries that authorize the downstream server to request an intermediate CA.

.Prerequisites

* You created the downstream kubeconfig Secret on the upstream cluster. For more information, see xref:#zero-trust-manager-nested-spire-kubeconfig_{context}[Creating a kubeconfig for a downstream cluster].
* The `UPSTREAM_KUBECONFIG`, `UPSTREAM_CLUSTER_NAME`, and `DOWNSTREAM_CLUSTER_NAME` environment variables are set.
* `spec.nestedSpire` requires `spec.grpcEndpoint`.

.Procedure

. Create a file named `upstream-nested-spire.yaml` with the following contents:
+
[source,yaml]
----
spec:
  grpcEndpoint:
    managedRoute: "true"
  nestedSpire:
    downstreamClusters:
    - name: <downstream_cluster_name>
      kubeConfigSecret: spire-downstream-<downstream_cluster_name>
----
+
where:

`<downstream_cluster_name>`:: Specifies the downstream cluster's `ZeroTrustWorkloadIdentityManager.spec.clusterName`. This value is immutable after you set it. Use the same value for the Secret name that you created in the previous procedure.
+
`spec.grpcEndpoint.managedRoute`:: Specifies whether {zero-trust-full} creates the gRPC Route. `"true"` creates a passthrough Route named `spire-server-grpc`. `"false"` leaves Route creation to you. The default is `"true"`.
+
`spec.nestedSpire.downstreamClusters[].kubeConfigSecret`:: Specifies the Secret in the `zero-trust-workload-identity-manager` namespace that contains the downstream kubeconfig. The Secret data key is `kubeconfig`.

. Apply the configuration by running the following command:
+
[source,terminal]
----
$ oc patch spireserver cluster --type=merge --patch-file=upstream-nested-spire.yaml --kubeconfig="${UPSTREAM_KUBECONFIG}"
----
+
Changing `spec.nestedSpire.downstreamClusters` restarts the upstream SPIRE server.

. Wait for the SPIRE server to roll out by running the following command:
+
[source,terminal]
----
$ oc rollout status statefulset/spire-server -n zero-trust-workload-identity-manager --kubeconfig="${UPSTREAM_KUBECONFIG}" --timeout=300s
----

.Verification

. Confirm that the gRPC Route is admitted by running the following command:
+
[source,terminal]
----
$ oc get route spire-server-grpc -n zero-trust-workload-identity-manager --kubeconfig="${UPSTREAM_KUBECONFIG}"
----
+
The Route host is `grpc.<upstream_cluster_name>.<trust_domain>`. For example, if the upstream cluster name is `upstream` and the trust domain is `example.com`, the host is `grpc.upstream.example.com`. The host must resolve to the upstream cluster ingress. Record this host. The downstream cluster sets it as `spec.upstreamAuthority.spire.serverAddress`, without a scheme, port, or path.
+
The `GRPCEndpointAvailable` condition on the upstream `SpireServer` CR is `True` with reason `RouteCreated` when the Route is reconciled.

. Confirm that the downstream registration entries are applied by running the following command:
+
[source,terminal]
----
$ oc get clusterstaticentries.spire.spiffe.io -o custom-columns=NAME:.metadata.name,RENDERED:.status.rendered,MASKED:.status.masked --kubeconfig="${UPSTREAM_KUBECONFIG}"
----
+
{zero-trust-full} creates `nested-spire-<downstream_cluster_name>-node-alias` and `nested-spire-<downstream_cluster_name>-downstream`. Both entries show `rendered=true` and `masked=false`. The `DownstreamClustersValid` condition is `True` with reason `Ready`.
+
Do not edit these `ClusterStaticEntry` objects. {zero-trust-full} recreates them if they are deleted.
