= TNF recovery scenarios

[role="_abstract"]
A two-node {product-title} cluster with fencing (TNF) recovers from most disruption events automatically. When automated recovery is unavailable, the recovery procedure depends on which failure state the cluster is in. Identify your scenario from the diagnostics below, and follow only the procedure for that scenario. Do not work through the procedures in sequence; in particular, manually restoring corosync quorum applies to exactly one scenario and is not a fallback for other failed recovery attempts.

[NOTE]
====
These procedures apply only to TNF clusters. They do not apply to two-node clusters with an arbiter (TNA), which use a different quorum mechanism.
====

== Identifying your scenario

Run the following commands on a control plane node, or from the `PacemakerCluster` custom resource if the API is available:

[source,terminal]
----
$ sudo pcs status --full
$ sudo pcs quorum status
$ oc get pacemakercluster cluster -o yaml
----

.Match your observations to a scenario
[cols="2,2,2",options="header"]
|===
| What you observe | Diagnostic source | Scenario

| STONITH resource failed; `fence_redfish` returns an authentication error; the pacemaker journal shows BMC login failures
| `pcs status --full`, `journalctl -u pacemaker`
| Fencing credentials are wrong or outdated; see xref:../installing_tnf/install-post-tnf.adoc#updating-fencing-credentials-script_install-post-tnf[Updating fencing credentials by using the script] or xref:../installing_tnf/install-post-tnf.adoc#tnf-updating-fencing-credentials-manually_install-post-tnf[Manually updating fencing credentials].

| One node is `Offline`, the survivor is `Online` and quorate, and resources are stopped on the failed node only
| `pcs status --full`
| One node failed while its peer kept running; see xref:../installing_tnf/install-post-tnf.adoc#tnf-recovering-single-node-failure_install-post-tnf[Recovering from a single-node failure in a TNF cluster].

| Both nodes lost power and both can be powered on
| Power state, `pcs status corosync` after boot
| Recovery is automatic once both nodes are online; see xref:../installing_tnf/install-post-tnf.adoc#tnf-recovering-dual-node-power-loss_install-post-tnf[Recovering from dual node power loss in a TNF cluster] for verification and for stalled recovery.

| `Current DC: NONE`, both nodes are `UNCLEAN (offline)` in the node list while PCSD shows the local node online, and `pcs quorum status` reports `Quorate: No` with `Flags: 2Node WaitForAll`
| `pcs status --full`, `pcs quorum status`
| Both nodes lost power and only one can be restarted; see xref:../installing_tnf/install-post-tnf.adoc#tnf-restoring-c-quorum-manual_install-post-tnf[Manually restoring corosync quorum after dual node power loss], followed by node replacement.

| A failed node has unrecoverable hardware
| Physical or BMC inspection
| Replace the node; see xref:../installing_tnf/install-post-tnf.adoc#installation-replacing-control-plane-nodes_install-post-tnf[Replacing control plane nodes in a two-node {product-title} cluster with fencing].

| The etcd resource is stopped or failed on the surviving node although fencing is healthy
| `pcs resource status etcd`, `journalctl -u pacemaker | grep podman-etcd`
| See xref:../installing_tnf/operating-degraded-two-node-fencing-cluster.adoc#resolving-etcd-not-recovering-on-the-surviving-node_install-post-tnf[Resolving etcd not recovering on the surviving node].

|===

If fencing credentials are the root cause, repair them first: stale BMC credentials can block recovery in every other scenario.
