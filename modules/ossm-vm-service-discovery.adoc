= Making the virtual machine discoverable in the mesh

[role="_abstract"]

When the proxy connects to the control plane, the control plane registers the virtual machine as a `WorkloadEntry` resource, based on the `WorkloadGroup` resource that the proxy refers to. Auto-registration alone does not make the workload reachable: a `WorkloadEntry` resource carries an address and a set of labels, but no hostname that clients can call. A hostname comes from a `Service` or a `ServiceEntry` resource whose selector matches the labels of the `WorkloadEntry` resource.

Create one of the following resources, depending on how clients address the workload:

* A `Service` resource, when the workload belongs to an in-cluster service. The same selector matches pods and virtual machines, so a single hostname can resolve to endpoints in both places.

* A `ServiceEntry` resource, when the workload has a hostname of its own, such as `vm-app.external-vm.vm`.

.Prerequisites

* The `istio-proxy` service runs on the virtual machine, and the virtual machine is registered as a `WorkloadEntry` resource.

* You know the labels that the `WorkloadGroup` resource defines in the `spec.metadata.labels` field.

.Procedure

. To publish the workload as an in-cluster service, create a `Service` resource named `service.yaml` similar to the following example:
+
[source,yaml]
----
apiVersion: v1
kind: Service
metadata:
  name: vm-app
  namespace: external-vm
spec:
  selector:
    app: vm-app # <1>
  ports:
  - name: http
    port: 8000
    targetPort: 8080 # <2>
----
<1> The labels that the `WorkloadGroup` resource defines. The control plane adds every `WorkloadEntry` resource with these labels to the endpoints of the service. Pods with the same labels remain endpoints of the service as well.
<2> The port that the application listens on inside the virtual machine. Clients call the service on the `port` value.

. To publish the workload under a hostname of its own, create a `ServiceEntry` resource named `serviceentry.yaml` similar to the following example:
+
[source,yaml]
----
apiVersion: networking.istio.io/v1
kind: ServiceEntry
metadata:
  name: vm-app
  namespace: external-vm
spec:
  hosts:
  - vm-app.external-vm.vm # <1>
  location: MESH_INTERNAL # <2>
  resolution: STATIC # <3>
  ports:
  - number: 8000
    name: http
    protocol: HTTP
    targetPort: 8080 # <4>
  workloadSelector:
    labels:
      app: vm-app # <5>
----
<1> The hostname that clients call. The hostname does not have to follow the naming of in-cluster services.
<2> Treats the workload as a member of the mesh, so that clients connect to it over mutual TLS and authorization policies apply to the identity of the workload.
<3> Resolves the hostname to the addresses of the workloads that the `workloadSelector` field matches.
<4> The port that the application listens on inside the virtual machine.
<5> The labels that the `WorkloadGroup` resource defines.
+
[NOTE]
====
A hostname that is not a Kubernetes service name does not resolve through cluster DNS. The control plane assigns an address from the `240.240.0.0/16` range to the `ServiceEntry` resource, and the proxy of the client resolves the hostname to that address, provided that DNS proxying is enabled. Enable DNS proxying for in-cluster workloads by setting the `ISTIO_META_DNS_CAPTURE` variable to `"true"` in the `spec.values.meshConfig.defaultConfig.proxyMetadata` field of the `Istio` resource.
====

. Apply the resource by running one of the following commands:
+
[source,terminal]
----
$ oc apply -f service.yaml
----
+
[source,terminal]
----
$ oc apply -f serviceentry.yaml
----

.Verification

. Verify that the virtual machine is registered by running the following command:
+
[source,terminal]
----
$ oc get workloadentries -n external-vm
----

. Verify that the proxy of a client resolves the hostname to the virtual machine by running one of the following commands:
+
[source,terminal]
----
$ istioctl proxy-config endpoints <pod_name>.<namespace> --cluster "outbound|8000||vm-app.external-vm.svc.cluster.local"
----
+
[source,terminal]
----
$ istioctl proxy-config endpoints <pod_name>.<namespace> --cluster "outbound|8000||vm-app.external-vm.vm"
----
+
*Example output:*
+
[source,terminal]
----
ENDPOINT          STATUS      OUTLIER CHECK     CLUSTER
10.0.2.2:8080     HEALTHY     OK                outbound|8000||vm-app.external-vm.vm
----
