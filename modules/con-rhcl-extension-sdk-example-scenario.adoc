= Extension SDK example scenario

[role="_abstract"]
You can use the Extension SDK to build extensions for various scenarios that require specific policies.

For example, your organization operates an API across {ocp} clusters in several regions, such as North America, the European Union (EU), and Asia-Pacific (APAC) nations.

You have a compliance requirement stating that only callers located in the EU can reach the endpoints that your EU cluster serves. Your compliance team already runs a service that classifies a source IP address into a region, and an auditor expects evidence that the rule was applied to every request.

Static configuration cannot express this rule because the answer depends on who is calling, and you can only know that when the request arrives.

To address this situation, you can write a `DataResidencyPolicy` extension by creating a custom resource definition (CRD) called `DataResidencyPolicy`.

* You define the regions that you accept, for example, `allowedRegions: ["eu"]`, and the address of your classification service.

* Platform teams then attach a `DataResidencyPolicy` custom resource (CR) to the `Gateway` or `HTTPRoute` object that serves EU traffic.

After you deploy it, the extension binary runs as a standalone pod. Using the SDK, the extension communicates over gRPC with {prodname} and does the following four main tasks:

* First, the extension reads the cluster topology. It asks the {prodname} Operator for the hostname of the listener that the policy targets, and for any `AuthPolicy` objects already attached to the same target. Because the Operator answers from the topology that it already maintains, the extension does not need permission to read `Gateway` objects.

* Next, the extension creates the resources that the policy implies. For example, it reconciles an `AuthPolicy` object that requires a verified identity on the targeted route. The extension owns that object, so deleting the `DataResidencyPolicy` CR removes it again.

* Then, the extension publishes data bindings. It exposes the residency claim from the verified token so that later evaluators can read it, and registers a metric label so that your observability dashboards can break traffic down by declared region.

* Finally, the extension acts on the traffic itself. On each request, it calls your classification service with the source address of the caller.

** The accepted regions come from the CR and are resolved when the extension reconciles the policy. The caller's region is resolved for each request in the data plane.
** The extension denies the request with a `403 Forbidden` status if the region that the service returns is not in `allowedRegions`. On the response, it adds a header recording the region that served the request.

Other common extension examples include the following types:

* `TieredBillingPolicy` CRD. Reads customer API usage, dynamically updates user rate limits through gRPC data bindings based on their subscription tier in an external billing system.

* `WorkloadIdentityPolicy` CRD.	Queries dynamic cluster topology to verify that incoming route requests originate from trusted SPIFFE/SPIRE identity tokens before injecting headers into Envoy.

* `ContentInspectionPolicy` CRD. Calls an external classification service on each request and denies those it rates above a configurable threshold, recording the rating as a metric label.
