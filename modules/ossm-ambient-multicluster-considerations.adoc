= Limitations and considerations for multi-cluster ambient meshes

[role="_abstract"]

Multi-primary, multi-network is currently the only multi-cluster topology supported for ambient meshes. Note the following limitations and considerations when deploying this topology.

== Top priority (foundational requirements)

Certificate authority requirements::
All clusters must share a common root Certificate Authority and use the same trust domain. Ambient mode has no equivalent to `meshConfig.caCertificates` in sidecar mode, so a shared root CA is the only option. A single trust domain is necessary because different domains fail even when using the same root CA.
+
These concerns surface primarily when you join existing clusters that were set up independently. (The clusters likely have different CAs and trust domains.)
+
To change an existing cluster's CA or trust domain to match other clusters in the mesh, you need to redeploy {istio}, which involves: (1) uninstalling the existing {istio} control plane and data plane components, (2) backing up and preserving your {istio} configurations and custom resources, (3) reinstalling {istio} with the new shared CA and trust domain configurations, and (4) restarting workloads to pick up the new certificates.
+
[NOTE]
====
For new multi-cluster deployments, configure a shared CA and trust domain from the beginning to avoid this complexity.
====

East-west gateway limitation for API servers::
Ambient east-west gateways cannot expose API servers because they only handle mesh traffic. If clusters cannot reach each other's API servers through direct network routing (public network load balancers, VPC peering, VPN, or other connectivity), you must deploy a standalone non-ambient Envoy east-west gateway as a workaround. If a remote API server becomes unreachable, the mesh continues running on cached state and only fails at the next istiod restart, serving local-only traffic silently.

== High priority (critical operational issues)

Cross-cluster service naming requirement::
For a service to be reachable across clusters, a Service object with the same name must exist in each cluster that needs to access it. If a service's pods only run in one cluster, other clusters that need to call it must deploy stub Services (Service objects without pod selectors). Services that are purely local to one cluster do not require stubs elsewhere. (Issue #60888)

Service scope configuration::
After ensuring Service objects exist in all relevant clusters (see Cross-cluster service naming requirement above), their scope configuration must also match. Only the local cluster's service scope configuration is used as the source of truth; remote cluster scope configurations are ignored (Issue #58269). If scope labels (such as `istio.io/global`) do not match across clusters, you will experience asymmetric one-way routing with no istiod warnings—503 errors on the waypoint path or silent local-only serving on the L4 path.

Waypoint synchronization::
Waypoint deployments must be identical across all clusters, including both the deployment configuration and any attached policies. There is no built-in synchronization mechanism—you must use GitOps tools like {gitops-title} or maintain consistency manually. Policy mismatches create security vulnerabilities: for example, a DENY policy applied in only one cluster allows other clusters to freely access pods that the policy should protect.

Global waypoint scope::
Marking a waypoint as global makes all services behind it global. During failover scenarios, a healthy local service sharing a waypoint with a global service can become 100% unavailable. The `preferClose` setting hides this issue in steady state. Workaround: use separate waypoints for local and global services. (Issue #57710)

== Medium priority (important considerations)

Sidecar migration risk::
Do not enable ambient multi-network mode on an existing sidecar-based multi-cluster mesh without preparation. The service scope feature applies to sidecars as well, causing them to lose all remote endpoints unless every service is labeled with `istio.io/global` first. (Issues #61713, #57878, #57877)

Silent failure modes::
Most multi-cluster ambient failures are silent or misleading—endpoints appear healthy, istiod produces no warnings, and gateways report success. A healthy control plane and passing local smoke tests do not confirm that the multi-cluster mesh is functioning correctly.

== Lower priority (specific feature limitations)

Load distribution::
Traffic to a remote network may not be evenly distributed on the waypoint path due to HTTP multiplexing and connection pooling (Issue #58039). Testing shows all requests can route to a single pod while L4 traffic remains evenly distributed. This limitation also affects sidecar mode.

DestinationRule handling::
DestinationRules with `ISTIO_MUTUAL` TLS mode are silently ignored by waypoints. (Issues #60084, #59627)
