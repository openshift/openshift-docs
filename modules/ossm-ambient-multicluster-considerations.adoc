= Ambient multi-primary, multi-network meshes

[role="_abstract"]

Currently, the only multi-cluster topology supported for ambient mode is multi-primary, multi-network. Before deploying the topology, review the following limitations and considerations.

== Foundational considerations

Certificate authority requirements::
All the clusters must share a common root Certificate Authority (CA) and use the same trust domain. Ambient mode has no equivalent to `meshConfig.caCertificates` in sidecar mode, so a shared root CA is the only option. A single trust domain is also necessary; different domains fail even when using the same root CA.
+
These concerns surface primarily when you join existing clusters that were set up independently. (The clusters likely have different CAs and trust domains.)
+
To change the CA or trust domain of an existing cluster to match other clusters in the mesh:
+
. Back up and preserve your existing {istio} configurations and custom resources.
. Uninstall the existing {istio} control plane and data plane components.
. Redeploy {istio} with the new shared CA and trust domain configurations.
. Restart workloads to pick up the new certificates.
+
For new multi-cluster deployments, configure a shared CA and trust domain from the beginning to avoid this complexity.

`AMBIENT_ENABLE_MULTI_NETWORK` impact on existing sidecar meshes::
{SMProduct} 3.4 enabled the coexistence of both sidecar and ambient workloads on the same mesh. Before deploying ambient mode on an existing sidecar multi-cluster mesh, label all `Service` resources that require cross-cluster access with `istio.io/global: "true"` to configure global scope.
+
The `AMBIENT_ENABLE_MULTI_NETWORK` flag applies service scoping to both ambient and sidecar workloads. Without the global scope label, services lose all remote endpoints when ambient mode is deployed. This interrupts existing cross-cluster traffic.

East-west gateway limitation for API servers::
Ambient east-west gateways cannot expose API servers because they only handle mesh traffic. Use direct network routing (such as public network load balancers) to connect clusters' API servers. If direct routing is unavailable, deploy a standalone, non-ambient Envoy east-west gateway as a workaround. 
[NOTE]
====
If a remote API server becomes unreachable, the mesh continues running on cached state and only fails at the next istiod restart, serving local-only traffic silently.
====

== Critical operational considerations

Cross-cluster service naming requirements::
For a service to be reachable across clusters, every cluster that needs to access it must have a `Service` object with the same name and namespace. How you configure this depends on where the workload pods run:
+
* *Pods in multiple clusters:* Each cluster that runs pods for the service needs a `Service` definition with a `spec.selector` pointing to those pods.
* *Pods in only one cluster:* The cluster running the pods needs a normal `Service` definition. Other clusters that need to access it must deploy a stub `Service` (defined without a `spec.selector`).

Service scope configuration::
After ensuring `Service` objects exist in all relevant clusters, confirm that their scope configurations match. 
+
The control plane in each cluster uses only its local service scope configuration and ignores remote cluster configurations. Because of this isolation, mismatched scope labels cause asymmetric routing failures with no warnings from `istiod`. Symptoms depend on the traffic path: 503 errors on the waypoint path, or silent local-only traffic on the L4 path.

Waypoint synchronization::
Across all clusters, `waypoint` deployments and attached policies must match. Policy mismatches can create security vulnerabilities: for example, a `DENY` policy applied in only one cluster allows other clusters to freely access pods that the policy should protect.
+
To keep `waypoints` in sync, use GitOps tools such as {gitops-title} or synchronize them manually. (Currently, there is no built-in, automatic synchronization mechanism.)

Global waypoint scope::
Use separate `waypoints` for local and global services. When a `waypoint` proxy is marked as global, it forces all attached services to behave as global services, overriding their individual service-level scope configurations. Consequently, the mesh might route traffic for cluster-local services to a remote `waypoint` instance instead of keeping that traffic local, causing:
+
* *Availability failures:* Traffic drops or HTTP 503 errors if the backend service lacks pods in the remote cluster
* *Performance and cost:* Increased latency from unnecessary cross-cluster network hops and higher egress fees

`DestinationRule` handling::
Waypoints silently ignore the `ISTIO_MUTUAL` TLS setting in `DestinationRule` resources, which can cause non-HBONE destinations to reject requests. (HBONE stands for HTTP-Based Overlay Network Encapsulation.) When applications that rely on `ISTIO_MUTUAL` for mTLS origination send plaintext traffic, the waypoint-to-destination connection remains unencrypted. Destinations requiring TLS reject the connection, causing requests to fail. Ambient east-west traffic protected by HBONE remains encrypted.
+
For non-HBONE destinations that accept explicitly configured client certificates, use `MUTUAL` with appropriate credentials instead. The destination authenticates the configured certificate identity rather than the Istio identity of the originating workload. For destinations that require the workload identity, run the workloads in sidecar mode.

== Additional limitations

Uneven remote load distribution::
Traffic routed through a `waypoint` to a remote network might be unevenly distributed across backend endpoints. HTTP multiplexing and connection pooling through the east-west gateway can concentrate requests on a single remote backend, degrading performance and creating a single point of failure even when multiple healthy replicas exist.

Validation and monitoring::
Many of the limitations inherit with ambient multi-primary, multi-network meshes produce silent or misleading failures. Endpoints can appear healthy when they are not; `istiod` fails to generate warnings; gateways report success even when cross-cluster routing fails. To minimize risk, verify multi-cluster functionality with explicit cross-cluster traffic tests, not just control plane health checks or local smoke tests.
