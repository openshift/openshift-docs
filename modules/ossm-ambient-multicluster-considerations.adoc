= Ambient multi-primary, multi-network meshes

[role="_abstract"]

Currently, the only multi-cluster topology supported for ambient mode is multi-primary, multi-network. Before deploying the topology, review the following limitations and considerations.

== Foundational requirements

Certificate authority requirements::
All the clusters must share a common root Certificate Authority (CA) and use the same trust domain. Ambient mode has no equivalent to `meshConfig.caCertificates` in sidecar mode, so a shared root CA is the only option. A single trust domain is also necessary; different domains fail even when using the same root CA.
+
These concerns surface primarily when you join existing clusters that were set up independently. (The clusters likely have different CAs and trust domains.)
+
To change the CA or trust domain of an existing cluster to match other clusters in the mesh:
+
. Uninstall the existing {istio} control plane and data plane components.
. Back up and preserve your {istio} configurations and custom resources.
. Redeploy {istio} with the new shared CA and trust domain configurations.
. Restart workloads to pick up the new certificates.
+
For new multi-cluster deployments, configure a shared CA and trust domain from the beginning to avoid this complexity.

East-west gateway limitation for API servers::
Ambient east-west gateways cannot expose API servers because they only handle mesh traffic. If clusters cannot reach each other's API servers through direct network routing (using public network load balancers, for example), you must deploy a standalone, non-ambient Envoy east-west gateway as a workaround. 
[NOTE]
====
If a remote API server becomes unreachable, the mesh continues running on cached state and only fails at the next istiod restart, serving local-only traffic silently.
====

== Critical operational considerations

Cross-cluster service naming requirements::
For a service to be reachable across clusters, every cluster that needs to access it must have a `Service` object with the same name and namespace. How you configure this depends on where the workload pods run:
+
* *Pods in multiple clusters:* Each cluster that runs pods for the service needs a `Service` definition with a `spec.selector` pointing to those pods.
* *Pods in only one cluster:* The cluster running the pods needs a normal `Service` definition. Other clusters that need to access it must deploy a stub `Service` (defined without a `spec.selector`).

Service scope configuration::
After ensuring `Service` objects exist in all relevant clusters, confirm that their scope configurations match. 
+
The control plane in each cluster uses only its local service scope configuration and ignores remote cluster configurations. Because of this isolation, mismatched scope labels cause asymmetric routing failures with no warnings from `istiod`. Symptoms depend on the traffic path: 503 errors on the waypoint path, or silent local-only traffic on the L4 path.

Waypoint synchronization::
Across all clusters, waypoint deployments and attached policies must match. Policy mismatches can create security vulnerabilities: for example, a `DENY` policy applied in only one cluster allows other clusters to freely access pods that the policy should protect.
+
To keep waypoints in sync, use GitOps tools such as {gitops-title} or maintain consistency manually. (Currently, there is no automatic, built-in synchronization mechanism.)

Global waypoint scope::
Marking a waypoint as global makes all services behind it global. During failover scenarios, a healthy local service sharing a waypoint with a global service can become 100% unavailable. The `preferClose` setting hides this issue in steady state. Workaround: use separate waypoints for local and global services.

== Additional limitations

Silent failure modes::
Most multi-cluster ambient failures are silent or misleading—endpoints appear healthy, istiod produces no warnings, and gateways report success. A healthy control plane and passing local smoke tests do not confirm that the multi-cluster mesh is functioning correctly.

Load distribution::
Traffic to a remote network may not be evenly distributed on the waypoint path due to HTTP multiplexing and connection pooling (Issue #58039). Testing shows all requests can route to a single pod while L4 traffic remains evenly distributed. This limitation also affects sidecar mode.

DestinationRule handling::
DestinationRules with `ISTIO_MUTUAL` TLS mode are silently ignored by waypoints.
