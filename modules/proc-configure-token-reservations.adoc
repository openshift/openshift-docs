= Reserve token capacity for concurrent requests

[role="_abstract"]
You can hold an estimated number of tokens for the duration of each request by adding a `reservation` block to a limit in your `TokenRateLimitPolicy` custom resource (CR).

A reservation stops concurrent requests from pushing consumption past the limit while the Large Language Model (LLM) API is still generating its responses.

.Prerequisites

* You installed {prodname} on the {ocp} cluster you are working with.
* You created and applied a `TokenRateLimitPolicy` CR, such as the `llm-protection` policy.
* The `spec.tokenRateLimiting.mode` field of your `Kuadrant` CR is either unset or set to `Reservation`.

.Procedure

. Update your existing policy by adding a `reservation` block to a limit in your `TokenRateLimitPolicy` object by using the following example:
+
.Example TokenRateLimitPolicy YAML with a reservation
[source,yaml,subs="+quotes"]
----
apiVersion: kuadrant.io/v1alpha1
kind: TokenRateLimitPolicy
metadata:
  name: llm-protection
spec:
  targetRef:
    group: gateway.networking.k8s.io
    kind: Gateway
    name: _<ai_gateway>_
  limits:
    free-users:
      rates:
        - limit: 10000
          window: 24h
      when:
        - predicate: request.path == "/v1/chat/completions"
        - predicate: |
            auth.identity.groups.split(",").exists(g, g == "free")
      counters:
        - expression: auth.identity.userid
      reservation:
        amount: 1000
        ttl: 'duration("30s")'
----
+
* The `metadata.name` value must match your existing policy so that applying this file updates that policy.
* Replace `_<ai_gateway>_` with the name of the `Gateway` object that your policy targets.
* The `spec.limits.free-users.reservation.amount` parameter is set to hold 1,000 tokens for the duration of each request. Set this value to a realistic estimate of the number of tokens that one request consumes. Valid values are a whole number of tokens, or a Common Expression Language (CEL) expression that evaluates to a whole number.
* The `spec.limits.free-users.reservation.ttl` parameter is a CEL expression that sets how long the reservation is held when no response arrives. To use the `backendRequest` timeout of the route, omit this parameter.
* 5,000 is the maximum tokens that you can reserve in the `spec.limits.free-users.reservation.amount` parameter value, which is half of the 10,000 token limit. The `spec.reservations.maxFraction` field of the `Limitador` CR sets this fraction and defaults to `0.5`.
* The `reservation.amount` parameter defaults to `0`. A limit that does not set this parameter does not reserve capacity.

. Apply the `TokenRateLimitPolicy` policy by running the following command:
+
[source,terminal,subs="+quotes"]
----
$ oc apply -f _<tokenratelimitpolicy.yaml>_ -n _<gateway_namespace>_
----
+
* Replace `_<tokenratelimitpolicy.yaml>_` with the filename you used.
* Replace `_<gateway_namespace>_` with your `Gateway` object namespace.

. Check the status of the policy to ensure it was accepted and enforced on the target `Gateway` object. Look for conditions with `type: Accepted` and `type: Enforced` with `status: "True"`.
+
[source,terminal,subs="+quotes"]
----
$ oc get tokenratelimitpolicy llm-protection -n _<gateway_namespace>_ -o jsonpath='{.status.conditions}'
----
+
Replace `_<gateway_namespace>_` with your `Gateway` object namespace.

.Verification

. Send more requests at the same time than the limit allows to be in flight. For example, a limit of 10,000 tokens that reserves 1,000 tokens for each request admits 10 requests at a time, so send at least 15 requests by running the following command:
+
[source,terminal,subs="+quotes"]
----
$ for i in $(seq 1 15); do
    curl -s -o /dev/null -w "%{http_code}\n" \
         -H "Authorization: _<auth_policy>_" \
         -d '{"model": "gpt-4", "messages": [{"role": "user", "content": "Hello"}]}' \
         _<api_endpoint>_ &
  done
  wait
----
+
Replace `_<auth_policy>_` and `_<api_endpoint>_` with your values.
+
.Example output
[source,text]
----
200
200
429
429
----
+
Requests that fit in the remaining capacity receive a `200 OK` response or another success status. The rest receive a `429 Too Many Requests` response before they reach the LLM API. The exact split depends on how many requests arrive before the first response returns.

. Confirm that unused capacity returns by running the following command:
+
[source,terminal,subs="+quotes"]
----
$ curl -s -o /dev/null -w "%{http_code}\n" \
       -H "Authorization: _<auth_policy>_" \
       -d '{"model": "gpt-4", "messages": [{"role": "user", "content": "Hello"}]}' \
       _<api_endpoint>_
----
+
Replace `_<auth_policy>_` and `_<api_endpoint>_` with your values.
+
.Example output
[source,text]
----
200
----
+
[NOTE]
====
Each response commits the real token count and releases the rest of its reservation, so a request sent after the earlier responses return succeeds while the limit still has capacity.
