= About nested SPIRE

[role="_abstract"]
After you configure nested {spiffe-full} Runtime Environment (SPIRE), workloads in any tier can authenticate workloads in any other tier. Trust the shared root so that you can accept an X.509 identity from any cluster. Each certificate chains through the intermediate certificate authority (CA) to that root. For a JSON Web Token (JWT) identity, you check the signature with keys that SPIRE distributes across the topology.

Clusters in one nested topology share a trust domain. They do not use SPIFFE federation with each other. If you need the clusters to trust a different trust domain, see "Configuring Zero Trust Workload Identity Manager SPIRE federation".

Review the following nested spire terms:

Parent cluster:: A SPIRE server of this cluster signs intermediate CAs for other clusters. CA is either self-signed or it chains to an external public key infrastructure (PKI).
Nested cluster:: A SPIRE server of this cluster holds an intermediate CA from one parent server.
Mid-tier cluster:: A cluster that signs intermediate CAs for other clusters and also holds an intermediate CA from a parent server.
Agent sidecar:: A SPIRE Agent that runs as the `spire-agent-upstream` container in the nested `spire-server` pod. The local SPIRE server attested the `spire-agent` `DaemonSet` and needs the parent CA. The parent server attests the sidecar.

Create `kubeconfig` and the trust bundle. {zero-trust-full} does not copy them between clusters.
