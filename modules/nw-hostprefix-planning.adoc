= Planning for a cluster network hostPrefix increase

[role="_abstract"]
Before you increase `hostPrefix`, verify address capacity, workload disruption tolerance, and operational sequencing requirements. Increasing the per-node subnet size reduces the total number of node subnets available from the cluster CIDR.

When you increase the per-node subnet size, each node consumes a larger address block from the same `clusterNetwork` CIDR.
As a result, the maximum number of nodes that can be allocated from that CIDR decreases.
Validate that your target `hostPrefix` supports both your current and expected node count.

You must test the full workflow in a representative non-production environment before applying the change to production. This testing must include:

* validating node draining
* validating reboot sequencing
* validating pod rescheduling behavior
* validating that the selected `hostPrefix` range and target pod density are appropriate for the environment
* validating drain command options against workload and operational requirements
* validating workload behavior during node evacuation and restart
* validating post-change checks

You must also assess workload risk before you start, including:

* *Pod disruption budgets (PDBs)* can block eviction and delay node processing.
* Workloads that use `emptyDir` volumes can lose local data depending on drain options.
* Stateful and latency-sensitive workloads can experience disruption during drain and reboot cycles.
* Cluster autoscaling activity can interfere with node-by-node sequencing.

For cluster planning guidance, review the "Planning your environment according to object maximums" documentation.
