= Enabling KMS encryption

[role="_abstract"]
You can enable external Key Management Service (KMS) encryption for etcd data to centralize key management and meet compliance requirements.

.Prerequisites

* You have access to the cluster as a user with the `cluster-admin` role.
* You have enabled the `TechPreviewNoUpgrade` feature set to enable the `KMSEncryption` feature gate. For more information, see xref:../../nodes/clusters/nodes-cluster-enabling-features.adoc#nodes-cluster-enabling-features[Enabling features using feature gates]. // cite:1
// cite:1 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/features/features.go#L669 - FeatureGateKMSEncryption enabled in inTechPreviewNoUpgrade()
// cite:1 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L866 - "gated by KMSEncryptionProvider feature gate (DevPreviewNoUpgrade, TechPreviewNoUpgrade)"
// Verify: Confirm the exact OLM operator name and catalog source for the Vault KMS plugin operator
* You have installed the HashiCorp Vault KMS plugin OLM Operator from the OperatorHub. // cite:2
// cite:2 VERIFIED [88]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L211 - "Cluster admin installs the OLM operator for their KMS plugin provider"
// cite:2 VERIFIED [88]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L764-L770 - OLM-Managed Plugins section describes OLM operator for Vault KMS
* You have a HashiCorp Vault Enterprise instance accessible from your cluster. Vault Community Edition is not supported. // cite:3
// cite:3 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_kmsencryption.go#L17-L19 - "The plugin connects to a Vault Enterprise server that is managed by the user outside the purview of the control plane"
// cite:3 VERIFIED [88]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L880 - "Users are expected to fully configure and support Vault Enterprise themselves"
* You have configured your Vault instance with:
** Transit secrets engine enabled at a mount path, such as the default `transit/` path // cite:4
** Encryption key created with type `aes256-gcm96` (recommended for FIPS 140-3 compliance) // cite:5
// cite:4 VERIFIED [88]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L883 - Vault KMS Plugin configuration docs reference Transit secrets engine
// cite:5 UNVERIFIED [15]: aes256-gcm96 key type and FIPS 140-3 recommendation not found in openshift/api or enhancement — requires manual verification against HashiCorp Vault documentation
** Vault policy that allows the KMS plugin to encrypt, decrypt, and read key information // cite:6
** Authentication method, such as `AppRole`, configured with the policy attached // cite:7
// cite:6 UNVERIFIED [15]: Vault policy capabilities not specified in openshift/api or enhancement — derived from Vault Transit API conventions
// cite:7 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_kmsencryption.go#L87-L106 - VaultAuthentication union with Enum=AppRole

The KMS plugin requires a Vault policy with the following capabilities:

[source,hcl]
----
path "transit/encrypt/kms-key" {
  capabilities = ["update"]
}

path "transit/decrypt/kms-key" {
  capabilities = ["update"]
}

path "transit/keys/kms-key" {
  capabilities = ["read"]
}

path "auth/token/lookup-self" {
  capabilities = ["read"]
}
----
Replace `kms-key` with your Vault Transit key name if you are using a different name. // cite:8
// cite:8 UNVERIFIED [15]: Vault policy HCL capabilities (update on encrypt/decrypt, read on keys, read on auth/token/lookup-self) not specified in OpenShift sources — requires verification against HashiCorp Vault Transit plugin documentation

[IMPORTANT]
====
Create an etcd backup before enabling KMS encryption.
====

.Procedure

. Create a secret in the `openshift-config` namespace that contains your Vault authentication credentials by entering the following command:
+
// Verify: Confirm exact secret data key names (role-id, secret-id) and whether other auth methods use different keys
[source,terminal]
----
$ oc create secret generic vault-approle-secret \
  --from-literal=role-id=<your_role_id> \
  --from-literal=secret-id=<your_secret_id> \
  -n openshift-config
----
// cite:9 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_kmsencryption.go#L115-L120 - VaultAppRoleAuthentication.Secret references secret in openshift-config with keys "role-id" and "secret-id"
// cite:9 VERIFIED [88]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L228 - Enhancement example: "Secret in openshift-config namespace with roleID and secretID keys"
+
Replace `<your_role_id>` and `<your_secret_id>` with your Vault AppRole credentials.

. Optional: If your Vault server uses a custom TLS certificate authority, create a config map in the `openshift-config` namespace that contains the CA bundle by entering the following command:
+
[source,terminal]
----
$ oc create configmap vault-ca-bundle \
  --from-file=ca-bundle.crt=<path_to_ca_bundle> \
  -n openshift-config
----
// cite:10 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_kmsencryption.go#L271-L292 - VaultTLSConfig.CABundle references ConfigMap in openshift-config with key "ca-bundle.crt"

// Verify: Confirm exact VaultKMSConfig CRD apiVersion, kind, and field names from the OLM operator
. Create a `VaultKMSConfig` custom resource that defines the KMS plugin configuration by creating a YAML file with the following content:
+
[source,yaml]
----
apiVersion: vault.hashicorp.io/v1
kind: VaultKMSConfig
metadata:
  name: my-vault-kms
spec:
  vaultAddress: https://vault.example.com:8200
  vaultNamespace: my-namespace
  tls:
    caBundle:
      name: vault-ca-bundle
    serverName: vault.example.com
  authentication:
    type: AppRole
    appRole:
      secret:
        name: vault-approle-secret
  vaultKeyPath: transit/keys/kms-key
----
// cite:11 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_kmsencryption.go#L124-L231 - VaultKMSPluginConfig struct defines vaultAddress, vaultNamespace, tls, authentication, vaultKeyPath fields
// cite:11 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L213-L230 - Enhancement VaultKMSConfig CR example with matching field structure
+
where:
+
`vaultAddress`:: Specifies the URL of your Vault server. // cite:12
// cite:12 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_kmsencryption.go#L149-L167 - vaultAddress: HTTPS URL, 1-512 chars, no path/query/fragment
`vaultNamespace`:: Specifies the Vault namespace, if you are using Vault namespaces. This value is optional. // cite:13
// cite:13 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_kmsencryption.go#L169-L182 - vaultNamespace: optional, "only applicable for Vault Enterprise installations"
`tls.caBundle.name`:: Specifies the name of the config map in the `openshift-config` namespace that contains the CA bundle. Required only if your Vault server uses a custom CA. This value is optional. // cite:14
`tls.serverName`:: Specifies the TLS server name for certificate verification. This value is optional. // cite:15
// cite:14 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_kmsencryption.go#L271-L292 - VaultTLSConfig.CABundle: optional, ConfigMap in openshift-config with key "ca-bundle.crt"
// cite:15 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_kmsencryption.go#L294-L305 - serverName: optional, SNI for TLS, valid DNS hostname max 253 chars
`authentication.appRole.secret.name`:: Specifies the name of the secret in the `openshift-config` namespace that contains the AppRole credentials. // cite:16
// cite:16 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_kmsencryption.go#L114-L120 - VaultAppRoleAuthentication.Secret: VaultSecretReference in openshift-config namespace
`vaultKeyPath`:: Specifies the path to the Transit encryption key in Vault. // cite:17
// cite:17 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_kmsencryption.go#L211-L231 - vaultKeyPath: format <mount>/keys/<key-name>, 8-1542 chars
+
Apply the custom resource by entering the following command:
+
[source,terminal]
----
$ oc apply -f <vault-kms-config>.yaml
----

. Verify that the OLM Operator has reconciled the custom resource and populated the status by entering the following command:
+
[source,terminal]
----
$ oc get vaultkmsconfig my-vault-kms -o jsonpath='{.status.image}'
----
+
// Verify: Confirm the exact status field name that contains the image reference
The output shows the plugin image reference. If the output is empty, wait for the OLM Operator to reconcile. // cite:18
// cite:18 VERIFIED [88]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L232-L264 - OLM operator writes status mirroring spec plus plugin image reference
// cite:18 VERIFIED [88]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L760 - "For now, that is just the image field that is appended to the status"
// cite:18 INFERRED [30]: Exact status field name "image" inferred from enhancement example at L264 — field name not in openshift/api types (CRD is OLM-operator-defined, not in openshift/api)

// Verify: Confirm the exact APIServer spec structure for V2 KMS configuration (kms.type, pluginConfig fields)
. Edit the `APIServer` custom resource by entering the following command:
+
[source,terminal]
----
$ oc edit apiserver cluster
----

. Add the KMS configuration to the `spec.encryption` section:
+
[source,yaml]
----
apiVersion: config.openshift.io/v1
kind: APIServer
metadata:
  name: cluster
spec:
  encryption:
    type: KMS
    kms:
      type: Vault
      pluginConfig:
        apiVersion: vault.hashicorp.io/v1
        kind: VaultKMSConfig
        name: my-vault-kms
----
// cite:19 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_apiserver.go#L211-L244 - APIServerEncryption struct with KMS field (KMSPluginConfig), EncryptionType "KMS"
// cite:19 VERIFIED [97]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_kmsencryption.go#L7-L14 - KMSPluginConfig.Type with Vault discriminator
// cite:19 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L267-L280 - Enhancement APIServer pluginConfig reference example with matching structure

. Save and exit.
+
The platform runs pre-flight validation to verify the KMS configuration. After validation succeeds, migration begins automatically. The `kube-apiserver`, `openshift-apiserver`, and `oauth-apiserver` operators restart and roll out new revisions. // cite:20
// cite:20 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L337 - "keyController runs pre-flight checks by deploying a pod with the KMS plugin to verify status and encrypt/decrypt capability"
// cite:20 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L449 - "Before applying any configuration change, a dedicated controller deploys a pod with the KMS plugin to verify status and encrypt/decrypt capability"
+
[NOTE]
====
The `openshift-apiserver` and `authentication` operators typically complete migration in 5-10 minutes. The `kube-apiserver` operator uses a conservative rollout strategy, updating one control plane node at a time and waiting for health checks before proceeding to the next node. This process can take 30 minutes or longer depending on cluster load. // cite:21
// cite:21 INFERRED [30]: Rollout timing (5-10 min, 30+ min) and one-node-at-a-time strategy inferred from general kube-apiserver static pod rollout behavior — no specific timing in enhancement or API docs
====

.Verification

. Verify the encryption type by entering the following command:
+
[source,terminal]
----
$ oc get apiserver cluster -o jsonpath='{.spec.encryption.type}'
----
+
The output shows `KMS`.

. Check the KMS plugin health by entering the following command:
+
[source,terminal]
----
$ oc get co kube-apiserver -o jsonpath='{.status.conditions[?(@.type=="Degraded")].message}'
----
+
If the output is empty or does not reference KMS, the plugin is healthy.

. Monitor the `kube-apiserver` rollout progress by entering the following command:
+
[source,terminal]
----
$ oc get kubeapiserver cluster -o jsonpath='{.status.nodeStatuses}' | jq -r '.[] | "\(.nodeName | split(".")[0]): current=\(.currentRevision) target=\(.targetRevision)"'
----
+
.Example output during rollout
[source,terminal]
----
ip-10-0-16-166: current=10 target=0
ip-10-0-32-93: current=9 target=10
ip-10-0-69-106: current=9 target=0
----
+
The operator rolls out one node at a time. When all nodes show the same `current` revision and `target` is `0`, the rollout is complete.

. Check the encryption migration status by entering the following command:
+
[source,terminal]
----
$ oc get kubeapiserver cluster -o jsonpath='{.status.conditions[?(@.type=="Encrypted")]}' | jq .
----
+
.Example output when complete
[source,terminal]
----
{
  "lastTransitionTime": "2026-05-15T17:39:02Z",
  "message": "All resources encrypted: secrets, configmaps",
  "reason": "EncryptionCompleted",
  "status": "True",
  "type": "Encrypted"
}
----
+
Wait for `reason` to show `EncryptionCompleted` before you verify encryption in etcd.

. Verify that secrets are encrypted in etcd:
+
[WARNING]
====
Wait for the `kube-apiserver` rollout to complete on all control plane nodes before you verify encryption. During the rollout, API requests are distributed across nodes. Secrets that are created while some nodes are on an earlier revision are not encrypted with KMS.
====
+
--
.. Create a test secret by entering the following command:
+
[source,terminal]
----
$ oc create secret generic test-secret --from-literal=key=value -n default
----

.. Get an etcd pod name by entering the following command:
+
[source,terminal]
----
$ oc get pods -n openshift-etcd -l app=etcd -o name | head -1
----

.. Check the secret data in etcd by entering the following command:
+
[source,terminal]
----
$ oc exec -n openshift-etcd <etcd_pod_name> -- etcdctl get /kubernetes.io/secrets/default/test-secret --print-value-only | hexdump -C | head -1
----
+
The output begins with `k8s:enc:kms:v2:` followed by encrypted binary data. // cite:22
// cite:22 VERIFIED [45]: https://kubernetes.io/docs/tasks/administer-cluster/kms-provider/#verifying-that-the-data-is-encrypted - Kubernetes docs confirm KMS v2 encrypted prefix format "k8s:enc:kms:v2:"

.. Delete the test secret by entering the following command:
+
[source,terminal]
----
$ oc delete secret test-secret -n default
----
--
