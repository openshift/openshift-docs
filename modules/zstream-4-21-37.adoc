== Fixed issues

* Before this update, the Berkeley Packet Filter (BPF) filesystem did not allow dots (".") in filenames. As a consequence, the Ingress Node Firewall could not attach rules to virtual LAN (VLAN) subinterfaces such as `bond0.12`. Attempting to pin a link for an interface containing a dot failed with an `operation not permitted` error. With this release, the Ingress Node Firewall sanitizes pin filenames by converting dots to a placeholder string. For example, `vlan.100` becomes `vlan_dot_100` before writing to the BPF filesystem. As a result, firewall rules can be successfully applied to subinterfaces such as VLANs on top of bonded interfaces. (link:https://issues.redhat.com/browse/OCPBUGS-31495[OCPBUGS-31495])

* Before this update, when deploying a hosted cluster on AWS in non-commercial ISO or classified regions, the Cluster Network Operator (CNO) assumed a maximum transmission unit (MTU) of 9001 for hosted cluster nodes. Because some of these regions do not support jumbo frames at this MTU value, and the setting could not be overridden during cluster creation, networking for hosted clusters in these regions could fail to configure correctly. With this release, you can specify an OVN-Kubernetes tunnel interface MTU between 576 and 9216 at cluster creation time. You can configure this setting by using the optional, immutable `mtu` field in the `ovnKubernetesConfig` configuration of the `HostedCluster` custom resource (CR) or by using the `--ovn-kubernetes-mtu` hosted control planes CLI flag. As a result, you can successfully deploy hosted clusters in AWS regions that do not support jumbo frames, and the CNO applies the correct MTU value. (link:https://issues.redhat.com/browse/OCPBUGS-81489[OCPBUGS-81489])

* Before this update, in dual-stack hosted clusters, mismatched IP SAN byte lengths such as 4-byte versus 16-byte IPv4-mapped addresses caused false validation failures. As a consequence, the Control Plane Operator was forced to continuously regenerate `kas-server-crt`, causing generation churn that could stall installations. With this release, IP SANs are normalized using `net.IP.To16()` before comparison. As a result, unnecessary certificate regeneration and continuous `kube-apiserver` rolling updates do not occur. (link:https://issues.redhat.com/browse/OCPBUGS-112732[OCPBUGS-112732])

* Before this update, the `kube-apiserver-check-endpoints` container generated a TLS certificate for the `check-endpoint` service on port `17697` with a validity of only 1 second. As a consequence, the certificate expired almost immediately after generation, which differed from previous {product-title} versions where the certificate was valid for 1 month. With this release, the `kube-apiserver-check-endpoints` container generates certificates with an appropriate validity period. As a result, the `check-endpoint` service certificate remains valid for the expected duration, consistent with previous releases. (link:https://issues.redhat.com/browse/OCPBUGS-127407[OCPBUGS-127407])

* Before this update, when a node with an EgressIP was rebooted, the ovnkube-cluster-manager reassigned the EgressIP to a new node but did not immediately remove it from the rebooting node. Both the old and new nodes responded to ARP requests for the same IP address. As a consequence, this MAC address flapping could cause network switches, firewalls, or other devices to malfunction or block EgressIP traffic. With this release, nftables rules block ARP responses from the old node after EgressIP migration. As a result, EgressIP failover completes without MAC address conflicts during node reboots. (link:https://issues.redhat.com/browse/OCPBUGS-128910[OCPBUGS-128910])
