= Configure cluster-wide token rate limit reservations

[role="_abstract"]
As a platform engineer, you can ensure that {prodname} uses reservation mode for token-based rate limiting of requests to LLM APIs.

When several requests are in progress at once, checking only recorded token usage can allow them all through before their usage is counted. Reservations hold estimated token capacity while each request is in progress, helping prevent concurrent requests from exceeding the limit.

The `reservation.amount` parameter defaults to `0` for each limit. If the `reservation` block or its `amount` parameter is omitted, no capacity is held for requests in progress, even when the cluster-wide mode is `Reservation`.

Limitador caps every reservation, so `Reservation` mode still permits some overshoot. The `spec.reservations.maxFraction` field of the `Limitador` CR sets the largest fraction of a limit that a single reservation can hold, and defaults to `0.5`. Limitador therefore holds at least two reservations before it rejects a request for lack of capacity. A lower value allows more concurrent requests, but it widens the overshoot.

The `spec.reservations.maxTtl` field sets the longest time that Limitador holds a reservation, and defaults to `60s`, or 60 seconds. Limitador caps a longer `reservation.ttl` value at that value, as well as a longer `backendRequest` route timeout used in its place.

A reservation is also released when a request does not complete normally. If the upstream call fails, times out, or returns a response from which no token count can be extracted, the capacity returns immediately instead of at the end of the counter window.

.Prerequisites

* You installed {prodname} on the {ocp} cluster you are working with.
* You have permissions to view the `Kuadrant` custom resource (CR).

.Procedure

* Confirm that `spec.tokenRateLimiting.mode` in the `Kuadrant` CR is either unset or set to `Reservation`.
+
** `Reservation` is the default. Requests reserve estimated token capacity before being forwarded when the matching limit specifies a nonzero `reservation.amount`. Actual usage is committed when the response completes.
** `Optimistic` checks capacity before forwarding requests and records actual usage afterward, without reserving capacity for requests in progress.
+
The selected mode applies to all `TokenRateLimitPolicy` resources managed by this Kuadrant installation.
+
.Example `Kuadrant` CR that sets the enforcement mode
[source,yaml,subs="+quotes"]
----
apiVersion: kuadrant.io/v1beta1
kind: Kuadrant
metadata:
  name: kuadrant
  namespace: _<kuadrant_system>_
spec:
  tokenRateLimiting:
    mode: Reservation
----
+
* Replace `_<kuadrant_system>_` with the namespace where you installed {prodname}.
* Omitting the `spec.tokenRateLimiting` field does not select `Optimistic` mode. The mode defaults to `Reservation`.

.Verification

* With `Reservation` mode active and a nonzero `reservation.amount` configured for the matching limit, send concurrent requests to the protected API by running the following command:
+
[source,terminal,subs="+quotes"]
----
$ for i in $(seq 1 15); do
    curl -s -o /dev/null -w "%{http_code}\n" \
         -H "Authorization: _<auth_policy>_" \
         -d '{"model": "gpt-4", "messages": [{"role": "user", "content": "Hello"}]}' \
         _<api_endpoint>_ &
  done
  wait
----
+
Replace `_<auth_policy>_` and `_<api_endpoint>_` with your values.
+
.Example output
[source,text]
----
200
200
429
429
----
+
Requests that fit in the remaining capacity receive a `200 OK` response or another success status. The rest receive a `429 Too Many Requests` response before they reach the LLM API.
* Confirm that completed requests release their reservations and record actual token usage.
