= Prepare cluster templates for a new release

[role="_abstract"]
Before you can upgrade a cluster, you must create a new `ClusterTemplate` custom resource version for the target {product-title} release. This involves updating the cluster installation defaults, policy templates, and upgrade configuration for the new version.

.Prerequisites

* The GitOps repository is configured and ArgoCD synchronizes resources to the hub cluster.
* The target {product-title} version is available as a `ClusterImageSet` on the hub cluster.

.Procedure

. Create new `clustertemplates` and `policytemplates` directories in the GitOps repository for the target release version, following the same directory structure as existing versions:
+
[source,terminal]
----
clustertemplates/
├── version_4.Y.Z/
│   └── sno-ran-du/
└── version_4.Y.Z+1/        # new release directory
    └── sno-ran-du/

policytemplates/
├── version_4.Y.Z/
│   └── sno-ran-du/
└── version_4.Y.Z+1/        # new release directory
    └── sno-ran-du/
----

. Create a `ClusterInstance` defaults ConfigMap resource for the new version with the updated `clusterImageSetNameRef`:
+
[source,yaml]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: clusterinstance-defaults-v1
  namespace: <template_namespace>
data:
  clusterinstance-defaults: |
    clusterImageSetNameRef: "<target_version>"
    extraLabels:
      ManagedCluster:
        cluster-version: "<version_label>"
        <template_name>-policy: "v1"
----
+
where:
+
--
`<template_namespace>`:: Specifies the namespace for the new `ClusterTemplate` version, such as `sno-ran-du-v4-Y-Z+1`.
`<target_version>`:: Specifies the target {product-title} version, such as `4.22.0`.
`<version_label>`:: Specifies a label value identifying the cluster version, such as `v4-22-0`.
`<template_name>`:: Specifies the template name used for policy binding, such as `sno-ran-du`.
--

. Create policy templates for the new version with updated Operator index images and any new configuration manifests.

. Create the `ClusterTemplate` CR for the target release with upgrade configuration:
+
[source,yaml]
----
apiVersion: clcm.openshift.io/v1alpha1
kind: ClusterTemplate
metadata:
  name: <template_name>.v4-Y-Z+1-1
  namespace: <template_namespace>
spec:
  name: <template_name>
  version: v4-Y-Z+1-1
  release: "<target_version>"
  templateDefaults:
    clusterInstanceDefaults: clusterinstance-defaults-v1
    policyTemplateDefaults: policytemplate-defaults-v1
    upgradeDefaults:
      imageBasedGroupUpgrade:     # for SNO clusters
        ibuSpec:
          seedImageRef:
            image: "quay.io/seed-repo/seed-image:<target_version>"
            version: "<target_version>"
----
+
* `spec.release` must match the target {product-title} version.
* `spec.templateDefaults.upgradeDefaults` must contain either `imageBasedGroupUpgrade` for single-node clusters or `clusterVersion` for multi-node clusters. Do not configure both in the same `ClusterTemplate` CR.
+
For multi-node clusters, configure `upgradeDefaults` with `clusterVersion` instead:
+
[source,yaml]
----
    upgradeDefaults:
      clusterVersion:             # for MNO clusters
        channel: "stable-<target_version>"
        desiredUpdate:
          version: "<target_version>"
----

. Commit the new resources to the GitOps repository and wait for ArgoCD to synchronize them to the hub cluster.

.Verification

* Verify that the new `ClusterTemplate` CR is validated on the hub cluster by running the following command:
+
[source,terminal]
----
$ oc get clustertemplates.clcm.openshift.io -n <template_namespace>
----
+
A validated `ClusterTemplate` CR appears in the output and can be referenced by `ProvisioningRequest` CRs.
