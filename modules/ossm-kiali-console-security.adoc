= Mutual TLS in the console

[role="_abstract"]

The console shows how mutual TLS (mTLS) is applied in the mesh. You can read mesh-wide status from the masthead, namespace status from the Namespaces page, and per-edge status from the graph.

.Mesh-wide mTLS enabled in the Kiali masthead
image::ossm-kiali-masthead-mtls-enabled.png[Kiali masthead showing that mesh-wide mTLS is enabled]

.Partial mesh-wide mTLS in the Kiali masthead
image::ossm-kiali-masthead-mtls-partial.png[Kiali masthead showing that mesh-wide mTLS is only partially enabled]

On the Mesh page, a solid lock on the control plane means every request in the mesh uses mTLS. A hollow lock means the mesh is in `PERMISSIVE` mode or the mesh-wide mTLS configuration is inconsistent.

The Namespaces page shows a lock for each namespace. A solid lock is strict mTLS. An open lock is permissive. A red open lock means mTLS is disabled. A downward arrow means the namespace inherits the mesh-wide policy.

.Security badges on graph edges
image::ossm-kiali-graph-badge-security.png[Kiali graph with mTLS lock badges on traffic edges]

On the graph, enable the *Security* badge in the *Display* menu. A lock on an edge means at least one request in the selected period used mTLS. If some requests used mTLS and others did not, the side panel shows the percentage that used mTLS.

The console also validates `DestinationRule` and `PeerAuthentication` objects that affect mTLS. Those messages appear on the {istio} configuration pages.
