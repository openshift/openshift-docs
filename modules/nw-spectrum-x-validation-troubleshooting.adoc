= Verify and troubleshoot Spectrum-X

[role="_abstract"]
You can verify Spectrum-X worker interfaces and test workload connectivity and performance. Resource status and Operator events help diagnose configuration failures.

.Prerequisites

* You have configured the NVIDIA Network Operator and all single-plane rail resources.
* You have verified that the Operators have applied the single root I/O virtualization (SR-IOV) and NMState policies and created the rail resources.
* You have access to the cluster and worker nodes.

.Procedure

. On each worker, verify that the configured rail interface is present, has the expected maximum transmission unit (MTU), and uses `switchdev` mode:
+
[source,terminal]
----
$ oc debug node/<worker_node> -- chroot /host ip -d link show eth_r0_p0
$ oc debug node/<worker_node> -- chroot /host devlink dev eswitch show pci/<PCI_BDF>
----
+
Replace `<worker_node>` with the worker node name and `<PCI_BDF>` with the Peripheral Component Interconnect (PCI) bus, device, and function address of the adapter.
+
Repeat the checks for each rail and confirm that the interface names and PCI addresses match the node policies.

. Optional: If the selected reference architecture provides `rcp-tool`, run its topology, switch, host, and ping checks from the host on which the tool runs:
+
[source,terminal]
----
$ rcp-tool topology validate
$ rcp-tool validation switch-config
$ rcp-tool validation host-config
$ rcp-tool validation ping
----

. Run a workload-level connectivity and performance test that is supported for the installed Spectrum-X release. Use the vendor-provided test workload, images, and expected values for the target platform. Check the NVIDIA Spectrum-X verification and troubleshooting guidance for required switch, traffic-class, priority-flow-control, congestion-control, and end-to-end checks.

. If a resource does not become ready, inspect its status and the corresponding Operator logs before changing configuration:
+
[source,terminal]
----
$ oc describe nicclusterpolicy nic-cluster-policy
$ oc get events -n nvidia-network-operator --sort-by=.lastTimestamp
----
+
Common causes include an unsupported combination of OpenShift, Operator, firmware, adapter, and Spectrum-X profile versions. PCI addresses might not match the installed hardware, or an interface name might differ from the SR-IOV policy. Rail address pools might overlap, or the switch MTU might differ from the host MTU. Resolve version and topology issues with the applicable vendor support matrix and reference architecture. Do not use repository workarounds that change PCIe settings, alter operating system labels, or replace driver images unless the hardware and software vendors approve them.

. If the Open vSwitch (OVS) Container Network Interface (CNI) plugin is missing, check the NVIDIA Spectrum-X verification and troubleshooting guidance. Confirm the SR-IOV Operator subscription and plugin image with the vendors before updating the subscription:

.. Identify the SR-IOV Operator subscription:
+
[source,terminal]
----
$ oc get subscriptions -n openshift-sriov-network-operator
----

.. After the vendors confirm that the image is compatible, update the subscription. The Network Operator 26.1.0 example uses the following image:
+
[source,terminal]
----
$ oc patch subscription <SRIOV_SUBSCRIPTION_NAME> -n openshift-sriov-network-operator --type=merge --patch '{"spec":{"config":{"env":[{"name":"OVS_CNI_IMAGE","value":"nvcr.io/nvidia/mellanox/ovs-cni-plugin:network-operator-v26.1.0"}]}}}'
----
+
Replace `<SRIOV_SUBSCRIPTION_NAME>` with the name of the SR-IOV Operator subscription.
