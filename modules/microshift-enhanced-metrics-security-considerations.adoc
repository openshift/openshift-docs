[id="microshift-enhanced-metrics-security-considerations_{context}"]
= Enhanced metrics security considerations

[role="_abstract"]
When you enable enhanced metrics in {microshift-short}, you expose additional endpoints that can reveal information about the host, cluster objects, and resource usage. Review the following considerations before installing exporters and before configuring external scrapers or monitoring back ends.

[id="microshift-enhanced-metrics-sensitive-data_{context}"]
== Sensitive information in metrics

Enhanced metrics can help you monitor {microshift-short}, but the data that exporters return can also help an attacker understand your environment.

node-exporter::
Exposes hardware, operating system, and network utilization metrics from the {microshift-short} host. This information can reveal host configuration, capacity, and workload patterns.

kube-state-metrics::
Exposes metadata about Kubernetes API objects, such as deployments, pods, and nodes. {microshift-short} applies a default metric denylist to reduce exposure of secret and annotation data, but metrics can still include object names, labels, and state information that describe your workloads.

metrics-server::
Registers the `metrics.k8s.io` API and exposes resource usage for nodes and pods. Any principal that can query this API can run commands such as `oc top nodes` and `oc top pods`.

[id="microshift-enhanced-metrics-authn-authz_{context}"]
== Authentication and authorization

{microshift-short} reuses OpenShift monitoring component images and applies controls that differ by exporter.

node-exporter and kube-state-metrics::
The exporters listen on localhost inside the pod. A `kube-rbac-proxy` sidecar terminates HTTPS on the Service endpoint and authorizes `GET` requests to `/metrics` through the Kubernetes API. Scrapers must present a valid bearer token, and the API server must authorize the request.

metrics-server::
The metrics-server Deployment serves the aggregated `metrics.k8s.io` API over HTTPS. Access is controlled by Kubernetes RBAC on the API group, not through a separate metrics proxy.

When you install `microshift-observability`, the OpenTelemetry Collector uses the `openshift-observability-client` service account, which includes permission to issue `GET` requests to `/metrics` non-resource URLs. If you deploy your own scraper, create a dedicated service account and grant only the RBAC permissions required to scrape the exporters that you enable.

[IMPORTANT]
====
Grant metrics scraping permissions only to trusted monitoring components. Avoid using cluster-admin credentials for scrapers.
====

[id="microshift-enhanced-metrics-tls_{context}"]
== Transport security

Exporter Services in the `openshift-monitoring` namespace use OpenShift service serving certificates. The `kube-rbac-proxy` sidecars for node-exporter and kube-state-metrics also require client certificate validation against the cluster `metrics-client-ca` bundle.

When you configure a scraper or forwarder, verify TLS connections to exporter endpoints and trust the service CA or the CA bundle that {microshift-short} provides. Do not disable TLS verification for production deployments.

[id="microshift-enhanced-metrics-network-exposure_{context}"]
== Network exposure

By default, enhanced metrics endpoints are intended for in-cluster access through Kubernetes Services in the `openshift-monitoring` namespace.

node-exporter host exposure::
The node-exporter DaemonSet uses `hostNetwork` and publishes port `9100` on the host through `kube-rbac-proxy`. Network policies do not apply to pods that use host networking, and host-network traffic is not subject to the same isolation as pod network traffic. Restrict host-level network access with firewalld or other host firewall controls if untrusted networks can reach the {microshift-short} node.

metrics-server and kube-state-metrics::
These components expose HTTPS endpoints through cluster Services. Limit which namespaces and workloads can reach the `openshift-monitoring` namespace by using `NetworkPolicy` objects where appropriate.

Remote scraping::
If you forward metrics to a central observability platform, secure the path between the edge node and the remote endpoint. Use encrypted transport, authenticate the collector, and protect stored metrics with access controls that match the sensitivity of the exported data.

[id="microshift-enhanced-metrics-hardening_{context}"]
== Hardening recommendations

Use the following practices to reduce risk when you enable enhanced metrics:

* Install only the exporter RPM packages that your monitoring workflow requires.
* Remove enhanced metrics RPM packages when you no longer need the exporters.
* Restrict RBAC permissions for principals that scrape metrics endpoints or query the `metrics.k8s.io` API.
* Configure host and cluster network controls to limit access to exporter Services and to the node-exporter host port.
* Review kube-state-metrics collector configuration before enabling additional custom resource metrics.
* Treat forwarded metrics with the same confidentiality requirements as the source cluster, especially when edge nodes operate in untrusted or shared networks.

[NOTE]
====
{microshift-short} deploys enhanced metrics without the full {product-title} Cluster Monitoring Operator stack. You are responsible for securing scrapers, remote endpoints, and any long-term storage for metrics that you collect outside the cluster.
====
