= Deploying the control plane for virtual machine integration

[role="_abstract"]

A virtual machine reaches the control plane from outside the cluster, over a hostname that resolves in public DNS. Configure the control plane so that it accepts connections on that hostname and so that it treats in-cluster workloads and virtual machine workloads as members of separate networks.

.Prerequisites

* You have installed the {SMProduct} Operator 3.5 or later in the {ocp-product-title} cluster.

* You have deployed the `IstioCNI` resource.

* You have installed the `istioctl` tool.

* You have logged in to the {ocp-product-title} cluster with the `oc` command as a user with the `cluster-admin` role.

* You have a Red Hat Enterprise Linux (RHEL) 9 virtual machine that can resolve names under the cluster ingress domain and reach the resolved addresses.

.Procedure

. Determine the cluster ingress domain by running the following command:
+
[source,terminal]
----
$ oc get ingresses.config.openshift.io cluster -o jsonpath='{.spec.domain}'
----
+
*Example output:*
+
[source,terminal]
----
apps.example.com
----
+
Use this value wherever `<ingress_domain>` appears in the following procedures.
+
[IMPORTANT]
====
This configuration assumes that the DNS resolver of the virtual machine can resolve names under the cluster ingress domain, and that the resolved address is reachable from the virtual machine. The {ocp-product-title} ingress domain is normally backed by a wildcard `*.<ingress_domain>` record in public DNS that points at the router load balancer, so this requirement is usually met without additional configuration.

Meeting this requirement is what removes the need to maintain an `/etc/hosts` file on the virtual machine.
====

. Create the `istio-system` namespace by running the following command:
+
[source,terminal]
----
$ oc create namespace istio-system
----

. Assign the control plane namespace to the cluster network by running the following command:
+
[source,terminal]
----
$ oc label namespace istio-system topology.istio.io/network=cluster-network
----

. Create an `Istio` resource named `istio.yaml` similar to the following example:
+
[source,yaml]
----
apiVersion: sailoperator.io/v1
kind: Istio
metadata:
  name: default
spec:
  namespace: istio-system
  updateStrategy:
    type: InPlace
  values:
    global:
      network: cluster-network # <1>
    pilot:
      env:
        ISTIOD_CUSTOM_HOST: istiod.istio-system.svc.<ingress_domain> # <2>
----
<1> The network that in-cluster workloads belong to. The virtual machine is assigned to a different network, which causes the mesh to route traffic between the two through an east-west gateway.
<2> The hostname of the route that exposes the control plane to the virtual machine. Replace `<ingress_domain>` with the value from the first step.
+
[NOTE]
====
The `ISTIOD_CUSTOM_HOST` variable adds the route hostname to the subject alternative name (SAN) list of the certificate that the control plane serves on port 15012. The variable adds to the default names rather than replacing them, so the in-cluster names, such as `istiod.istio-system.svc`, continue to work for the injection and validation webhooks.

This variable is required because the proxy on the virtual machine uses the host part of its discovery address as both the TLS server name indication (SNI) and the name that it verifies the control plane certificate against. The SNI must be the route hostname so that the router selects the correct route, so that same hostname must also be present in the control plane certificate.
====

. Apply the `Istio` custom resource (CR) by running the following command:
+
[source,terminal]
----
$ oc apply -f istio.yaml
----

.Verification

. Verify that the control plane is ready by running the following command:
+
[source,terminal]
----
$ oc wait --for=condition=Ready istios/default --timeout=3m
----
