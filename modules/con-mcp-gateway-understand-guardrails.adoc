= Understand {mcpg} guardrails

[role="_abstract"]
You can add programmable safety rails to any LLM application by using NeMo Guardrails.

When you integrate guardrails on the {mcpg}, every tool call request and response routed through the `Gateway` object is checked against the guardrails path. Guardrails can block dangerous calls or hide sensitive information.

For incoming requests to the MCP gateway, the `Gateway` object uses NeMo Guardrails to inspect the arguments in the request body before the proxy sends the request to a server backend.

For responses, the `Gateway` object uses the guardrails to inspect content in the tool result before sending the result back to the client. This happens independently of any authentication or authorization. Tool call traffic is checked according to guardrail configurations, a set of files that define different text classification algorithms and how they are applied.

MCP gateway guardrails technical definitions::

* Guardrail configurations: A set of files that define what type of guardrails are applied, such as PII detection or prompt injection detection, and how they are applied. These need to be defined as part of the NeMo Guardrails deployment process, before referencing them in the {mcpg}.

* Global guardrails: Guardrail configurations that applied to every registered MCP server behind the `Gateway` object.

* Per-server guardrails: Additional guardrail configurations that are applied to specific MCP servers, such as servers that have access to sensitive information or vulnerable tools. When defined, per-server guardrails are merged with the global guardrails. During runtime, the global guardrails run first in order, before the per-server guardrails for each MCP server.
