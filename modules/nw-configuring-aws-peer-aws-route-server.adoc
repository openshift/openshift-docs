= Configuring BGP to peer with AWS Route Server

[role="_abstract"]
After you prepare the {aws-short} environment, configure BGP Cloud Connector so that {product-title} compute nodes establish BGP peering sessions with the {aws-short} Route Server and advertise {VirtProductName} virtual machine (VM) network routes.

.Prerequisites

* You have created and configured a Layer 2 Cluster User Default Network (CUDN).
For more information about CUDNs, see "About the ClusterUserDefinedNetwork CR".
** You have verified that the CUDN CIDR block does not overlap with any existing CIDR blocks in your VPC.
** You have enabled IP Address Management (IPAM) on the CUDN.
* You prepared the {aws-short} environment for BGP peering.
* You installed the BGP Cloud Connector Operator on your cluster.
* You have the {aws-short} Region, Route Server ID, and local autonomous system number (ASN) that you noted while preparing the {aws-short} environment.

.Procedure

. Get the OpenID Connect (OIDC) provider and account ID for the cluster by entering the following commands:
+
[source,terminal]
----
$ OIDC_PROVIDER=$(oc get authentication cluster -o jsonpath='{.spec.serviceAccountIssuer}' | sed 's|https://||')
----

. Create an IAM role that trusts the Operator's service account by entering the following command:
+
[source,terminal]
----
$ aws iam create-role --role-name bgp-cloud-connector-operator --assume-role-policy-document '{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {"Federated": "arn:aws:iam::'$AWS_ACCOUNT_ID':oidc-provider/'$OIDC_PROVIDER'"},
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "'$OIDC_PROVIDER':sub": "system:serviceaccount:openshift-bgp-cloud-connector:openshift-bgp-cloud-connector-controller-manager"
      }
    }
  }]
}'
----

. Attach the required permissions policy to the role by entering the following command:
+
[source,terminal]
----
$ aws iam put-role-policy --role-name bgp-cloud-connector-operator --policy-name bgp-cloud-connector-operator-policy --policy-document '{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "sts:GetCallerIdentity",
      "ec2:DescribeRouteServers",
      "ec2:DescribeRouteServerEndpoints",
      "ec2:DescribeSubnets",
      "ec2:DescribeRouteServerPeers",
      "ec2:CreateRouteServerPeer",
      "ec2:DeleteRouteServerPeer",
      "ec2:CreateTags",
      "ec2:DescribeInstances",
      "ec2:ModifyNetworkInterfaceAttribute"
    ],
    "Resource": "*"
  }]
}'
----

. Configure {aws-short} authentication for the Operator by using a `CredentialsRequest` CR.
The Cloud Credential Operator (CCO) automatically manages credentials based on your cluster's credential mode:
+
* Mint Mode: No manual credential setup is required.
CCO automatically creates an IAM user with the necessary permissions and populates the required secret in the operator's namespace.
* Manual or STS Mode: Pass your pre-created IAM role ARN to the Operator by using the `ROLEARN` environment variable. CCO updates the `CredentialsRequest` and provisions a secret containing the projected web identity token.
+
If you are deploying the operator manually via a `Subscription` CR, set the `ROLEARN` environment variable in your manifest:
+
[source,yaml]
----
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: bgp-cloud-connector-operator
  namespace: openshift-bgp-cloud-connector
spec:
  channel: stable
  name: bgp-cloud-connector-operator
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  config:
    env:
      - name: ROLEARN
        value: arn:aws:iam::<aws_account_id>:role/<iam_role_name>
----
+
[NOTE]
====
If you install the Operator by using the web console, the console automatically prompts you for the `Role ARN` and then populates `ROLEARN` for you.

You must create the IAM role in {aws-short} before setting `ROLEARN`.
The Operator cannot generate its own IAM role.
Ensure the trust policy of the role trusts the OIDC provider of yoru cluster.
====

. Create a `BGPCloudConfiguration` custom resource (CR) to define the cluster-wide BGP configuration:
+
[source,yaml]
----
apiVersion: networking.openshift.io/v1beta1
kind: BGPCloudConfiguration
metadata:
  name: cluster
spec:
  platform: AWS
  bgp:
    localASN: <local_asn>
    livenessDetection: bgp-keepalive
  routerNodeSelector:
    bgp_router: "true"
  aws:
    region: <aws_region>
    routeServerIDs:
      - <route_server_id>
----
+
where:
+
--
`<local_asn>`:: Specifies the Autonomous System Number (ASN) for the FRRouting (FRR) router of your cluster. The `<local_asn>` value must be different from the Route Server ASN that you configured with `--amazon-side-asn`, which the Operator discovers automatically.

`bgp_router`:: Specifies the label key used in the `routerNodeSelector` to identify which compute nodes participate in BGP routing. Nodes that match this selector have the following characteristsics:
+
* Establish BGP peering sessions with Route Server Endpoints in their local subnet.
* Act as the next-hop for BGP-advertised routes for traffic ingressing from the VPC to the primary Cluster Default Network (CUDN) of the workload.
* Have source/destination checks disabled on their Elastic Network Interfaces (ENIs).
+
[IMPORTANT]
====
Traffic always egresses from pods or VMs directly through their own compute node ENI. Therefore, you must apply this selector to any node where these workloads can be scheduled, not just the nodes intended to receive incoming traffic.
====

`<aws_region>`:: Specifies the {aws-short} region in which cloud resources get created.
Replace `<aws_region>` with the {aws-short} Region of your Route Server.

`<route_server_id>`:: Specifies the Route Server ID. Replace `<route_server_id>` with the Route Server ID that you noted while preparing the {aws-short} environment.
--

. Apply the updates to the BGP cloud configuration resource on your cluster by entering the following command:
+
[source,terminal]
----
$ oc apply -f bgpcloudconfiguration.yaml
----
+
[NOTE]
====
`BGPCloudConfiguration` is a cluster-scoped singleton.
You must provide the name `cluster` to the CR.
====

. Label each compute node that you want to participate in BGP peering.
The label also applies to every node that can host a VM or pod connected to a UDN for the purposes of egress traffic handling.
Ensure the labels match the `spec.routerNodeSelector` label from an earlier step.
+
[source,terminal]
----
$ oc label node <node_name> bgp_router=true
----
+
Replace `<node_name>` with the name of the compute node.

. Create a namespace for your workload. Use the labels that the BGP Cloud Connector requires.
+
[source,yaml]
----
apiVersion: v1
kind: Namespace
metadata:
  name: <namespace_name>
  labels:
    k8s.ovn.org/primary-user-defined-network: ""
    cluster-udn: <network_name>
----
+
Replace `<namespace_name>` with a name for the namespace.
Replace `<network_name>` with the network name that you plan to use in the following step.
+
[IMPORTANT]
====
You must set the `k8s.ovn.org/primary-user-defined-network` label when you create the namespace.
{product-title} admission policy prevents you from adding this label to an existing namespace.
====
+
[source,terminal]
----
$ oc apply -f namespace.yaml
----

. Create a `BGPRouting` CR to declare the network to advertise over BGP:
+
[source,yaml]
----
apiVersion: networking.openshift.io/v1beta1
kind: BGPRouting
metadata:
  name: <routing_name>
spec:
  network:
    name: <network_name>
    subnets:
      - <pod_network_cidr>
----
+
Replace `<routing_name>` with a name for the CR.
Replace `<network_name>` with the same value that you used for `cluster-udn` in the previous step.
Replace `<pod_network_cidr>` with the CIDR block that the primary network interfaces of the VM get assigned from, for example `10.100.0.0/16`.
+
[source,terminal]
----
$ oc apply -f bgprouting.yaml
----

.Verification

. Confirm that both custom resources report a `Ready` phase by entering the following commands:
+
[source,terminal]
----
$ oc get bgpcloudconfiguration cluster -o jsonpath='{.status.phase}'
----
+
[source,terminal]
----
$ oc get bgprouting <routing_name> -o jsonpath='{.status.phase}'
----
+
If either resource reports `Degraded`, inspect its conditions for the failure reason:
+
[source,terminal]
----
$ oc get bgpcloudconfiguration cluster -o jsonpath='{.status.conditions}' | jq .
----

. Confirm that the Operator generated the supporting resources by entering the following commands:
+
[source,terminal]
----
$ oc get frrconfiguration -n openshift-frr-k8s
----
+
[source,terminal]
----
$ oc get clusteruserdefinednetwork
----
+
[source,terminal]
----
$ oc get routeadvertisements
----

. Deploy a virtual machine into the namespace that you created, and verify that it uses `bridge` binding on its network interface:
+
[source,yaml]
----
spec:
  domain:
    devices:
      interfaces:
        - name: default
          bridge: {}
  networks:
    - name: default
      pod: {}
----
+
[IMPORTANT]
====
Use `bridge` binding, not `masquerade` binding. `masquerade` binding installs nftables rules that drop inbound traffic on the user-defined network (UDN) interface, which blocks the direct connectivity that this feature provides.
====

. From an EC2 instance in the same VPC as your cluster, verify that you can reach the VM at its pod network IP address by entering the following command:
+
[source,terminal]
---- 
$ ping <vm_pod_ip> 
----
+
Replace `<vm_pod_ip>` with the pod network IP address of the VM.
When BGP peering is established, the {aws-short} Route Server propagates the `<pod_network_cidr>` route into the VPC route tables, with the compute node Elastic Network Interface (ENI) as the nexthop. As a result, hosts in the VPC can reach the VM directly, with no NAT device in the path and no additional configuration.

. Optional: To verify connectivity from an external network, such as an on-premises network connected over {aws-short} Direct Connect or a VPN, first ensure that the external network can route traffic for the VM pod network into the VPC. See "Enabling access to VM pod networks from external networks".
