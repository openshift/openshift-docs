= About {DTShortName} for outbound requests

[role="_abstract"]
Use {DTShortName} to follow the path of an outbound request through your egress `Gateway` object, including the policy evaluation that the `wasm-shim` module, Authorino, and Limitador perform. The tracing infrastructure is the same for outbound and incoming traffic.

Tracing on an egress `Gateway` object requires two layers of configuration:

* Proxy tracing in {service-mesh}, which consists of a `Telemetry` object and an extension provider. This layer produces the gateway spans.
* Component tracing in {prodname}, which you configure in the `spec.observability.tracing` field of the `Kuadrant` custom resource (CR). This layer sends the policy evaluation spans of the `wasm-shim` module, Authorino, and Limitador to your collector.

You also need at least one policy, such as an `AuthPolicy` CR, a `RateLimitPolicy` CR, or a `TokenRateLimitPolicy` CR, attached to the egress `Gateway` object or to one of its routes. For the configuration steps, see "Configure data plane tracing in {prodname}".

When the `Kuadrant` CR has a tracing endpoint and a policy targets the egress `Gateway` object, the {prodname} Operator creates a tracing `EnvoyFilter` object named `kuadrant-tracing-_<gateway_name>_`. That object defines the upstream cluster of your collector and adds a tracing service to the configuration of the `wasm-shim` module. You do not need any egress-specific configuration.

[id="rhcl-egress-tracing-boundaries_{context}"]
== Two trace boundaries

{service-mesh} does not propagate trace context to WebAssembly filters, so each request produces two independent traces:

* The gateway trace, which holds the proxy spans for the request through the egress `Gateway` object.
* The {prodname} filter trace, which holds the policy evaluation spans across the `kuadrant-filter` service, Authorino, and Limitador.

Both traces carry the same `x-request-id` header value, which you use to correlate them.

[id="rhcl-egress-tracing-no-sidecar_{context}"]
== Traces for workloads without a sidecar

A calling workload might have no {service-mesh} sidecar, for example when it reaches the egress `Gateway` object through the `ClusterIP` service of the gateway. In that case, the first proxy span starts at the egress `Gateway` object, and no outbound span exists for the workload.

Traces from the `wasm-shim` module are the same whether or not the workload has a sidecar. For trace continuity, workloads must propagate the `x-request-id` header so that the `wasm-shim` module can correlate the traces.

[id="rhcl-egress-tracing-missing-spans_{context}"]
== Common causes of missing spans

* No `kuadrant-filter` service is displayed in your tracing UI. Verify that the `spec.observability.dataPlane.defaultLevels` field of the `Kuadrant` CR is set to at least `debug: "true"`, because the default level of `ERROR` exports spans only for errors. Verify that the tracing `EnvoyFilter` object exists, and that at least one policy targets the egress `Gateway` object or one of its routes.
* The gateway trace and the {prodname} filter trace have different trace IDs. This behavior is expected, because {service-mesh} does not propagate trace context to WebAssembly filters. Use the `x-request-id` header to correlate the two traces.
* Spans from Limitador or Authorino are displayed in traces of their own. Verify that the tracing endpoint is configured correctly. When the configuration is correct, the `wasm-shim` module propagates trace context through gRPC metadata, and the spans of both components are children of the `kuadrant-filter` trace.
