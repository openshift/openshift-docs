= Workflow identifiers and versioning

Workflow identifiers must comply with RFC 1123 DNS label standards across all deployment variants, from standalone Java applications to deployments managed by {ServerlessLogicOperatorName}.

In practice, a workflow identifier must:

* Contain only:
** Lowercase letters (a–z)
** Digits (0–9)
** Hyphens (-)
* Start with a lowercase letter or digit
* End with a lowercase letter or digit

Identifiers that do not meet these requirements may lead to deployment or runtime issues.

.Valid workflow identifiers
[source,text]
----
hello-world
customer-onboarding-flow
flow-01
----

.Invalid workflow identifiers
[source,text]
----
Hello-World (uppercase letters not allowed)
_myflow (cannot start with an underscore)
order_processing (underscores not allowed)
orderflow- (cannot end with a hyphen)
----

Ensure that the workflow identifier is consistent across all build and deployment configurations, especially when using the `gitops` profile.

The following example shows a `sw.yaml` workflow definition with a correctly configured `id`:

[#workflow_identifiers_{context}]
.Example of a valid workflow `id` configuration for a `sw.yaml` workflow definition
[source,yaml]
----
id: hello-world
version: "1.0"
specVersion: 0.8.0
name: Hello World
description: An example workflow to say Hello World
start: HelloWorld
----

where:

`id`:: The workflow identifier. Must comply with RFC 1123 DNS label standards.
`version`:: The workflow version.
`specVersion`:: The Serverless Workflow specification version.
`name`:: Optional human-readable name.
`description`:: Optional workflow description.

Two strategies are available for managing multiple versions of a workflow. {ServerlessLogicProductName} 1.39.0 introduces logical workflow versioning; if you are using 1.38.0, or building workflow images with the 1.38.0 builder image, only isolated workflow deployments is available.
The following sections explain each strategy and how the workflow `id` maps to the `SonataFlow` CR configuration.

[NOTE]
====
While the following sections show examples using the `gitops` profile, the same rules apply when working with the `preview` profile.
====

[#isolated_deployment_versioning_{context}]
== Isolated workflow deployments

In this strategy, each version is deployed as an independent workflow with a unique `id` and a corresponding `SonataFlow` CR `metadata.name`.

Assign a unique `id` to each version and maintain the relationship between deployments using a consistent naming convention.
For example:

* `hello-world-v1` implements and deploys version 1.0
* `hello-world-v2` implements and deploys version 2.0

This strategy maintains complete isolation between workflow versions, including in supporting services. For example, Data Index entries appear under separate workflow IDs for each version.

The following examples use two `sw.yaml` files for version `1.0` and `2.0` of the `Hello World` workflow:

.`sw.yaml` file for version `1.0` of the workflow (isolated deployments)
[source,yaml]
----
id: hello-world-v1
version: "1.0"
specVersion: 0.8.0
name: Hello World
description: Version 1.0 of an example workflow to say Hello World
start: HelloWorld
# rest of the workflow definition according to version 1.0
----

.`sw.yaml` file for version `2.0` of the workflow (isolated deployments)
[source,yaml]
----
id: hello-world-v2
version: "2.0"
specVersion: 0.8.0
name: Hello World
description: Version 2.0 of an example workflow to say Hello World
start: HelloWorld
# rest of the workflow definition according to version 2.0
----

where:

`id`:: In this strategy, the `id` must be unique across versions. Use a version-specific value such as `hello-world-v1` or `hello-world-v2`.
`version`:: The version of this workflow. Set to `1.0` or `2.0` respectively.
`specVersion`:: The Serverless Workflow specification version.
`name`:: Optional human-readable name for the workflow.

The examples assume the generated images are `quay.io/my-workflows/hello-world:1.0` and `quay.io/my-workflows/hello-world:2.0` respectively.

[IMPORTANT]
====
Build a separate container image for each workflow version.
====

Create the following `SonataFlow` CR files, then run `oc apply -f <filename>` to deploy each version to your cluster:

.`SonataFlow` CR for version `1.0` of the workflow (isolated deployments)
[source,yaml]
----
apiVersion: sonataflow.org/v1alpha08
kind: SonataFlow
metadata:
  name: hello-world-v1
  annotations:
    sonataflow.org/name: Hello World
    sonataflow.org/description: Version 1.0 of an example workflow to say Hello World
    sonataflow.org/version: 1.0
    sonataflow.org/profile: gitops
spec:
  podTemplate:
    container:
      image: "quay.io/my-workflows/hello-world:1.0"
  flow:
    start: HelloWorld
    # rest of the workflow definition corresponding to version 1.0
----

.`SonataFlow` CR for version `2.0` of the workflow (isolated deployments)
[source,yaml]
----
apiVersion: sonataflow.org/v1alpha08
kind: SonataFlow
metadata:
  name: hello-world-v2
  annotations:
    sonataflow.org/name: Hello World
    sonataflow.org/description: Version 2.0 of an example workflow to say Hello World
    sonataflow.org/version: 2.0
    sonataflow.org/profile: gitops
spec:
  podTemplate:
    container:
      image: "quay.io/my-workflows/hello-world:2.0"
  flow:
    start: HelloWorld
    # rest of the workflow definition corresponding to version 2.0
----

where:

`metadata.name`:: The `SonataFlow` CR Kubernetes name. Must match the workflow `id` in the `sw.yaml` or `sw.json` file.
`sonataflow.org/name`:: Optional human-readable workflow name, matching the `name` field in the `sw.yaml` or `sw.json` file.
`sonataflow.org/description`:: Optional human-readable workflow description, matching the `description` field in the `sw.yaml` or `sw.json` file.
`sonataflow.org/version`:: Must match the `version` field in the `sw.yaml` or `sw.json` file.
`spec.podTemplate.container.image`:: The image generated from the `sw.yaml` or `sw.json` file for the corresponding workflow version.
`spec.flow`:: The workflow definition for the corresponding version. In the `gitops` profile, this must match the workflow definition embedded in the container image.

[IMPORTANT]
====
If you are using {ServerlessLogicProductName} 1.38.0, or building workflow images with the 1.38.0 builder image, isolated workflow deployments is the only available strategy for creating multiple workflow versions. To use logical workflow versioning, upgrade to {ServerlessLogicProductName} 1.39.0.
====

[#logical_workflow_versioning_{context}]
== Logical workflow versioning

Starting in {ServerlessLogicProductName} 1.39.0, multiple deployments can share the same logical workflow `id`, allowing supporting services like Data Index to group versions under the same workflow lineage.

[NOTE]
====
As part of these runtime updates, REST API endpoints now include the workflow version in their path.

{ServerlessLogicProductName} 1.38.0 endpoint format:: `\http://<service-url>/<workflow-id>`
{ServerlessLogicProductName} 1.39.0+ endpoint format:: `\http://<service-url>/<workflow-id>/<version>`
====

The following examples use two `sw.yaml` files for version `1.0` and `2.0` of the `hello-world` workflow, both sharing the same `id`:

.`sw.yaml` file for version `1.0` of the workflow (logical versioning)
[source,yaml]
----
id: hello-world
version: "1.0"
specVersion: 0.8.0
name: Hello World
description: Version 1.0 of an example workflow to say Hello World
start: HelloWorld
# rest of the workflow definition according to version 1.0
----

.`sw.yaml` file for version `2.0` of the workflow (logical versioning)
[source,yaml]
----
id: hello-world
version: "2.0"
specVersion: 0.8.0
name: Hello World
description: Version 2.0 of an example workflow to say Hello World
start: HelloWorld
# rest of the workflow definition according to version 2.0
----

where:

`id`:: In this strategy, the `id` is shared across all versions. Use the same logical workflow identifier, such as `hello-world`, for every version.
`version`:: The version of this workflow. Set to `1.0` or `2.0` respectively.
`specVersion`:: The Serverless Workflow specification version.
`name`:: Optional human-readable name for the workflow.

The examples assume the generated images are `quay.io/my-workflows/hello-world:1.0` and `quay.io/my-workflows/hello-world:2.0` respectively.

[IMPORTANT]
====
In this strategy, set the `sonataflow.org/id` annotation on each `SonataFlow` CR to the shared workflow `id`. This annotation links separate CR deployments into the same logical workflow lineage, and `metadata.name` does not need to match the workflow `id`.
====

[IMPORTANT]
====
Build a separate container image for each workflow version.
====

Create the following `SonataFlow` CR files, then run `oc apply -f <filename>` to deploy each version to your cluster:

.`SonataFlow` CR for version `1.0` of the workflow (logical versioning)
[source,yaml]
----
apiVersion: sonataflow.org/v1alpha08
kind: SonataFlow
metadata:
  name: hello-world-v1
  annotations:
    sonataflow.org/id: hello-world
    sonataflow.org/name: Hello World
    sonataflow.org/description: Version 1.0 of an example workflow to say Hello World
    sonataflow.org/version: 1.0
    sonataflow.org/profile: gitops
spec:
  podTemplate:
    container:
      image: "quay.io/my-workflows/hello-world:1.0"
  flow:
    start: HelloWorld
    # rest of the workflow definition corresponding to version 1.0
----

.`SonataFlow` CR for version `2.0` of the workflow (logical versioning)
[source,yaml]
----
apiVersion: sonataflow.org/v1alpha08
kind: SonataFlow
metadata:
  name: hello-world-v2
  annotations:
    sonataflow.org/id: hello-world
    sonataflow.org/name: Hello World
    sonataflow.org/description: Version 2.0 of an example workflow to say Hello World
    sonataflow.org/version: 2.0
    sonataflow.org/profile: gitops
spec:
  podTemplate:
    container:
      image: "quay.io/my-workflows/hello-world:2.0"
  flow:
    start: HelloWorld
    # rest of the workflow definition corresponding to version 2.0
----

where:

`metadata.name`:: The `SonataFlow` CR Kubernetes name representing this workflow version deployment. In this strategy, it does not need to match the `id` in the `sw.yaml` or `sw.json` file. Do not deploy two `SonataFlow` CRs that share the same `id` and `version` combination.
`sonataflow.org/id`:: The logical workflow identifier. Must match the `id` in the `sw.yaml` or `sw.json` file and remains the same across all versions.
`sonataflow.org/name`:: Optional human-readable workflow name, matching the `name` field in the `sw.yaml` or `sw.json` file.
`sonataflow.org/description`:: Optional human-readable workflow description, matching the `description` field in the `sw.yaml` or `sw.json` file.
`sonataflow.org/version`:: Must match the `version` field in the `sw.yaml` or `sw.json` file.
`spec.podTemplate.container.image`:: The image generated from the `sw.yaml` or `sw.json` file for the corresponding workflow version.
`spec.flow`:: The workflow definition for the corresponding version. In the `gitops` profile, this must match the workflow definition embedded in the container image.

[#avoid_duplicated_deployment_{context}]
[WARNING]
====
Never deploy multiple `SonataFlow` CRs that share the exact same workflow `id` and `version` pair (for example, creating two separate CRs named `hello-world-v1` and `hello-world-v1-secondary` that both specify `sonataflow.org/id: hello-world` and `sonataflow.org/version: 1.0`).

Deploying duplicate ID and version combinations creates multiple Kubernetes services pointing to the same workflow definition, which leads to endpoint registration conflicts in supporting services such as Data Index and unpredictable runtime behavior.
====

[#workflow_resource_mapping_{context}]
== Generated Kubernetes resources and configuration mapping

Regardless of the versioning strategy, {ServerlessLogicOperatorName} applies consistent resource generation and property mapping rules when provisioning Kubernetes assets for a `SonataFlow` CR.

Deployment and Service naming::
{ServerlessLogicOperatorName} automatically creates a `Deployment` and a `Service` for each `SonataFlow` CR, deriving their names and the internal Kubernetes DNS URL from `metadata.name`.

Custom properties via ConfigMap::
To supply custom application properties to a workflow, create a `ConfigMap` named `<sonataflow-cr-name>-props` and apply it using `oc apply -f <configmap-filename>`. For example, if a `SonataFlow` CR has `metadata.name: hello-world-v1`, a `ConfigMap` named `hello-world-v1-props` automatically maps its properties to the running workflow container.
