= Understanding corosync quorum in a two-node cluster with fencing

[role="_abstract"]
A two-node {product-title} cluster with fencing (TNF) relies on two independent consensus systems: corosync, which decides which *nodes* are alive, and etcd, which decides which *etcd members* form a majority. Understanding the difference explains why a single healthy node sometimes refuses to start cluster services, and why manual recovery of corosync quorum is a last-resort procedure with strict preconditions.

== Corosync quorum and etcd quorum

* *Corosync quorum* (c-quorum) is the consensus about node membership that corosync computes from its communication rings. Pacemaker uses c-quorum as the authority for when it is safe to run cluster services: it does not start etcd or kubelet on a node that does not hold c-quorum.
* *etcd quorum* (e-quorum) is the consensus internal to etcd about which etcd members form a majority. When a node loses e-quorum, etcd goes read-only until quorum is recovered.

The two can disagree. For example, after a node failure the surviving node can lose e-quorum while still holding c-quorum; Pacemaker then fences the failed node and restarts etcd as a cluster-of-one to recover e-quorum.

== Why a single node cannot form quorum alone

In a two-node cluster, corosync runs with the `2Node` and `WaitForAll` votequorum flags. With two expected votes, quorum requires both nodes: a single node, no matter how healthy, cannot reach quorum on its own. This is a deliberate safety property, not a malfunction. If a node booted into service without its peer, and the peer later returned independently, the two nodes could each claim the etcd data set and fence each other in a loop.

As a result, when a node boots and cannot form corosync membership with its peer, it remains inert: corosync and pacemaker run, but etcd and kubelet stay stopped. You can recognize this state in the output of `pcs status --full` and `pcs quorum status`:

[source,terminal]
----
$ sudo pcs quorum status
Quorum information
------------------
Date:             Fri Oct  3 14:25:31 2025
Quorum provider:  corosync_votequorum
Nodes:            1
Node ID:          1
Ring ID:          1.16
Quorate:          No

Votequorum information
----------------------
Expected votes:   2
Highest expected: 2
Total votes:      1
Quorum:           1 Activity blocked
Flags:            2Node WaitForAll
----

`Quorate: No` with `Flags: 2Node WaitForAll` and `Activity blocked` is the expected signature of a node that is waiting for its peer. The automatic way out of this state is for the peer to come back; the manual way out, `pcs quorum unblock`, overrides the safety mechanism and is documented in xref:../installing_tnf/install-post-tnf.adoc#tnf-restoring-c-quorum-manual_install-post-tnf[Manually restoring corosync quorum after dual node power loss].
