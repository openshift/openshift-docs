= About cloud identity credential injection for virtual machines

[role="_abstract"]
Pods receive short-lived tokens in their filesystem through platform webhooks, but virtual machine (VM) guests cannot access pod files natively. `containerPath` volumes bridge this using `virtiof` filesystems to expose the `virt-launcher` pod path to the VM guest.

The credential injection workflow is as follows:

. A `ServiceAccount` is annotated with an AWS IAM role ARN.
. The platform webhook detects the annotation and injects a projected volume containing a short-lived authentication token into the `virt-launcher` pod.
. A `containerPath` volume source in the VM specification points to the injected token path in the `virt-launcher` pod.
. A `virtiofs` filesystem device in the VM specification exposes the token to the VM guest as a mounted filesystem.
. Applications inside the VM guest use the token to authenticate with cloud provider APIs.

[id="virt-supported-backing-volume-types_{context}"]
== Supported backing volume types

`containerPath` volumes support the following backing volume types:

* `ConfigMap`
* `Secret`
* `Projected`
* `DownwardAPI`
* `EmptyDir`

[id="virt-containerpath-live-migration_{context}"]
== Live migration considerations

`containerPath` volumes are compatible with live migration for the following backing volume types:

* `Secret`
* `ConfigMap`
* Sidecar-populated volumes

`EmptyDir` volumes without sidecar containers do not survive live migration.

[NOTE]
====
`containerPath` volumes are read-only from the VM guest perspective.
====
