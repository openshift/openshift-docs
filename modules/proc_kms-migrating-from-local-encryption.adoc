= Migrating from local encryption to KMS encryption

[role="_abstract"]
You can migrate from local etcd encryption to external KMS encryption to centralize key management and improve compliance. // cite:1
// cite:1 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L411-L412 - "From static encryption to KMS: keyController creates a new encryption key secret with KMS configuration"

.Prerequisites

* You have access to the cluster as a user with the `cluster-admin` role.
* You have enabled the `TechPreviewNoUpgrade` feature set to enable the `KMSEncryption` feature gate.
* Your cluster is currently using `aescbc` or `aesgcm` encryption. // cite:2
// cite:2 VERIFIED [95]: https://github.com/openshift/api/blob/9edb1b2/config/v1/types_apiserver.go#L258-L262 - EncryptionTypeAESCBC = "aescbc" and EncryptionTypeAESGCM = "aesgcm" defined as valid encryption types
* You have installed the HashiCorp Vault KMS plugin OLM Operator from the OperatorHub. // cite:3
* You have created a `VaultKMSConfig` custom resource with your KMS plugin configuration and verified that the OLM Operator has reconciled the status.
* You have created the credential secret and optional CA bundle config map in the `openshift-config` namespace.
// cite:3 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L211 - "Cluster admin installs the OLM operator for their KMS plugin provider and creates a provider-specific custom resource"

[IMPORTANT]
====
Create an etcd backup before migrating.
====

.Procedure

. Back up the current etcd encryption configuration by entering the following command:
+
[source,terminal]
----
$ oc get apiserver cluster -o yaml > apiserver-backup.yaml
----

. Edit the APIServer custom resource by entering the following command:
+
[source,terminal]
----
$ oc edit apiserver cluster
----

. Change the encryption type from `aescbc` or `aesgcm` to `KMS` and add the KMS provider reference:
+
[source,yaml]
----
apiVersion: config.openshift.io/v1
kind: APIServer
metadata:
  name: cluster
spec:
  encryption:
    type: KMS
    kms:
      type: Vault
      pluginConfig:
        apiVersion: vault.hashicorp.io/v1
        kind: VaultKMSConfig
        name: my-vault-kms
----

. Save and exit.
+
The platform runs pre-flight validation, then starts migration automatically. Migration typically takes several minutes. // cite:4
// cite:4 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L337 - "keyController runs pre-flight checks by deploying a pod with the KMS plugin to verify status and encrypt/decrypt capability before generating the first encryption key"
// cite:4 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L411-L412 - Static-to-KMS migration: keyController creates new key secret, EncryptionConfiguration contains KMS as write key and static as read key

.Verification

. Verify migration completion for the OpenShift API server by entering the following command:
+
[source,terminal]
----
$ oc get openshiftapiserver -o=jsonpath='{range .items[0].status.conditions[?(@.type=="Encrypted")]}{.reason}{"\n"}{end}'
----

. Verify migration completion for the Kubernetes API server by entering the following command:
+
[source,terminal]
----
$ oc get kubeapiserver -o=jsonpath='{range .items[0].status.conditions[?(@.type=="Encrypted")]}{.reason}{"\n"}{end}'
----

. Verify migration completion for the authentication Operator by entering the following command:
+
[source,terminal]
----
$ oc get authentication.operator.openshift.io -o=jsonpath='{range .items[0].status.conditions[?(@.type=="Encrypted")]}{.reason}{"\n"}{end}'
----
+
All outputs show `EncryptionCompleted`. // cite:5
