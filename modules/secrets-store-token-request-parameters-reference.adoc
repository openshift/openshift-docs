= Token request configuration parameters

[role="_abstract"]
You can configure Workload Identity Federation for the {secrets-store-operator} by setting parameters in the `tokenRequests` section under `spec.driverConfig.secretsStore` of the `ClusterCSIDriver` custom resource. It enables credential-free authentication to cloud provider secret stores.

The following table describes the parameters available for configuring service account token requests:

.Token request configuration parameters
[cols="2,1,3,2",options="header"]
|===
|Parameter
|Type
|Description
|Default value

|`type`
|String
|Specifies the token request management mode. Set to `Managed` to enable Workload Identity Federation with operator-managed token configuration. When omitted, the operator preserves any existing token request configuration on the `CSIDriver` object.
|Not configured by default

|`managed.audiences`
|Array of objects
|Configures the service account token projection for Workload Identity Federation. Each entry specifies an audience and optional expiration. The {secrets-store-operator} uses these tokens to authenticate to external secret management systems without storing long-lived credentials. This field is required when `type` is set to `Managed`.
|Empty array

|`managed.audiences[].audience`
|String
|Specifies the intended audience claim (`aud`) for the projected service account token. The audience must match the value expected by the cloud provider's identity federation system. Different cloud providers require different audience values. This field is required for each audience entry.
|No default value

|`managed.audiences[].expirationSeconds`
|Integer
|Specifies the token validity duration in seconds. Valid range is 600 to 315,360,000 seconds. If omitted, the platform applies a default value.
|Platform default

|===

Different cloud providers and secret management systems require specific audience values:

.Audience values by provider
[cols="2,3,3",options="header"]
|===
|Provider
|Audience value
|Description

|Azure Key Vault
|`api://AzureADTokenExchange`
|Required for Azure Active Directory Workload Identity integration

|AWS Secrets Manager
|`sts.amazonaws.com`
|Required for AWS Security Token Service (STS) integration

|Google Secret Manager
|Default service account audience
|Google Workload Identity typically uses the default service account token audience; explicit configuration is often not required

|HashiCorp Vault
|Custom audience
|The audience value configured in your Vault Kubernetes authentication backend, such as `vault.example.com` or a custom identifier

|===

The following examples demonstrate different token request configurations for various cloud providers:

.Example 1: Azure Key Vault with Workload Identity
[source,yaml]
----
apiVersion: operator.openshift.io/v1
kind: ClusterCSIDriver
metadata:
  name: secrets-store.csi.k8s.io
spec:
  driverConfig:
    driverType: SecretsStore
    secretsStore:
      tokenRequests:
        type: Managed
        managed:
          audiences:
            - audience: "api://AzureADTokenExchange"
              expirationSeconds: 3600
----

.Example 2: AWS Secrets Manager with IAM Roles for Service Accounts
[source,yaml]

apiVersion: operator.openshift.io/v1

      tokenRequests:
        type: Managed

----

.Example 3: HashiCorp Vault with Kubernetes authentication
[source,yaml]
----

  name: secrets-store.csi.k8s.io

.Example 4: Multiple token audiences for multi-cloud deployments
[source,yaml]
----
apiVersion: operator.openshift.io/v1
kind: ClusterCSIDriver
metadata:
  name: secrets-store.csi.k8s.io
spec:
  driverConfig:
    driverType: SecretsStore
    secretsStore:
      tokenRequests:
        type: Managed
        managed:
          audiences:
            - audience: "sts.amazonaws.com"
              expirationSeconds: 3600
            - audience: "api://AzureADTokenExchange"
              expirationSeconds: 3600
----

When configuring token request parameters, consider the following:

* The audience value must exactly match the value configured in your cloud provider's trust policy or identity federation configuration.
* Token requests enable the {secrets-store-operator} to obtain projected service account tokens with the specified audience claim.
* Different workloads can use different service accounts, allowing fine-grained access control through cloud provider IAM policies.
* Workload Identity Federation eliminates the need to store cloud provider credentials in {product-title}, improving security.
* You must configure your cloud provider to trust your {product-title} cluster's OIDC provider before using Workload Identity Federation.
* Multiple audience values can be specified to support multi-cloud or hybrid deployments where different external secret stores require different audiences.
