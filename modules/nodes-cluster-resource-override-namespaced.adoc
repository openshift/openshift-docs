= Project-level overcommit using the Cluster Resource Override Operator

[role="_abstract"]
You can set CPU and memory override ratios for a single project, or for a labeled subset of pods in that project, by creating a `ResourceOverride` object. A `ResourceOverride` object replaces the cluster-wide ratios for matching pods so that workloads in one project do not have to share one overcommit profile.

A project can run mixed workloads, such as batch jobs and databases. You can apply one set of ratios to pods with a given label and leave the other pods on the cluster-wide profile. The workload manifests stay unchanged.

When the admission webhook admits a new pod in an opted-in namespace, it looks for a `ResourceOverride` object in that namespace.

* If a `ResourceOverride` object matches the pod, the webhook uses that object and ignores the `ClusterResourceOverride` object named `cluster` for that pod. Unset ratio fields on the matching object are not filled in from the cluster-wide object.
* If no `ResourceOverride` object matches the pod, the webhook uses the `ClusterResourceOverride` object named `cluster`.

The webhook admits new pods only. Pods that already exist keep their current requests and limits until you recreate them.

To opt in a namespace, add the `clusterresourceoverrides.admission.autoscaling.openshift.io/enabled=true` label to the namespace. A `ResourceOverride` object does not apply in a namespace that does not have this label. Clusters that already use the cluster-wide object and this label keep that behavior. You add a `ResourceOverride` object only when a project needs different ratios.

If you omit `spec.podSelector`, or set `podSelector: {}`, the object matches every pod in the namespace. To change only some pods, set `spec.podSelector` so that unmatched pods keep the cluster-wide ratios.

If more than one `ResourceOverride` object in the namespace matches the same pod, the webhook applies the object whose name comes first in alphabetical order. The webhook records a warning event with reason `OverrideConflict` on each object that it does not apply.

You cannot create a `ResourceOverride` object in a system namespace. System namespaces are `openshift`, `kube`, and `kubernetes`, and any namespace whose name starts with `openshift-`, `kube-`, or `kubernetes-`.

Ratio fields on a `ResourceOverride` object are directly under `spec.podResourceOverride`. On the cluster-wide `ClusterResourceOverride` object, the same fields are under `spec.podResourceOverride.spec`.

Users with the `admin` or `edit` role in a project can create and manage `ResourceOverride` objects in that project. Users with the `view` role can get, list, and watch them. After you install the Cluster Resource Override Operator, the Operator creates the following aggregated cluster roles. These cluster roles are Operator-managed.

.Aggregated cluster roles for a ResourceOverride object
[cols="2,2,3",options="header"]
|===
|Cluster role
|Aggregated to
|Verbs

|`resourceoverrides-admin-edit`
|`admin` and `edit`
|`get`, `list`, `watch`, `create`, `update`, `patch`, `delete`

|`resourceoverrides-view`
|`view`
|`get`, `list`, `watch`
|===

These roles do not include `resourceoverrides/status` or `deletecollection`. If you use a custom role that does not aggregate to `admin`, `edit`, or `view`, grant the verbs that you need on `resourceoverrides` in the `autoscaling.openshift.io` API group.

For more information, see "Create a ResourceOverride object in a project".
