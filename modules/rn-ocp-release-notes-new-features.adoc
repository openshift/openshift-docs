This release adds improvements related to the following components and concepts:

[id="ocp-release-notes-ai-apps_{context}"]
== AI applications

Troubleshooting NIDS issues with an AI agent::
+
You can use the netedge toolset in the MCP server for {product-title} to diagnose Network Ingress and DNS (NIDS) issues by describing symptoms to a connected LLM client in natural language.
+
For more information, see xref:../networking/ingress_load_balancing/configuring_ingress_cluster_traffic/configuring-ingress-cluster-traffic-ingress-controller.adoc#ai-driven-networking-troubleshooting_configuring-ingress-cluster-traffic-ingress-controller[Troubleshooting NIDS issues with an AI agent].

MCP server for Red{nbsp}Hat {product-title} is generally available::
When a problem occurs on your {product-title} cluster, you want to determine exactly what is happening, so that you can fix the issue as soon as possible. The MCP server for Red{nbsp}Hat {product-title} feature provides an AI tool for this purpose to quickly and easily diagnose your {product-title} cluster.
+
New features include:

* Declarative lifecycle management through the MCP Lifecycle Operator using a single MCPServer custom resource, instead of managing multiple Kubernetes manifests or Helm charts.
* Safe, automated rollouts for MCP server version upgrades, with status and health reporting for each deployment.
* MCP gateway integration (Red Hat Connectivity Link), aggregating MCP servers behind a single endpoint with authentication and rate limiting.
* RBAC-enforced, read-only operation, restricting the server to non-mutating actions.
* Expanded toolsets, including `netedge` for Network Ingress and DNS (`NIDS`) troubleshooting, `ossm` for OpenShift Service Mesh (Kiali) mesh inspection, `tekton`, alongside the core and config toolsets.
* Support for latest (2026-07-28) MCP server specification.
+
{product-title} 4.22 introduced MCP server for Red{nbsp}Hat {product-title} as a Technology Preview feature. For 5.0, this feature is generally available.
+
For more information, see xref:../ai_applications/mcp_server/mcp-server-overview.adoc[Inspect clusters with MCP server for Red{nbsp}Hat {product-title}].

== Authentication and authorization

Advanced direct authentication fields are now generally available::
+
Advanced direct authentication fields for OIDC-based authentication are now generally available for standalone and hosted control plane (HCP) clusters. These fields, which include custom OIDC discovery URLs, CEL-based claim mapping and validation rules, and user validation rules, no longer require the `TechPreviewNoUpgrade` feature set.
+
For more information, see xref:../authentication/structured-auth-config-fields.adoc#structured-auth-config-fields[Advanced direct authentication fields].

External claims sourcing for external OIDC authentication (Technology Preview)::
+
Clusters that use external OIDC authentication can now retrieve user identity information, such as group memberships, from sources beyond the identity provider's JSON Web Token (JWT). Cluster administrators can configure external claims sources in the `Authentication` resource to fetch user attributes from endpoints such as UserInfo or Microsoft Graph APIs when JWT size limits prevent including all claim data. This feature requires the `TechPreviewNoUpgrade` feature set.

Component-scoped proxy for authentication is now available as a Technology Preview::
+
You can configure a dedicated proxy for the authentication stack to reach external identity providers instead of the cluster-wide egress proxy. Setting the `spec.proxy` field on the `Authentication` Operator resource limits proxy-based egress to the Cluster Authentication Operator and the OAuth server. This feature requires the `AuthenticationComponentProxy` feature gate, enabled by the `TechPreviewNoUpgrade` feature set.
+
For more information, see xref:../authentication/configuring-authentication-proxy.adoc#configuring-authentication-proxy[Configuring proxy settings for the authentication stack].

[id="ocp-release-notes-auto_{context}"]
== Autoscaling

Cluster autoscaler enforcement of node group minimum size::
You can configure the cluster autoscaler to keep each node group at or above the `minReplicas` value in the corresponding `MachineAutoscaler` resource, including when the cluster autoscaler considers the nodes unneeded, by setting the `enforceNodeGroupMinSize` parameter to `Enabled` in the `ClusterAutoscaler` custom resource.
+
The default value is `Disabled`. When `Disabled`, the cluster autoscaler can scale a node group below the `minReplicas` value if it considers the nodes unneeded.
+
For more information, see xref:../machine_management/applying-autoscaling.adoc#cluster-autoscaler-cr_applying-autoscaling[Cluster autoscaler resource definition].

Per-project overcommit ratios for the Cluster Resource Override Operator::
You can create a `ResourceOverride` object in a project to set CPU and memory override ratios that differ from the cluster-wide ratios. New pods in that project that have a specific label get these override ratios. New pods that do not have the label use the cluster-wide ratios. Existing pods keep their current requests and limits until you re-create them.
////
For more information, see xref:../nodes/clusters/nodes-cluster-overcommit.adoc#nodes-cluster-resource-override-namespaced_nodes-cluster-overcommit[Project-level overcommit using the Cluster Resource Override Operator].
////

Pause and restart the Verical Pod Autoscaler::
You can pause Verical Pod Autoscaler (VPA) behavior without uninstalling the Operator or removing any vertical pod autoscalers by deleting the `VerticalPodAutoscalerController` CR. You can restart the VPA by re-creating the CR.
////
For more information, see "Pausing and restarting the Vertical Pod Autoscaler Operator"	.

[id="ocp-release-notes-extensions_{context}"]
== Extensions ({olmv1})

{olmv1} uses cluster administrator permissions to manage extensions::
+
You no longer need to create a service account or configure service account permissions for each cluster extension.
+
{olmv1-first} uses the Operator Controller service account with cluster administrator permissions to install and manage extensions.
+
Use role-based access control (RBAC) and validating admission policies to control access to cluster extension resources.

Cluster extension installation and update deadlines (Technology Preview)::
+
You can set installation and update deadlines for cluster extensions in {olmv1-first} as a Technology Preview feature.
+
Use the `spec.progressDeadlineMinutes` field in a `ClusterExtension` object to specify the deadline in minutes.
+
If an installation or update exceeds the deadline, {olmv1} reports `ProgressDeadlineExceeded` in the `Progressing` status condition. This message indicates that the installation or update needs manual intervention.

Default catalog images match the cluster version::
+
{olmv1-first} selects image tags for default Operator catalogs based on the cluster version. On {product-title} 5.0 clusters, the default catalogs use the `v5.0` image tag.

== Installation and update

AI-powered update risk and status assessments::
With this release, you can use the web console to generate AI-powered guidance specific to your cluster to assess the risk of an update path or the status of an in-progress update.
+
For more information, see xref:../updating/preparing_for_updates/updating-cluster-prepare.adoc#update-assessment-ai_updating-cluster-prepare[Analyzing update risk and status using AI].

Installing a cluster on {aws-first} with a user-provisioned DNS is generally available::
You can enable a user-provisioned domain name server (DNS) instead of the default cluster-provisioned DNS solution. For example, your organization's security policies might not allow the use of public DNS services such as {aws-first} DNS. As a result, you can manage the API and Ingress DNS records in your own system rather than adding the records to the DNS of the cloud. If you use this feature, you must provision the cluster first and then provide your own DNS solution that includes records for `api.<cluster_name>.<base_domain>.` and `*.apps.<cluster_name>.<base_domain>.`.
+
Installing a cluster on {aws-short} with a user-provisioned DNS was introduced in {product-title} 4.21 with Technology Preview status. In {product-title} 5.0, it is now generally available.
+
For more information, see xref:../installing/installing_aws/ipi/installing-aws-vpc.adoc#installation-aws-enabling-user-managed-DNS_installing-aws-vpc[Enabling a user-managed DNS] and xref:../installing/installing_aws/ipi/installing-aws-vpc.adoc#installation-aws-provisioning-own-dns-records_installing-aws-vpc[Provisioning your own DNS records].

Firewall requirements when interactively generating {aws-first} install configurations::
+
With this release, if you install a cluster on {aws-first} and use the interactive installer to generate the `install-config.yaml` file, you must allow outbound access to `ec2.us-east-1.amazonaws.com` on port 443. This access is required to retrieve the list of available {aws-short} regions during the interactive installation process.
+
For more information, see xref:../installing/install_config/configuring-firewall.adoc#configuring-firewall-module_configuring-firewall[Configuring your firewall].

Installing {product-title} in {gcp-short} Dedicated regions::
You can install {product-title} in {gcp-short} Dedicated (GCD) regions by using installer-provisioned infrastructure. GCD is a sovereign cloud platform that provides {gcp-short} technology in a fully isolated environment with strict data and operational sovereignty guarantees. If you require strict data residency and operational control, you can deploy to sovereign cloud environments.
+
GCD is available from 4.22.16 and later.
+
For more information, see xref:../installing/installing_gcp/installing-gcp-dedicated.adoc#installing-gcp-dedicated[Installing a cluster on {gcp-short} Dedicated].

{rhoso} token authentication::
You can now use OpenStack Identity API v3 token authentication for clusters deployed on {rhoso}.
+
For more information, see "Defining parameters for the installation program" in "Installing a cluster on OpenStack with customizations".

Dual-stack networking on {aws-first} is generally available::
With this release, dual-stack networking support for {product-title} clusters on {aws-first} is generally available. Dual-stack networking allows clusters to use both IPv4 and IPv6 addresses for network traffic.
+
Dual-stack networking on {aws-short} was introduced in {product-title} 4.22 with Technology Preview status. In {product-title} 5.0, it is now generally available.
+
For more information, see xref:../installing/installing_aws/installation-config-parameters-aws.adoc#installation-config-parameters-aws[Installation configuration parameters for AWS].

Updated support for Nutanix AOS and Prism Central versions::
With this release, {product-title} now supports version 7.6 for Nutanix AOS and Prism Central. No changes are required for existing deployments.
+
For more information, see xref:../installing/installing_nutanix/preparing-to-install-on-nutanix.adoc#installation-nutanix-infrastructure_preparing-to-install-on-nutanix[Nutanix version requirements].

Installing a cluster using {op-system-base-full} 10 is generally available::
+
With this update, you can install a cluster using {op-system-base} version 10 as the base image for all machines in the cluster. To enable this feature, set the `osImageStream` parameter to `rhel-10` in your `install-config.yaml` file.
+
Installing a cluster using {op-system-base-full} 10 was introduced in {product-title} 4.22 with Technology Preview status. In {product-title} 5.0, it is now generally available.
+
For more information, see xref:../installing/install_config/installation-config-parameters-generic.adoc#installation-config-parameters-generic[Installation configuration parameters].

VMware Cloud Foundation 9.1 support::
+
You can install and run {product-title} {product-version} on VMware Cloud Foundation (VCF) 9.1.
+
For more information, see xref:../installing/installing_vsphere/ipi/ipi-vsphere-installation-reqs.adoc#installation-vsphere-infrastructure_ipi-vsphere-installation-reqs[VMware vSphere infrastructure requirements].

Creating cluster update assessments with OpenShift Lightspeed::
With this release, as a Technology Preview you can use the agentic OpenShift Lightspeed-driven *Cluster Update* page on the web console to check update availability, evaluate compatibility with your cluster, and produce an update assessment that you can review as you prepare for a cluster update.
+
For more information, see xref:../updating/updating_a_cluster/update-ai.adoc#updating-ai[Creating cluster update assessments with OpenShift Lightspeed].

== Machine Config Operator

Overriding storage or partition setup is generally available::
With this update, the overriding storage or partition setup feature is generally available. With this feature, you can change the installed disk partition schema, file systems, and RAID configurations for new nodes.
+
For more information, see xref:../machine_configuration/machine-configs-configure.adoc#machine-config-install-time-configs_machine-configs-configure[Overriding storage and partition setup].

Updated boot images for {aws-short} Marketplace now supported::
Updated boot images are now supported for clusters that use {aws-short} Marketplace boot images. With this feature, you can configure your cluster to update the node boot image whenever you update your cluster. By default, the boot image in your cluster is not updated along with your cluster.
+
For more information, see xref:../machine_configuration/mco-update-boot-images.adoc#mco-update-boot-images[Boot image management].

Network policy support for the Machine Config Operator::
The Machine Config Operator now has multiple network policies that control network traffic to and from the Operator and operand pods. These policies restrict traffic to only traffic that is explicitly allowed or required.

Paused machine config pools report on-cluster image build status::
With this update, a paused machine config pool reports the progress of an on-cluster custom layered image build in the machine config pool status. You can confirm that the build succeeded before you unpause the pool and roll the image out to nodes. When the affected machine config pool is paused, if the build fails or is interrupted, the nodes keep their current operating system image.
+
For more information, see xref:../machine_configuration/mco-coreos-layering.adoc#coreos-layering-configuring-on-build-paused_mco-coreos-layering[Build an on-cluster custom layered image without rolling it out].

Boot loader updates for Secure Boot clusters created on {product-title} 4.15 or earlier::
With this update, the Machine Config Operator updates the boot loader on `x86_64` and ARM nodes before it applies a new operating system image. The operator does this for clusters that were created on {product-title} 4.15 or earlier and have Secure Boot enabled. The update covers existing nodes and nodes that start from an older boot image.
+
The automatic boot loader update in {op-system} does not update a boot loader that is already installed from an older boot image. Boot images used after {product-title} 4.15.23 and 4.16 already include the current Secure Boot certificates.
+
Before this update, nodes in these clusters did not boot the new operating system image, because the installed boot loader did not trust the certificates used to sign that image.
+
As a result, those nodes can start and update to the new operating system image.

Selectable HAProxy versions on Ingress Controllers::
+
With this release, you can set `spec.haproxyVersion` on an `IngressController` custom resource to choose HAProxy 2.8 or HAProxy 3.2. Set `2.8` on {product-title} 4.22 before you update if you need Ingress Controllers to keep HAProxy 2.8. Pin HAProxy 3.2 after you update when you want a later cluster update to keep the current default. If you set a version that a target release does not support, a preflight check blocks the cluster update until you unset the field or change it to a supported version. For more information, see xref:../updating/preparing_for_updates/updating-cluster-prepare.adoc#update-preparing-haproxy-version_updating-cluster-prepare[HAProxy version changes before a cluster update] and xref:../networking/networking_operators/ingress-operator.adoc#nw-selecting-haproxy-version_configuring-ingress[Selecting an HAProxy version].

HAProxy version update to 3.2.22::
+
{product-title} {product-version} uses HAProxy 3.2.22 as the default Ingress Controller version and includes HAProxy 2.8.27 for migration. {product-title} 4.22 used HAProxy 2.8.18. Set `spec.haproxyVersion` to `2.8` if you need to defer HAProxy 3.2-specific behavior. HAProxy 2.8.27 still includes tighter request validation than HAProxy 2.8.18.
+
If Ingress Controllers use the default HAProxy 3.2.22, the following behavior changes can affect applications:
+
--
* Requests with a malformed target that does not start with `/` now receive HTTP `400` instead of being accepted.
* Requests with a comma or other disallowed characters in the `Host` header now receive HTTP `400` instead of HTTP `503` or `404`.
* Passthrough routes that use consistent-hash affinity remap backend pods one time after the update.
* Denied or redirected HTTP/1 requests no longer force `Connection: close`; keep-alive connections stay open.
* Requests that exceed header or URI size limits now return HTTP `414` or `431` instead of HTTP `400`.
* `OPTIONS` requests with an empty path keep that empty path instead of rewriting it to `/`. CORS handlers that match only `/` might stop matching.
--
+
If you pin HAProxy 2.8, Ingress Controllers run HAProxy 2.8.27. That version still rejects commas and additional disallowed characters in `Host` headers, preserves empty `OPTIONS` paths, and sanitizes inconsistent WebSocket `Upgrade` headers.
+
For the complete upstream change lists, see the link:https://www.haproxy.org/download/2.8/src/CHANGELOG[HAProxy 2.8 changelog] and the link:https://www.haproxy.org/download/3.2/src/CHANGELOG[HAProxy 3.2 changelog].

OVN-Kubernetes and CNI diagnostics toolsets for the MCP server for Red{nbsp}Hat OpenShift is generally available::

With this release, you can troubleshoot OVN-Kubernetes networking issues in {product-title} by using the `ovn-kubernetes` and `cni-diagnostics` toolsets in the Open MCP server for Red{nbsp}Hat OpenShift.

// TELCODOCS-2917
High availability for PTP boundary clocks with dual time receiver ports on Intel E810 hardware::
+
You can configure dual time receiver (TR) ports on a single Intel Westport Channel E810-XXVDA4T network interface controller (NIC) for Precision Time Protocol (PTP) Telecom Boundary Clock (T-BC) high availability.
This configuration uses the Alternate Best Master Clock Algorithm (A-BMCA) to support automatic switchover between upstream paths if the active port fails or its quality degrades.
As a result, downstream devices maintain continuous time synchronization without manual intervention during upstream path failures.
+
The `PtpConfig` custom resource (CR) uses a two-profile architecture with a time receiver profile and a time transmitter profile on separate PTP domains.
Both TR ports share the same Physical Hardware Clock (PHC), so failover relies on A-BMCA reselection rather than switching between separate clock servos.
+
For more information, see xref:../networking/advanced_networking/ptp/configuring-ptp.adoc#ptp-configuring-linuxptp-services-dual-port-bc_configuring-ptp[Configuring PTP boundary clock high availability with dual time receiver ports].

Dynamic resource allocation (DRA) improvements::
With this update, the following improvements have been made to the DRA feature:
+
* Partitionable devices with DRA is generally available. With this update, manually partitioning physical hardware into smaller, logical instances, such as Multi-Instance GPUs, to use with dynamic resource allocation is generally available.
+
For more information, see xref:../nodes/pods/nodes-pods-allocate-dra.adoc#nodes-pods-allocate-dra[Allocating GPUs to pods by using DRA].

* Consumable capacity for DRA. With this update, the consumable capacity method for DRA is available. You can share a single device, such as a GPU, among multiple independent resource claims without creating fixed partitions in advance. Each claim requests a quantity of device capacity, and the scheduler ensures that the total consumed capacity does not exceed the device's capacity.
+
As a result, workloads can use only the device capacity they need, which improves utilization of accelerators compared to exclusive allocation or predefined partitions.
+
For more information, see xref:../nodes/pods/nodes-pods-allocate-dra.adoc#nodes-pods-allocate-dra[Allocating GPUs to pods by using DRA].

* Device taints and tolerations for DRA. With this update, device taints and tolerations for DRA are available. You can use your DRA driver in a resource slice to taint individual devices, such as GPUs, so that the scheduler does not place new pods on them and can remove pods that already use the devices. Cluster administrators can apply the same effect to matching devices by creating a `DeviceTaintRule` object. Workloads tolerate those taints in a resource claim, not in the pod specification.
+
For more information, see xref:../nodes/pods/nodes-pods-allocate-dra.adoc#nodes-pods-allocate-dra[Allocating GPUs to pods by using DRA].

* Device binding conditions for DRA. With this update, device binding conditions for DRA are available. For devices that must be attached or prepared on a node before a pod starts, such as fabric-attached or network-attached accelerators, the scheduler waits until the device is ready instead of binding the pod immediately. DRA drivers declare the required readiness and failure conditions on the device. If the driver also requires the allocation to stay on the selected node, the scheduler records that node on the resource claim so that a controller can attach or prepare the device there.
+
As a result, pods that need those devices start only after the hardware is actually available on the node, which avoids failed startups caused by devices that are still being attached.
+
For more information, see xref:../nodes/pods/nodes-pods-allocate-dra.adoc#nodes-pods-allocate-dra[Allocating GPUs to pods by using DRA].

* Device health status in pod status. With this update, reporting the health of allocated DRA devices in the pod status is available. When your DRA driver reports that a device such as a GPU is unhealthy, the kubelet records that information on each container that uses the device. You can inspect the pod status to see whether an allocated device is `Healthy`, `Unhealthy`, or `Unknown`. If the driver provides extra detail, the status can also include a message that explains the health result.
+
As a result, you can determine whether a failing pod is caused by the application or by the underlying device, without relying only on application logs.
+
For more information, see xref:../nodes/pods/nodes-pods-allocate-dra.adoc#nodes-pods-allocate-dra[Allocating GPUs to pods by using DRA].
