= About the ClusterResourceOverrideBinding object

[role="_abstract"]
You can assign different `ClusterResourceOverride` profiles to specific namespaces and pods by using a `ClusterResourceOverrideBinding` object. By using a binding you can run different workloads that have different overcommit ratios based on their resource guarantees.

In the default single-profile mode, all namespaces labeled with `clusterresourceoverrides.admission.autoscaling.openshift.io/enabled: "true"` share the same overcommit ratios defined in the `cluster` profile. Using the same ratios can be limiting in multi-tenant environments for a number of reasons, including the following reasons:

* Production namespaces need conservative overcommit to maintain SLAs
* Development and batch namespaces can use aggressive overcommit to maximize density
* Different teams require different resource policies

A cluster administrator can use a `ClusterResourceOverrideBinding` to perform the following tasks:

* Create multiple named `ClusterResourceOverride` profiles with different ratios.
* Assign each profile to specific namespaces using label selectors.
* Filter which pods receive the override using optional pod label selectors.
* Avoid conflicts by using hierarchical label-matching rules.

A `ClusterResourceOverrideBinding` CR consists of:

* The name of the `ClusterResourceOverride` profile to apply.
* A label selector that matches the namespaces where this binding applies.
* An optional label selector that matches specific pods within those namespaces. When omitted, all pods in matching namespaces are mutated.

If a namespace matches multiple bindings, the binding that matches the smallest set of namespaces is used. If the specificity is equal, the alphabetically first binding name is applied. A warning event is logged when conflicts are detected.
