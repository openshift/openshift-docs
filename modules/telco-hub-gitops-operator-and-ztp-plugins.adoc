= GitOps Operator and {ztp}

[role="_abstract"]
GitOps Operator and {ztp} provide a GitOps-based infrastructure for managing cluster deployment and configuration in {product-title}. 

You can maintain cluster definitions as a declarative state in Git and apply `ClusterInstance` custom resources (CRs) to the hub cluster for rendering as installation CRs.

New in this release::
* The `clusters` and `policies` ArgoCD `Application` resources, which manage `ClusterInstance` and policy definitions for the fleet of managed clusters, use a least-privilege `ClusterRole` instead of a `cluster-admin` `ClusterRoleBinding`.
* The hub reference configuration demonstrates policy generation by using `PolicyGenerator` CRs, replacing the deprecated `PolicyGenTemplate` CRs.
* A new `extra-manifests-policy` policy is included to keep `MachineConfig` resources on managed clusters synchronized with the `ClusterInstance` `extraManifestsRefs` ConfigMaps used during installation.
* You can replace a failed control plane node on a managed cluster by using the `ClusterInstance` CR.

Description::
GitOps Operator and {ztp} provide a GitOps-based infrastructure for managing cluster deployment and configuration.
Cluster definitions and configurations are maintained as a declarative state in Git.
You can apply `ClusterInstance` custom resources (CRs) to the hub cluster where the `SiteConfig` Operator renders them as installation CRs.
In earlier releases, a {ztp} plugin supported the generation of installation CRs from `SiteConfig` CRs.
This plugin is now deprecated.
A separate {ztp} plugin is available to enable automatic wrapping of configuration CRs into policies based on the `PolicyGenerator` or the `PolicyGenTemplate` CRs.
`PolicyGenTemplate` CRs are deprecated, and the hub reference configuration uses `PolicyGenerator` CRs to generate policies.
+
You can deploy and manage multiple versions of {product-title} on managed clusters by using the baseline reference configuration CRs.
You can use custom CRs alongside the baseline CRs.
To maintain multiple per-version policies simultaneously, use Git to manage the versions of the source and policy CRs by using the `PolicyGenerator` or the `PolicyGenTemplate` CRs.
+
Grant the ArgoCD application controller service account only the permissions required for the resources it manages, rather than `cluster-admin`.
The `clusters` and `policies` `Application` resources use a dedicated `ClusterRole` that is aggregated into the {rh-rhacm} `cluster-manager-admin` `ClusterRole` and grants only the permissions needed to manage `ClusterInstance` CRs, together with the secret access already provided through `cluster-manager-admin`.
This least-privilege model applies only to the `clusters` and `policies` `Application` resources.
The `hub-config` `Application`, which synchronizes the hub cluster's own reference configuration, is unaffected.


Limits and requirements::
* To ensure consistent and complete cleanup of managed clusters and their associated resources during cluster or node deletion, you must configure ArgoCD to use background deletion mode.

Engineering considerations::
* To avoid confusion or unintentional overwrite when updating content, use unique and distinguishable names for custom CRs in the `source-crs` directory and extra manifests.
* Keep reference source CRs in a separate directory from custom CRs.
This facilitates easy update of reference CRs as required.
* To help with multiple versions, keep all source CRs and policy creation CRs in versioned Git repositories to ensure consistent generation of policies for each {product-title} version.
* If the `clusters` or `policies` `Application` resources need to manage additional CR kinds, add rules to the `hub-rds-cluster-role` `ClusterRole` rather than widening the `ClusterRoleBinding`.
The `rbac.authorization.k8s.io/aggregate-to-ocm-cluster-manager-admin: "true"` label on this `ClusterRole` automatically aggregates any added rules into the {rh-rhacm} `cluster-manager-admin` `ClusterRole` used by the ArgoCD application controller.
* The `extra-manifests-policy` policy references the same `MachineConfig` content as the `ClusterInstance` `extraManifestsRefs` ConfigMaps used during day-0 installation.
Maintaining a single copy of the `MachineConfig` resources for both day-0 installation and day-2 policy enforcement keeps managed cluster `MachineConfig` resources up to date and avoids drift between the installation-time and policy-enforced configurations.
If you use custom day-2 patches for `MachineConfig` resources, remove them and make updates directly in the extra-manifest ConfigMaps to avoid conflicts with this policy.
