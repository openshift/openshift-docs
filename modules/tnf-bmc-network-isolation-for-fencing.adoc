= BMC network isolation for fencing

[role="_abstract"]
Fencing in a two-node {product-title} cluster with fencing relies on each node being able to power off its peer through the peer's baseboard management controller (BMC). The BMC network must be isolated from the cluster network to prevent a single network failure from disabling both cluster communication and fencing simultaneously.

== Why network isolation is required

Pacemaker uses STONITH (Shoot The Other Node In The Head) to fence an unresponsive node by sending a Redfish power-off command to its BMC. If the fencing network shares the same physical path as the cluster network, a network failure that causes a split-brain condition also prevents the surviving node from fencing the failed node.

[IMPORTANT]
====
Both the TNF design specification and Pacemaker upstream documentation require that fencing devices do not rely on the same network as cluster communication. Network isolation is mandatory, not optional.
====

== VLAN separation

Use VLAN separation to isolate BMC traffic from cluster traffic. The BMC interfaces are typically on a dedicated management VLAN.

Configure firewall and routing rules to allow each node to reach the BMC of its peer node across VLANs. The required traffic flows are:

* Node 1 passes through TOR Switch 2 to reach the Node 2 BMC on the management VLAN.
* Node 2 passes through TOR Switch 1 to reach the Node 1 BMC on the management VLAN.

== Cross-cabling for fencing resilience

In the recommended topology, each node's BMC connects to the TOR switch on the opposite side of the cluster. This cross-cabling provides an additional layer of resilience:

* If TOR Switch 1 fails, Node 2 can still fence Node 1 because the Node 1 BMC is connected to TOR Switch 2, which is still operational.
* If TOR Switch 2 fails, Node 1 can still fence Node 2 because the Node 2 BMC is connected to TOR Switch 1, which is still operational.

[NOTE]
====
A BMC has a single network interface. Dual-path redundancy to the BMC itself is not possible. Cross-cabling to the opposite switch is the recommended mitigation.
====

[NOTE]
====
A direct BMC-to-BMC crossover cable between the two nodes is not recommended because it removes external management access to the BMC. External BMC access is required for bare-metal provisioning and out-of-band operations.
====
