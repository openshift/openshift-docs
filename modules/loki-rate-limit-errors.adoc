= Troubleshoot Loki rate limit errors

[role="_abstract"]
Resolve Loki ingestion rate limit errors when log volume persistently exceeds the configured limits for your LokiStack deployment.

If the Log Forwarder API forwards logs to Loki at a rate that exceeds the configured ingestion limit, Loki generates rate limit (`429`) errors. Vector retries requests that receive a 429 response. If the rate limit persists over time, Vector might lose log records.

Rate limit errors can occur during normal operation and might not require action. For example, when you first add {logging} to a cluster that already has logs, or after an incident where the collector was temporarily stopped, rate limit errors might occur while the collector processes the backlog. If the rate of new logs is lower than the rate limit, the system recovers without intervention.

If rate limit errors persist continuously, the log ingestion rate exceeds the LokiStack ingestion rate limit, and you must take action.

[IMPORTANT]
====
The `LokiStack` CR is not available on Grafana-hosted Loki. This procedure does not apply to Grafana-hosted Loki servers.
====

.Prerequisites

* You have administrator permissions.
* You have configured the Log Forwarder API to forward logs to Loki.
* The collector logs show `429 Too Many Requests` errors. For example:
+
[source,text]
----
2023-08-25T16:08:49.301780Z  WARN sink{component_kind="sink" component_id=default_loki_infra component_type=loki component_name=default_loki_infra}: vector::sinks::util::retries: Retrying after error. error=Server responded with an error: 429 Too Many Requests internal_log_rate_limit=true
----

.Procedure

. Run the following query in the OpenShift web console under *Observe* -> *Metrics* to confirm that rate limiting is active and to discover the log tenants that the rate limit affects:
+
[source,promql]
----
sum by (tenant, reason) (rate(loki_discarded_samples_total[2m]))
----
+
A nonzero result with `reason="RateLimit"` confirms that rate limiting is active. Monitor the metric over time to check whether the situation resolves on its own. If the result returns to zero, no further action is necessary.

. If rate limiting persists, reduce the volume of logs sent to LokiStack before adjusting the ingestion limits:
+
--
* Apply input rate limits to containers that produce excessive logs.
* Use drop filters to discard log records that are not required.
--
+
For more information, see xref:../optimize/fine-tune-log-forwarding.adoc#fine-tune-log-forwarding[Fine-tune log forwarding] and xref:../configure/configure-filters.adoc#configure-filters[Configure filters].

. If reducing log volume is not enough, update the `ingestionBurstSize` and `ingestionRate` fields in the `LokiStack` CR:
+
[NOTE]
====
Increasing the ingestion rate limit increases resource usage in the LokiStack distributor pods. Before increasing these values, verify that the nodes where LokiStack pods run have enough CPU and memory available.
====
+
To find an appropriate value for `ingestionRate`, run the following query in the OpenShift web console under *Observe* -> *Metrics* to measure the actual ingestion rate per tenant:
+
[source,promql]
----
sum by (tenant) (rate(loki_distributor_bytes_received_total[5m]))
----
+
Use the result, in bytes per second, as a baseline. Convert to MB and set `ingestionRate` to at least that value.
+
[source,yaml]
----
apiVersion: loki.grafana.com/v1
kind: LokiStack
metadata:
  name: logging-loki
  namespace: openshift-logging
spec:
  limits:
    global:
      ingestion:
        ingestionBurstSize: 16
        ingestionRate: 8
# ...
----

`spec.limits.global.ingestion.ingestionBurstSize`::
  The maximum local rate-limited sample size per distributor replica, in MB. This value is a hard limit. Set this value to at least the maximum size expected in a single push request. Loki rejects requests that exceed this value.

`spec.limits.global.ingestion.ingestionRate`::
  The maximum ingestion rate per second across all distributor replicas, in MB. This is a soft limit. When the log rate exceeds the limit, rate limit errors occur, but Vector retries the request. If the average rate is lower than the limit, the system recovers automatically.
