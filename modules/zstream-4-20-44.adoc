== Fixed issues

* Before this update, on {hcp} clusters where the management cluster required a proxy for outbound internet access, the `Konnectivity` proxy sidecar containers did not receive the management cluster proxy environment variables such as `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY`. As a consequence, cloud API calls to {aws-first}, {azure-first}, or {ibm-cloud-name} endpoints made through the direct cloud API bypass path failed with TLS handshake timeouts. With this release, management cluster proxy environment variables are propagated to the `Konnectivity` sidecar containers when the direct cloud API connection feature is enabled. As a result, cloud API calls succeed through the proxy. (link:https://issues.redhat.com/browse/OCPBUGS-100104[OCPBUGS-100104])

* Before this update, the machine controller in the Hosted Cluster Config Operator (HCCO) included non-routable ovn-kubernetes routes in the node network configuration. As a consequence, the machine controller caused networking conflicts and routing issues. With this release, non-routable routes are filtered out during configuration. As a result, networking conflicts are resolved. (link:https://issues.redhat.com/browse/OCPBUGS-122206[OCPBUGS-122206])

* Before this update, the `kube-apiserver-check-endpoints` container generated a TLS certificate for the `check-endpoint` service on port `17697` with a validity of only 1 second. As a consequence, the certificate expired almost immediately after generation, which differed from previous {product-title} versions where the certificate was valid for 1 month. With this release, the `kube-apiserver-check-endpoints` container generates certificates with an appropriate validity period. As a result, the `check-endpoint` service certificate remains valid for the expected duration, consistent with previous releases. (link:https://issues.redhat.com/browse/OCPBUGS-127411[OCPBUGS-127411])

* Before this update, when two EgressIP custom resources (CRs) used the same IP address and the OVN-Kubernetes control-plane pod restarted or a node rebooted, the IP address was incorrectly assigned to more than one egress node. As a consequence, multiple egress nodes shared the same IP address, which caused unpredictable routing behavior. With this update, OVN-Kubernetes ensures that only the first assigned IP address is re-assigned to an egress node, while duplicate assignments are prevented. As a result, only one egress node is assigned the IP address defined in the EgressIP CR, preventing address conflicts. (link:https://issues.redhat.com/browse/OCPBUGS-129457[OCPBUGS-129457])

* Before this update, when you removed failure domains from the infrastructure specification, the {vmw-first} Problem Detector (VPD) logged errors about failure domain labels missing from nodes. As a consequence, VPD logged warnings that were not relevant. With this release, VPD improves processing logic for failure domain changes in the infrastructure specification. As a result, these unnecessary warnings do not appear. (link:https://issues.redhat.com/browse/OCPBUGS-130578[OCPBUGS-130578])

* Before this update, {vmw-first} machine reconciliation made redundant vCenter API calls and repeated operations. As a consequence, heavy API load, duplicate tasks, and slower provisioning in large clusters occurred. With this release, virtual machine (VM) state and tag lookups are cached, queries are batched, and task references are retained. As a result, provisioning is more reliable and vCenter load is reduced. (link:https://issues.redhat.com/browse/OCPBUGS-130608[OCPBUGS-130608])
