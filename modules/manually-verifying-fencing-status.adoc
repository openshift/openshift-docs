= Manually verifying fencing status

[role="_abstract"]
If the `fencing_validator` script is not available, or you need to investigate further after the script reports a failure, you can manually verify the fencing and quorum state of a two-node {product-title} cluster with fencing (TNF) by running `pcs` and `systemctl` commands directly on a control plane node.

.Prerequisites

* You have administrative access to the control plane nodes.
* You can connect to the nodes by using SSH.

.Procedure

. Verify that fencing is enabled at the cluster level by running the following command:
+
[source,terminal]
----
$ sudo pcs property show stonith-enabled
----
+
Example output when fencing is enabled:
+
[source,terminal]
----
Cluster Properties:
 stonith-enabled: true
----
+
[IMPORTANT]
====
If this command returns `stonith-enabled: false`, Pacemaker does not fence failed nodes under any circumstances, regardless of how the fencing devices themselves are configured. Someone might have disabled fencing intentionally for maintenance or debugging. Confirm no maintenance window is active before re-enabling it by running `sudo pcs property set stonith-enabled=true`.
====

. Check the status of the configured fencing devices by running the following command:
+
[source,terminal]
----
$ sudo pcs stonith status
----
+
Example output when both fencing devices are healthy:
+
[source,terminal]
----
  * master-0_redfish    (stonith:fence_redfish):     Started master-1
  * master-1_redfish    (stonith:fence_redfish):     Started master-0
----
+
Example output when the fencing devices have failed to start:
+
[source,terminal]
----
  * master-0_redfish    (stonith:fence_redfish):     Stopped
  * master-1_redfish    (stonith:fence_redfish):     Stopped

Failed Resource Actions:
  * master-0_redfish start on master-0 returned 'error' at Fri Oct 16 14:20:15 2026 after 2025ms
----
+
A fencing device that is `Stopped` cannot fence its target node, even if `stonith-enabled` is `true`. For how to interpret this, see "Why fencing might not occur".

. Review the fencing history to confirm whether a node was already fenced by running the following command:
+
[source,terminal]
----
$ sudo pcs stonith history show
----
+
Example output when no fencing has occurred:
+
[source,terminal]
----
0 events found
----
+
Example output after a node was fenced:
+
[source,terminal]
----
reboot of master-1: delegate=master-0, client=stonith_admin.12345, origin=master-0, completed='2026-10-16 14:22:03 +00:00'
1 event found
----
+
Use this output to distinguish between fencing that never triggered, which points to a configuration problem, and fencing that already completed, which means the cluster should proceed with automated recovery.

. Check corosync cluster quorum by running the following command:
+
[source,terminal]
----
$ sudo pcs quorum status
----
+
Example output when the cluster has quorum:
+
[source,terminal]
----
Quorum information
------------------
Date:             Fri Oct 16 14:20:00 2026
Quorum provider:  corosync_votequorum
Nodes:            2
Node ID:          1
Ring ID:          1.12
Quorate:          Yes

Votequorum information
----------------------
Expected votes:   2
Highest expected: 2
Total votes:      2
Quorum:           1
Flags:            2Node Quorate WaitForAll
----
+
Example output when the cluster has lost quorum:
+
[source,terminal]
----
Quorum information
------------------
Date:             Fri Oct 16 14:22:00 2026
Quorum provider:  corosync_votequorum
Nodes:            2
Node ID:          1
Ring ID:          1.13
Quorate:          No

Votequorum information
----------------------
Expected votes:   2
Highest expected: 2
Total votes:      1
Quorum:           2 Activity blocked
Flags:            2Node WaitForAll
----
+
[NOTE]
====
`Quorate` reports corosync-level cluster quorum, which is separate from etcd quorum. Pacemaker cannot schedule fencing or recover resources while corosync quorum is lost (`Quorate: No`), even if etcd itself still reports its members as healthy. If both control plane nodes lost power and only one can be restarted, corosync quorum does not recover automatically. See xref:../installing_tnf/install-post-tnf.adoc#installation-manual-recovering-when-auto-recovery-is-unavail_install-post-tnf[Manually recovering from a disruption event when automated recovery is unavailable] to restore it.
====

. Check whether the cluster daemons are running by running the following command:
+
[source,terminal]
----
$ sudo systemctl status corosync pacemaker pcsd
----
+
Example output when all daemons are running:
+
[source,terminal]
----
● corosync.service - Corosync Cluster Engine
     Active: active (running)
● pacemaker.service - Pacemaker High Availability Cluster Manager
     Active: active (running)
● pcsd.service - PCS GUI and remote configuration interface
     Active: active (running)
----
+
If `corosync`, `pacemaker`, or `pcsd` is not `active (running)`, Pacemaker cannot evaluate fencing or quorum on that node, regardless of how `stonith-enabled` or the fencing devices are configured. Restart the affected daemon, for example by running `sudo systemctl restart pacemaker`, then repeat the previous checks.
