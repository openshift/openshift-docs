= Preparing the AWS environment for BGP peering

[role="_abstract"]
Before you can configure BGP Cloud Connector on your cluster, you must prepare the supporting {aws-short} infrastructure.
This preparation ensures the BGP Cloud Connector discovers and peers with an {aws-short} Route Server that already exists.

.Prerequisites

* You have an {product-title} cluster running on {aws-short} with an existing VPC.
* You have an {aws-short} IAM user that you use to perform this setup.

.Procedure

. Get the OpenID Connect (OIDC) provider and {aws-short} account ID for the cluster by entering the following commands:
+
[source,terminal,subs="attributes+"]
----
$ OIDC_PROVIDER=$(oc get authentication cluster -o jsonpath='{.spec.serviceAccountIssuer}' | sed 's|https://||')
----
+
[source,terminal]
----
$ AWS_ACCOUNT_ID=$(aws sts get-caller-identity --query "Account" --output text)
----

. Create an AWS IAM permission policy for the BGP Cloud Connector Operator.
+
.. Create the permission policy document file by entering the following command:
+
[source,terminal]
----
$ cat <<EOF > operator-permission-policy.json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "sts:GetCallerIdentity",
      "ec2:DescribeRouteServers",
      "ec2:DescribeRouteServerEndpoints",
      "ec2:DescribeSubnets",
      "ec2:DescribeRouteServerPeers",
      "ec2:CreateRouteServerPeer",
      "ec2:DeleteRouteServerPeer",
      "ec2:CreateTags",
      "ec2:DescribeInstances",
      "ec2:ModifyNetworkInterfaceAttribute"
    ],
    "Resource": "*"
  }]
}
EOF
----
+
.. Create the IAM permission policy by entering the following command:
+
[source,terminal]
----
$ POLICY_ARN=$(aws iam create-policy \
    --policy-name bgp-cloud-connector-operator-policy \
    --policy-document file://operator-permission-policy.json \
    --query 'Policy.Arn' --output text)
----

. Create an {aws-short} IAM role for the BGP Cloud Connector Operator:
+
.. Create the trust policy document for the Operator role by entering the following command:
+
[source,terminal]
----
$ cat <<EOF > operator-trust-policy.json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Federated": "arn:aws:iam::${AWS_ACCOUNT_ID}:oidc-provider/${OIDC_PROVIDER}"
    },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "${OIDC_PROVIDER}:sub": "system:serviceaccount:bgp-cloud-connector:openshift-bgp-cloud-connector-controller-manager"
      }
    }
  }]
}
EOF
----
+
.. Create the IAM role by using the trust policy by entering the following command:
+
[source,terminal]
----
$ aws iam create-role --role-name bgp-cloud-connector-operator \
    --assume-role-policy-document file://operator-trust-policy.json
----
+
.. Attach the permission policy to the IAM role by entering the following command:
+
[source,terminal]
----
$ aws iam attach-role-policy \
    --role-name bgp-cloud-connector-operator \
    --policy-arn ${POLICY_ARN}
----

. Create a dedicated security group for BGP traffic in your cluster's VPC by entering the following command:
+
[source,terminal]
----
BGP_SG_ID=(aws ec2 create-security-group \
    --group-name "bgp-peering-sg" \
    --description "Security group for BGP Cloud Connector peering traffic" \
    --vpc-id ${vpc_id} \
    --query 'GroupId' --output text)
----
+
Replace `<vpc_id>` with the ID of the VPC of the cluster.

. Add rules to the security group to allow the following BGP traffic and workload traffic patterns. You can add any ports to the security group that your VMs or pods on the CUDN need for traffic. You can edit this security group at a later stage.
* TCP Ingress/Egress on port `179` for bidirectional BGP traffic.
* TCP/UDP Ingress `32768-60999`, because bidirectional traffic originating from a VM might enter the cluster through a different compute node than the bidirectional traffic exits.
+
[source,terminal]
----
$ aws ec2 authorize-security-group-ingress --group-id ${BGP_SG_ID} --ip-permissions '[
  {"IpProtocol": "tcp", "FromPort": 179, "ToPort": 179, "IpRanges": [{"CidrIp": "0.0.0.0/0", "Description": "BGP"}]},
  {"IpProtocol": "tcp", "FromPort": 32768, "ToPort": 60999, "IpRanges": [{"CidrIp": "0.0.0.0/0", "Description": "Ephemeral"}]},
  {"IpProtocol": "udp", "FromPort": 32768, "ToPort": 60999, "IpRanges": [{"CidrIp": "0.0.0.0/0", "Description": "Ephemeral"}]}
]'
----
+
[source,terminal]
----
$ aws ec2 authorize-security-group-egress --group-id ${BGP_SG_ID} --ip-permissions '[
  {"IpProtocol": "tcp", "FromPort": 179, "ToPort": 179, "IpRanges": [{"CidrIp": "0.0.0.0/0", "Description": "BGP"}]}
]'
----
+
[NOTE]
====
If you plan to use Bidirectional Forwarding Detection (BFD), repeat the commands to allow the appropriate UDP control traffic ports,such as UDP port `3784`. Restrict the `--cidr` range to your specific Route Server endpoint subnets if required by the security policies of your organization.
====

. Create one or more new {product-rosa} machine pools that include the BGP security group and the required BGP router label. Repeat for each machine pool:
+
[source,terminal]
----
$ rosa create machinepool \
    --cluster <cluster_name> \
    --name bgp-workers \
    --additional-security-group-ids ${BGP_SG_ID} \
    --labels "bgp_router=true" \
    --instance-type <instance_type> \
    --replicas 2
----
+
where:
+
--
`<cluster_name>`:: Specifies the name of the cluster
`bgp-workers`:: Specifies the name of the new machine pool dedicated to BGP workloads.
`--additional-security-group-ids`:: Attaches the BGP security group created in step 1 to all worker nodes provisioned in this machine pool.
`--labels "bgp_router=true"`:: Automatically labels all compute nodes in this machine pool to participate in BGP.
`<instance_type>:: Specifies the {aws-short} instance type of the compute nodes.
`--replicas 2`:: Specifies the number of compute nodes the machine pool should have.

. Verify that the new machine pool was created with the additional security group and label by entering the following command:
+
[source,terminal]
----
$ rosa describe machinepool --cluster{CLUSTER_NAME} bgp-workers
----

. Confirm that the compute nodes provisioned by the machine pool inherit the `bgp_router=true` label:
+
[source,terminal]
----
$ oc get nodes -l bgp_router=true
----

. Create an {aws-short} Route Server by entering the following command:
+
[source,terminal]
----
$ aws ec2 create-route-server --amazon-side-asn <asn>
----
+
Replace `<asn>` with the Border Gateway Protocol (BGP) Autonomous System Number (ASN) that you want the Route Server to use.
Note the `RouteServerId` value in the command output that is required in a later step.
In the example that follows, the ID is `rs-0abc123456789abcd`.
+
[source,terminal]
----
{
   "RouteServer": {
       "RouteServerId": "rs-0abc123456789abcd",
       "AmazonSideAsn": 65100,
       "State": "pending",
       "PersistRoutes": "disable",
       "SnsNotificationsEnabled": false
   }
}
----

. Associate the Route Server with the VPC of the cluster by entering the following command:
+
[source,terminal]
----
$ aws ec2 associate-route-server --route-server-id <route_server_id> \
   --vpc-id <vpc_id>
----
+
where:
+
`<route_server_id>`:: Specifies the Route Server ID from an earlier step.
`<vpc_id>`:: Specifies the ID of the VPC of the cluster.

. Find the private subnets used by the compute nodes of the cluster by entering the following command:
+
[source,terminal]
----
$ rosa list machinepools --cluster <cluster_name>
----
+
Replace `cluster_name` with the name of the cluster.
+
[NOTE]
====
From the output of the command, ignore any duplicate subnet IDs in the `SUBNET` column
====

. Create Route Server endpoints, two per subnet, by entering the following command.
Do this task for each private subnet that contains BGP-enabled compute nodes.
+
[source,terminal]
----
$ aws ec2 create-route-server-endpoint --route-server-id <route_server_id> \
   --subnet-id <subnet_id> && \
   aws ec2 create-route-server-endpoint --route-server-id <route_server_id> \
   --subnet-id <subnet_id>
----
+
Replace `<route_server_id>` with the ID of your Route Server.
+
Replace `<subnet_id>` with the ID of the subnet. Repeat this command for each private subnet that contains BGP-enabled compute nodes.
+
[NOTE]
====
{aws-short} allows a maximum of two Route Server endpoints per subnet.
====

. Enable route propagation from the Route Server to the relevant VPC route tables.
+
.. Identify the route tables associated with your VPC by entering the following command:
+
[source,terminal]
----
$ aws ec2 describe-route-tables \
  --filters "Name=vpc-id,Values=<vpc_id>" \
  --query "RouteTables[].{RouteTableId:RouteTableId, Subnets:Associations[].SubnetId}" \
  --output table
----
+
Replace `<vpc_id>` with the ID of the VPC for your cluster.
+
.. Enable route propagation for each required route table by entering the following command:
+
[source,terminal]
----
$ aws ec2 enable-route-server-propagation --route-server-id <route_server_id> \
  --route-table-id <route_table_id>
----
+
where:
+
--
`<route_server_id>`:: Specifies the ID of your Route Server.
`<route_table_id>`:: Specifies the ID of a route table identified in an earlier step.
--
+
Repeat this command for all of the following route tables:
+
* Compute node subnets (Minimum): Every route table associated with the private subnets containing your compute nodes.
* External connectivity subnets (If applicable): Any route table associated with subnets that host network interfaces for external connectivity mechanisms into the VPC, such as Transit Gateway ENIs.

.Verification

. Confirm that the network ACLs for both the compute node subnet and the Route Server endpoint subnet permit this traffic.
This is required because network ACLs are stateless and apply in addition to security groups.
+
[source,terminal]
----
$ aws ec2 describe-network-acls --filters \
   "Name=association.subnet-id,Values=<subnet_id>" --query \
   "NetworkAcls[].Entries"
----
+
Replace `<subnet_id>` with the ID of the compute node subnet. Repeat the command for the Route Server endpoint subnet.
+
In the output, confirm that both the inbound and outbound rule sets include an `Allow` entry for TCP port `179` between the two subnets' CIDR blocks.
+
[IMPORTANT]
====
Network ACL rules are evaluated in ascending order by rule number, and the first matching rule wins.
A `Deny` rule with a lower rule number than your `Allow` rule blocks the traffic even though an `Allow` rule exists further down the list.
If your VPC uses the default network ACL, all traffic is allowed by default and no further action is needed.
====
