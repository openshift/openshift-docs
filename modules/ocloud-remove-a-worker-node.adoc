= Remove a worker node from a provisioned cluster

[role="_abstract"]
To reduce compute capacity, you can remove a worker node from a multi-node cluster. When you update the `ProvisioningRequest` CR, the O-Cloud Manager coordinates the drain, resource cleanup, and hardware deallocation automatically.

The following example scales a cluster from 3 workers to 2 workers by creating new `ConfigMap` CR and `ClusterTemplate` CR versions, and then updating the `ProvisioningRequest` CR to remove the worker node entry. Because `ClusterTemplate` CRs and their referenced `ConfigMap` CRs are immutable after validation, each configuration change requires new versions of these resources.

[NOTE]
====
Only worker nodes can be removed. Attempting to remove a control-plane node is rejected by the O-Cloud Manager. Node removal and upgrade operations cannot run concurrently on the same cluster.
====

.Prerequisites

* The cluster is fully provisioned with `ClusterProvisioned=Completed` status on the `ProvisioningRequest` CR.
* No upgrade operation is in progress on the cluster.

.Procedure

. Create a `ConfigMap` CR that defines the cluster instance defaults, with the target `role: worker` entry removed. The following example scales from 3 workers to 2 workers:
+
[source,yaml]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: clusterinstance-defaults-v3
  namespace: <template_namespace>
data:
  clusterinstance-defaults: |
    nodes:
      - role: master
        bootMode: UEFI
        nodeNetwork:
          interfaces:
            - name: eno1
              label: boot-interface
      - role: master
        bootMode: UEFI
        nodeNetwork:
          interfaces:
            - name: eno1
              label: boot-interface
      - role: master
        bootMode: UEFI
        nodeNetwork:
          interfaces:
            - name: eno1
              label: boot-interface
      - role: worker
        bootMode: UEFI
        nodeNetwork:
          interfaces:
            - name: eno1
              label: boot-interface
      - role: worker
        bootMode: UEFI
        nodeNetwork:
          interfaces:
            - name: eno1
              label: boot-interface
----
+
* `<template_namespace>` specifies the namespace where you store the `ClusterTemplate` CR and associated resources.
* `metadata.name` uses a new name, for example, `v3`, to differentiate it from the original `ConfigMap` CR. This preserves the previous configuration for rollback.
* The ConfigMap now contains 2 worker node entries instead of 3.

. Create a new `ClusterTemplate` CR version that references the reduced `ConfigMap` CR, such as the following example:
+
[source,yaml]
----
apiVersion: clcm.openshift.io/v1alpha1
kind: ClusterTemplate
metadata:
  name: <template_name>.v4-Y-Z-3
  namespace: <template_namespace>
spec:
  name: <template_name>
  version: v4-Y-Z-3
  release: "4.Y.Z"
  templateDefaults:
    clusterInstanceDefaults: clusterinstance-defaults-v3
    policyTemplateDefaults: policytemplate-defaults-v1
    hwMgmtDefaults:
      nodeGroupData:
        - name: master
          role: master
          resourceSelector:
            server-type: master
        - name: worker
          role: worker
          resourceSelector:
            server-type: worker
----
+
* `spec.templateDefaults.clusterInstanceDefaults` references the reduced `ConfigMap` CR that excludes the removed worker node entry.

. Apply the new `ConfigMap` CR and `ClusterTemplate` CR to the hub cluster, or commit them to the GitOps repository and wait for ArgoCD to synchronize them.

. Verify that the new `ClusterTemplate` CR passes validation by running the following command:
+
[source,terminal]
----
$ oc get clustertemplates.clcm.openshift.io <template_name>.v4-Y-Z-3 -n <template_namespace>
----
+
The `STATE` column must show `Completed` before proceeding.

. Update the `ProvisioningRequest` CR to reference the new `ClusterTemplate` CR version and remove the worker node by running the following command:
+
[source,terminal]
----
$ oc edit provisioningrequests.clcm.openshift.io <uuid>
----
+
where:
+
`<uuid>`:: Specifies the UUID of the `ProvisioningRequest` CR for the target cluster.
+
Update `spec.templateVersion` and remove the target worker node entry from `spec.templateParameters.clusterInstanceParameters.nodes`:
+
[source,yaml]
----
# ...
spec:
  templateName: std-ran-du
  templateVersion: v4-Y-Z-3
  templateParameters:
    clusterInstanceParameters:
      nodes:
        - hostName: master-1.cluster.example.com
        - hostName: master-2.cluster.example.com
        - hostName: master-3.cluster.example.com
        - hostName: worker-1.cluster.example.com
        - hostName: worker-2.cluster.example.com
# ...
----
+
* `spec.templateVersion` references the new `ClusterTemplate` CR.
* The removed worker node entry is no longer present in the `nodes` array.

. Apply the updated `ProvisioningRequest` CR to the hub cluster, or commit it to the GitOps repository for ArgoCD synchronization.

.Verification

* Verify that the `ProvisioningRequest` CR returns to `fulfilled` after the node is removed by running the following command:
+
[source,terminal]
----
$ oc get provisioningrequests.clcm.openshift.io <uuid> -o jsonpath='{.status.provisioningStatus.provisioningPhase}'
----
+
The `ProvisioningRequest` CR transitions from `fulfilled` to `pending` to `progressing` and back to `fulfilled` once the node removal completes and the deprovisioned server returns to `available` state.
