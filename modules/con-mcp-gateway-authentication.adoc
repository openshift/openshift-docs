= Understand {mcpg} authentication

[role="_abstract"]
When you enable authentication, the Model Context Protocol (MCP) clients can discover your authorization server and complete the authentication flow. The {mcpg} broker component makes OAuth 2.0 Protected Resource Metadata accessible.

You can implement the following actions by using authentication:

* Set up the {mcpg} to validate access tokens issued by your identity provider.
* Return a `401` error message with authorization server discovery information.
* Expose OAuth configuration at `/.well-known/oauth-protected-resource`.
* Enable MCP clients to discover and use your identity provider's client registration.

The following example uses {prodname} `AuthPolicy` CRs with {keycloak} as an identity provider. The {mcpg} supports Istio or Gateway API compatible authentication mechanisms.

Protect both the broker route set and the back-end MCP server route set. In the sample configuration, these use the `mcp` and `mcps` listeners, respectively. An authentication policy that covers only the broker does not protect requests routed to back-end servers.

The router rewrites `:authority` to the configured public hostname during request header processing and to the registered back-end route hostname when routing a tool call upstream. These are routing operations, not token validation, and do not replace authentication for either route set.

Router audit logs decode the `user` subject from the JWT without validating the token. An entry for a request rejected before authentication can contain an unverified subject even when both route sets have authentication policies.
