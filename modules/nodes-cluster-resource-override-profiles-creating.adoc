= Create a project-level resource override

[role="_abstract"]
You can create a `ResourceOverride` custom resource (CR) if selected pods in a project need ratios that differ from the cluster-wide `ClusterResourceOverride` object.

.Prerequisites

* The Cluster Resource Override Operator is installed.
* A `ClusterResourceOverride` CR named `cluster` exists.
* You have the `admin` or `edit` role on the project.
* For `memoryRequestToLimitPercent`, `cpuRequestToLimitPercent`, and `limitCPUToMemoryPercent`, the containers have a memory or CPU limit in the pod spec or from a `LimitRange` object.
* For `cpuRequestToRequestPercent`, the containers have a CPU request in the pod spec or from a `LimitRange` object.

.Procedure

. Add the Cluster Resource Override opt-in label to the project:
+
[source,terminal]
----
$ oc label namespace <namespace_name> clusterresourceoverrides.admission.autoscaling.openshift.io/enabled=true
----
+
Replace `<namespace_name>` with the name of the project to apply the label.
+
.Example command
[source,terminal]
----
$ oc label namespace my-namespace clusterresourceoverrides.admission.autoscaling.openshift.io/enabled=true
----
+
If the project already has the label, the command reports that the namespace was not labeled. You can continue to the next step.

. Create a `ResourceOverride` object YAML file (for example, `ro-cr.yaml`):
+
[source,yaml]
----
apiVersion: autoscaling.openshift.io/v1
kind: ResourceOverride
metadata:
  name: stateless
  namespace: my-namespace
spec:
  podResourceOverride:
    memoryRequestToLimitPercent: 25
    cpuRequestToLimitPercent: 10
    limitCPUToMemoryPercent: 150
    cpuRequestToRequestPercent: 50
  podSelector:
    matchLabels:
      tier: stateless
----
+
where:
+
--
`apiVersion`:: Specifies `autoscaling.openshift.io/v1`. 
`metadata.name`:: Specifies the name of the object. The name must be unique in the project.
`metadata.namespace`:: Specifies the project for this object. A `ResourceOverride` object belongs to one project. A project can have more than one `ResourceOverride` object. The webhook reads `ResourceOverride` objects in the project of the admitted pod.
`spec.podResourceOverride.memoryRequestToLimitPercent`:: If a container memory limit has been specified or defaulted, the memory request is overridden to this percentage of the limit, from 1 to 100. This parameter is optional.
`spec.podResourceOverride.cpuRequestToLimitPercent`:: If a container CPU limit has been specified or defaulted, the CPU request is overridden to this percentage of the limit, from 1 to 100. This parameter is optional.
`spec.podResourceOverride.limitCPUToMemoryPercent`:: If a container memory limit has been specified or defaulted, the CPU limit is overridden to a percentage of the memory limit. Scaling 1Gi of RAM at 100 percent is equal to 1 CPU core. The webhook processes this parameter before it overrides the CPU request. This parameter is optional.
`spec.podResourceOverride.spec.cpuRequestToRequestPercent`:: Sets the CPU request to this percentage of the CPU request in the pod that you submit, from 1 to 100. For example, `50` changes a request of `2000m` to `1000m`. This parameter is optional. The webhook applies this parameter after the other override parameters.
`spec.podSelector`:: Optional label selector for pods in the same project. If you omit `podSelector`, or leave `matchLabels` and `matchExpressions` empty, the object matches every pod in the project. If the selector is not a valid label selector, the webhook ignores the object.
`spec.podSelector.matchLabels`:: A map of labels. A pod must include every label in the map to match. You can use a `matchLabels` or `matchExpressions` parameter.
--

. Create the `ResourceOverride` object:
+
[source,terminal]
----
$ oc create -f <file_name>.yaml
----
+
.Example
[source,terminal]
----
$ oc create -f ro-cr.yaml
----

. Label pods in the project with the resource override object to match the pod selector in the object.
+
[source,terminal]
----
$ oc label pod <name> -n <namespace_name> <key>=<value>
----
+
For a workload such as a deployment, set the label on the pod template so every new pod gets the label by running a command similar to the following:
+
[source,terminal]
----
$ oc patch deployment <name> -n <namespace_name> --type=merge -p '{"spec":{"template":{"metadata":{"labels":{"<key>":"<value>"}}}}}'
----
+
Replace `<name>` with the workload name, <namespace_name> with the namespace where the workload is deployed, and `<key>/<value>` with the pod selector.
+
.Example commands
[source,terminal]
----
$ oc label pod my-pod -n my-namespace tier=stateless
----
+
[source,terminal]
----
$ oc patch deployment my-deployment -n my-namespace --type=merge -p '{"spec":{"template":{"metadata":{"labels":{"tier":"stateless"}}}}}'
----

.Verification

* Confirm that the object exists:
+
[source,terminal]
----
$ oc get resourceoverride <name> -n <namespace_name>
----
+
Replace `<name>` with the name of the resource override object and `<namespace_name>` with the name of namespace where the object should be applied.
+
.Example command
[source,terminal]
----
$ oc get resourceoverride stateless -n my-namespace
----

* Check that the resource override ratios are applied to a pod in the namespace:

.. In the workload, check the original container CPU request and memory limit by running a command similar to the following:
+
.Example command
[source,terminal]
----
$ oc get deployment <workload_name> -n <namespace_name> -o jsonpath='{.spec.template.spec.containers[*].resources}{"\n"}'
----
+
Replace `<workload_name>` with the name of your workload and `<namespace_name>` with the name of namespace where the deployment is deployed.
+
.Example output
[source,terminal]
----
{"limits":{"cpu":"500m","memory":"128Mi"},"requests":{"cpu":"100m"}}
----
	
.. Check the CPU request and memory limit values from new pods in that workload that have the appropriate pod selector, created after the resource override object was created, by running a command similar to the following:
+
.Example command
[source,terminal]
----
$ oc get pods -n <namespace_name> -l <key>=<value> -o custom-columns=NAME:.metadata.name,REQUESTS:.spec.containers[*].resources.requests,LIMITS:.spec.containers[*].resources.limits
----
+
.Example pod output
[source,terminal]
----
NAME                               REQUESTS                    LIMITS
my-deployment-2-6857c84855-25xxk   map[cpu:250m memory:32Mi]   map[cpu:187m memory:128Mi]
my-deployment-2-6857c84855-97qqp   map[cpu:250m memory:32Mi]   map[cpu:187m memory:128Mi]
my-deployment-749f9646fc-xjgnq     map[cpu:62m memory:64Mi]    map[cpu:250m memory:128Mi]
----
+
For the `my-deployment-2-*` pods, using the example values in the previous step, `cpuRequestToRequestPercent: 50`, `memoryRequestToLimitPercent: 25`, and `limitCPUToMemoryPercent: 150`, a submitted CPU request of `500m` becomes `250m`, a memory limit of `128Mi` produces a memory request of `32Mi`, and that same memory limit produces a CPU limit of `187m`.
+
The `cpuRequestToLimitPercent: 10` parameter would have been applied first and would have set the CPU request to about `18m`. The `cpuRequestToRequestPercent` parameter was then applies, replacing the request with `250m`.
+
If `cpuRequestToRequestPercent` is set in the resource override, the `clusterresourceoverrides.admission.autoscaling.openshift.io/original-cpu-request-<container_name>` annotation is added to the pod, as shown in the following example:
+
.Example pod spec
[source,yaml]
----
apiVersion: v1
kind: Pod
metadata:
  annotations:
    clusterresourceoverrides.admission.autoscaling.openshift.io/original-cpu-request-agnhost: 100m
# ...
  generateName: hello-node-76578fb446-
# ....
----
+
In the example pod output, the `my-deployment-749f9646fc-xjgnq` pod was generated by a deployment that had the same resource requests. But the pod did not match the resource override object. So, the pod uses the cluster-wide ratios from the cluster resource override object.
