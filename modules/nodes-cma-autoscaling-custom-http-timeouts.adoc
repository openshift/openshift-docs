= Configure HTTP request timeouts

[role="_abstract"]
You can limit how long the interceptor waits for a request, for response headers, and for a scale-up from zero replicas. Set the limits on the `InterceptorRoute` resource. When you omit a field, the interceptor default applies. A value of `0s` disables that timeout for the route.

.Prerequisites

* An `InterceptorRoute` resource exists for the workload.

.Procedure

. Set `spec.timeouts` on the `InterceptorRoute` resource. For example:
+
.Example per-route timeouts
[source,yaml]
----
apiVersion: http.keda.sh/v1beta1
kind: InterceptorRoute
metadata:
  name: sample-app
  namespace: my-namespace
spec:
  target:
    service: sample-app
    port: 8080
  scalingMetric:
    concurrency:
      targetValue: 100
  timeouts:
    request: 60s <1>
    responseHeader: 30s <2>
    readiness: 10s <3>
----
<1> Specifies the total time allowed for the request, from arrival at the interceptor until the response is complete.
<2> Specifies how long the interceptor waits for response headers after it forwards the request. This timer does not include cold-start wait time.
<3> Specifies how long the interceptor waits for a pod to become ready during a scale-up from zero replicas.

. Apply the updated resource by running the following command:
+
[source,terminal]
----
$ oc apply -f interceptorroute.yaml
----

. When a timeout expires, the interceptor returns one of the following HTTP status codes:
+
[cols="2,1",options="header"]
|===
|Condition
|HTTP status

|The request timeout expired.
|`504`

|The response header timeout expired.
|`504`

|The readiness timeout expired and no cold-start fallback service is configured.
|`504`

|The backend failed for a reason other than a timeout, and no fallback service is configured.
|`502`
|===
