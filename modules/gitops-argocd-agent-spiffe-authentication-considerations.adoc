= SPIFFE/SPIRE authentication considerations

When you configure SPIFFE/SPIRE authentication for the Argo CD Agent, consider the following configuration parameters, default patterns, and behavior notes.

*Configuration precedence*

SPIFFE takes precedence over legacy configuration:: When you configure SPIFFE authentication, it takes precedence over any legacy `tls` and `creds` configuration. However, a non-empty `principal.auth` field always takes precedence over the SPIFFE-inferred pattern.

Principal auth field behavior:: Leave the `principal.auth` field unset to allow the controller to infer the correct pattern automatically. Set it explicitly only when your SPIRE deployment uses a different SVID format than the default pattern.

Agent-side configuration:: The agent does not have an equivalent override field for the SPIFFE-inferred pattern. The agent always uses the pattern based on `spiffe.authMethod` and cannot be overridden.

*Default SVID patterns*

The operator expects SVIDs to follow specific patterns based on the `spiffe.authMethod` value. If your SPIRE deployment issues SVIDs matching these default patterns, you do not need to set the `principal.auth` field explicitly.

[cols="1,2",options="header"]
|===
|Authentication method
|Default SVID pattern

|`jwt`
|`spiffe-jwt:spiffe://<trust_domain>/ns/<namespace>/argocd/agent/(.+)`

The agent identity is extracted from the SPIFFE ID in the JWT-SVID token.

|`mtls`
|`mtls:uri:spiffe://<trust_domain>/ns/<namespace>/argocd/agent/(.+)`

The agent identity is extracted from the URI SAN of the X.509-SVID certificate, not the CN field that SPIRE-issued SVIDs use.
|===

*Custom SVID formats*

If your SPIRE deployment issues SVIDs in a different format than the default patterns, explicitly set `principal.auth` to a regex pattern that matches your custom SVID format. The controller uses your custom value instead of inferring one from `spiffe.authMethod`.

*Configuration parameters*

[cols="1,2,1",options="header"]
|===
|Parameter
|Description
|Required

|`spiffe.enabled`
|Activates SPIFFE authentication for the component. Set to `false` by default. You must set this to `true` on both the principal and agent for authentication to succeed.
|Yes

|`spiffe.authMethod`
|Specifies the SPIFFE authentication method. Use `jwt` for JWT-SVIDs with federated SPIRE deployments, or `mtls` for X.509-SVIDs with centralized SPIRE deployments. Set to `jwt` by default.
|No

|`spiffe.csiDriverName`
|Specifies the name of the CSI driver that mounts the SPIFFE Workload API socket. Set to `csi.spiffe.io` by default.
|No

|`principal.auth`
|Overrides the default SVID pattern. Use this only when your SPIRE deployment issues SVIDs in a custom format. This field takes precedence over the SPIFFE-inferred pattern.
|No
|===

*Important behavior notes*

Both sides must enable SPIFFE:: SPIFFE must be enabled on both the principal and agent components for the authentication handshake to succeed. Enabling SPIFFE on only one side breaks the connection.

Authentication methods must match:: The `authMethod` value on the agent and principal must match because they negotiate the same SPIFFE authentication method with each other.

Legacy TLS configuration ignored:: When both SPIFFE and legacy `tls.secretName` or `tls.rootCASecretName` fields are configured on the agent, SPIFFE takes precedence for the connection to the principal. The operator logs a warning and the agent binary ignores the legacy TLS secret names at runtime.

Minimal configuration option:: To use SPIFFE with all default values, set only `spiffe.enabled: true` in both the principal and agent configurations. The operator uses `jwt` as the authentication method and `csi.spiffe.io` as the CSI driver name.
