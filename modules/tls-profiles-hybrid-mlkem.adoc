= Hybrid ML-KEM key exchange

[role="_abstract"]
{product-title} supports the `Old`, `Intermediate`, and `Modern` TLS security profiles. {zero-trust-full} inherits the profile from `spec.tlsSecurityProfile` in the cluster `APIServer` custom resource (CR), `apiserver.config.openshift.io/cluster`.

The `Modern` profile is recommended for {zero-trust-full}. It requires a minimum TLS version of 1.3.

The `Intermediate` profile is the default. It requires a minimum TLS version of 1.2 and can still negotiate hybrid Module-Lattice-Based Key-Encapsulation Mechanism (ML-KEM) when the server offers a hybrid group. The server and the client agree on the highest TLS version that both support.

The hybrid groups are `X25519MLKEM768`, `SecP256r1MLKEM768`, and `SecP384r1MLKEM1024`. Each group combines ML-KEM with a classical elliptic curve: `X25519`, `secp256r1`, or `secp384r1`. The server offers these hybrid groups together with the classical groups in the same profile. The handshake uses a hybrid group when the client supports one. The handshake uses a classical group when the client supports only classical groups.

Hybrid groups keep a classical algorithm in the key exchange. {product-title} does not support pure ML-KEM, which uses ML-KEM without a classical curve in the same group. The TLS security profile excludes post-quantum signature algorithms.

[NOTE]
====
The hybrid ML-KEM groups are not FIPS-approved. In FIPS mode, components exclude these groups from the key exchange.
====

During a TLS 1.3 key exchange, a {spire-full} (SPIRE) server listener offers `X25519MLKEM768`, `SecP256r1MLKEM768`, and `SecP384r1MLKEM1024` together with the classical groups. For workload-to-workload mutual TLS, {zero-trust-full} issues the {spiffe-full} identity, and the TLS stack of each workload selects the key-exchange group.
