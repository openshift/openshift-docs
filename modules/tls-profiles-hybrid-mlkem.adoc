= Hybrid ML-KEM key exchange

[role="_abstract"]
You can use the `Old`, `Intermediate`, or `Modern` Transport Layer Security (TLS) security profile. {zero-trust-full} inherits that profile from the cluster `APIServer` custom resource (CR). Set the `spec.tlsSecurityProfile` field in the `apiserver.config.openshift.io/cluster` CR.

Select the `Modern` profile for {zero-trust-full}. This profile requires a minimum TLS version of 1.3.

The `Intermediate` profile is the default. It requires a minimum TLS version of 1.2. You can still use this profile to negotiate a hybrid Module-Lattice-Based Key-Encapsulation Mechanism (ML-KEM) group when the server offers that group. The server and the client use the highest TLS version that both support.

The server offers these hybrid groups with the classical groups in the same profile. Each group combines ML-KEM with one classical curve:

* `X25519MLKEM768` with the `X25519` curve.
* `SecP256r1MLKEM768` with the `secp256r1` curve.
* `SecP384r1MLKEM1024` with the `secp384r1` curve.

If the client supports a hybrid group, the handshake uses that group. If the client supports only classical groups, the handshake uses a classical group.

A hybrid group keeps a classical algorithm in the key exchange. Pure ML-KEM uses ML-KEM without a classical curve. Therefore, {product-title} does not support pure ML-KEM. The TLS security profile excludes post-quantum signature algorithms.

[NOTE]
====
Because hybrid ML-KEM groups are not Federal Information Processing Standards (FIPS)-approved, components exclude these groups from the key exchange in FIPS mode.
====

During a TLS 1.3 key exchange, a {spiffe-full} Runtime Environment (SPIRE) server listener offers the hybrid groups with the classical groups. For workload-to-workload mutual TLS, {zero-trust-full} issues the SPIFFE identity. The TLS stack of each workload selects the key-exchange group.
