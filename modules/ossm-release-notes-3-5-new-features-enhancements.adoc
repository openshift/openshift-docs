= {SMProductName} version 3.5 new features and enhancements

[role="_abstract"]

This release makes {SMProductName} 3.5 generally available, adds new features, addresses Common Vulnerabilities and Exposures (CVEs), and is supported on {ocp-product-title} 4.20 and later.

For lists of supported component versions (such as the {istio} control plane) and feature support levels, see:

* "{SMProductShortName} component versions"
* "{SMProductShortName} feature support tables"

Ambient mode multi-primary multi-network topology is generally available::
The ambient mode multi-primary multi-network topology (a multi-cluster service mesh topology), introduced in {SMProduct} 3.3 as Technology Preview, is fully supported in this release. Each cluster runs its own control plane and communicates through ambient east-west gateways. With HBONE (HTTP-Based Overlay Network Environment) mutual TLS, workloads communicate securely across clusters. Before deploying this topology, review the documented configuration requirements and known limitations.
+
link:https://redhat.atlassian.net/browse/OSSM-14671[OSSM-14671]

IPv6 single-stack and dual-stack networking support for ambient mode is generally available::
{SMProduct} can operate on clusters with IPv6 single-stack or dual-stack networking, enabling deployment in cloud environments that require IPv6.
+
To enable dual-stack operation:
+
. Configure your Kubernetes cluster for dual-stack networking (Kubernetes 1.23 or later).
. Set the `ISTIO_DUAL_STACK` environment variable to `true` in your Istio configuration.
. Configure `pilot.ipFamilyPolicy` to `RequireDualStack` in your Istio installation.
+
Once configured, ambient proxies automatically route traffic to both IPv4 and IPv6 endpoints without requiring changes to applications. Organizations can operate a single mesh across different network types rather than maintaining separate infrastructure for each protocol.
+
link:https://redhat.atlassian.net/browse/OSSM-15863[OSSM-15863]

Security-hardened configuration for internet-facing gateway proxies::
Gateway proxies can use a new `EDGE` profile that applies security-focused settings for internet-facing deployments. The profile configures a subset of Envoy edge proxy hardening recommendations through standard {Istio} APIs, reducing the need for custom `EnvoyFilters` for these settings.
+
The `EDGE` profile provides:
+
** Defaults for Envoy listener and cluster buffers, HTTP timeouts, and downstream HTTP/2 limits.
** Enhanced header and path handling for edge-proxy deployments.
** Support for configuring a global downstream connection limit through `ProxyConfig.connectionSettings.profile`.
+
Enable the profile by setting `ProxyConfig.connectionSettings.profile` to `EDGE`. Existing gateway configurations are not affected unless the profile or individual `ConnectionSettings` fields are explicitly configured.
+
link:https://redhat.atlassian.net/browse/OSSM-11503[OSSM-11503]

Integration with the Zero Trust Workload Identity Manager is generally available::
With this release, OpenShift Service Mesh integration with the Red Hat Zero Trust Workload Identity Manager (ZTWIM) Operator is generally available. ZTWIM deploys and manages SPIRE (the SPIFFE Runtime Environment), which provides deep workload attestation for Service Mesh. This feature was introduced as a Technology Preview in Service Mesh 3.4.
+
Implementing SPIRE replaces the built-in Istio certificate authority (CA). Envoy sidecar proxies and gateways receive X.509 SPIFFE Verifiable Identity Documents (SVIDs) from the SPIRE Agent through the Secret Discovery Service (SDS) API. This gives you stronger workload attestation and central control of workload identities.
+
Service Mesh 3.5 also adds support for SPIRE federation. With federation, workloads in different trust domains can authenticate each other by exchanging SPIFFE trust bundles. Use cases include multiple OpenShift clusters that each run their own SPIRE server, and external workloads that run SPIRE agents outside the mesh.
+
Known limitations:
+
** The integration supports sidecar mode only.
** You must create SPIRE registrations before you start workload pods. For example, use `ClusterSPIFFEID` resources. A pod without a matching registration waits indefinitely for an identity.
** SPIFFE IDs must use the format `spiffe://<trust_domain>/ns/<namespace>/sa/<service_account>`.
** The SPIRE server trust domain must match the Istio `meshConfig.trustDomain` value.
** For federation, you must list each federated trust domain and its `spiffeBundleUrl` in `meshConfig.caCertificates` on every participating cluster.
+
link:https://redhat.atlassian.net/browse/OSSM-13239[OSSM-13239]

Upgrade {SMProduct} two versions at a time in sidecar mode::
You can upgrade sidecar mode deployments two versions at a time with the `RevisionBased` strategy, reducing upgrade time and workload disruption. For example, upgrading directly from {SMProduct} 3.3 to 3.5 requires only one workload restart instead of multiple restarts at each intermediate version.
+
The `InPlace` strategy still upgrades {SMProduct} one version at a time.
+
link:https://redhat.atlassian.net/browse/OSSM-14856[OSSM-14856]

Upstream enhancements and behavior changes in {SMProduct} 3.5::
As an enterprise distribution based on upstream Istio, OpenShift Service Mesh inherits enhancements from the core project, Envoy, and the broader community ecosystem. Review the following upstream changes in this release to decide whether your deployment needs configuration updates.
+
** Unhealthy endpoint routing: With this release, Istio routes traffic to unhealthy endpoints when most healthy endpoints are unavailable, preventing complete service failure. If you already configured `OutlierDetection.minHealthPercent` in a `DestinationRule`, this new default behavior does not apply to that service. To disable this behavior globally, set the `PILOT_AUTO_SEND_UNHEALTHY_ENDPOINTS` environment variable to `false` in your `istiod` deployment.
+
** Gateway resource merging: The new `PILOT_ENABLE_STRICT_GATEWAY_MERGING` environment variable prevents Istio `Gateway` resources in different namespaces from merging with managed Gateway API `Gateway` resources. (Unmanaged Gateway API `Gateway` resources are not affected.) This new variable is enabled by default. To disable it, set `PILOT_ENABLE_STRICT_GATEWAY_MERGING` to `false`.
+
Action to take: If your existing mesh configuration merges Istio `Gateway` resources with managed Gateway API `Gateway` proxies across namespaces, either refactor your gateway setup or disable strict gateway merging by setting `PILOT_ENABLE_STRICT_GATEWAY_MERGING` to `false`.
+
** Gateway distributed tracing: The `PILOT_SPAWN_UPSTREAM_SPAN_FOR_GATEWAY` feature flag was removed. Gateway distributed tracing of requests to backend services is now always enabled. If you had set this flag to false, you should remove that configuration, because it no longer has effect.
+
For complete details, see the upstream Istio release documentation:
