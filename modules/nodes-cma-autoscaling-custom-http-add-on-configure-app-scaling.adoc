= Configure HTTP-based autoscaling for your application

[role="_abstract"]
After installing the HTTP Add-on, you configure per-application autoscaling by creating an `InterceptorRoute` custom resource to define traffic routing and scaling metrics, and a `ScaledObject` custom resource to link your scaling configuration to your application deployment.

.Prerequisites

* The HTTP Add-on is installed in your cluster.

* You have access to a terminal with the `oc` command-line tool installed and authenticated to your {product-title} cluster.

* You have permissions to create deployment, service, route, interceptor route, and scaledbject` custom resources in the `default` namespace.

.Procedure

. Create a namespace for the example application by running the following command:
+
[source,terminal]
----
$ oc new-project <namespace>
----
+
Replace `<namespace>` with the name of your namespace.

. Create a sample HTTP application deployment.

.. Create a file with the following content:
+
[source,yaml]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-http-app
  namespace: http-add-on-example
spec:
  replicas: 1
  selector:
    matchLabels:
      app: sample-http-app
  template:
    metadata:
      labels:
        app: sample-http-app
    spec:
      containers:
      - name: app
        image: openshift/hello-openshift
        ports:
        - containerPort: 8080
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
          limits:
            cpu: 500m
            memory: 256Mi
----

.. Create the deployment:
+
[source,terminal]
----
$ oc create -f <file_name>.yaml
----

.. Verify the deployment is operating by running the following command:
+
[source,terminal]
----
$ oc get pods -n <namespace>
----
+
Replace `<namespace>` with the name of your namespace.
+
.Example output
[source,terminal]
----
NAME                               READY   STATUS    RESTARTS   AGE
sample-http-app-5fc8679bf4-prb46   1/1     Running   0          6m57s
----

. Create a service to expose the application:

.. Create a file with the following content:
+
[source,yaml]
----
apiVersion: v1
kind: Service
metadata:
  name: sample-http-app
  namespace: http-add-on-example
spec:
  selector:
    app: sample-http-app
  ports:
  - name: http
    port: 8080
    targetPort: 8080
    protocol: TCP
----

.. Create the service:
+
[source,terminal]
----
$ oc create -f <file_name>.yaml
----

.. Verify the service was created by running the following command:
+
[source,terminal]
----
$ oc get service -n  -n <namespace>
----
+
Replace `<namespace>` with the name of your namespace.
+
.Expected output
[source,terminal]
----
NAME              TYPE        CLUSTER-IP       EXTERNAL-IP   PORT(S)    AGE
sample-http-app   ClusterIP   172.30.154.127   <none>        8080/TCP   6m19s
----

. Create a route to expose the application externally.

.. Create the route that uses edge termination in the `openshift-keda` namespace by running the following command:
+
[source,yaml]
----
oc create route edge <name> \
  --service=keda-add-ons-http-interceptor-proxy \
  --port=proxy \
  -n openshift-keda
----
+
where:
+
--
* Replace `<name>` with a name of your route.
* `service=keda-add-ons-http-interceptor-proxy` specifies the service you want to expose. This must be `keda-add-ons-http-interceptor-proxy`.
* `port=proxy` specifies the port on the `keda-add-ons-http-interceptor-proxy` that the route uses. Specifying `proxy` sets the port to `8080`. With a route that uses edge termination, the port must be `8080`.
* `openshift-keda` specifies the namespace where your route is located. This must be `openshift-keda`.
--
+
Leave `spec.host` parameter unset to allow the cluster to assigns the host host name on the apps domain.

.. Get the route host name to use in the following step by running the following command:
+
[source,terminal]
----
$ oc get route <route_name> -n openshift-keda -o jsonpath={.spec.host}
----
+
Replace `<route_name>` with the name of the route.
+
.Example output
[source,terminal]
----
sample-http-app-openshift-keda.apps.ci-ln-wszd8jt-72292.origin-ci-int-gce.dev.rhcloud.com
----

. Create an `InterceptorRoute` custom resource to intercept traffic:

.. Create a file with the following content:
+
[source,yaml]
----
apiVersion: http.keda.sh/v1beta1
kind: InterceptorRoute
metadata:
  name: sample-app-interceptor
  namespace: http-add-on-example
spec:
  rules:
    - hosts:
        - sample-http-app-openshift-keda.apps.ci-ln-74rphxb-72292.gcp-3.ci.openshift.org
  target:
    service: sample-http-app
    port: 8080
  scalingMetric:
    requestRate:
      targetValue: 5
      window: 10s
      granularity: 1s
----
+
Modify the following fields for your application:

* `metadata.name`: Specifies a descriptive name for this interceptor route.
* `metadata.namespace`: Specifies the namespace where your application is deployed.
* `spec.rules.hosts`: Specifies the host name where traffic arrives for your application from your route or ingress. Use the host name from the previous step.
* `spec.target.service`: Specifies the name of your application's service.
* `spec.target.port`: Specifies the port exposed by the Kubernetes service. For example, if the service exposes port `80` and forwards to `targetPort: 8080`, the interceptor route must use port `80`.
* `spec.scalingMetric`. Specifies the default metric thresholds. Specify either requests per second (`requestRate`) or concurrent request count (`concurrency`) or both:
** `requestRate`. The `requestRate` metric measures incoming requests averaged over a measurement window. The baseline `requestRate` value is used as the scaling reference. You can set the following paramters:
+
--
* `targetValue` specifies how much traffic each replica should handle. The horizontal pod autoscaler adds replicas when the average load per pod rises above that number.
* `window` is the sliding time window over which the average request rate is calculated. The default is 1 minute. 
* `granularity` is the bucket size within that window. The default is 1 second. Smaller granularity makes scaling more responsive but also more sensitive to burst traffic.
--

** `concurrency`. The `concurrency` metric measures in-flight HTTP requests. The baseline `concurrency` value is used as the scaling reference. For `concurrency` you can set `targetValue`. The `window` and `granularity` parameters are not available.

.. Create the interceptor route by running the following command:
+
[source,terminal]
----
$ oc create -f <file_name>.yaml
----

.. Verify the interceptor route is created by running the following command:
+
[source,terminal]
----
$ oc get interceptorroute <route_name> -n <namespace_name>
----
+
Replace `<route_name>` with the name of the interceptor route and `<namespace_name>` with the namespace where the interceptor route was created.
+
.Expected output
[source,terminal]
----
NAME                     TARGETSERVICE     READY   AGE
sample-app-interceptor   sample-http-app   True    11s
----
+
Wait until the route interceptor is the `READY:True` state.

. Create a `ScaledObject` to configure scaling:

.. Create a file with the following content:
+
[source,yaml]
----
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: sample-app-scaler
  namespace: http-add-on-example
spec:
  scaleTargetRef:
    name: sample-http-app
  minReplicaCount: 0
  maxReplicaCount: 10
  cooldownPeriod: 30
  triggers:
    - type: external-push
      metadata:
        scalerAddress: keda-add-ons-http-external-scaler.openshift-keda.svc:9090
        interceptorRoute: sample-app-interceptor
----
+
Modify the following fields for your application:

* `metadata.name`: Specifies a descriptive name for this scaled object.
* `metadata.namespace`: Specifies the namespace where your application is deployed. Must be applied in the same namespace as the interceptor route.
* `spec.scaleTargetRef.name`: Specifies the exact name of your deployment or stateful set.
* `spec.minReplicaCount`: Specifies the minimum replicas your application should scale down to.
* `spec.maxReplicaCount`: Specifies the maximum replicas your application should scale up to.
* `spec.cooldownPeriod`: Specifies the time in seconds to wait before scaling to zero after traffic drops.
* `spec.triggers.type`: Specifies the underlying core KEDA metric scaler engine that watches your workload. Must be `external-push`.
* `spec.triggers.metadata.scalerAddress`: Specifies the endpoint for the HTTP add-on scaler service. Must be `keda-add-ons-http-external-scaler.openshift-keda.svc:9090`.
* `spec.triggers.metadata.interceptorRoute`: Specifies the name of your interceptor route.

.. Create the scaled object by running the following command:
+
[source,terminal]
----
$ oc apply -f <file_name>.yaml
----

.. Verify the scaled object is created by running the following command:
+
[source,terminal]
----
$ oc get scaledobject <object_name> -n <namespace_name>
----
+
Replace `<object_name>` with the name of the interceptor route and `<namespace_name>` with the namespace where the interceptor route was created.
+
.Example output
[source,terminal]
----
NAME                SCALETARGETKIND      SCALETARGETNAME   MIN   MAX   READY   ACTIVE    FALLBACK   PAUSED   TRIGGERS        AUTHENTICATIONS   AGE
sample-app-scaler   apps/v1.Deployment   sample-http-app   0     10    True    Unknown   False      False    external-push                     12s
----

.Verification

. Verify the autoscaling configuration is active:

.. Verify that the deployment currently has zero replicas by running the following command:
+
[source,terminal]
----
$ oc get deployment <deployment_name> -n <namespace_name>
----
+
Replace `<deployment_name>` with the name of the deployment and `<namespace_name>` with the namespace where the deployment was created.
+
.Expected output
[source,terminal]
----
NAME               READY   UP-TO-DATE   AVAILABLE   AGE
sample-http-app    0/0     0            0           5m
----
+
There are no replicas because there is no traffic going to the application.

.. Check that an HPA was created by the scaled object by running the following command:
+
[source,terminal]
----
$ oc get hpa -n <namespace_name>
----
+
Replace `<namespace_name>` with the namespace where the scaled object was created.
+
.Example output
[source,terminal]
----
NAME                         REFERENCE                    TARGETS             MINPODS   MAXPODS   REPLICAS   AGE
keda-hpa-sample-app-scaler   Deployment/sample-http-app   <unknown>/5 (avg)   1         10        0          117s
----
+
The target is `unknown` because the deployment has no replicas.

. Generate traffic to observe autoscaling behavior by running the following command:

.. Run the following script to generate HTTP traffic to your cluster. This creates concurrent requests that can be monitored in your metrics dashboard:
+
[source,terminal]
----
for i in $(seq 1 30); do
  for j in $(seq 1 20); do
    curl -sk "https://<host_name>/"/dev/null &
  done
  wait
done
----
+
The curl command in this example sends one HTTP request to the route and prints the response, generating 600 total HTTP requests, 30 batches with 20 concurrent requests per batch, to populate performance metrics. 

.. Watch the deployment scale up in response to traffic by running the following command:
+
[source,terminal]
----
$ oc get deployment <deployment_name> -n <namespace_name>
----
+
Replace `<deployment_name>` with the name of the deployment and `<namespace_name>` with the namespace where the deployment was created.
+
.Example output
[source,terminal]
----
NAME              READY   UP-TO-DATE   AVAILABLE   AGE
sample-http-app   6/6     6            6           26m
----
+
You should see the `READY` and `AVAILABLE` fields increase. In this example, the deployment scaled up to 6 replicas.

.. Check the HPA status to see the current metrics and scaling activity by running the following command:
+
[source,terminal]
----
$ oc get hpa -n <namespace>
----
+
Replace `<namespace>` with the namespace where the scaled object was created.
+
[source,terminal]
----
NAME                         REFERENCE                    TARGETS         MINPODS   MAXPODS   REPLICAS   AGE
keda-hpa-sample-app-scaler   Deployment/sample-http-app   6500m/5 (avg)   1         10        6          15m
----
+
In this example, the HPA target 6500m/5 is 6.5 requests per second per pod against your target of 5 in the interceptor route, so the deployment grew to 6 replicas.

.. After traffic stops, wait for the 30-second cooldown, check the scaled object status by running the following command:
+
[source,terminal]
----
$ oc get deploy sample-http-app -n http-add-on-example
----
+
[source,terminal]
----
NAME              READY   UP-TO-DATE   AVAILABLE   AGE
sample-http-app   0/0     0            0           27m
----
+
The HPA scales the replicas down to the `minReplicaCount` value in the scaled object. The Custom Metrics Autoscaler then scales the replicas down to 0.
