= Disabling the automatic creation of RBAC resources

[role="_abstract"]
Setting `createRbacResource` to `"false"` in the `TektonConfig` custom resource disables automatic role-based access control (RBAC) reconciliation by the {pipelines-title} Operator to improve security and control over permissions.

The default installation of the {pipelines-title} Operator creates role-based access control (RBAC) resources for all namespaces in the cluster, except namespaces matching the `^(openshift|kube)-*` regular expression pattern. Among these resources, the `pipelines-scc-rolebinding` Security Context Constraint (SCC) role binding grants the `pipelines-scc` SCC, which includes the `RunAsAny` privilege.

[WARNING]
====
Before setting `createRbacResource` to `"false"`, prepare replacement RBAC permissions in your workload namespaces. When this parameter is set to `"false"`, the Operator deletes the existing RBAC installer set rather than pausing reconciliation.
====

.Prerequisites

* You have access to the cluster with `cluster-admin` permissions.
* You installed the OpenShift CLI (`oc`).
* You created the required workload service account in the workload namespace.
* You granted the necessary RBAC permissions and bound an appropriate Security Context Constraint (SCC) to the workload service account:
** Inspect the `securityContext` of each task or step to identify required user IDs (UIDs), group IDs (GIDs), and Linux capabilities.
** For container image build workloads such as Buildah or Source-to-Image (S2I), ensure that the assigned SCC allows required capabilities such as `SETFCAP`.
** Grant only the minimum required SCC permissions to the selected service account to follow the principle of least privilege. For more information, see xref:../install_config/customizing-configurations-in-the-tektonconfig-cr.adoc#op-changing-default-service-account_customizing-configurations-in-the-tektonconfig-cr[Changing the default service account] and the OpenShift documentation on managing Security Context Constraints.

.Procedure

. Edit the `TektonConfig` custom resource by running the following command:
+
[source,terminal]
----
\$ oc edit TektonConfig config
----

. In the `TektonConfig` custom resource, set `createRbacResource` to `"false"`:
+
[source,yaml]
----
apiVersion: operator.tekton.dev/v1alpha1
kind: TektonConfig
metadata:
  name: config
spec:
  params:
    - name: createRbacResource
      value: "false"
    - name: createCABundleConfigMaps
      value: "true"
----
+
[NOTE]
====
Although `createRbacResource` and `createCABundleConfigMaps` are independently configurable parameters, omitting `createCABundleConfigMaps` when `createRbacResource` is set to `"false"` causes the Operator to default `createCABundleConfigMaps` to `"false"`. To maintain automatic CA bundle ConfigMap provisioning, explicitly set `createCABundleConfigMaps` to `"true"`.
====

. In your pipeline runs or task runs, explicitly specify the workload service account:
* In a `TaskRun`, set `spec.serviceAccountName`.
* In a `PipelineRun`, set `spec.taskRunTemplate.serviceAccountName` to apply the service account to all tasks, or use `spec.taskRunSpecs[].serviceAccountName` to override the service account for specific tasks.
+
.Example PipelineRun specifying workload service accounts
[source,yaml]
----
apiVersion: tekton.dev/v1
kind: PipelineRun
metadata:
  name: example-pipelinerun
spec:
  pipelineRef:
    name: example-pipeline
  taskRunTemplate:
    serviceAccountName: <workload_service_account> <1>
  taskRunSpecs:
    - pipelineTaskName: build-task
      serviceAccountName: <buildah_service_account> <2>
----
<1> Specifies the default service account for all tasks in the pipeline run.
<2> Overrides the service account specifically for the `build-task` pipeline task.
+
[NOTE]
====
If you do not specify a service account, the run uses the configured default service account (typically `pipeline`). Pod admission might fail if the default service account does not have an SCC that satisfies the security context requirements of the task.
====
