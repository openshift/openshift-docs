= Injecting cloud provider credentials into a virtual machine

[role="_abstract"]
You can inject cloud provider service account tokens into a VM by configuring a `ServiceAccount` with the appropriate cloud provider annotation and defining a VM manifest with a `containerPath` volume and `virtiofs` filesystem device.

.Prerequisites

* You have installed {VirtProductName}.
* You have cluster administrator privileges.
* You have installed the {oc-first}.
* The cluster’s OIDC provider is configured in AWS IAM.
* An IAM role exists with permissions for the AWS resources the application needs. The role’s trust policy allows `sts:AssumeRoleWithWebIdentity` through that OIDC provider for `system:serviceaccount:<namespace>:<service_account_name>`, matching the namespace and service account used by the VM.
* You have installed the `aws` CLI inside the guest VM.

.Procedure

. Create a `ServiceAccount` object with an IAM role ARN annotation:
+
[source,yaml]
----
apiVersion: v1
kind: ServiceAccount
metadata:
  name: <service_account_name>
  namespace: my-namespace
  annotations:
    eks.amazonaws.com/role-arn: <AWS_IAM_role_ARN>
----
+
where:
+
<service_account_name>:: Specifies the name of the service account. You reference this name in the VM manifest.
<AWS_IAM_role_ARN>:: Specifies the ARN of the AWS IAM role that grants the required permissions.

. Apply the `ServiceAccount` object by running the following command:
+
[source,terminal]
----
$ oc apply -f <filename>.yaml
----

. Create a `VirtualMachine` manifest that references the `ServiceAccount` and defines a `containerPath` volume with a `virtiofs` filesystem device.
+
[NOTE]
====
Use the same name for the `containerPath` volume and `virtiofs` filesystem device.
====
+
[source,yaml]
----
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: example-vm
  namespace: my-namespace
spec:
  running: true
  template:
    spec:
      serviceAccountName: <service_account_name>
      domain:
        devices:
          filesystems:
          - name: <name>
            virtiofs: {}
        resources:
          requests:
            memory: 1Gi
      volumes:
      - name: <name>
        containerPath:
          path: <path>
----
+
where:
+
<service_account_name>:: Specifies the name of the service account with the AWS IAM role annotation.
<name>:: The name shared by the `virtiofs` filesystem device and `containerPath` volume. The `virtiofs` filesystem device name must match the `containerPath` volume name.
<path>:: The path in the `virt-launcher` pod where the AWS webhook injects the token.

. Apply the `VirtualMachine` manifest by running the following command:
+
[source,terminal]
----
$ oc apply -f <filename>.yaml
----

. Connect to the VM console by running the following command:
+
[source,terminal]
----
$ virtctl console example-vm -n my-namespace
----

. Create the mount directory by running the following command:
+
[source,terminal]
----
$ sudo mkdir -p /mnt/aws-creds
----

. Verify that the cloud provider token is available inside the guest. List the `virtiofs` mount by running the following commands:
+
--
[source,terminal]
----
$ sudo mount -t virtiofs <name> /mnt/aws-creds
----

where:

<name>:: The name shared by the `virtiofs` filesystem device and `containerPath` volume. The `virtiofs` filesystem device name must match the `containerPath` volume name.
--
+
[source,terminal]
----
$ sudo mount | grep virtiofs
----
+
[source,terminal]
----
$ ls /mnt/aws-creds
----
+
The mount point depends on the guest operating system configuration. Check for the token file in the `virtiofs`-mounted directory.

. Configure the AWS SDK to use web identity tokens, by running the following commands:
+
[source,terminal]
----
export AWS_WEB_IDENTITY_TOKEN_FILE=/mnt/aws-creds/token
----
+
[source,terminal]
----
export AWS_ROLE_ARN="<iam_role_arn>"
----

.Verification

. Verify authentication as the expected role, by running the following command and observing the output:
+
[source,terminal]
----
aws sts get-caller-identity --output json
----
+
Expected output:
+
[source,terminal]
----
{
  "UserId": "AROAXXXXXXXXXXXXXXXXX:example-session",
  "Account": "123456789012",
  "Arn": "arn:aws:sts::123456789012:assumed-role/example-role/example-session"
}
----

. Verify that the returned account matches the expected AWS account, and that ARN identifies an assumed-role session for the IAM role annotated on the service account.
