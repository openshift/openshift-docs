= Configuration examples for connecting a virtual machine to a localnet network

[role="_abstract"]
The following examples show complete end-to-end configurations for connecting a virtual machine (VM) to a localnet network by using the machine network or dedicated network interfaces.

Connecting through the machine network:: While it is recommended to use a dedicated network interface to separate VM traffic from management, you can also share a single uplink. In this example, the machine network belongs to the native VLAN.
+
--
Configure the node network by defining the bridge mapping in a `NodeNetworkConfigurationPolicy` manifest:

[source,yaml]
----
apiVersion: nmstate.io/v1
kind: NodeNetworkConfigurationPolicy
metadata:
  name: network-config
spec:
  desiredState:
    ovn:
      bridge-mappings:
      - localnet: provider-network <1>
        bridge: br-ex <2>
        state: present <3>
----
<1> The localnet identifier. This value must match the `spec.network.localnet.physicalNetworkName` field in the `ClusterUserDefinedNetwork` manifest.
<2> The name of the existing OVS bridge on the node.
<3> The state of the mapping.

Expose the network to namespaces by creating a `ClusterUserDefinedNetwork` manifest. The following example allows you to request access to VLAN 100 on the physical network:

[source,yaml]
----
apiVersion: k8s.ovn.org/v1
kind: ClusterUserDefinedNetwork
metadata:
  name: provider-network-100
spec:
  namespaceSelector:
    matchLabels:
      provider-network-vlan: "100"
  network:
    topology: Localnet
    localnet:
      role: Secondary
      physicalNetworkName: provider-network
      ipam:
        mode: Disabled
      mtu: 1500
      vlan:
        mode: Access
        access:
          id: 100
----

Assign the network to namespaces by labeling the `Namespace` object:

[source,yaml]
----
apiVersion: v1
kind: Namespace
metadata:
  name: red
  labels:
    provider-network-vlan: "100"
----

Access the network by referencing it in the `VirtualMachine` manifest:

[source,yaml]
----
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: example-vm
  namespace: red
spec:
  template:
    spec:
      domain:
        devices:
          interfaces:
            - name: provider-network
              bridge: {}
      networks:
      - name: provider-network
        multus:
          networkName: provider-network-100
# ...
----
--

Connecting through dedicated interfaces:: To prevent network congestion and isolate the traffic, you can use dedicated network interface controllers (NICs) for the VM network. The following example uses two interfaces bonded with OVS `balance-slb` mode, to provide VM-friendly link redundancy without requiring switch-side link-aggregation configuration.
+
--
Configure the node network by defining an OVS bridge in a `NodeNetworkConfigurationPolicy` manifest:

[source,yaml]
----
apiVersion: nmstate.io/v1
kind: NodeNetworkConfigurationPolicy
metadata:
  name: network-config
spec:
  desiredState:
    interfaces:
    - name: eno1np0
      type: ethernet
      state: up
      mtu: 1500
    - name: eno2np1
      type: ethernet
      state: up
      mtu: 1500
    - name: br1
      type: ovs-bridge
      state: up
      bridge:
        allow-extra-patch-ports: true
        options:
          stp: false
          mcast-snooping-enable: true
        port:
        - name: bond1
          link-aggregation:
            mode: balance-slb
            port:
              - name: eno1np0
              - name: eno2np1
        - name: br1
    - name: br1
      type: ovs-interface
      state: up
      ipv4:
        enabled: false
      ipv6:
        enabled: false
    ovn:
      bridge-mappings:
      - localnet: provider-network <1>
        bridge: br1 <2>
        state: present <3>
----
<1> The localnet identifier. This value must match the `spec.network.localnet.physicalNetworkName` field in the `ClusterUserDefinedNetwork` manifest.
<2> The name of the OVS bridge on the node.
<3> The state of the mapping.
