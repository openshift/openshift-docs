= Generating the configuration files for the virtual machine

[role="_abstract"]

The `istioctl` tool reads the `WorkloadGroup` resource and generates the set of files that the virtual machine needs to join the mesh. Two of the generated files assume that the virtual machine reaches the control plane under its in-cluster name, so edit them to point at the route instead.

.Procedure

. Generate the configuration files by running the following command:
+
[source,terminal]
----
$ istioctl x workload entry configure \
  --name vm-app \
  --namespace external-vm \
  --autoregister \
  -o vm-files
----
+
With the `--autoregister` option, the control plane creates a `WorkloadEntry` resource for the virtual machine when the proxy connects to it, and removes the resource when the proxy disconnects.
+
[NOTE]
====
The command prints the following warning, which you can ignore:

[source,terminal]
----
Could not auto-detect IP for istiod.istio-system.svc/istio-system. Use --ingressIP to manually specify the Gateway address to reach istiod from the VM.
----

The `--ingressIP` option exists only to generate a `hosts` file that pins the in-cluster control plane name to a gateway address. The virtual machine reaches the control plane through a route hostname that resolves in public DNS, so the generated `hosts` file is not required and you do not need to modify the `/etc/hosts` file on the virtual machine.
====
+
The command writes the following files to the `vm-files` directory:
+
.Generated configuration files
[options="header"]
[cols="1,3"]
|===
|File |Description

|`cluster.env`
|Environment variables that the proxy startup script reads, including the namespace, service account, and the ports to intercept.

|`istio-token`
|A Kubernetes service account token that the proxy presents to the control plane to obtain its workload certificate.

|`mesh.yaml`
|The proxy configuration, including the control plane discovery address.

|`root-cert.pem`
|The mesh root certificate, which the proxy uses to authenticate the control plane.

|`hosts`
|DNS entries for resolving the control plane. This file is not used in this configuration.
|===

. Edit the `vm-files/mesh.yaml` file to set the Envoy binary path and the discovery address:
+
[source,yaml]
----
defaultConfig:
  binaryPath: /usr/bin/envoy # <1>
  discoveryAddress: istiod.istio-system.svc.<ingress_domain>:443 # <2>
  proxyMetadata:
    CANONICAL_REVISION: latest
    CANONICAL_SERVICE: vm-app
    ISTIO_META_CLUSTER_ID: ""
    ISTIO_META_DNS_CAPTURE: "true"
    ISTIO_META_MESH_ID: ""
    ISTIO_META_NETWORK: vm-network
    ISTIO_META_WORKLOAD_NAME: vm-app
    ISTIO_METAJSON_LABELS: '{"app":"vm-app","service.istio.io/canonical-name":"vm-app","service.istio.io/canonical-revision":"latest"}'
    POD_NAMESPACE: external-vm
    SERVICE_ACCOUNT: vm-app
    TRUST_DOMAIN: cluster.local
----
<1> Add this line. The `istio-proxy` RPM installs the Envoy binary at `/usr/bin/envoy`, whereas the generated file assumes the community package path.
<2> Replace the generated value of `istiod.istio-system.svc:15012` with the route hostname and port 443.

. Append the certificate authority (CA) address to the `vm-files/cluster.env` file:
+
[source,terminal]
----
CA_ADDR=istiod.istio-system.svc.<ingress_domain>:443
----
+
The proxy uses a separate connection for certificate signing requests, which does not read the `discoveryAddress` field. Without the `CA_ADDR` variable, the proxy cannot obtain a workload certificate.
