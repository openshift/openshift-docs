= Monitor and verify a VCF migration

[role="_abstract"]
Check migration conditions and events to follow progress, identify blockers, and verify completion. You can pause the {vcf-migration-operator} and resume the migration after resolving a problem.

.Prerequisites

* You have created the `cluster` migration custom resource (CR) and started the migration.
* You have installed the {oc-first} and logged in with `cluster-admin` privileges.

.Procedure

. Monitor the migration by running the following command:
+
[source,terminal]
----
$ oc get vcfm cluster -n openshift-vcf-migration
----
+
Migration is complete when the `READY` column is `True`. The `STATE` column reflects `spec.state` and remains `Running` after completion.

. Examine the conditions and machine replacement progress by running the following command:
+
[source,terminal]
----
$ oc describe vcfm cluster -n openshift-vcf-migration
----
+
A condition with a status of `False` can indicate work in progress. Read its reason and message to distinguish progress from a failure. Control plane replacement can take several hours.

. If the migration does not progress, examine its events by running the following command:
+
[source,terminal]
----
$ oc get events -n openshift-vcf-migration --field-selector involvedObject.kind=VmwareCloudFoundationMigration,involvedObject.name=cluster
----
+
For a `ConditionFailed` event, resolve the problem in the condition message. An `OldWorkersStalled` event identifies source machines whose deletion is blocked, for example, by a pod disruption budget. Review the affected workload and its disruption requirements before making changes.

. Optional: Pause migration processing by running the following command:
+
[source,terminal]
----
$ oc patch vcfm cluster -n openshift-vcf-migration --type=merge -p '{"spec":{"state":"Paused"}}'
----
+
When the Operator observes the change, the `Ready` condition becomes `False` with reason `Paused`. Pausing stops further migration reconciliation; machine operations already started by other controllers can continue. Pausing does not undo completed changes.

. If you paused the migration, resume it by running the following command:
+
[source,terminal]
----
$ oc patch vcfm cluster -n openshift-vcf-migration --type=merge -p '{"spec":{"state":"Running"}}'
----

.Verification

. Verify that the `Ready` condition is `True` by running the following command:
+
[source,terminal]
----
$ oc get vcfm cluster -n openshift-vcf-migration -o jsonpath='{.status.conditions[?(@.type=="Ready")].status}{"\n"}'
----
+
Before reporting completion, the Operator checks that cluster Operators and machine configuration pools are stable and that only target vCenters remain in the cluster configuration.

. Verify that the cluster lists only the target vCenter servers by running the following command:
+
[source,terminal]
----
$ oc get infrastructure cluster -o jsonpath='{.spec.platformSpec.vsphere.vcenters[*].server}{"\n"}'
----

. Verify that the replacement nodes are ready by running the following command:
+
[source,terminal]
----
$ oc get nodes
----

. Verify that your applications are running and accessible on the migrated cluster.

.Next steps

* Restore any autoscaler and user-created machine health check resources that you removed. Before recreating them, update machine autoscaler `spec.scaleTargetRef.name` values to reference target compute machine sets and review machine health check selectors for the replacement nodes.
* If you uninstall the Operator, retain the `cluster-metadata` secret, which contains installer metadata and credentials for the target vCenter. Delete the migration CR or uninstall the Operator only after migration completes.
