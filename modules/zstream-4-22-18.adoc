Issued: 13 October 2026

[role="_abstract"]

The list of fixed issues that are included in the update is documented in the link:https://access.redhat.com/errata/RHSA-2026:79154[RHSA-2026:79154] advisory. == Enhancements

* As a General Availability feature, you can deploy a 4.22 cluster without an external registry, using self-contained installation media that also provides a simplified user interface similar to the {ai-full} during on-premise installations.
As a postinstallation task, you can also configure your cluster to use an external registry and use the registry for cluster updates.

== Fixed issues

* Before this update, the Berkeley Packet Filter (BPF) filesystem did not allow dots (".") in filenames. As a consequence, the Ingress Node Firewall could not attach rules to virtual LAN (VLAN) subinterfaces such as `bond0.12`. Attempting to pin a link for an interface containing a dot failed with an `operation not permitted` error. With this release, the Ingress Node Firewall sanitizes pin filenames by converting dots to a placeholder string. For example, `vlan.100` becomes `vlan_dot_100` before writing to the BPF filesystem. As a result, firewall rules can be successfully applied to subinterfaces such as VLANs on top of bonded interfaces. (link:https://issues.redhat.com/browse/OCPBUGS-31495[OCPBUGS-31495])

* Before this update, the {product-title} Router performed synchronous and sequential `SubjectAccessReview` (SAR) API calls to validate each externally-managed certificate for a route during startup. As a consequence for a cluster with a high amount of external certificate routes, the kubelet killed any router pod that exceeded the `120` second startup probe timeout value. With this update, an SAR caching mechanism, `sarCache`, and a semaphore throttles concurrent SAR API calls in the router. This process happens alongside any increasing route status that has a writer-lease concurrency. As a result, the initialization time of an {product-title} Router is dramatically reduced. This change allows thousands of routes with external certificates to load within the startup probe window and prevents router pods from entering a `CrashLoopBackOff` loop. (link:https://issues.redhat.com/browse/OCPBUGS-99286[OCPBUGS-99286])

* Before this update, installing a Helm chart by using the Chart URL option in the {product-title} web console with an OCI URL that included a version number, for example, `oci://registry-1.docker.io/bitnamicharts/nginx:22.6.12` failed with an error indicating that the chart was not available or could not be found. As a consequence, users could not install Helm charts from OCI registries when specifying the version number directly in the URL. With this release, the Helm chart installation process correctly handles OCI URLs that include version numbers. As a result, users can now successfully install Helm charts from OCI registries by providing the complete URL with the version number in the web console Chart URL field. (link:https://issues.redhat.com/browse/OCPBUGS-122042[OCPBUGS-122042])

* Before this update, when a node with an EgressIP was rebooted, the ovnkube-cluster-manager reassigned the EgressIP to a new node but did not immediately remove it from the rebooting node. Both the old and new nodes responded to ARP requests for the same IP address. As a consequence, this MAC address flapping could cause network switches, firewalls, or other devices to malfunction or block EgressIP traffic. With this release, nftables rules block ARP responses from the old node after EgressIP migration. As a result, EgressIP failover completes without MAC address conflicts during node reboots. (link:https://issues.redhat.com/browse/OCPBUGS-128643[OCPBUGS-128643])

* Before this update, the rendezvous node IP address list was not refreshed after a static IP address was added through the agent TUI networking screen. As a consequence, the newly added IP address was not shown or available in the rendezvous node IP address selection screen. With this release, the host IP address list refreshes whenever the selection screen opens. As a result, newly configured IP addresses appear for selection. (link:https://issues.redhat.com/browse/OCPBUGS-127041[OCPBUGS-127041])

* Before this update, the {gcp-short} platform quota check of the installation program did not retry transient HTTP errors from the Service Usage API. When the Service Usage API returned HTTP 503 `backendError` or HTTP 429 responses, the installer exited. As a consequence, installations failed due to temporary {gcp-short} API issues. With this release, the installation program retries {gcp-short} Service Usage quota reads after HTTP 429 and 5xx responses, stopping after five attempts. As a result, installations can proceed successfully despite transient {gcp-short} Service Usage API errors. (link:https://issues.redhat.com/browse/OCPBUGS-128831[OCPBUGS-128831])
