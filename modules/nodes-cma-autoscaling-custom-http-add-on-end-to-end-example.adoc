= HTTP Add-on autoscaling end-to-end example

[role="_abstract"]
This example demonstrates a complete HTTP Add-on deployment with a sample application, traffic routing, and scaling verification. You can use this as a template for configuring the HTTP Add-on with your own applications.

.Prerequisites

* The KEDA HTTP Add-on is installed in your cluster.

* You have access to a terminal with the `oc` command-line tool installed and authenticated to your {product-title} cluster.

* You have permissions to create deployment, service, route, interceptor route, and scaledbject` custom resources in the `default` namespace.

.Procedure

. Create a namespace for the example application:
+
[source,terminal]
----
$ oc new-project http-add-on-example
----

. Create a sample HTTP application deployment.

.. Create a file named `app-deployment.yaml` with the following content:
+
[source,yaml]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-http-app
  namespace: http-add-on-example
spec:
  replicas: 1
  selector:
    matchLabels:
      app: sample-http-app
  template:
    metadata:
      labels:
        app: sample-http-app
    spec:
      containers:
      - name: app
        image: openshift/hello-openshift
        ports:
        - containerPort: 8080
        env:
        - name: RESPONSE_DELAY
          value: "0"
        resources:
          requests:
            cpu: 100m
            memory: 128Mi
          limits:
            cpu: 500m
            memory: 256Mi
----

.. Create the deployment:
+
[source,terminal]
----
$ oc create -f app-deployment.yaml
----

.. Verify the deployment is running:
+
[source,terminal]
----
$ oc get pods -n http-add-on-example
----
+
.Expected output
[source,terminal]
----
NAME                              READY   STATUS    RESTARTS   AGE
sample-http-app-7d9f8c5dbb-xyz   1/1     Running   0          2m
----

. Create a service to expose the application:

.. Create a file named `app-service.yaml` with the following content:
+
[source,yaml]
----
apiVersion: v1
kind: Service
metadata:
  name: sample-http-app
  namespace: http-add-on-example
spec:
  selector:
    app: sample-http-app
  ports:
  - port: 8080
    targetPort: 8080
    protocol: TCP
  type: ClusterIP
----

.. Create the service:
+
[source,terminal]
----
$ oc create -f app-service.yaml
----

.. Verify the service was created:
+
[source,terminal]
----
$ oc get service -n http-add-on-example
----
+
.Expected output
[source,terminal]
----
NAME              TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)    AGE
sample-http-app   ClusterIP   172.30.140.75   <none>        8080/TCP   51s
----

. Create a route to expose the application externally:

.. Create a file named `app-route.yaml` with the following content. Note that the route initially points to your application service. You will update it in a subsequent step to route through the interceptor.
+
[source,yaml]
----
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: sample-http-app-route
  namespace: http-add-on-example
spec:
  host: sample-app.example.com
  to:
    kind: Service
    name: sample-http-app
    weight: 100
  port:
    targetPort: 8080
----

.. Create the route:
+
[source,terminal]
----
$ oc create -f app-route.yaml
----

.. Get the actual route hostname if you want to use it instead of `sample-app.example.com`:
+
[source,terminal]
----
$ oc get route sample-http-app-route -n http-add-on-example -o jsonpath='{.spec.host}'
----
+
.Expected output
[source,terminal]
----
sample-app.example.com
----
+

. Create an `InterceptorRoute` custom resource to intercept traffic:

.. Create a file named `interceptor-route.yaml` with the following content:
+
[source,yaml]
----
apiVersion: http.keda.sh/v1beta1
kind: InterceptorRoute
metadata:
  name: sample-app-interceptor
  namespace: http-add-on-example
spec:
  rules:
    - hosts:
      - "sample-app.example.com"
  target:
    service: sample-http-app
    port: 8080
    protocol: http
  scalingMetric:
    rps:
      threshold: 100
    concurrency:
      targetValue: 50
----

.. Create the InterceptorRoute:
+
[source,terminal]
----
$ oc create -f interceptor-route.yaml
----

.. Verify the interceptor route is created:
+
[source,terminal]
----
$ oc get interceptorroute -n http-add-on-example
----
+
.Expected output
[source,terminal]
----
NAME                     TARGETSERVICE     READY   AGE
sample-app-interceptor   sample-http-app   True    18s
----

. Create a `ScaledObject` to configure autoscaling:

.. Create a file named `scaled-object.yaml` with the following content:
+
[source,yaml]
----
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: sample-app-scaler
  namespace: http-add-on-example
spec:
  scaleTargetRef:
    name: sample-http-app
  minReplicaCount: 0
  maxReplicaCount: 10
  cooldownPeriod: 300
  triggers:
    - type: external-push
      metadata:
        scalerAddress: keda-add-ons-http-external-scaler.openshift-keda.svc:9090
        interceptorRoute: sample-app-interceptor 
----

.. Create the scaled object:
+
[source,terminal]
----
$ oc apply -f scaled-object.yaml
----

.. Verify the scaled object is created:
+
[source,terminal]
----
$ oc get scaledobject -n http-add-on-example
----
+
.Expected output
[source,terminal]
----

sample-app-scaler   apps/v1.Deployment   sample-http-app   0     10    True    Unknown   False      False    external-push                     10s
----

.. Get the interceptor service endpoint by running the following command:

. Generate traffic to observe autoscaling behavior:

.. Create a load generation pod that sends requests to the application. Create a file named `load-gen-pod.yaml`:
+
[source,yaml,subs=verbatim]
----
apiVersion: v1
kind: Pod
metadata:
  name: load-generator
  namespace: http-add-on-example
spec:
  containers:
  - name: load-gen
    securityContext:
       allowPrivilegeEscalation: false
       runAsNonRoot: true
       seccompProfile:
         type: RuntimeDefault
       capabilities:
         drop: [ALL]
    image: busybox
    command:
    - sh
    - -c
    - |
      while true; do
        wget -q -O- http://my-app-proxy-openshift-keda.apps.ci-ln-22h2fyk-72292.gcp-3.ci.openshift.org \
        sleep 0.1
      done
  restartPolicy: Never
----

.. Create the load generation pod:
+
[source,terminal]
----
$ oc create -f load-gen-pod.yaml
----

.. Watch the deployment scale up in response to traffic:
+
[source,terminal]
----
$ oc get deployment sample-http-app -n http-add-on-example -w
----
+
.Expected output
[source,terminal]
----
NAME              READY   UP-TO-DATE   AVAILABLE   AGE
sample-http-app   1/1     1            1           30m
----
+
You should see:
+
--
* The `READY` and `AVAILABLE` fields change from `0` to `1`.
* Further scaling to multiple replicas as traffic increases.
--
+

. Stop the load generator and observe scale-to-zero:

.. Delete the load generation pod:
+
[source,terminal]
----
$ oc delete pod load-generator -n http-add-on-example
----

.. Wait for the cooldown period (300 seconds in this example) and watch the deployment scale down to zero replicas:
+
[source,terminal]
----
$ oc get deployment sample-http-app -n http-add-on-example -w

. Verify the scaling behavior was successful:

.. Check the pod count went to zero:
+
[source,terminal]
----
$ oc get pods -n http-add-on-example | grep sample-http-app
----
+
Output should be empty because no pod is running.
+
.Expected output
[source,terminal]
----
sample-http-app-864f476f45-6pfzx   1/1     Running   0          44m
----

.. Generate traffic again to verify that the application wakes up:
+
[source,terminal]
----
$ oc create -f load-gen-pod.yaml
----

.. Confirm that replicas scale back up within a few seconds:
+
[source,terminal]
----
$ oc get pods -n http-add-on-example -w | grep sample-http-app
----
+
You should see the pod transition to `Running` state as the scaler detects traffic and activates the application.
