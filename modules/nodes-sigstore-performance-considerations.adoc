= Performance and resource considerations for signature verification

[role="_abstract"]
Enabling signature verification on your cluster has minimal impact on performance and resource consumption. You can use signature verification on clusters with large numbers of Operators and workloads without significant performance impact. Review these considerations to understand the impact on your environment and ensure your deployment is properly configured.

[id="nodes-sigstore-performance-startup_{context}"]
== Pod startup latency

Signature verification adds a small amount of latency to pod startup time. The verification process occurs during image pull and typically adds less than 5 seconds per image. This latency is consistent regardless of image size because verification only requires fetching and validating the small signature image, not re-processing the container image itself.

The verification latency includes:

* Fetching the signature image from the registry (typically a few KB)
* Validating the signature against the configured trust anchor (public key, PKI certificate, or Fulcio certificate)
* Optional Rekor transparency log verification, if configured

[id="nodes-sigstore-performance-scale_{context}"]
== Scalability

Signature verification scales to large clusters with many operators and workloads. Testing has verified signature verification performance on clusters with:

* More than 200 operator images
* Multiple `ClusterImagePolicy` and `ImagePolicy` objects
* Concurrent pod scheduling across many nodes

The Machine Config Operator (MCO) efficiently distributes the policy configuration to all nodes in the cluster. After the initial configuration is applied, later pod startups verify signatures without additional MCO processing.

[id="nodes-sigstore-performance-resources_{context}"]
== Resource consumption

Signature verification has minimal resource impact:

Storage:: Signature images are small (typically a few KB) and are stored alongside the container images in your registry. The storage requirements for signatures are negligible compared to the container images themselves.

Memory:: The verification process uses minimal memory. The policy configuration files (`/etc/containers/policy.json` and `/etc/containers/registries.d/sigstore-registries.yaml`) are small and do not significantly impact node memory consumption.

Network:: Signature verification requires fetching the signature image from the registry during image pull. Because signatures are small, the network impact is minimal. In disconnected environments, the cluster fetches all signature images from your local mirror registry.

CPU:: Cryptographic signature validation requires minimal CPU resources. The verification process is not computationally intensive and does not impact cluster performance.

[id="nodes-sigstore-performance-gitops_{context}"]
== GitOps and ZTP compatibility

Signature verification is compatible with GitOps-based deployment workflows, including {rh-rhacm-first} and Zero Touch Provisioning (ZTP). You can include `ClusterImagePolicy` and `ImagePolicy` manifests in your GitOps repository and deploy them alongside other cluster configuration.

When using GitOps:

* Include the `ClusterImagePolicy` manifests in your configuration repository
* Ensure that the policy manifests are applied after the cluster is installed and the MCO is ready
* Verify that all required images and signatures are mirrored before applying policies that enforce verification

[id="nodes-sigstore-performance-limitations_{context}"]
== Current limitations

The following use cases are not currently supported or are out of scope:

{sno} and RAN deployments:: Signature verification for {sno} and RAN DU (Distributed Unit) deployments has not been validated. These environments have unique constraints and might require additional configuration.

Notary v2:: {product-title} signature verification uses sigstore and Cosign. Notary v2 is not supported.

Real-time verification updates:: Changes to `ClusterImagePolicy` or `ImagePolicy` objects require the MCO to update the node configuration. During this update, nodes are cordoned and drained, which temporarily reduces cluster capacity.
