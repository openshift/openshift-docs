= Release notes for {external-secrets-operator} 1.3.0

[role="_abstract"]
Review the new features and resolved issues in {external-secrets-operator} 1.3.0 to plan your deployment or upgrade.

Issued: 2026-11-05

The following advisories are available for the {external-secrets-operator} 1.3.0:


Version 1.3.0 of the {external-secrets-operator} is based on the upstream external-secrets version v2.12.0 and bitwarden-sdk-server v0.8.1.

[id="external-secrets-operator-1-3-0-features-enhancements_{context}"]
== New features and enhancements

*Per-component replica scaling with leader election*

With this release, you can set the desired number of pod replicas for each operand component through the `ExternalSecretsConfig` custom resource (CR). Set the `spec.controllerConfig.componentConfigs[].deploymentConfigs.replicas` field for any of the following components:

* `ExternalSecretsCoreController`
* `Webhook`
* `CertController`
* `BitwardenSDKServer`

Valid values are from 1 through 10. The default replica count is 1 if you omit this field.

Leader election is always enabled for the `ExternalSecretsCoreController` and `CertController` components. Only one replica of each component reconciles at a time. This also applies during rolling updates, when multiple pods can briefly run. The `Webhook` and `BitwardenSDKServer` components do not use leader election, regardless of the replica count.

*advancedOverrides for external-secrets-components*

The `ExternalSecretsConfig` CR supports an `advancedOverrides` field for each entry in the `spec.controllerConfig.componentConfigs` list. Set this field only when dedicated fields do not provide the deployment settings you need. The Operator applies the value as a strategic merge patch onto the operator-generated `Deployment` for that component.

Only the following field paths are allowed:

* `spec.template.spec.affinity`
* `spec.template.spec.tolerations`
* `spec.template.spec.nodeSelector`
* `spec.template.spec.topologySpreadConstraints`
* `spec.template.spec.containers[*].args`
* `spec.template.spec.containers[*].resources`

If you set a field that is outside this allowlist, validation fails and the {external-secrets-operator-short} reports a `Degraded` condition on the `ExternalSecretsConfig` CR. If a dedicated field and the `advancedOverrides` field configure the same setting, the `advancedOverrides` value takes precedence.

*{external-secrets-operator} Transport Layer Security profile support*

The {external-secrets-operator-short} applies the cluster Transport Layer Security (TLS) security profile configured in the `apiserver` cluster object. This object is `apiserver.config.openshift.io/cluster`. The Operator applies the resolved minimum TLS version and cipher suites to the secure serving endpoints of the Operator. Managed operand components with TLS listeners receive equivalent settings.

When a cluster TLS profile is unavailable or not enforced, the {external-secrets-operator-short} uses the default TLS configuration.


[id="external-secrets-operator-1-3-0-bug-fixes_{context}"]
== Fixed issues

* Before this release, secondary watch predicates for managed and watched resources could evaluate only one side of an update event. As a result, some label or resource changes that should have triggered reconciliation were missed. With this release, update predicates evaluate both the old and new objects so that qualifying changes enqueue reconciliation as expected.

* Before this release, some `secret-store` provider calls and readiness checks could bypass the configured Hypertext Transfer Protocol (HTTP) proxy. These requests could attempt a direct connection. When direct egress was blocked, those calls timed out. The `SecretStore` or `ClusterSecretStore` resources could fail validation even when access through the proxy was available. With this release, provider traffic and readiness validation consistently use the configured HTTP proxy.
+
The configuration uses these environment variables:

** `HTTP_PROXY`
** `HTTPS_PROXY`
** `NO_PROXY`
