== New features and enhancements

*Support for replicas on external-secrets components*

With this release, you can set the number of pod replicas for each `external-secrets` component in the `ExternalSecretsConfig` custom resource. You set the `deploymentConfigs.replicas` field of each component entry under the `spec.controllerConfig.componentConfigs` field. The value ranges from 1 to 10, and the default is 1. For the `ExternalSecretsCoreController` and `CertController` components, leader election stays enabled, so only one replica processes changes at a time.

*advancedOverrides for external-secrets-components*

With this release, you can use the `advancedOverrides` field to apply a restricted strategic merge patch to the `Deployment` of an individual `external-secrets` component. You can patch the `affinity`, `tolerations`, `nodeSelector`, and `topologySpreadConstraints` fields, and the container `args` and `resources` fields. A field outside the allowed `Deployment` field paths is rejected and puts the `ExternalSecretsConfig` custom resource into a `Degraded` condition.

*Cluster-wide TLS security profile for the {external-secrets-operator-short}*

With this release, the {external-secrets-operator} follows the cluster-wide Transport Layer Security (TLS) security profile from the cluser `APIServer` custom resource. The Operator does this when the `tlsAdherence` field of that resource requires it. The Operator applies the profile to its own serving endpoints. It also adds the `--tls-min-version` argument and, when applicable, the `--tls-ciphers` argument to the `Deployment` of each `external-secrets` component. As a result, the Operator and its components use the same TLS settings.

[id="external-secrets-operator-1-2-0-bug-fixes_{context}"]
== Fixed issues

* Before this release, outbound provider traffic and `SecretStore` readiness checks did not honor the configured `HTTP_PROXY` and `HTTPS_PROXY` settings. Some providers built bare HTTP transports to apply custom TLS settings, which bypassed the proxy during synchronization. The readiness check also opened a direct network connection that ignored the proxy environment variables. As a result, `ClusterSecretStore` or `SecretStore` resources could fail to become `Ready`, and connections could time out. With this release, provider clients preserve the proxy settings from the environment. The readiness check now uses the proxy-aware provider path instead of opening a direct network connection. (link:https://redhat.atlassian.net/browse/OCPBUGS-91653[OCPBUGS-91653])
