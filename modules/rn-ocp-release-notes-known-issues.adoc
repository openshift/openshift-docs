= Known issues

[role="_abstract"]
Known issues in {product-title} {product-version} can affect nodes, pods, and network devices. Review each issue for its impact and workaround.

* When you run Cloud-native Network Functions (CNF) latency tests on an {product-title} cluster, the test might return results that exceed the latency threshold, such as 20 microseconds for cyclictest testing.
This can result in intermittent test failures even when the cluster is correctly configured for low-latency workloads.
As a workaround, revert the `stalld` backend to `sched_debug` to reduce the frequency and magnitude of latency spikes.
(link:https://redhat.atlassian.net/browse/OCPBUGS-86339[OCPBUGS-86339])

* Deleting and recreating test workloads with a BlueField-3 NIC causes clock jumps due to inconsistent PTP synchronization.
This disrupts time synchronization in test workloads.
The time synchronization stabilizes when the workloads are stable.
(link:https://redhat.atlassian.net/browse/RHEL-93579[RHEL-93579])

* When you use the {op-system-base-full} 10 stream, which is the default for new installations of 5.0 but not for upgrades from 4.22, throughput of messages less than 4KB in size is approximately 30-50% lower than {op-system-base} 9. The regression is most pronounced at small message sizes, for example, 64 bytes and 1 KB, and diminishes at message sizes of 4 KB or larger. (link:https://redhat.atlassian.net/browse/OCPBUGS-128611[OCPBUGS-128611])

* Worker nodes lock up after you apply a performance profile with strict CPU reservation and `isolated` or `reserved` CPUs.
+
When you apply a performance profile that configures strict CPU reservation along with `isolated` and `reserved` CPUs, the worker node locks up and enters a `NotReady` state. This issue occurs because the CPU Manager state file does not match the available CPUs after the node reboots.
+
To work around this problem, clear the CPU Manager state file and restart the kubelet service:
+
. Start a debug session on the affected node:
+
[source,terminal]
----
$ oc debug node/<node_name>
----
+
. Change the root directory to `/host`:
+
[source,terminal]
----
# chroot /host
----
+
. Remove the CPU Manager state file:
+
[source,terminal]
----
# rm /var/lib/kubelet/cpu_manager_state
----
+
. Restart the kubelet service:
+
[source,terminal]
----
# systemctl restart kubelet
----
+
(link:https://redhat.atlassian.net/browse/OCPBUGS-77659[OCPBUGS-77659])

* Currently, pods that use Single Root I/O Virtualization (SR-IOV) virtual functions (VFs) on Intel 710 network interface cards (NICs) might experience delays during deletion. A kernel regression that involves the `netdev` lock causes a deadlock during restoration of the original MAC address of a VF. As a consequence, deleting affected pods takes up to 90 seconds because of a Container Network Interface (CNI) timeout. (link:https://redhat.atlassian.net/browse/OCPBUGS-97994[OCPBUGS-97994])

* Currently, pods that use the `guaranteed` Quality of Service (QoS) class and request whole CPUs might not restart automatically after a node reboot or kubelet restart. This issue can occur on nodes with a static CPU Manager policy and the `full-pcpus-only` specification. It occurs when most or all CPUs on the node are already allocated by such workloads. As a consequence, the affected pods remain in a pending or failed state. To work around this problem, manually delete and re-create the affected pods. (link:https://redhat.atlassian.net/browse/OCPBUGS-43280[OCPBUGS-43280])

* The NUMA Resources Operator deploys a secondary scheduler for non-uniform memory access (NUMA) aware scheduling. When you enable preemption on this scheduler, a stale Node Resource Topology (NRT) cache can cause extra pod evictions.
+
After a pod that requests exclusive resources terminates, the scheduler removes that pod from the list of running pods on the node. A topology updater runs asynchronously and can take a few seconds to record the termination. Until the updater refreshes the NRT cache, the scheduler still treats the resources of the terminated pod as reserved and uses this stale accounting for the next scheduling decision.
+
The NUMA-aware scheduler uses this stale accounting when it cannot place a pod and then checks whether evicting lower-priority pods would free enough resources. If lower-priority pods are running, the scheduler can evict them even though the terminated pod has already released its resources. These evictions can continue until the topology updater refreshes the NRT cache with the released resources.
+
To work around this problem, use a controller, such as a `Deployment`, `ReplicaSet`, or `DaemonSet`, for pods that run on the cluster. The controller re-creates an evicted pod. The scheduler might not place the re-created pod because placement depends on the position of the pod in the scheduling queue.
+
(link:https://redhat.atlassian.net/browse/OCPBUGS-123679[OCPBUGS-123679])

* A pod that the Node Resource Topology (NRT) plugin rejects because of stale NRT information can remain in a pending state after the scheduler refreshes the NRT cache.
+
While a pod is in the unschedulable queue, the scheduler retries the pod only after a node event that changes resource availability or allocatable resources, or after the unschedulable timeout expires. The default timeout is 5 minutes. If the NRT plugin rejects the pod because of stale NRT information, refreshing the NRT cache does not generate one of those events. The pod stays in the unschedulable queue until one of those events occurs.
+
To work around this problem, delete and re-create the pending pod after the scheduler refreshes the NRT cache. You can also schedule a pod on the target node that uses the `guaranteed` Quality of Service (QoS) class and requests a small amount of resources.
+
(link:https://redhat.atlassian.net/browse/OCPBUGS-123706[OCPBUGS-123706])

* While the NUMA-aware scheduler runs preemption attempts for a high-priority pod, an update to the Node Resource Topology (NRT) cache does not stop the scheduler from evicting lower-priority pods.
+
During these attempts, the NRT cache can update and show enough free resources for the high-priority pod. No more resources need to be freed for that pod. The cache update does not stop the preemption flow or the scheduling cycle. As a consequence, the scheduler can still evict lower-priority pods. If the cache is updated before preemption starts and shows enough free resources, the scheduler does not make additional preemption attempts.
+
To work around this problem, use a controller, such as a `Deployment`, `ReplicaSet`, or `DaemonSet`, for pods that run on the cluster. The controller re-creates an evicted pod. The scheduler might not place the re-created pod because placement depends on the position of the pod in the scheduling queue.
+
(link:https://redhat.atlassian.net/browse/OCPBUGS-123515[OCPBUGS-123515])

* Currently, you cannot use Single Root I/O Virtualization (SR-IOV) virtual functions (VFs) as ports in a bond device. The affected VFs are on Intel `i40e` (710 series) or `ice` (E810 series) network interface cards (NICs). A kernel regression causes the `set_mac_address` operation to fail when you add a second VF to the bond. The operation returns `Error -11 calling set_mac_address` (resource temporarily unavailable). As a consequence, the bond device does not become active, and you cannot add the affected VFs to the bond. To work around this problem, do not configure bond devices that use `i40e` or `ice` VFs as ports on affected nodes. (link:https://redhat.atlassian.net/browse/RHEL-143410[RHEL-143410])

* Currently, the `ListenerSet` custom resource definition (CRD) is installed on the cluster, but the {product-title} Gateway API implementation does not support `ListenerSet` resources. As a consequence, a `ListenerSet` that targets a {product-title}-managed `Gateway` is not reconciled, and the listeners that it defines are not programmed onto the `Gateway` and do not route traffic. The `ListenerSet` reports an `Accepted=False` status condition with the `UnsupportedByController` reason, and the `ListenerSetOnManagedGateway` alert fires. As a workaround, define listeners directly on the `Gateway` resource instead of using a `ListenerSet`. (link:https://redhat.atlassian.net/browse/OCPBUGS-100435[OCPBUGS-100435])

* Currently, {op-system-first} version 10 {vmw-first} installer-provisioned infrastructure nodes experience a `serial-getty@ttyS0` restart loop. This state occurs because there is no serial port present. The restart loop causes continuous `mount-table` churn that is visible on every node. In long-lived clusters, this might lead to `node-exporter` memory exhaustion, and control-plane degradation. (link:https://redhat.atlassian.net/browse/OCPBUGS-133499[OCPBUGS-133499])
