= Known issues

[role="_abstract"]
This section includes several known issues for {product-title} {product-version}.

* Worker nodes lock up after applying a performance profile with strict CPU reservation and `isolated` or `reserved` CPUs.
When you apply a performance profile that configures strict CPU reservation along with isolated and reserved CPUs, the worker node locks up and enters a `NotReady` state. This issue occurs because the CPU manager state file does not match the available CPUs after the node reboots.
+
*Workaround:* To resolve this issue, clear the CPU manager state file and restart the kubelet service. You can perform this workaround by using one of the following options:
+
. Start a debug session on the affected node:
+
[source,terminal]
----
$ oc debug node/<node_name>
----
+
. Change your root directory to `/host`:
+
[source,terminal]
----
# chroot /host
----
+
. Remove the CPU manager state file:
+
[source,terminal]
----
# rm /var/lib/kubelet/cpu_manager_state
----
+
. Restart the kubelet service:
+
[source,terminal]
----
# systemctl restart kubelet
----
+
(link:https://redhat.atlassian.net/browse/OCPBUGS-77659[OCPBUGS-77659])

* Currently, pods using Single Root I/O Virtualization (SR-IOV) virtual functions (VFs) on Intel 710 network interface cards (NICs) might experience delays during deletion. A kernel regression involving the `netdev` lock causes a deadlock when restoring the original MAC address of a virtual function (VF). Consequently, deleting affected pods takes up to 90 seconds due to a Container Network Interface (CNI) timeout. (link:https://redhat.atlassian.net/browse/OCPBUGS-97994[OCPBUGS-97994])

* Currently, pods that use the `guaranteed` Quality of Service (QoS) class and request whole CPUs might not restart automatically after a node reboot or kubelet restart. This issue can occur on nodes that are configured with a static CPU Manager policy and use the `full-pcpus-only` specification, when most or all CPUs on the node are already allocated by such workloads. As a consequence, the affected pods remain in a pending or failed state. As a workaround, manually delete and re-create the affected pods. (link:https://redhat.atlassian.net/browse/OCPBUGS-43280[OCPBUGS-43280])

* When you enable preemption on the secondary scheduler with the NUMA Resources Operator (NROP) installed, the Node Resource Topology (NRT) cache does not immediately reflect resources released by terminated pods. As a result, during a preemption cycle, the scheduler could trigger additional, unnecessary pod evictions because the stale cache indicated that resources were still occupied. For more information, see xref:../scalability_and_performance/cnf-numa-aware-scheduling.adoc#cnf-numa-scheduler-preemption-nrt-cache_numa-aware[NodeResourceTopology cache timing considerations].
+
