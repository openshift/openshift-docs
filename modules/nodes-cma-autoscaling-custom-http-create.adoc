= Create an interceptor route and scaled object

[role="_abstract"]
You can scale an HTTP workload by creating an `InterceptorRoute` resource and a `ScaledObject` resource. The interceptor route selects the service and the scaling metric. The scaled object connects that metric to the Custom Metrics Autoscaler Operator.

Create the `InterceptorRoute` resource before the scaled object. If the scaled object is reconciled first, the scaler can return an empty metric specification and the resulting horizontal pod autoscaler uses CPU instead of HTTP traffic.

.Prerequisites

* The HTTP add-on is enabled.
* The workload has a deployment, or another scalable resource, and a service in the same namespace.
* The OpenShift CLI (`oc`) is installed.
* You are logged in to the cluster.

.Procedure

. Create an `InterceptorRoute` resource. For example:
+
.Example interceptor route
[source,yaml]
----
apiVersion: http.keda.sh/v1beta1
kind: InterceptorRoute
metadata:
  name: sample-app
  namespace: my-namespace
spec:
  target:
    service: sample-app <1>
    port: 8080 <2>
  rules:
    - hosts:
        - sample-app.example.com <3>
  scalingMetric:
    concurrency:
      targetValue: 100 <4>
----
<1> Specifies the service that receives forwarded requests.
<2> Specifies the service port.
<3> Specifies the HTTP host to match. This value must be the host that clients send, including the host on the {product-title} route.
<4> Specifies the target number of in-flight requests for each replica. The autoscaler adds replicas when concurrent requests exceed this value.

. Apply the `InterceptorRoute` resource by running the following command:
+
[source,terminal]
----
$ oc apply -f interceptorroute.yaml
----

. Confirm that the interceptor route is ready by running the following command:
+
[source,terminal]
----
$ oc get interceptorroute sample-app -n my-namespace
----
+
.Example output
[source,terminal]
----
NAME         TARGETSERVICE   READY   AGE
sample-app   sample-app      True    10s
----
+
Wait until the `READY` column is `True` before you create the scaled object.

. Create a scaled object that uses the `external-push` trigger. Set `minReplicaCount` to `0` when the workload must scale to zero replicas:
+
.Example scaled object for the HTTP add-on
[source,yaml,subs="+attributes"]
----
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: sample-app
  namespace: my-namespace
spec:
  scaleTargetRef:
    name: sample-app <1>
  minReplicaCount: 0 <2>
  maxReplicaCount: 10 <3>
  cooldownPeriod: 300 <4>
  triggers:
    - type: external-push <5>
      metadata:
        scalerAddress: keda-add-ons-http-external-scaler.{cma-namespace}.svc:9090 <6>
        interceptorRoute: sample-app <7>
----
<1> Specifies the deployment to scale. The deployment must be in the same namespace as the scaled object.
<2> Specifies the minimum replica count. A value of `0` allows scale-to-zero after the cooldown period. Cold-start behavior applies only when the workload can reach zero replicas.
<3> Specifies the maximum replica count.
<4> Specifies how many seconds the metrics must stay at zero before the workload scales down. The default is `300`.
<5> Specifies the external push trigger that receives metrics from the HTTP add-on scaler.
<6> Specifies the HTTP add-on scaler service in the `{cma-namespace}` namespace.
<7> Specifies the `InterceptorRoute` name in the same namespace as the scaled object.

. Apply the scaled object by running the following command:
+
[source,terminal]
----
$ oc apply -f scaledobject.yaml
----

.Verification

. Confirm that the Custom Metrics Autoscaler Operator created a horizontal pod autoscaler by running the following command:
+
[source,terminal]
----
$ oc get hpa -n my-namespace
----
+
The output includes an HPA for `sample-app`, typically named `keda-hpa-sample-app`.

. Send traffic through the interceptor, as described in "Create a route to the HTTP interceptor", and confirm that the deployment replica count changes by running the following command:
+
[source,terminal]
----
$ oc get deployment sample-app -n my-namespace
----
