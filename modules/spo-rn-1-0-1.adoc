= Release notes for OpenShift Security Profiles Operator 1.0.1

[role="_abstract"]
OpenShift Security Profiles Operator 1.0.1 is now available. The `stable` update channel tracks and receives updates for the Security Profiles Operator. The following advisory is available:

* link:https://access.redhat.com/errata/RHSA-2026:97843[RHSA-2026:97843 - OpenShift Security Profiles Operator bug fix and enhancement update]

[id="spo-1-0-1-new-features-and-enhancements_{context}"]
== New features and enhancements

* With this release, every Security Profiles Operator API is available as `v1`, and `v1` is the stored version. The earlier API versions are still served and are converted by the Operator's conversion webhook, so objects created with Security Profiles Operator 0.10 keep working after the upgrade. The `v1alpha1` versions of the `SecurityProfilesOperatorDaemon` and `SecurityProfileNodeStatus` APIs are deprecated.

* With this release, the Security Profiles Operator applies a TLS security profile to the TLS servers of the Operator, the daemon and the webhook. On {product-title}, they use the cluster TLS security profile when the TLS adherence policy is `StrictAllComponents`, and the `Intermediate` profile otherwise. By default, they offer the `X25519MLKEM768`, `X25519`, `secp256r1` and `secp384r1` key exchange groups. The Operator and webhook metrics are now served over TLS on port 8443, with authentication and authorization. (link:https://issues.redhat.com/browse/ROX-34979[ROX-34979], link:https://issues.redhat.com/browse/ROX-38668[ROX-38668])

* This update includes upgraded dependencies in the underlying base images.

[id="spo-1-0-1-notable-technical-changes_{context}"]
== Notable technical changes

* The `v1` `SecurityProfilesOperatorDaemon` API groups most daemon settings into nested fields. Settings that you configured in 0.10 are converted during the upgrade. If you configure the daemon with `oc patch`, use the new field paths:
+
[options="header"]
|===
|0.10 field (`v1alpha1`) |1.0 field (`v1`)

|`spec.enableLogEnricher`
|`spec.enricher.enableLogEnricher`

|`spec.enableJsonEnricher`
|`spec.enricher.enableJsonEnricher`

|`spec.jsonEnricherOptions`
|`spec.enricher.jsonEnricherOptions`

|`spec.selinuxOptions`
|`spec.selinux.options`

|`spec.priorityClassName`
|`spec.scheduling.priorityClassName`

|`spec.webhookOptions`
|`spec.webhook.options`

|`spec.allowedSyscalls`
|`spec.security.allowedSyscalls`
|===
+
A merge patch that uses a 0.10 field name through the `v1` API does not change anything, and the API server returns only a warning about an unknown field. The `nodeName` field of `SecurityProfileNodeStatus` objects is now `spec.nodeName`.

[id="spo-1-0-1-bug-fixes_{context}"]
== Bug fixes

* Before this update, a `ProfileRecording` object that was still recording when the Security Profiles Operator was upgraded from 0.10 never completed: its partial profiles were not merged, and the recording could not be deleted. With this update, the Operator adopts the partial profiles when it starts, merges them into an installed profile, and releases the recording. (link:https://issues.redhat.com/browse/ROX-39218[ROX-39218])

* Before this update, the Security Profiles Operator looked for SELinux profile names with the `_.process` suffix instead of `.process`, so it did not link pods to the SELinux profiles that they use. With this update, the Operator uses the `.process` suffix.
