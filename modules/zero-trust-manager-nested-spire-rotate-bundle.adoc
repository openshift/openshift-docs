= Updating the trust bundle

[role="_abstract"]
Replace `trustBundleSecret` on every nested cluster when the trust domain root certificate authority (CA) changes. A running {spiffe-full} Runtime Environment (SPIRE) agent sidecar learns the new bundle from the parent server. A recreated pod reads the secret.

If the secret still holds the old root, and the old root is no longer in the parent certificate chain, TLS verification fails and the agent cannot attest.

.Prerequisites

* You can read the current trust bundle `ConfigMap` on the cluster that holds the root CA.
* You can update secrets in the Operator namespace on each nested cluster.

.Procedure

. Export the current root bundle by running the following command on the root cluster:
+
[source,terminal]
----
$ oc get configmap spire-bundle -n zero-trust-workload-identity-manager -o jsonpath='{.data.bundle\.crt}' > bundle.crt
----

. On each nested cluster, replace the secret by running the following command:
+
[source,terminal]
----
$ oc create secret generic spire-trust-bundle \
  -n zero-trust-workload-identity-manager \
  --from-file=bundle.crt=bundle.crt \
  --dry-run=client -o yaml | oc apply -f -
----
+
Replace the secret name, if needed.

. Delete the local bundle file by running the following command:
+
[source,terminal]
----
$ rm -f bundle.crt
----

. Rebuild a nested cluster `kubeconfig` and replace secret `nested-spire-<cluster_name>-kubeconfig` on the parent cluster.
+
Keep the data key as `kubeconfig`. Confirm that `DownstreamClustersValid` returns to `True`.

.Verification

* After a nested SPIRE server pod restarts, confirm that the agent sidecar status is `UpstreamAgentAvailable=True Ready` by running the following command:
+
[source,terminal]
----
$ oc get spireserver cluster -o jsonpath='{range .status.conditions[*]}{.type}={.status} {.reason}{"\n"}{end}'
----
