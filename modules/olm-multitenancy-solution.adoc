= Separate Operator instances for individual tenants

[role="_abstract"]
To manage separate Operator instances for individual tenants, install each instance in a namespace separate from the tenant namespace that the instance watches.

The install modes declared in the cluster service version (CSV) must support targeting a single namespace other than the installation namespace. Support for only `OwnNamespace` does not meet this requirement.

Use the following workflow to install multiple instances of the same Operator:

// In OSD/ROSA, dedicated-admins can create projects, but not namespaces.
ifndef::openshift-dedicated,openshift-rosa,openshift-rosa-hcp[]
. Create a namespace for the tenant Operator that is separate from the tenant's namespace.
endif::openshift-dedicated,openshift-rosa,openshift-rosa-hcp[]
ifdef::openshift-dedicated,openshift-rosa,openshift-rosa-hcp[]
. Create a namespace for the tenant Operator that is separate from the tenant's namespace. You can do this by creating a project.
endif::openshift-dedicated,openshift-rosa,openshift-rosa-hcp[]

. Create an Operator group for the tenant Operator. Set `spec.targetNamespaces` to the tenant namespace.
. Install the Operator in the tenant Operator namespace.

The Operator runs in the tenant Operator namespace and watches the tenant namespace. Review `RoleBinding` and `ClusterRoleBinding` objects to determine whether tenants have `get`, `list`, or `watch` permissions for pods and service accounts in the tenant Operator namespace.

A separate Operator instance for each tenant allows you to configure tenant access to the Operator namespace independently of access to the tenant namespace. Each instance requires resources, and you must coordinate the instances to meet the following limitations. For a detailed procedure, see "Preparing for multiple instances of an Operator for multitenant clusters".

[id="olm-multitenancy-permissions-tenant-access_{context}"]
== Permissions and tenant access

Separate Operator namespaces do not by themselves restrict the permissions granted to Operators or tenants. Review the following permissions independently:

* Permissions granted to each Operator to access cluster resources.
* Permissions granted to tenants in each Operator installation namespace, including permissions to create service account tokens or workloads.
* Permissions available to OLM when installing or upgrading an Operator.

// In OSD/ROSA, tenants shouldn't be able to install Operators. Dedicated-admins can, but they can't grant non-admin users the ability to install their own Operators.
ifndef::openshift-dedicated,openshift-rosa,openshift-rosa-hcp[]
[WARNING]
====
Before delegating Operator installation privileges, review the permissions requested by the Operator and the permissions granted to non-administrator users in the installation namespace. For more information, see "Allow non-cluster administrators to install Operators".
====
endif::openshift-dedicated,openshift-rosa,openshift-rosa-hcp[]

[id="olm-multitenancy-shared-apis-version-compatibility_{context}"]
== Shared APIs and version compatibility

Operator instances in separate namespaces share the custom resource definitions (CRDs) installed on the cluster. Separate namespaces do not provide a separate CRD definition for each instance.

For this workflow, use the same Operator version for all instances. Version coordination addresses compatibility with shared CRDs. Using the same Operator version for all instances does not restrict the permissions granted to Operators or tenants.

The following additional restrictions determine whether an Operator can use this workflow. These restrictions do not limit the permissions granted to Operators or tenants:

* The Operator cannot have dependencies on other Operators.
* The Operator cannot ship a CRD conversion webhook.

For information about the supported scenarios for running different Operator versions on the same cluster, see "Limitations for multitenant Operator management".

ifndef::openshift-dedicated,openshift-rosa,openshift-rosa-hcp[]
When delegating Operator installation privileges for this workflow, restrict tenants to a curated catalog containing Operators that do not depend on other Operators. Coordinate installations and upgrades so that all instances use the same Operator version. Create curated catalogs in the Operator installation namespaces.

Catalogs in the global `openshift-marketplace` namespace remain available across the cluster. Disable the default global catalogs and review any custom global catalogs for Operators or versions outside the curated selection. Disabling a global catalog changes catalog availability across the cluster. For more information, see "Operator catalog access control".
endif::openshift-dedicated,openshift-rosa,openshift-rosa-hcp[]

[TIP]
====
If you need one Operator instance to watch multiple selected namespaces, check whether the Operator supports the `MultiNamespace` install mode.
====
