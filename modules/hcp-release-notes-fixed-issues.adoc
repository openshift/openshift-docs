= Fixed issues

[role="_abstract"]
This section lists the fixed issues in this release of {hcp} for {product-title}.

* Before this update, the wrong restoration of `kubeadmin` password hashes caused new passwords not to work in a restored cluster. As a consequence, the restored cluster used the old `kubeadmin` password instead of the new one, resulting in login failure. With this release, the `kubeadmin` password hash mismatch in restored clusters has been addressed, and reconciliation logic has been updated. As a result, new `kubeadmin` passwords in restored clusters now match, allowing successful login. (link:https://redhat.atlassian.net/browse/OCPBUGS-38898[OCPBUGS-38898])

* Before this update, the `control-plane-pki-operator` reported incorrect `certificate revoked` conditions without waiting for CA bundle reloads on Kubernetes API Server. As a consequence, intermittent invalid certificates were issued, causing temporary unauthorized access. This release ensures that the `control-plane-pki-operator` waits for the CA bundle reload, preventing intermittent certificate use. As a result, the `control-plane-pki-operator` correctly reports certificate revocation, ensuring immediate invalidation across all Kubernetes API Server instances. (link:https://redhat.atlassian.net/browse/OCPBUGS-62177[OCPBUGS-62177])

* Before this update, {aws-short} ISO domains were omitted from the `IsCloudAPI` list of the `Konnectivity` service. As a consequence, {aws-short} ISO domain communication was proxied instead of direct, causing necessary endpoints to fail. With this release, {aws-short} ISO domains have been added to the `IsCloudAPI` list for {product-title} 4.21 and later versions. As a result, the `Konnectivity` service now adds {aws-short} ISO domains to the `NO_PROXY` list of the Ingress Operator, enabling direct communication with endpoints in those namespaces. (link:https://redhat.atlassian.net/browse/OCPBUGS-77040[OCPBUGS-77040])

* Before this update, the Hosted Cluster Config Operator would crash loop on an un-customized Kubernetes cluster because the Operator was unconditionally attempting to watch the {product-title} Route resource. With this release, the Operator attempts to watch the resource only when it exists on the management cluster. As a result, the Operator is no longer crash looping on an un-customized Kubernetes cluster. (link:https://issues.redhat.com/browse/OCPBUGS-87364[OCPBUGS-87364])

* Before this update, the `Konnectivity` component of {hcp} failed to add specific {aws-short} ISO regions to the `NO_PROXY` list. As a consequence, the proxy routed cluster communication with these {aws-short} domains instead of sending it directly, causing connectivity issues. With this release, `Konnectivity` component automatically adds {aws-short} ISO domains to the `NO_PROXY` list of the Ingress Operator. As a result, this update resolves {aws-short} ISO domain connectivity issues, enabling direct communication for the required endpoints. (link:https://redhat.atlassian.net/browse/OCPBUGS-85781[OCPBUGS-85781])

* Before this update, the `IsCloudAPI` method for the `Konnectivity` proxy did not include {aws-first} ISO region domain suffixes, such as `.c2s.ic.gov`, `.hci.ic.gov`, or `.sc2s.sgov.gov` in its cloud API detection lists. As a consequence, the Ingress Operator could not add {aws-short} ISO domains to the `NO_PROXY` list, blocking direct communication with endpoints. With this release, the {aws-short} ISO suffixes are added to the `IsCloudAPI` detection list. As a result, the `Konnectivity` proxy correctly identifies the {aws-short} ISO region endpoints as cloud APIs, so that the Ingress Operator can route traffic to those domains directly. (link:https://redhat.atlassian.net/browse/OCPBUGS-85779[OCPBUGS-85779])

* Before this update, the wrong restoration of `kubeadmin` password hashes caused new passwords not to work in a restored cluster. As a consequence, the restored cluster used the old `kubeadmin` password instead of the new one, resulting in login failure. With this release, the `kubeadmin` password hash mismatch in restored clusters has been addressed, and reconciliation logic has been updated. As a result, new `kubeadmin` passwords in restored clusters now match, allowing successful login. (link:https://redhat.atlassian.net/browse/OCPBUGS-38898[OCPBUGS-38898])

* Before this update, the Hosted Cluster Config Operator failed to start on non-OpenShift management clusters due to an unconditional watch for `route.openshift.io` routes. As a consequence, {hcp} deployment was prevented. With this release, the Hosted Cluster Config Operator now ignores route watches on non-OpenShift management clusters, preventing failure during startup. As a result, the Hosted Cluster Config Operator now starts cleanly on non-OpenShift management clusters, improving deployment on un-customized Kubernetes. (link:https://redhat.atlassian.net/browse/OCPBUGS-86008[OCPBUGS-86008])

* Before this update, when a KubeVirt hosted cluster and its management cluster both used OVN-Kubernetes with dual-stack networking, they each defaulted to `fd98::/64` for the IPv6 join switch subnet. As a consequence, external IPv6 `LoadBalancer` traffic targeting VM pods was moved to join IP of the management cluster; for example, `fd98::2`. Inside the VM, the OVN of the hosted cluster intercepts the response because it also owns `fd98::/64`, black-holing the packet and breaking IPv6 connectivity. With this release, the reconciler now automatically sets `IPv6.InternalJoinSubnet` to `fd99::/64`, avoiding the collision with the `fd98::/64` of the management cluster. A new `OVNIPv6Config` API field also allows explicit user configuration of the IPv6 join subnet on any platform. As a result, IPv6 `LoadBalancer` traffic flows correctly in dual-stack KubeVirt hosted clusters without routing collisions between the management and hosted OVN networks. (link:https://redhat.atlassian.net/browse/OCPBUGS-84303[OCPBUGS-84303])

* Before this update, the `HostedCluster` controller set the `AWSDefaultSecurityGroupDeleted` condition on all `HostedCluster` resources during deletion, regardless of platform type. The `AWSDefaultSecurityGroupCreated` condition was correctly gated behind an {aws-short} platform check, but the deletion counterpart had no such gate. As a consequence, non-{aws-short} `HostedCluster` resources, such as {azure-short} and KubeVirt, displayed an {aws-short}-specific `AWSDefaultSecurityGroupDeleted` condition with `Status: Unknown` during deletion, producing misleading status information. With this release, a platform-type check gates the `AWSDefaultSecurityGroupDeleted` condition to {aws-short}-only `HostedCluster` resources, matching the existing pattern used for `AWSDefaultSecurityGroupCreated`.As a result, non-{aws-short} `HostedCluster` resources no longer display the `AWSDefaultSecurityGroupDeleted` condition during deletion. The condition is set for only {aws-short} platform clusters. (link:https://redhat.atlassian.net/browse/OCPBUGS-84971[OCPBUGS-84971])

* Before this update, the `CertificateRevocationController` verified certificate revocation through the Kubernetes API Server service load balancer, which routes to a single pod. In high availability (HA) deployments with three Kubernetes API Server replicas, the check could hit a pod that had loaded the updated trust bundle while others did not, causing premature state transitions in the revocation flow. With this release, the controller has been updated to verify certificate trust and revocation against every individual Kubernetes API Server pod by IP, rather than through the service. Certificate revocation now completes reliably in HA deployments by confirming all Kubernetes API Server pods have propagated the change. (link:https://issues.redhat.com/browse/OCPBUGS-86039[OCPBUGS-86039])

* Before this update, when the `hypershift.openshift.io/restart-date` annotation was set on a `HostedCluster` resource, the `cleanupClusterNetworkOperatorResources` function in the Control Plane Operator restarted several Cluster Network Operator-managed operands, but omitted the `cloud-network-config-controller` deployment. As a consequence, the `cloud-network-config-controller` pod was not restarted when the `restart-date` annotation was applied. Stale cloud API credentials or `kubeconfig` references could persist after rotation, causing cloud networking operations to fail on {aws-short}, {azure-short}, and OpenStack platforms with OVN networking. With this release, the `restart-date` annotation propagation is moved from the Control Plane Operator into the Cluster Network Operator. The Cluster Network Operator reads the `hypershift.openshift.io/restart-date` annotation from the `HostedControlPlane` custom resource and injects it into pod template annotations of all rendered `Deployments`, `DaemonSets`, and `StatefulSets` within the {hcp} namespace. The redundant Control Plane Operator-side restart logic was removed. As a result, when the `restart-date` annotation is set on a `HostedCluster` resource, all Cluster Network Operator-managed operands are now restarted correctly. (link:https://redhat.atlassian.net/browse/OCPBUGS-88531[OCPBUGS-88531])

* Before this update, on dual-stack hosted clusters, Kubernetes API Server certificates churned due to improper IP Subject Alternative Name (SAN) normalization. As a consequence, {hcp} installations with IPv6 public networks repeatedly failed, causing continuous restarts of `kube-apiserver` pods. With this release, IP SANs in certificates have been normalized to stop dual-stack Kubernetes API Server certificate churn. As a result, {hcp} installation no longer fails with IPv6 public networks in `ClusterNetwork` and `ServiceNetwork`, ensuring smooth dual-stack cluster setup. (link:https://redhat.atlassian.net/browse/OCPBUGS-112730[OCPBUGS-112730])

* Before this update, KubeVirt hosted clusters that used Multus as the primary network received `nmstate` IPv6 configuration that was intended for the default OVN network. As a consequence, affected compute nodes could not obtain an IPv6 address through Stateless Address AutoConfiguration (SLAAC), and could not become Ready. With this release, {hcp} conditionally overrides the configuration for IPv6-enabled Multus-primary node pools. As a result, compute nodes can obtain their IPv6 addresses through SLAAC and become Ready. (link:https://redhat.atlassian.net/browse/OCPBUGS-121866[OCPBUGS-121866])

* Before this update, an invalid tagged registry entry in the `blockedRegistries` field of a `HostedCluster` resource caused an error. As a consequence, nodes failed to join the cluster. With this release, a fix validates registry entries. As a result, invalid registry config errors are now caught earlier and reported in node pool condition and ignition logs, making it easier to debug and join the cluster. (link:https://redhat.atlassian.net/browse/OCPBUGS-43353[OCPBUGS-43353])

* Before this update, the Private Link controller retrieved the `DNSZoneID` from {aws-short} instead of the status, causing health checks to enter a continuous reconciliation loop and potential {aws-short} rate limit hits. As a consequence, {aws-short} a Distributed denial-of-service (DDoS) attack was possible. With this release, the controller now uses `Status.DNSZoneID` before it queries {aws-short} Route53, reducing {aws-short} rate limit hits. As a result, {aws-short} rate limits are no longer exceeded due to continuous reconciliation loops in health checks, improving the overall system stability. (link:https://redhat.atlassian.net/browse/OCPBUGS-57453[OCPBUGS-57453])

* Before this update, the error message for installing an unsupported {product-title} patch version was misleading. As a consequence, users encountered difficulties installing unsupported {product-title} release versions. With this release, the error message in the unsupported {product-title} release version selection now shows the correct minor version. As a result, the `HostedCluster` resource no longer enters a degraded state when installing unsupported {product-title} versions beyond 4.18.0. (link:https://redhat.atlassian.net/browse/OCPBUGS-59142[OCPBUGS-59142])

* Before this update, the `oauth-apiserver` resource in {hcp} was started without the `--tls-cipher-suites` argument. With this fix, the `oauth-apiserver` resource now includes the appropriate TLS cipher suites based on the configured TLS security profile. (link:https://redhat.atlassian.net/browse/OCPBUGS-65730[OCPBUGS-65730])

* Before this update, an in-place upgrade error occurred due to an unnamed degraded node during disk validation, causing the upgrade to stall. As a consequence, the degraded node was not identified in logs, resulting in silent upgrade failures. With this release, the upgrade error message now includes the degraded node name. As a result, the degraded node is identified in Hosted Cluster Config Operator logs, and the `NodePool` resource status reflects stalled upgrades, enabling clearer troubleshooting for users. (link:https://redhat.atlassian.net/browse/OCPBUGS-75887[OCPBUGS-75887])

* Before this update, the headless `etcd-client` service caused intermittent peer TLS rejections due to duplicate PTR records, because its IP address was not covered in the DNS SANs of the certificate. As a consequence, intermittent etcd peer connection rejections occurred due to duplicate DNS records in the headless service. With this release, the missing DNS name for the `etcd-client` service has been added to prevent intermittent peer connection rejections. As a result, this bug fix resolves intermittent rejections of etcd peer connections due to duplicate PTR records, improving etcd reliability in bare metal deployments. (link:https://redhat.atlassian.net/browse/OCPBUGS-76530[OCPBUGS-76530])

* Before this update, the validation rule for the API Server `LoadBalancer` hostname in the `servingCerts` section lacked `has()` guards. As a consequence, validation failures occurred during upgrades of {mce-short}, preventing the patching of `HostedCluster` CRDs. With this release, the missing `has()` guards have been fixed in the `servingCerts` validation rule. As a result, validation failures during `HostedCluster` CRD patching are resolved, enabling successful {mce-short} upgrades. (link:https://redhat.atlassian.net/browse/OCPBUGS-77827[OCPBUGS-77827])

* Before this update, non-{aws-short} platforms triggered repetitive vCPU log messages due to unsupported platform usage in metrics collection. As a consequence, repetitive `info` logs created rapid log growth in complex environments. With this release, repetitive vCPU logs for non-{aws-short} platforms are removed from the metrics collector. As a result, repetitive vCPU log messages are suppressed, reducing log noise for non-{aws-short} users. (link:https://redhat.atlassian.net/browse/OCPBUGS-81631[OCPBUGS-81631])

* Before this update, when multiple node pools in a hosted cluster on {aws-short} referenced subnets in the same availability zone (AZ), VPC endpoint reconciliation failed with an {aws-short} `DuplicateSubnetsInSameZone` error. The {aws-short} API requires at most one subnet per AZ per VPC endpoint, so affected clusters experienced indefinite endpoint unavailability. With this update, the Control Plane Operator deduplicates subnets by AZ before calling the {aws-short} endpoint API, selecting one subnet per AZ deterministically. VPC endpoint reconciliation no longer fails due to multiple subnets in the same AZ. (link:https://redhat.atlassian.net/browse/OCPBUGS-82443[OCPBUGS-82443])

* Before this update, in hosted clusters on OpenShift Virtualization, users could not change the default storage class. With this release, users can set a different default storage class other than `kubevirt-csi-infra-default` on hosted clusters on OpenShift Virtualization. (link:https://redhat.atlassian.net/browse/OCPBUGS-43444[OCPBUGS-43444])

* Before this update, a substring matching approach for skipping HTTP proxy in the `noProxy` list caused the Node-local API to always tunnel via the proxy. As a consequence, TLS handshake timeouts and workload failures occurred. With this release, standard `NO_PROXY` matching is used for `skipProxyForKAS`. As a result, the API server no longer tunnels via the proxy for excluded hostnames in `NO_PROXY`, improving the stability of workloads and Operator experience. (link:https://redhat.atlassian.net/browse/OCPBUGS-83328[OCPBUGS-83328])

* Before this update, during hosted cluster creation on {azure-short}, the private DNS zone creation for the base domain shadowed `*.apps` DNS resolution. As a consequence, hosted clusters on {azure-short} failed to provision due to DNS resolution errors. With this release, the fix prevents {azure-short} private DNS zone shadowing of the apps domain when `externalDNSDomain` equals `name.baseDomain`. As a result, creating hosted clusters on {azure-short} no longer results in console and ingress failures due to DNS resolution errors. (link:https://redhat.atlassian.net/browse/OCPBUGS-85351[OCPBUGS-85351])

* Before this update, during a KubeVirt `NodePool` rolling update, the HyperShift Operator deleted the old `userdata` Secret as soon as a new configuration version was computed, while existing worker VMs still referenced it. As a consequence, the worker VMs failed to mount the `cloudinitvolume-udata` volume, blocking live migration and potentially stalling infrastructure and hub cluster upgrades. This release extended the existing `userdata` Secret retention logic to also cover the KubeVirt platform, deferring Secret cleanup until the rollout is complete and all old-generation VMs are gone. As a result, KubeVirt worker VMs continue to operate and live-migrate normally during `NodePool` rolling updates. (link:https://redhat.atlassian.net/browse/OCPBUGS-86494[OCPBUGS-86494])

* Before this update, the Control Plane Operator attempted to delete the {aws-short} default security group during `HostedCluster` resource deletion, but skipped the health check due to an early return, causing an infinite re-queue loop when the OIDC provider was deleted before the `HostedCluster` resource. As a consequence, the `HostedCluster` resource leaked on the management cluster, causing test failures and resource waste. With this release, the health check controller now evaluates {aws-short} credentials during deletion, preventing the infinite re-queue loop when the OIDC provider is deleted. As a result, the `HostedCluster` resource deletion process no longer gets stuck in a loop, preventing permanent resource leaks when the OIDC provider is removed before the `HostedCluster` resource. (link:https://redhat.atlassian.net/browse/OCPBUGS-91511[OCPBUGS-91511])
