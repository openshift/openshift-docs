= Nested SPIRE requirements

[role="_abstract"]
You must set the trust domain, cluster names, certificate authority (CA) lifetimes, and network paths before you configure nested {spiffe-full} Runtime Environment (SPIRE).

*Supported clusters*

Use nested SPIRE on standalone clusters. Hosted control planes, {sno}, and {ms} do not support nested SPIRE.

A nested server chains to exactly one parent server. The `clusters` list accepts at most 100 names. Use a unique name in the `clusters` list.

A three-tier layout is a root, an optional mid-tier, and leaf clusters. Deeper chains lengthen the certificate path and add time at each CA rotation.

You must meet the following requirements on every cluster in the hierarchy:

* Same trust domain: Set the same `spec.trustDomain` on every `ZeroTrustWorkloadIdentityManager` custom resource (CR). You cannot change `spec.trustDomain` after you set it.
* Same Operator namespace: Install {zero-trust-full} in the same namespace on every cluster. The product default is `zero-trust-workload-identity-manager`. A mismatch causes attestation to fail.
* Stable cluster name: The `spec.clusterName` field on the nested CR is the name you register on the parent CR. You cannot change `spec.clusterName`. Set it to a DNS subdomain of at most 63 characters.
* Single SPIRE server replica: Keep one SPIRE server replica. The server pod is `spire-server-0`.
* One authority plugin: Set only one of `spec.upstreamAuthority.certManager`, `spec.upstreamAuthority.vault`, or `spec.upstreamAuthority.spire`.

The agent sidecar uses `k8s_psat` attestation only.

*Certificate lifetime*

The `spec.caValidity` field sets the SPIRE server CA lifetime. A child CA cannot outlive the parent CA that signed it. If the parent has less time remaining than the child requests, SPIRE shortens the child certificate.

You must assign each child CA to at most one sixth of the parent CA lifetime, and to at most 7 days. For 1-hour workload certificates, you must assign an 8-hour leaf CA and a 64-hour parent CA meet that guidance.

The `spec.defaultX509Validity` field sets the workload certificate lifetime. It does not set the intermediate CA lifetime.

If the root CA comes from an external public key infrastructure (PKI), set the issuing CA path length so that it covers every intermediate tier.

[IMPORTANT]
====
You must enable nested SPIRE before the nested server issues workload identities. A server that already has a self-signed CA keeps that CA until the next rotation. Until then, new certificates do not chain to the shared root. To switch immediately, re-initialize the SPIRE server datastore during a maintenance window.
====

*Connectivity*

Make sure the nested SPIRE server pods can reach the parent gRPC endpoint. The default port is `443`/TCP. Make sure the parent SPIRE server pods can reach each nested cluster API server, typically on port `6443`/TCP.

When you set `spec.managedRoute` to `"true"`, ensure cluster ingress can reach the SPIRE server gRPC port `8081`/TCP. Clients still connect to the route on port `443`. {zero-trust-full} adds `NetworkPolicy` rules for the gRPC connection and the nested API connection.

*JWT keys and federation bundles*

Each SPIRE server publishes its own JWT signing keys in the shared JSON Web Key Set (JWKS). Rotation keeps a current key and a next key, so the key count grows with the number of servers. Some token consumers limit how many keys they accept. X.509 issuance can succeed after JWT verification starts to fail.

Nested SPIRE does not propagate federated trust bundles. To trust another trust domain, create `ClusterFederatedTrustDomain` resources on the nested cluster. See "Configuring Zero Trust Workload Identity Manager SPIRE federation".
