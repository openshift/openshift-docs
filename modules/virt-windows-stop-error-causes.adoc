= Common causes of Windows stop errors

[role="_abstract"]
Review the following common causes of Windows stop errors on {VirtProductName} and {op-system-base-full} KVM hosts, along with their resolutions and workarounds.

AMD CPU microcode issues::
On AMD CPUs, outdated firmware can trigger stop errors such as `PFN_LIST_CORRUPT` (`0x4e`), `IRQL_NOT_LESS_OR_EQUAL` (`0xa`), and `SYSTEM_SERVICE_EXCEPTION` (`0x3b`). Stop errors with varying codes, including `BAD_POOL_HEADER` (`0x19`), can also occur after you migrate a VM from VMware to {VirtProductName} on AMD EPYC hosts. The cause is a known issue in the `hv-tlbflush` Hyper-V enlightenment that corrupts guest kernel memory. Because the corruption affects essentially random guest kernel memory, a third-party antivirus or endpoint detection and response (EDR) driver is often listed in the resulting crash stack, but is typically not the cause.
+
To resolve this issue, update your hardware firmware to microcode version `0xb002151` or later, or upgrade the {op-system-base-full} or {product-title} hypervisor to a fixed kernel version.
+
As a workaround on an affected VM, disable the `tlbflush` Hyper-V enlightenment:
+
[source,terminal]
----
$ oc patch vm <vm_name> -n <namespace> --type merge -p '{"spec":{"template":{"spec":{"domain":{"features":{"hyperv":{"tlbflush":{"enabled":false}}}}}}}}'
----
+
[IMPORTANT]
====
This change takes effect only after you stop and start the VM. A guest-level reboot or live migration is not sufficient. Apply this workaround only to actively affected VMs, because disabling `tlbflush` has a performance cost.
====

Storage I/O delays::
Stop errors such as `MEMORY_MANAGEMENT` (`0x1a`), `KERNEL_DATA_INPAGE_ERROR` (`0x7a`), `PAGE_FAULT_IN_NONPAGED_AREA` (`0x50`), and `CRTCL_PROCESS_DIED` (`0xef`) can occur when storage I/O delays of 60 seconds or more cause the Windows guest to time out during a paging operation.
+
To resolve this issue, investigate and resolve any storage latency, and ensure the VM has sufficient RAM for its workload to avoid excessive use of the page file.
+
As a temporary workaround while you investigate storage delays, increase the I/O timeout value in the Windows guest registry for the storage driver that the VM uses:
+
--
* `HKLM\System\CurrentControlSet\Services\viostor\Parameters\IoTimeoutValue` for `virtio-blk`
* `HKLM\System\CurrentControlSet\Services\vioscsi\Parameters\IoTimeoutValue` for `virtio-scsi`
--
+
[NOTE]
====
Increasing the I/O timeout value does not resolve the underlying storage delay and can mask ongoing performance issues.
====

Virtio-blk multiqueue driver issue::
A `MEMORY_MANAGEMENT` (`0x1a`) stop error can also occur with no storage latency present, due to a driver issue that affects `virtio-blk` when multiqueue is enabled.
+
To resolve this issue, update the Windows guest `virtio-win` drivers to version 1.9.53-0.el9_6 or later.

Windows update compatibility on AMD processors::
After certain Windows updates, a Windows Server or Windows desktop VM running on an AMD CPU can fail to boot with an `UNSUPPORTED_PROCESSOR` (`0x5d`) stop error. This is a Microsoft Windows issue.
+
To resolve this issue, install the corresponding Microsoft update for your Windows version.
+
As a temporary workaround, disable the `arch-capabilities` CPU feature in the VM specification:
+
[source,yaml]
----
spec:
  template:
    spec:
      domain:
        cpu:
          features:
            - name: arch-capabilities
              policy: disable
----
+
[IMPORTANT]
====
Disabling `arch-capabilities` can affect VM performance. Use this workaround only until you apply the Microsoft update, and then revert the change.
====
+
Alternatively, set the VM CPU model to `EPYC`:
+
[source,yaml]
----
spec:
  template:
    spec:
      domain:
        cpu:
          model: EPYC
----

Leftover drivers after VMware migration::
A VM migrated from VMware can rarely experience a `HYPERVISOR_ERROR` (`0x20001`) stop error, particularly when nested virtualization features such as WSL, Hyper-V, or Virtualization-based security (VBS) are enabled. This can occur when a leftover VMware `VMMemCtl` driver remains active on the guest after migration.
+
To resolve this issue, remove any leftover VMware drivers from the Windows guest after migration.

Sapphire Rapids CPU boot failures::
A VM that uses an Intel Sapphire Rapids CPU model, or `host-model` or `host-passthrough` on a Sapphire Rapids host, can fail to boot or experience a stop error when nested virtualization features such as WSL, Hyper-V, or VBS are enabled. This issue primarily affects VMs migrated from VMware and VMs configured with more than one CPU core.
+
This issue is resolved in Windows updates released after January 2025. If you cannot update Windows, set the VM to use a lower CPU model as a workaround.

Virtio graphics crash dump failure::
When a Windows guest that uses virtio graphics crashes, it might not generate a memory dump, even when the guest is configured to create a complete memory dump.
+
To resolve this issue, update the Red{nbsp}Hat VirtIO GPU DOD controller driver in the Windows guest to `virtio-win` version 1.9.57-0 or later.
+
As a workaround to capture a memory dump, switch the VM video device to `vga`:
+
[source,yaml]
----
spec:
  template:
    spec:
      domain:
        devices:
          video:
            type: vga
----
