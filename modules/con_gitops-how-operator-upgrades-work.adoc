= How Operator upgrades work (OLM automatic vs. manual)

[role="_abstract"]
Understand how the Operator Lifecycle Manager (OLM) handles {gitops-title} Operator upgrades, including the differences between automatic and manual approval strategies.

*Operator upgrade process*

When a new {gitops-title} Operator version is released to your subscription channel, OLM performs the following steps:

. OLM detects the new version in the update channel
. OLM creates an `InstallPlan` containing the upgrade details
. Based on the approval strategy:
** *Automatic*: OLM approves the InstallPlan automatically
** *Manual*: The InstallPlan requires explicit approval by a cluster administrator
. After approval, OLM executes the upgrade:
.. Downloads the new Operator image
.. Updates the ClusterServiceVersion (CSV)
.. Restarts the Operator pod with the new version
.. The Operator reconciles managed Argo CD instances
. Argo CD component pods restart with updated versions

*Automatic approval*

With automatic approval:

* Upgrades install immediately when available in the subscription channel
* Requires no manual intervention
* Suitable for non-production environments or when you want the latest updates automatically
* Upgrades occur during OLM's reconciliation cycle, which can be at any time

*Benefits:*

* Always on the latest supported version
* No administrative overhead for approving updates
* Security fixes and patches apply quickly

*Risks:*

* Unexpected downtime if an upgrade causes issues
* Breaking changes may affect applications without warning
* Limited control over when upgrades occur

*Manual approval*

With manual approval:

* Upgrades require explicit approval through the {OCP} web console or CLI
* Administrators control when upgrades occur
* Suitable for production environments where change control is required
* Pending upgrades accumulate until approved

*Benefits:*

* Control over upgrade timing (for example, during maintenance windows)
* Opportunity to review release notes and test in non-production first
* Aligns with change management processes
* Prevents unexpected disruptions

*Risks:*

* May miss critical security updates if approvals are delayed
* Requires active monitoring for available updates
* Accumulated upgrades may introduce multiple changes at once

*Changing approval strategy*

Change the approval strategy by editing the Subscription:

[source,terminal]
----
$ oc edit subscription openshift-gitops-operator -n openshift-gitops-operator
----

Update the `installPlanApproval` field:

*Automatic approval:*
[source,yaml]
----
spec:
  installPlanApproval: Automatic
----

*Manual approval:*
[source,yaml]
----
spec:
  installPlanApproval: Manual
----

*Upgrade channels*

{gitops-title} provides update channels for managing upgrade scope:

* *stable* - Recommended for production; includes thoroughly tested releases
* *latest* - Includes the newest features; may have less extensive testing
* *gitops-<version>* - Channel-specific to a particular minor version (for example, `gitops-1.21`)

Select channels based on your stability and feature requirements. You cannot downgrade to an older channel once upgraded.

*Rollback considerations*

Operator upgrades are generally not reversible:

* OLM does not support automatic rollback of Operator versions
* CRD updates from upgrades persist and may not be compatible with older Operator versions
* To roll back, you must uninstall the Operator and reinstall the previous version
* Application data and configurations may be affected during rollback

Instead of rolling back:

* Test upgrades in non-production environments first
* Use manual approval for production upgrades
* Maintain backups of Argo CD custom resources before upgrades
* Keep applications in a known-good Git state to enable redeployment
