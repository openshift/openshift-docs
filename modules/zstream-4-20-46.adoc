== Fixed issues

* Before this update, the Kube API server Operator deployment disabled automatic service account token mounting and explicitly defined a `kube-api-access` projected volume. As a consequence, the Operator maintained a redundant custom configuration alongside default bound service account token volume injection. With this release, the explicit `kube-api-access` projected volume is removed, and automatic service account token mounting is re-enabled in the Kube API server Operator. As a result, manual configuration is replaced with the default injected volume.(link:https://issues.redhat.com/browse/OCPBUGS-60496[OCPBUGS-60496])

* Before this update, `syncPodsForUserDefinedNetwork()` returned an unhandled `InvalidPrimaryNetworkError` when a namespace had the primary user-defined network (UDN) label but no valid UDN or NetworkAttachmentDefinition (NAD). As a consequence, the UDN controller could stall for up to 60 seconds and block pod creation in other correctly configured namespaces. With this release, `InvalidPrimaryNetworkError` is handled gracefully during pod sync. As a result, the UDN controller initializes without being stalled by misconfigured namespaces. (link:https://issues.redhat.com/browse/OCPBUGS-121361[OCPBUGS-121361])

* Before this update, when reconciling virtual machines (VMs) on {azure-first}, a creation operation could fail and leave a virtual network interface controller (NIC) attached to a load balancer without a corresponding VM. As a consequence, the load balancer could not be used until the orphaned NIC was removed. With this release, the reconciler cleans up orphaned NICs when VM creation fails. As a result, load balancers are not blocked by orphaned NICs after a failed VM creation. (link:https://issues.redhat.com/browse/OCPBUGS-133111[OCPBUGS-133111])

* Before this update, an infinite boot loop occurred during Lenovo SR645 V3 hardware provisioning after {op-system-first} was written to the disk. As a consequence, the host stalled on a boot option restoration screen and could not complete the provisioning. With this release, the `ironic` resource skips setting the boot device. As a result, non-volatile random-access memory (NVRAM) loss does not occur, and provisioning succeeds. (link:https://issues.redhat.com/browse/OCPBUGS-134139[OCPBUGS-134139])

* Before this update, the `AWSMachine` controller queued machine instances again before confirming the presence of tags. As a consequence, duplicate {aws-first} EC2 instances were created. With this release, the `AWSMachine` controller verifies tags before it queues instances again. As a result, duplicate EC2 instances are not created. (link:https://issues.redhat.com/browse/OCPBUGS-134665[OCPBUGS-134665])
