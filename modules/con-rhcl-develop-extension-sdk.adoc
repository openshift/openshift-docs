= Extension SDK with {prodname}

[role="_abstract"]
An extension is an ordinary workload that you own and deploy yourself. You can build, roll out, and roll back extensions that each add a new policy kind against the {prodname} Operator on your own release cadence as required.

You might build an extension when the following situations exist:

* A workflow requires coordinating multiple `Kuadrant` policies behind a single interface. For example, when an `OIDCPolicy` custom resource (CR) creates `AuthPolicy` CRs and `HTTPRoute` CRs for OAuth purposes.
* You need information from the {prodname} topology to configure your implementation, such as when you need to extract `Gateway` listener details, `HTTPRoute` configurations, or other policy states.
* You need to influence {prodname} data plane components with dynamic data that adapts to topology changes.

Extensions are controllers that run as separate processes and communicate with the {prodname} Operator with gRPC over UNIX domain sockets. Each extension takes the following actions:

* Defines a Custom Resource Definition (CRD) with a `spec`.
* Runs as a separate controller process that reconciles instances of that CRD.
* Creates and manages `Kuadrant` policies such `AuthPolicy`, `RateLimitPolicy`, `DNSPolicy`, and `TLSPolicy` objects.
* Creates and manages Gateway API resources such as `HTTPRoute` CRs.
* Creates and manages Kubernetes resources such as `ConfigMaps`, `Secrets`, and `Services`.
* Publishes data bindings that influence downstream policy configurations.
* Evaluates common expression language (CEL) expressions with access to {prodname} topology.

The {prodname} Operator maintains an in-memory graph of Gateway API resources and `Kuadrant` policies. This is the topology. Your extension can query it with CEL expressions to discover relationships and extract configuration. This lets you build context-aware extensions that adapt to cluster state instead of requiring configuration to be duplicated in multiple places.
