= Release notes for {pipelines-title} 1.22.6

[role="_abstract"]
With this update, {pipelines-title} General Availability (GA) 1.22.6 is available on {OCP} 4.14, 4.16, and later supported versions.

[id="breaking-changes-1-22-6_{context}"]
== Breaking changes

.Manual Approval Gate

//SRVKP-12172
Manual Approval Gate controller role binding update::
Before this update, the Manual Approval Gate controller role binding included the `system:authenticated` group. As a result, any authenticated user or service account in the cluster could approve, reject, list, or describe approval tasks across namespaces without requiring specific RBAC permissions. With this update, the `system:authenticated` group is removed from the controller role binding. As a result, users and service accounts require explicit role bindings to manage approval tasks. To grant users approval task access, create a `RoleBinding` to the `manual-approval-gate-approver` `ClusterRole` in the relevant namespace. This `ClusterRole` is shipped with Manual Approval Gate and provides the minimum required permissions.
+
link:https://redhat.atlassian.net/browse/SRVKP-12172[SRVKP-12172]

[id="fixed-issues-1-22-6_{context}"]
== Fixed issues

.Manual Approval Gate

//SRVKP-12509
Manual Approval Gate spec field immutability::
Before this update, the Manual Approval Gate webhook did not enforce immutability on task parameters during updates. As a result, an approver could modify `spec.numberOfApprovalsRequired` or `spec.description` while submitting an approval, bypassing multi-approver requirements. With this update, the webhook enforces immutability on these fields for existing approval tasks.
+
link:https://redhat.atlassian.net/browse/SRVKP-12509[SRVKP-12509]

//SRVKP-12510
Manual Approval Gate approver list validation::
Before this update, the Manual Approval Gate webhook did not validate newly appended entries in `spec.approvers` during task updates. As a result, an approver could inject additional approver entries with a pre-approved status during their own approval action. With this update, the webhook rejects attempts to add, remove, or modify the identity of entries in `spec.approvers` on existing approval tasks.
+
link:https://redhat.atlassian.net/browse/SRVKP-12510[SRVKP-12510]

.Pipelines as Code

//SRVKP-12791
Pipelines as Code repository authorization check::
Before this update, Pipelines as Code did not verify whether a user creating or updating a Repository custom resource had permission to create pipeline runs in the target namespace. As a result, a user with repository creation access could trigger pipeline run execution by using the default pipeline service account in the target namespace. With this update, the Pipelines as Code validating webhook performs a Kubernetes SubjectAccessReview to ensure the requesting user has permission to create pipeline runs in the target namespace before accepting Repository custom resources.
+
link:https://redhat.atlassian.net/browse/SRVKP-12791[SRVKP-12791]

.Tekton CLI

//SRVKP-13570
Tekton CLI plugin resolution fallback::
Before this update, when the home directory (`$HOME`) was unresolvable, the Tekton CLI (`tkn`) plugin discovery fell back to searching the current working directory. As a result, executing `tkn` in a directory containing an unvalidated plugin binary could result in untrusted code execution. With this update, plugin discovery requires a valid home directory resolution and does not fall back to searching the current working directory.
+
link:https://redhat.atlassian.net/browse/SRVKP-13570[SRVKP-13570]

//SRVKP-13859
Tekton CLI non-executable plugin discovery::
Before this update, the Tekton CLI (`tkn`) plugin discovery checked file existence in the plugin directory without verifying the execute permission bit. As a result, `tkn` identified non-executable files matching `tkn-<name>` as valid plugins. With this update, plugin discovery verifies that candidate files have execute permissions (`0o111`) before registering them as valid plugins.
+
link:https://redhat.atlassian.net/browse/SRVKP-13859[SRVKP-13859]

.Multi-cluster proxy

//SRVKP-13585
Multi-cluster proxy pod ownership validation::
Before this update, multi-cluster proxy handlers accepted caller-supplied pod names and retrieved pod status or logs from worker clusters without validating ownership against the referenced pipeline run. As a result, users with access to a pipeline run could read status and log data for unauthorized pods in the same namespace on remote worker clusters. With this update, multi-cluster proxy handlers perform ownership validation between requested pods and referenced pipeline runs.
+
link:https://redhat.atlassian.net/browse/SRVKP-13585[SRVKP-13585]

//SRVKP-13791
List access required for TaskRun and Pod resources::
Before this update, the proxy did not verify that the caller was allowed to list TaskRun or Pod resources. As a consequence, callers could retrieve TaskRun or Pod data without list permission. With this update, the proxy verifies list permission in the namespace before processing those requests. As a result, callers without that access receive a 403 response.
+
link:https://redhat.atlassian.net/browse/SRVKP-13791[SRVKP-13791]

//SRVKP-13795
Multi-cluster proxy reuses Kubernetes clients per request::
Before this update, every inbound request created fresh Kubernetes clientsets with new TLS connections, both for authorization checks (one per caller token) and for worker cluster calls (one per handler invocation). Under load this could exhaust file descriptors and TCP connections, degrading service for all users. With this update, the proxy no longer builds a client per request. Authorization uses TokenReview and SubjectAccessReview on the existing service account client instead of SelfSubjectAccessReview. Worker clientsets are cached and reused, and you can rate-limit worker clients with the client-qps and client-burst settings.
+
link:https://redhat.atlassian.net/browse/SRVKP-13795[SRVKP-13795]

//SRVKP-13789
Proxy service account secret access limitation::
Before this update, the proxy service account could read any Secret in any namespace, which was broader than necessary to load MultiKueue worker kubeconfigs. With this update, that access is limited to get operations on the specific Secrets in the WorkersSecretNamespace namespace.
+
link:https://redhat.atlassian.net/browse/SRVKP-13789[SRVKP-13789]

//SRVKP-13796
Proxy Deployment security context settings::
Before this update, the proxy Deployment defined no pod-level or container-level security context settings. With this update, the proxy Deployment defines pod-level and container-level security context settings.
+
link:https://redhat.atlassian.net/browse/SRVKP-13796[SRVKP-13796]

.Tasks

//SRVKP-14125
`git-clone` task option injection protection::
Before this update, the `git-clone` task appended user-controlled `revision` and `refspec` parameters directly to `git fetch` and `git checkout` commands without option separators. As a result, passing values starting with hyphens allowed flag injection and arbitrary command execution. With this update, input validation and option separators (`--`) prevent parameter values from being parsed as Git options.
+
link:https://redhat.atlassian.net/browse/SRVKP-14125[SRVKP-14125]

//SRVKP-14126
`git-clone` task credential redaction in logs and results::
Before this update, the `git-clone` task did not redact embedded user credentials from repository clone URLs. As a result, repository URLs containing embedded usernames and tokens appeared in container logs, termination messages, and task results. With this update, credential redaction strips user information from repository URLs before writing logs or task results.
+
link:https://redhat.atlassian.net/browse/SRVKP-14126[SRVKP-14126]

//SRVKP-14127
`git-clone` task path traversal protection::
Before this update, the `git-clone` task did not validate the `subdirectory` parameter against relative path traversal sequences (such as `../../`). As a result, setting `subdirectory` to a path outside the workspace caused automated workspace cleanup functions (`cleandir()`) to delete files outside the intended target directory. With this update, path traversal guards prevent checkout targets from resolving outside workspace boundaries.
+
link:https://redhat.atlassian.net/browse/SRVKP-14127[SRVKP-14127]

//SRVKP-14128
`git-clone` task credential persistence in shared workspaces::
Before this update, the `git-clone` task copied `.git-credentials` and `.ssh` private keys into the directory specified by `userHome` without validating whether the path resolved inside a shared workspace. As a result, sensitive credentials persisted on shared persistent volume claims (PVCs) and were accessible by subsequent tasks or tenants. With this update, path validation prevents copying credentials into shared workspace paths.
+
link:https://redhat.atlassian.net/browse/SRVKP-14128[SRVKP-14128]
