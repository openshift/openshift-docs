= Release notes for the Multiarch Tuning Operator 1.4.1

[role="_abstract"]
The release notes for the Multiarch Tuning Operator 1.4.1 summarize all new features and enhancements, notable technical changes, major corrections from the previous version, and any known bugs upon general availability.

Some linked Jira tickets are accessible only with Red{nbsp}Hat credentials.

Issued: 24 November 2026

[id="multi-arch-tuning-operator-1-4-1-new-features-and-enhancements_{context}"]
== New features and enhancements

* With this release, the Multiarch Tuning Operator (MTO) is supported on {product-title} 5.0. MTO is delivered through both the 4.22 and 5.0 catalogs, and you do not need to update MTO when you upgrade a cluster from 4.22 to 5.0. link:https://redhat.atlassian.net/browse/MULTIARCH-6457[(MULTIARCH-6457)]

* With this release, the MTO cluster service version (CSV) includes sample custom resources for the `ClusterPodPlacementConfig`, `PodPlacementConfig`, and `ENoExecEvent` objects. You can use these samples as a starting point when you create these objects. link:https://redhat.atlassian.net/browse/MULTIARCH-6564[(MULTIARCH-6564)]

[id="multi-arch-tuning-operator-1-4-1-technical-changes_{context}"]
== Technical changes

* With this release, the `spec.plugins` field in the namespace-scoped `PodPlacementConfig` object is optional. In MTO versions prior to 1.4.1, this field was required. Existing `PodPlacementConfig` objects that omit the `plugins` field continue to pass validation after you upgrade. link:https://redhat.atlassian.net/browse/MULTIARCH-6340[(MULTIARCH-6340)]
+
[IMPORTANT]
====
If you create a `PodPlacementConfig` object that omits the `spec.plugins` field, do not downgrade MTO to version 1.3.x until you add the `plugins` field to that object. You can set the field to an empty value, such as `plugins: {}`.
====

* With this release, MTO uses the `k8s.io/client-go/tools/events` API instead of the deprecated `k8s.io/client-go/tools/record` API. Events that the pod placement controller, the pod placement webhook, and the `ENoExecEvent` controller generate now include an action that identifies the event. link:https://redhat.atlassian.net/browse/MULTIARCH-6087[(MULTIARCH-6087)]

* MTO has been updated to use `go` version 1.26.10. link:https://redhat.atlassian.net/browse/MULTIARCH-6533[(MULTIARCH-6533)]

[id="multi-arch-tuning-operator-1-4-1-bug-fixes_{context}"]
== Bug fixes

* Previously, if a transient API error occurred when MTO checked whether the monitoring API was available, MTO cached that error as a permanent absence of the API. As a result, MTO did not create `ServiceMonitor` or `PrometheusRule` objects, even after the monitoring API became available. With this release, MTO caches the result only when the monitoring API is definitively absent and retries the check after a transient error. link:https://redhat.atlassian.net/browse/MULTIARCH-6361[(MULTIARCH-6361)]

[id="multi-arch-tuning-operator-1-4-1-security-fixes_{context}"]
== Security fixes

* Previously, responses from the MTO admission and conversion webhooks did not include the `Strict-Transport-Security` and `X-Content-Type-Options` headers. With this release, the webhooks set both headers on their responses. link:https://redhat.atlassian.net/browse/MULTIARCH-6528[(MULTIARCH-6528)]
