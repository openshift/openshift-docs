= Troubleshooting DOCA Platform Framework

[role="_abstract"]
Use the following troubleshooting procedures to diagnose and resolve common issues with DPF installation, DPU provisioning, and cluster operations.
These procedures supplement the official NVIDIA debugging tools and documentation.

== DPU provisioning issues

If DPU provisioning does not start immediately after adding worker nodes to the cluster, use the following diagnostic steps to identify the root cause.

.Procedure

. Verify that all worker certificate signing requests (CSRs) are approved:
+
[source,terminal]
----
$ oc get csr
----
+
.Example output
[source,terminal]
----
NAME        AGE   SIGNERNAME                                    REQUESTOR                 CONDITION
csr-abc12   5m    kubernetes.io/kube-apiserver-client-kubelet   system:serviceaccount:... Approved,Issued
csr-def34   5m    kubernetes.io/kubelet-serving                 system:node:worker-1      Approved,Issued
----
+
Look for CSRs in a `Pending` state and approve them manually if automatic approval is not configured:
+
[source,terminal]
----
$ oc adm certificate approve <csr-name>
----

. Verify that all DPF Controller pods are running:
+
[source,terminal]
----
$ oc get pod -n dpf-operator-system
----
+
.Example output
[source,terminal]
----
NAME                                        READY   STATUS    RESTARTS   AGE
dpf-operator-controller-manager-...         2/2     Running   0          10m
dpfhcp-provisioner-controller-manager-...  2/2     Running   0          8m
----
+
If any pods are not in a `Running` state, check their logs:
+
[source,terminal]
----
$ oc logs -n dpf-operator-system deployment/dpf-operator-controller-manager
----

. Verify that worker nodes are labeled for DPU provisioning by the Node Feature Discovery (NFD) Operator:
+
[source,terminal]
----
$ oc get nodes -l feature.node.kubernetes.io/dpu-enabled=""
----
+
.Example output
[source,terminal]
----
NAME           STATUS     ROLES    AGE   VERSION
host-worker1   NotReady   worker   62s   v1.35.0
host-worker2   NotReady   worker   66s   v1.35.0
----
+
If no nodes are returned, verify that the NFD Operator is running and that the DPU hardware is properly detected.

. Check the BFB object to ensure that the BFB image was downloaded and is ready:
+
[source,terminal]
----
$ oc describe bfb -n dpf-operator-system bf-bundle
----
+
.Example output
[source,terminal]
----
Status:
  Conditions:
  - Type: Ready
    Status: "True"
    Reason: BFBReady
  Image URL: https://rhcos.mirror.openshift.com/art/storage/prod/streams/rhel-10.2/builds/10.2.20260715-0/aarch64/rhcos-10.2.20260715-0-nvidiabluefield.aarch64.bfb
----
+
Verify that the `Ready` condition is `True` and that the image URL is accessible.

. Check the `DPUDeployment` object status for information about prerequisite object states:
+
[source,terminal]
----
$ oc get dpudeployments -n dpf-operator-system dpudeployment -o yaml
----
+
Look for status conditions that indicate issues with:
+
* BFB object state
* `DPUServiceTemplate` object state
* `DPUServiceConfiguration` object state
+
You can also use the `dpfctl` utility for a summarized view:
+
[source,terminal]
----
$ oc -n dpf-operator-system exec deploy/dpf-operator-controller-manager -- /dpfctl describe dpudeployments
----

== DPU object state issues

If DPU objects remain in the `DPU Cluster Config` state for an extended period, the issue is typically related to pending CSRs in the hosted cluster.

.Procedure

. Switch to the hosted cluster context:
+
[source,terminal]
----
$ export KUBECONFIG=/path/to/hosted-cluster.kubeconfig
----

. Check for pending CSRs in the hosted cluster:
+
[source,terminal]
----
$ oc get csr -A
----
+
.Example output
[source,terminal]
----
NAMESPACE   NAME        AGE   SIGNERNAME                                    REQUESTOR               CONDITION
            csr-xyz89   2m    kubernetes.io/kube-apiserver-client-kubelet   system:bootstrap:...    Pending
----

. Approve pending CSRs:
+
[source,terminal]
----
$ oc adm certificate approve <csr-name>
----
+
[NOTE]
====
The DPF HCP Provisioner includes automatic CSR approval for DPU worker nodes. If CSRs remain pending, verify that the provisioner is running correctly.
====

. Verify that DPU worker nodes join the hosted cluster:
+
[source,terminal]
----
$ oc get nodes
----

. Switch back to the management cluster context:
+
[source,terminal]
----
$ export KUBECONFIG=/path/to/management-cluster.kubeconfig
----

== Management cluster node readiness issues

If management cluster nodes do not become `Ready` after DPU provisioning is complete, the issue is typically related to OVN-Kubernetes CNI configuration.

.Procedure

. Verify the management cluster context:
+
[source,terminal]
----
$ export KUBECONFIG=/path/to/management-cluster.kubeconfig
----

. Check OVN-Kubernetes pods on x86 worker nodes and control plane nodes:
+
[source,terminal]
----
$ oc get pods -n openshift-ovn-kubernetes -o wide
----
+
.Example output
[source,terminal]
----
NAME                    READY   STATUS    RESTARTS   AGE   IP              NODE
ovnkube-control-...     2/2     Running   0          15m   192.168.1.100   master-1
ovnkube-node-...        5/5     Running   0          15m   192.168.1.110   host-worker1
ovs-node-...            1/1     Running   0          15m   192.168.1.110   host-worker1
----
+
Verify that all OVN-Kubernetes pods are in a `Running` state.

. Switch to the hosted cluster context:
+
[source,terminal]
----
$ export KUBECONFIG=/path/to/hosted-cluster.kubeconfig
----

. Check OVN-Kubernetes pods on DPU worker nodes:
+
[source,terminal]
----
$ oc get pods -n openshift-ovn-kubernetes -o wide
----
+
Verify that OVN-Kubernetes pods are running on the DPU ARM cores.

. If OVN-Kubernetes pods are not starting, check for the following common issues:
+
* **MTU misconfigurations**: Verify that the `OVN_MTU` environment variable matches your network infrastructure.
* **Network connectivity**: Ensure that DPUs can communicate with the management cluster control plane.
* **Resource constraints**: Check that DPU nodes have sufficient CPU and memory resources.

. Check OVN-Kubernetes logs for specific error messages:
+
[source,terminal]
----
$ oc logs -n openshift-ovn-kubernetes <pod-name>
----

== Common diagnostic commands

Use the following commands for additional troubleshooting:

.DPF resource status overview
[source,terminal]
----
$ oc get dpudeployment,dpuservicetemplate,dpuserviceconfiguration,bfb -n dpf-operator-system
----

.DPU hardware detection verification
[source,terminal]
----
$ oc get nodes -o custom-columns=NAME:.metadata.name,LABELS:.metadata.labels | grep dpu
----

.DPF operator logs
[source,terminal]
----
$ oc logs -n dpf-operator-system -l app.kubernetes.io/name=dpf-operator --tail=100
----

.HCP Provisioner logs
[source,terminal]
----
$ oc logs -n dpf-operator-system -l app.kubernetes.io/name=dpfhcp-provisioner-operator --tail=100
----

.Worker node conditions
[source,terminal]
----
$ oc describe node <node-name> | grep -A 10 "Conditions:"
----
