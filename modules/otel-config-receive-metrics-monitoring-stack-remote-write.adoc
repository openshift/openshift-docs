= Sending metrics from the monitoring stack to the Collector by using remote write

[role="_abstract"]
You can configure the in-cluster monitoring stack to send the platform metrics and the user-defined project metrics to the OpenTelemetry Collector by using the Prometheus remote write protocol version 2. The Collector receives the metrics with the Prometheus Remote Write Receiver and can export them to any backend, for example by using the OpenTelemetry Protocol (OTLP).

:FeatureName: Exporting the monitoring stack metrics to the OpenTelemetry Collector by using remote write
include::snippets/technology-preview.adoc[]
:!FeatureName:

The Technology Preview has the following limitations:

* The monitoring stack does not send the metric type, unit, and help text. The Collector receives all metrics as gauges, including counters, histogram buckets, and summary quantiles. Backends that query the metrics with PromQL are not affected.
* Classic histograms arrive as separate `_bucket`, `_sum`, and `_count` series. Native histograms are not sent.
* Both Prometheus replicas of the monitoring stack send every sample. The samples differ only in the `prometheus_replica` label. Deduplicate them in the backend on this label.

Because of these limitations, send only the metrics that you need. Aggregated metrics, such as the `ALERTS` metric and the results of recording rules, are not affected by the missing metric types.

.Prerequisites

* The cluster runs {ocp-product-title} 5.0 or later.
* You have access to the cluster as a user with the `cluster-admin` role.
* The {OTelOperator} is installed.
* For the user-defined project metrics, monitoring for user-defined projects is enabled.

.Procedure

. Create an `OpenTelemetryCollector` custom resource (CR) that receives the metrics and exports them to your backend:
+
[source,yaml]
----
apiVersion: opentelemetry.io/v1beta1
kind: OpenTelemetryCollector
metadata:
  name: otel
  namespace: observability
spec:
  mode: deployment
  resources:
    requests:
      cpu: 500m
      memory: 512Mi
    limits:
      cpu: "2"
      memory: 2Gi
  config:
    receivers:
      prometheus_remote_write:
        endpoint: 0.0.0.0:9090
    processors:
      memory_limiter:
        check_interval: 1s
        limit_percentage: 80
        spike_limit_percentage: 20
    exporters:
      otlp_http:
        endpoint: https://<backend_otlp_endpoint>
        retry_on_failure:
          enabled: true
          max_elapsed_time: 0
        sending_queue:
          enabled: true
          sizer: items
          queue_size: 100000
          block_on_overflow: true
          batch:
            flush_timeout: 1s
            min_size: 4000
            max_size: 8000
    service:
      pipelines:
        metrics:
          receivers: [prometheus_remote_write]
          processors: [memory_limiter]
          exporters: [otlp_http]
----
where:
+
--
`resources`:: The requests and limits for up to 50,000 samples per second. See the table that follows.
`prometheus_remote_write`:: Receives the remote write requests on port `9090` at the `/api/v1/write` path.
`memory_limiter`:: Refuses requests when the Collector memory usage is high. Prometheus retries the refused requests.
`otlp_http`:: Exports the metrics to your backend. With these retry and queue settings, the Collector does not drop data while the backend is unavailable: it stops accepting new data, and Prometheus keeps the samples and sends them again later. Do not use the default settings, which drop the data after 5 minutes.
--
+
The following table lists the resources for one Collector replica. After you complete this procedure, the `prometheus_remote_storage_samples_total` metric shows the remote write rate. If you send all platform metrics, a cluster with about 350,000 series sends about 30,000 samples per second.
+
[options="header"]
[cols="a,a,a"]
|===
|Remote write rate |Requests |Limits

|Up to 50,000 samples per second
|CPU `500m`, memory `512Mi`
|CPU `2`, memory `2Gi`

|Up to 95,000 samples per second
|CPU `1`, memory `512Mi`
|CPU `2`, memory `2Gi`
|===
+
For more than 95,000 samples per second, increase the number of Collector replicas: the replicas share the rate evenly. Keep the memory limit at `2Gi` or more, because after a backend outage, Prometheus sends its backlog again and the Collector uses its full limits until it finishes.

. Configure the platform monitoring to send the metrics to the Collector:

.. Edit the `cluster-monitoring-config` config map:
+
[source,terminal]
----
$ oc -n openshift-monitoring edit configmap cluster-monitoring-config
----

.. Add the remote write configuration under `data.config.yaml.prometheusK8s`:
+
[source,yaml]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    prometheusK8s:
      remoteWrite:
        - name: otel-collector
          url: http://otel-collector.observability.svc.cluster.local:9090/api/v1/write
          messageVersion: V2.0
          writeRelabelConfigs:
            - sourceLabels: [__name__]
              regex: "up|ALERTS|instance:.*|namespace:.*"
              action: keep
----
where:
+
--
`url`:: The receiver endpoint of the Collector service, in the `<collector_name>-collector.<namespace>.svc.cluster.local` format.
`messageVersion`:: Required. The receiver accepts only the remote write protocol version 2.
`writeRelabelConfigs`:: Optional. Selects the metrics to send. This example sends the `up` and `ALERTS` metrics and the node and namespace recording rules, which are about 1,000 series on a small cluster. Without this field, the monitoring stack sends all platform metrics, which can be hundreds of thousands of series.
--

. Optional: Configure the monitoring for user-defined projects to send the metrics to the Collector:

.. Edit the `user-workload-monitoring-config` config map:
+
[source,terminal]
----
$ oc -n openshift-user-workload-monitoring edit configmap user-workload-monitoring-config
----

.. Add the remote write configuration under `data.config.yaml.prometheus`:
+
[source,yaml]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: user-workload-monitoring-config
  namespace: openshift-user-workload-monitoring
data:
  config.yaml: |
    prometheus:
      remoteWrite:
        - name: otel-collector
          url: http://otel-collector.observability.svc.cluster.local:9090/api/v1/write
          messageVersion: V2.0
----

.Verification

. In the *Administrator* view of the web console, go to *Observe* -> *Metrics*.

. Run the following query to check that the monitoring stack sends the samples:
+
[source,text]
----
sum by (job) (rate(prometheus_remote_storage_samples_total{remote_name="otel-collector"}[5m]))
----
+
The query returns a value greater than zero for the `prometheus-k8s` job and, if you configured the monitoring for user-defined projects, for the `prometheus-user-workload` job.

. Run the following query to check that no samples failed:
+
[source,text]
----
sum by (job) (increase(prometheus_remote_storage_samples_failed_total{remote_name="otel-collector"}[5m]))
----
+
The query returns `0`.
