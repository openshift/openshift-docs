= Add more hostnames for the web console

[role="_abstract"]
You can make the {product-title} web console available at more than one hostname; for example, you can use one hostname for internal users and another for external users. Separate hostnames help you keep internal and external traffic apart to meet network segmentation requirements, and each hostname can use its own Transport Layer Security (TLS) certificate.

You add hostnames in the cluster `Ingress` configuration resource, named `cluster`. This resource defines cluster-wide ingress settings, including custom hostnames for cluster components such as the web console. Each hostname has its own entry in the `spec.componentRoutes` section of this resource. The entry name must start with `console`. The Console Operator creates a route for each hostname and registers the hostname as a redirect URI for OAuth authentication. Users can then log in to the web console from any of the hostnames.

[IMPORTANT]
====
Clusters that use hosted control planes do not support more than one web console hostname.
====

.Prerequisites

* You have access to the cluster as a user with the `cluster-admin` role.
* You installed the OpenShift CLI (`oc`).
* You configured DNS so that each new hostname resolves to the default cluster Ingress Controller.
* If a new hostname is not in the cluster domain, you created a TLS secret in the `openshift-config` namespace that has the certificate and private key for that hostname.

.Procedure

. Open the cluster `Ingress` configuration resource by running the following command:
+
[source,terminal]
----
$ oc edit ingress.config.openshift.io cluster
----

. In the `spec.componentRoutes` section of the resource, add an entry for each new hostname. Keep any existing entries.
+
[source,yaml]
----
spec:
  componentRoutes:
  - name: <route_name>
    namespace: openshift-console
    hostname: <hostname>
    servingCertKeyPairSecret:
      name: <secret_name>
----
+
where:

`<route_name>`:: specifies a unique name for the entry. The name must start with `console`, for example, `console-internal`. Do not use `console` or `console-custom`, because the Console Operator uses those names for the default and custom console routes.
`namespace`:: specifies the namespace for the entry. The value must be `openshift-console`.
`<hostname>`:: specifies the new hostname for the web console, such as `console.internal.example.com`.
`<secret_name>`:: specifies the name of the TLS secret for the hostname in the `openshift-config` namespace. You must set this parameter if the hostname is not in the cluster domain. If the hostname is in the cluster domain, you can omit the `servingCertKeyPairSecret` parameter.

. Save your changes and exit the editor.

.Verification

. Verify that a route exists for each hostname by running the following command:
+
[source,terminal]
----
$ oc get routes -n openshift-console
----

. Open each hostname in a web browser and log in to the web console.

. If a route is missing or you cannot log in, check the status of the Console Operator by running the following command:
+
[source,terminal]
----
$ oc get clusteroperator console
----
+
If the `DEGRADED` column shows `True`, run `oc describe clusteroperator console` to find the cause.
