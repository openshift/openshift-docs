= Add more hostnames for the web console

[role="_abstract"]
You can make the {product-title} web console available at more than one hostname; for example, you can use one hostname for internal users and another for external users. Separate hostnames help you keep internal and external traffic apart to meet network segmentation requirements, and each hostname can use its own Transport Layer Security (TLS) certificate.

You add hostnames in the cluster `Ingress` configuration resource, named `cluster`. This resource defines cluster-wide ingress settings, including custom hostnames for cluster components such as the web console. Each hostname has its own entry in the `spec.componentRoutes` section of this resource. The entry name must start with `console`. The Console Operator creates a route for each hostname. If the cluster uses the built-in OAuth server, the Operator also registers each hostname as a redirect URI. Users can then log in to the web console from any of the hostnames.

[NOTE]
====
If the cluster uses an external OpenID Connect (OIDC) identity provider, the Console Operator does not register redirect URIs. You must add `\https://<hostname>/auth/callback` as a redirect URI for the console client in your identity provider for each new hostname.
====

[IMPORTANT]
====
On clusters that use hosted control planes, you can make the web console available at more than one hostname, but this procedure does not apply. The hosted cluster rejects changes to the cluster `Ingress` configuration resource. Instead, add the entries to the `spec.configuration.ingress.componentRoutes` section of the `HostedCluster` resource on the management cluster, and create any TLS secrets in the `openshift-config` namespace of the hosted cluster.
====

.Prerequisites

* You have access to the cluster as a user with the `cluster-admin` role.
* You installed the OpenShift CLI (`oc`).
* If a new hostname is not in the cluster domain, you configured DNS so that the hostname resolves to the Ingress Controller that exposes the routes in the `openshift-console` namespace. Unless you changed it, this is the default Ingress Controller.
* If a new hostname is not in the cluster domain, you created a `kubernetes.io/tls` secret in the `openshift-config` namespace. The secret must have the certificate (`tls.crt`) and private key (`tls.key`) for that hostname.
+
[TIP]
====
You can create a TLS secret by running the `oc create secret tls` command.
====

.Procedure

. Open the cluster `Ingress` configuration resource by running the following command:
+
[source,terminal]
----
$ oc edit ingress.config.openshift.io cluster
----

. In the `spec.componentRoutes` section of the resource, add an entry for each new hostname. Keep any existing entries.
+
[source,yaml]
----
spec:
  componentRoutes:
  - name: <route_name>
    namespace: openshift-console
    hostname: <hostname>
    servingCertKeyPairSecret:
      name: <secret_name>
----
+
where:

`<route_name>`:: specifies a unique name for the entry. The name must start with `console`; for example, `console-internal`. Do not use `console` or `console-custom`, because the Console Operator uses those names for the default and custom console routes.
`namespace`:: specifies the namespace for the entry. The value must be `openshift-console`.
`<hostname>`:: specifies the new hostname for the web console, such as `console.internal.example.com`.
`<secret_name>`:: specifies the name of the TLS secret for the hostname, if you created one. If the hostname is not in the cluster domain, set this parameter so that the route serves a valid certificate for the hostname. If you omit the `servingCertKeyPairSecret` parameter, the route uses the default ingress certificate, and browsers show a certificate warning for any hostname that the default certificate does not cover.

. Save your changes and exit the editor.
+
[NOTE]
====
To stop serving the web console at a hostname, remove its entry from the `spec.componentRoutes` section. The Console Operator then deletes the route for that hostname.
====

.Verification

. Verify that a route exists for each hostname by running the following command:
+
[source,terminal]
----
$ oc get routes -n openshift-console
----
+
The Console Operator can take up to a minute to create the routes. After it creates them, the web console pods restart to apply the new hostnames, so wait for the restart to finish before you log in.

. Open each hostname in a web browser and log in to the web console.

. If a route is missing or you cannot log in, check the status of the Console Operator by running the following command:
+
[source,terminal]
----
$ oc get clusteroperator console
----
+
If the `DEGRADED` column shows `True`, run `oc describe clusteroperator console` to find the cause. To find problems with a specific hostname, run `oc logs -n openshift-console-operator deployment/console-operator` and look for errors that mention the name of your `componentRoutes` entry. If a TLS secret is missing or is not a valid `kubernetes.io/tls` secret, the Operator still creates the route, but the route uses the default ingress certificate.
