= About compliance audit logging

[role="_abstract"]
{ols-long} provides compliance audit logging to create a durable, reconstructable record of all AI actions across the system. This audit trail supports regulatory requirements such as the EU AI Act by capturing every significant AI action—who asked what, what the AI proposed, who approved it, and what the system executed.

Audit logging is enabled by default on both {ols-long} and agentic {ols-long}. You configure audit behavior independently on each component through the `spec.audit` field of the `OLSConfig` and `AgenticOLSConfig` custom resources (CRs).

== Dual-emission design

Every audit event is emitted in two formats simultaneously:

* *Structured JSON to stdout* — Always active. Your cluster log aggregation stack collects these entries from pod logs. JSON output is available even when no OpenTelemetry endpoint is configured.
* *OpenTelemetry (OTEL) spans* — Active when you configure an OTEL collector endpoint. When no endpoint is configured, the system uses a no-op exporter and continues operating normally.

This dual-emission design ensures that audit records are available regardless of whether an OTEL backend is configured.

== Trace identifier

Every audit event carries a `trace_id` field that links all log lines and OTEL spans belonging to the same interaction:

* For {ols-long} Q&A and troubleshooting interactions: the `trace_id` is derived from the `conversation_id` with hyphens removed.
* For agentic {ols-long} operations: the `trace_id` is derived from the `AgenticRun` resource `metadata.uid` with hyphens removed.

The `trace_id` doubles as the OTEL trace ID, so you can correlate structured log output with distributed traces in your observability platform.

== OpenTelemetry GenAI semantic conventions

{ols-long} telemetry—traces, metrics, and structured logs—aligns with the OpenTelemetry GenAI semantic conventions, version 1.41. This alignment applies to both the agentic system, which comprises the agentic operator and sandbox, and the {ols-long} service (`lightspeed-service`). Standardized telemetry lets you interpret {ols-long} traces, metrics, and logs with common OpenTelemetry tooling.

*Traces*

* The agentic system emits a separate trace for each phase of an operation, rather than a single trace for the entire operation lifecycle. The {ols-long} service emits a separate trace for each request.
* Spans follow GenAI naming conventions, such as `chat <model>` for a model interaction and `execute_tool <name>` for a tool call, and carry `+gen_ai.*+` attributes.
* Span kinds reflect the type of work: `CLIENT` for calls to the large language model (LLM) and `INTERNAL` for agent framework operations.
* {ols-long} distinguishes the requested model from the responding model through the `gen_ai.request.model` and `gen_ai.response.model` attributes.
* Tool spans emitted by the {ols-long} service carry Model Context Protocol (MCP) semantic convention attributes.

*Metrics*

The system emits `+gen_ai.*+` Prometheus histogram metrics. For the agentic sandbox, these are the primary metrics. For the {ols-long} service, they are emitted alongside the existing `+ols_*+` metrics.

*Structured logs*

Structured logs use the OTEL JSON format and are written to stdout through the OTEL stdout exporter. Each record is emitted through a single path, known as the single-emission rule, to avoid duplicate log entries.

*Deferred capabilities*

The following capabilities are not yet part of this alignment:

* Content capture controls
* Evaluation events
* Cache token attributes

== Custom resource serialization

When an agentic operation completes, the agentic operator serializes the `AgenticRun` custom resource as a compliance record. The serialization captures the full `.spec` and the following metadata fields: `name`, `namespace`, `creationTimestamp`, and `uid`.

This serialized record is the authoritative compliance artifact for a given autonomous operation. Pod logs from the agentic sandbox and the {ols-long} service supplement this record as forensic evidence.

== Approver identity injection

{ols-long} injects the approver's identity into `AgenticRun` resources automatically, regardless of the approval path used. A mutating webhook intercepts all `PATCH` requests to `AgenticRun` resources and adds the identity of the authenticated user who submitted the approval. This applies to approvals made through the {ols-long} console, `kubectl`, or the API directly.

== Audit logging scope

Audit events are captured in the backend components only. The {ols-long} console and the agentic console do not emit audit events. All user interactions that affect the audit record are captured by the backend services at the point of receipt and processing.
