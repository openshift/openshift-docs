= Monitor upgrade progress

[role="_abstract"]
You can monitor the progress of a cluster upgrade by watching the `UpgradeCompleted` condition on the `ProvisioningRequest` custom resource. The O-Cloud Manager updates this condition at each stage of the upgrade, providing visibility into the current phase and any issues.

.Prerequisites

* An upgrade operation has been triggered on the `ProvisioningRequest` CR by updating it to reference a new `ClusterTemplate` version.

.Procedure

. Check the `UpgradeCompleted` condition on the `ProvisioningRequest` CR by running the following command:
+
[source,terminal]
----
$ oc get provisioningrequests.clcm.openshift.io <uuid> \
  -o jsonpath='{.status.conditions[?(@.type=="UpgradeCompleted")]}{"\n"}'
----
+
where:
+
--
`<uuid>`:: Specifies the UUID of the `ProvisioningRequest` CR for the target cluster.
--
+
The following table describes the possible states of the `UpgradeCompleted` condition:
+
[cols="1,1,2",options="header"]
|===
|Status |Reason |Description

|`False`
|`Pending`
|Upgrade not yet started or waiting for pre-upgrade checks.

|`False`
|`InProgress`
|Upgrade is running. The CVO is updating control plane and worker nodes.

|`True`
|`Completed`
|Upgrade finished successfully.

|`False`
|`Failed`
|Upgrade failed. See condition message for details.

|`False`
|`Unknown`
|Upgrade stalled. The CVO may not be progressing on the spoke cluster.

|`False`
|`PreconditionChecksFailed`
|Upgrade preconditions not met, such as schema validation failure or version mismatch.

|`False`
|`TimedOut`
|Upgrade exceeded the configured timeout.
|===
+
Default timeout values:
+
* Standard upgrades (z-stream or y-stream): 4 hours
* EUS-to-EUS upgrades: 8 hours

. View the upgrade status details in the `ProvisioningRequest` extensions by running the following command:
+
[source,terminal]
----
$ oc get provisioningrequests.clcm.openshift.io <uuid> \
  -o jsonpath='{.status.extensions.clusterDetails.clusterUpgradeStatus}'
----
+
.Example output
[source,json]
----
{"startedAt":"2026-07-20T15:30:00Z","startVersion":"4.18.25","intermediateVersion":"4.19.31"}
----
+
* `startedAt` records when the upgrade began.
* `startVersion` records the version the cluster was on before the upgrade.
* `intermediateVersion` is present only for EUS-to-EUS upgrades and shows the intermediate version being used.

. Check the overall provisioning phase for a quick status summary by running the following command:
+
[source,terminal]
----
$ oc get provisioningrequests.clcm.openshift.io <uuid>
----
+
The `provisioningPhase` maps to the upgrade state as follows:
+
[cols="1,1",options="header"]
|===
|UpgradeCompleted Reason |provisioningPhase

|`Pending`, `InProgress`, `Unknown`
|`progressing`

|`PreconditionChecksFailed`, `TimedOut`
|`failed`

|`Completed`
|`fulfilled`
|===
+
For multi-node clusters, the condition message reports per-stage progress, such as:
+
* `"Upgrade to target version 4.22.0 triggered. Waiting for upgrade to start"`
* `"Upgrading to target version 4.22.0: Working towards 4.22.0: 50% complete"`
* `"Cluster version upgrade completed. Waiting for worker MachineConfigPools to finish updating"`
