= Override hardware profiles for each deployment site

[role="_abstract"]
When deployments share the same cluster topology but differ in hardware at each site, you can use a single `ClusterTemplate` CR across multiple deployment sites by overriding the template's `hwMgmtDefaults` in each `ProvisioningRequest` CR. The `hwMgmtParameters` field in the `ProvisioningRequest` supplies site-specific values such as server model, firmware profile, or resource selector criteria — avoiding a separate template for every site.

.Prerequisites

* The O-Cloud Manager Operator is installed on the hub cluster.
* A validated `ClusterTemplate` CR exists with `hwMgmtParameters` defined in its `templateParameterSchema`.
* Bare-metal servers at the target site are onboarded with labels matching the override criteria.

.Procedure

. Ensure the `ClusterTemplate` CR includes `hwMgmtParameters` in the `templateParameterSchema` to permit overrides. The following snippet shows the required schema section:
+
[source,yaml]
----
spec:
  templateParameterSchema:
    properties:
      hwMgmtParameters:
        properties:
          hardwareProvisioningTimeout:
            type: string
          nodeGroupData:
            items:
              properties:
                name:
                  type: string
                hwProfile:
                  type: string
                resourceSelector:
                  type: object
                  additionalProperties:
                    type: string
              required:
                - name
              type: object
            type: array
        type: object
----
+
The `hwMgmtParameters` schema defines which fields a `ProvisioningRequest` CR can override. Only fields declared in the schema are accepted during validation.

. Create a `ProvisioningRequest` CR that includes `hwMgmtParameters` in `templateParameters` to override the template defaults for this site:
+
[source,yaml]
----
apiVersion: clcm.openshift.io/v1alpha1
kind: ProvisioningRequest
metadata:
  name: a1b2c3d4-e5f6-7890-abcd-ef1234567890
spec:
  name: site-boston-rack3
  description: "Cluster for Boston site using local server model"
  templateName: sno-ran-du
  templateVersion: v4-Y-Z-1
  templateParameters:
    nodeClusterName: boston-sno1
    oCloudSiteId: site-boston-rack3
    hwMgmtParameters:
      hardwareProvisioningTimeout: "120m"
      nodeGroupData:
        - name: controller
          hwProfile: rh-profile-xr8620t-bios-settings
          resourceSelector:
            server-type: dell-xr8620t
    clusterInstanceParameters:
      clusterName: boston-sno1
      baseDomain: boston.example.com
      nodes:
        - hostName: boston-sno1.boston.example.com
    policyTemplateParameters:
      cpu-isolated: "2-63"
      cpu-reserved: "0-1"
----
+
where:
+
`hwMgmtParameters.hardwareProvisioningTimeout`:: Overrides the timeout duration for hardware provisioning at this site. If not specified, the value from the `ClusterTemplate` CR's `hwMgmtDefaults` section applies.
`hwMgmtParameters.nodeGroupData[].name`:: Identifies the node group to override. This value must match the `name` field of a node group in the template's `hwMgmtDefaults.nodeGroupData[]`. Node groups are matched by name.
`hwMgmtParameters.nodeGroupData[].hwProfile`:: Overrides the `HardwareProfile` CR for this node group at this site. For example, a site with Dell XR8620t servers uses a different firmware profile than a site with HPE DL110 servers.
`hwMgmtParameters.nodeGroupData[].resourceSelector`:: Overrides or adds resource selector criteria for this node group. The O-Cloud Manager merges these values with the base selectors from the `ClusterTemplate` CR using the following rules:
+
* Override values replace existing values for the same key.
* New keys in the override are added to the base configuration.
* Existing keys not present in the override are preserved unchanged.
* Keys cannot be removed from the base template through an override.
+
When both the `ClusterTemplate` CR and the `ProvisioningRequest` CR specify the same field, the `ProvisioningRequest` value takes precedence.
+
[NOTE]
====
Node groups in the override that do not match any existing group by name are appended as new groups. This supports scaling scenarios where a `ProvisioningRequest` CR adds a `worker` node group not defined in the template defaults.
====

. Apply the `ProvisioningRequest` CR to the hub cluster, or commit it to the GitOps repository for ArgoCD synchronization.

.Verification

* Verify that the provisioning request is accepted and progressing by running the following command:
+
[source,terminal]
----
$ oc get provisioningrequests.clcm.openshift.io a1b2c3d4-e5f6-7890-abcd-ef1234567890
----
+
A `provisioningPhase` of `fulfilled` indicates that the overridden hardware profile and resource selector were applied successfully and the cluster provisioning completed.
