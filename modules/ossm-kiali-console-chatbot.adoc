= Kiali chatbot

[role="_abstract"]

The Kiali chatbot answers questions about the mesh from inside the console. Answers use live data from {KialiServer}, Prometheus, tracing, and the {ocp-product-title} API. {KialiServer} runs the tools itself.

The chatbot was introduced in Kiali 2.22 and is disabled by default.

== How the chatbot works

The console sends the prompt, the page context, and the selected model to {KialiServer}. The server calls the configured model. The model can request tools such as the traffic graph, metrics, traces, logs, or {istio} configuration. The server runs those tools and streams the reply back to the browser. When the model proposes a change to {istio} configuration, the console asks you to confirm before it writes the object.

== Enabling the chatbot

Enable the chatbot in the `Kiali` custom resource, then configure at least one provider and model. Store the API key in a secret. The value `secret:<secret-name>:<key>` tells {KialiServer} to read the key from that secret instead of from the custom resource.

[source,yaml]
----
spec:
  ai:
    enabled: true
    chat:
      enabled: true
      default_provider: openai
      allowed_users:
      - user1
      providers:
      - name: openai
        type: openai
        default_model: gpt
        models:
        - name: gpt
          model: gpt-4o
          key: "secret:my-secret:openai-api-key"
----

If `allowed_users` is empty, every user who can open the console can use the chatbot. If the list is set, only those users see the chatbot icon.

.Kiali chatbot in the console
image::ossm-kiali-chatbot.png[Kiali chatbot panel in the console]

The configuration key `chat_ai` is deprecated in Kiali 2.31. Use `ai.chat`.

`enabled_tools` is an allow list. When it is set, only those tools are exposed. `disabled_tools` is applied after the allow list. A filter on one provider can only remove tools that the global filter still allows. Disable `manage_istio_config` when the assistant must not propose configuration changes.

== Providers and models

Provider types are `openai`, `google`, `anthropic`, and `lightspeed`. The following example uses OpenShift Lightspeed. Set `endpoint` to the Lightspeed route or service in the cluster:

[source,yaml]
----
spec:
  ai:
    enabled: true
    chat:
      providers:
      - name: LightSpeed
        description: OpenShift Lightspeed
        type: lightspeed
        endpoint: https://lightspeed-app-server.openshift-lightspeed.svc:8443
        enabled: true
----

You can select the configured provider and model in the chatbot window.

== TLS for providers

{KialiServer} checks the provider certificate with the `kiali-cabundle` config map and the cluster TLS policy. Set `insecure_skip_verify` to `true` only for a test provider. On a production cluster, add the provider CA to `kiali-cabundle` instead.

[source,yaml]
----
spec:
  ai:
    enabled: true
    chat:
      providers:
      - name: LightSpeed
        type: lightspeed
        endpoint: https://lightspeed-app-server.openshift-lightspeed.svc:8443
        enabled: true
        insecure_skip_verify: true
----

== Streaming replies

The reply is a stream of events. `token` events add text, `tool_call` and `tool_result` events show which tool ran, `end` finishes the answer, and `error` reports a failure. Open a tool card in the chat to read the full tool output.

== Suggested prompts

Suggested prompts change with the page you are on, including Overview, Graph, Mesh, Namespaces, Applications, Services, Workloads, and {istio} config. Selecting a prompt fills the input so you can edit it before you send it.

Examples of questions that work well:

* Show the mesh graph for namespace `bookinfo`.
* Which workloads in `istio-system` look unhealthy, and why?
* Get traces for service `productpage` in `bookinfo` for the last 30 minutes.

What is sent to the model is the user message, the page context, the chat history when storage is enabled, the tool definitions, and the tool results needed to answer.

== Ask and Troubleshoot modes

The input has two modes. *Ask* is open questions about the mesh. *Troubleshoot* starts from a problem description, selects logs, traces, metrics, and {istio} checks, and ends with a recommended action. OpenShift Lightspeed handles the two modes in the provider. Other models receive a different system prompt for each mode.
