= Configure data plane tracing in {prodname}

[role="_abstract"]
Enable data plane tracing in {service-mesh} with the `kuadrant` CR. You must perform these steps on each {ocp} cluster that you want to use {prodname} on.

.Prerequisites

* You installed {prodname}.
* You are logged into a running {ocp} cluster as an administrator.
* You have {TempoName} installed and configured to support OpenTelemetry.
* You installed a compatible version of {service-mesh}.
* You configured a {OTELName} Collector with an OTLP gRPC receiver and export to your tracing back end, including any required TLS, authentication, and tenant configuration.

.Procedure

. Configure tracing for your Gateway workload in a `Telemetry` custom resource (CR). If a `Telemetry` CR already selects that Gateway workload, add the `tracing` configuration to that CR and preserve its existing metrics and access log configuration.
+
.Example {service-mesh} Telemetry CR with tracing
[source,yaml,subs="+quotes"]
----
apiVersion: telemetry.istio.io/v1
kind: Telemetry
metadata:
  name: gateway-telemetry
  namespace: _<gateway_namespace>_
spec:
  selector:
    matchLabels:
      gateway.networking.k8s.io/gateway-name: _<gateway_name>_
  tracing:
  - providers:
    - name: tempo-otlp
    randomSamplingPercentage: 100
# ...
----
+
* Replace `_<gateway_namespace>_` with the namespace containing the `Gateway` CR.
* Replace `_<gateway_name>_` with the name of the `Gateway` CR, not the name of the application deployment.
+
[IMPORTANT]
====
Only one namespace-wide `Telemetry` CR without a selector or target reference is valid in each namespace. Only one workload-specific `Telemetry` CR can select a given workload. Do not create a second resource for tracing if an existing resource already selects the same Gateway pods. Merge the required signals into the existing resource instead.
====

. Save the updated `Telemetry` CR as `gateway-telemetry.yaml` and apply it by running the following command:
+
[source,terminal]
----
$ oc apply -f gateway-telemetry.yaml
----

. Save a copy of your existing `Istio` CR by running the following command:
+
[source,terminal,subs="+quotes"]
----
$ oc get istio _<istio_name>_ -o yaml > istio.yaml
----
+
Replace `_<istio_name>_` with the name of your existing {service-mesh} control plane resource.

. Edit `istio.yaml` to enable tracing and add a provider to `spec.values.meshConfig.extensionProviders`, as shown in the following example. Preserve the existing providers and other configuration.
+
.Example Istio CR with tracing extension provider
[source,yaml,subs="+quotes"]
----
apiVersion: sailoperator.io/v1
kind: Istio
metadata:
  name: _<istio_name>_
spec:
  namespace: _<istio_namespace>_
  values:
    meshConfig:
      defaultConfig:
        tracing: {}
      enableTracing: true
      extensionProviders:
      - name: tempo-otlp
        opentelemetry:
          port: 4317
          service: _<otel_collector_service>_._<otel_collector_namespace>_.svc.cluster.local
# ...
----
+
* The `Istio` CR is cluster-scoped. Retain its existing `spec.namespace` value, which identifies the control plane installation namespace and can differ from the Gateway namespace.
* Replace `_<otel_collector_service>_` and `_<otel_collector_namespace>_` with the service name and namespace of your Collector.
* The example uses the Collector OTLP gRPC receiver on port `4317`, not the Tempo query endpoint or an authenticated Tempo gateway endpoint. Configure the Collector to forward traces to your tracing back end.
* Retain all existing `extensionProviders` entries, including access log providers. Replacing the array with only the tracing provider removes the other providers.
+
[IMPORTANT]
====
If you are setting the controller manually, you must set the OpenTelemetry protocol (OTLP) in the `Service` CR port `name` and `appProtocol` fields. For example, when using gRPC, the port name should begin with `grpc-` or the `appProtocol` should be `grpc`:
[source,yaml]
----
kind: Service
apiVersion: v1
metadata:
  name: otel-collector
spec:
  ports:
    - name: otlp-grpc
      port: 4317
      targetPort: 4317
      appProtocol: grpc
  selector:
    app: otel-collector
# ...
----
====

. Apply the configuration by running the following command:
+
[source,terminal]
----
$ oc apply -f istio.yaml
----

. Optional. If you want to collect `Authorino` and `Limitador` traces in a different location than your `Kuadrant` traces, complete the following steps:

.. Enable request tracing in your `Authorino` custom resource (CR) and send authentication and authorization traces to the central collector as follows:
+
.Example Authorino CR with request tracing
[source,yaml]
----
apiVersion: operator.authorino.kuadrant.io/v1beta1
kind: Authorino
metadata:
  name: authorino
spec:
  tracing:
    endpoint: rpc://authorino-collector:4317
    insecure: true
# ...
----
+
Set `insecure` to `true` to skip TLS certificate verification in development environments. Set to `false` for production environments.

.. Apply the configuration by running the following command:
+
[source,terminal]
----
$ oc apply -f authorino.yaml
----

.. Enable request tracing in your `Limitador` CR and send rate limit traces to the central collector as follows:
+
.Example Limitador CR with request tracing
[source,yaml]
----
apiVersion: limitador.kuadrant.io/v1alpha1
kind: Limitador
metadata:
  name: limitador
spec:
  tracing:
    endpoint: rpc://limitador-collector:4317
    insecure: true
# ...
----
+
Set `insecure` to `true` to skip TLS certificate verification in development environments. Set to `false` for production environments.

.. Apply the configuration by running the following command:
+
[source,terminal]
----
$ oc apply -f limitador.yaml
----
+
[IMPORTANT]
====
Trace IDs do not propagate to WebAssembly modules in {service-mesh}. This means that requests passed to Limitador do not have the relevant parent trace ID. However, if the trace initiation point is outside {service-mesh}, the parent trace ID is available to Limitador and included in traces. This impacts correlating traces from Limitador with traces from Authorino, the gateway, and any other components in the request path.
====

. Configure data-plane tracing in the `Kuadrant` CR by providing the collector endpoint as shown in the following example:
+
.Example `kuadrant` CR
[source,yaml,subs="+quotes"]
----
apiVersion: kuadrant.io/v1beta1
kind: Kuadrant
metadata:
  name: kuadrant
  namespace: kuadrant-system
spec:
  observability:
    dataPlane:
      defaultLevels:
        - debug: "true"
      httpHeaderIdentifier: x-request-id
    tracing:
      defaultEndpoint: rpc://_<otel_collector_service>_._<otel_collector_namespace>_.svc.cluster.local:4317
      insecure: true
----
+
* `spec.observability.dataPlane.defaultLevels`: Set this value to enable trace filtering at the required level, for example `debug: "true"` for debug-level trace filtering.
* `spec.observability.tracing.defaultEndpoint`: The OTLP gRPC endpoint of your Collector. Replace the service and namespace placeholders with the same values used for the tracing extension provider.
* `spec.observability.tracing.insecure`: Set to `true` to skip TLS certificate verification in development environments. Set to `false` for production environments.
+
[IMPORTANT]
====
Point to the Collector receiver, not a query service. The Collector exports traces to the configured back end and supplies any required authentication, TLS, and tenant information.
====

. Apply the configuration by running the following command:
+
[source,terminal]
----
$ oc apply -f kuadrant.yaml
----

.Verification

* Verify that the CR applied successfully by listing the objects of that `Kind` by running the following command:
+
[source,terminal]
----
$ oc get kuadrant
----
