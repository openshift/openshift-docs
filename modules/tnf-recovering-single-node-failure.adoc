= Recovering from a single-node failure in a TNF cluster

[role="_abstract"]
When one control plane node fails while its peer keeps running, the surviving node holds corosync quorum and continues to serve the cluster in degraded mode. Use this procedure to diagnose the failure, repair fencing credentials if they are the cause, and, only when the failed node is verified to be permanently down, confirm the fencing so that the surviving node can recover etcd.

[IMPORTANT]
====
Do not use this procedure if both control plane nodes lost power. See xref:../installing_tnf/install-post-tnf.adoc#tnf-recovery-scenarios-overview_install-post-tnf[TNF recovery scenarios] to identify your scenario.
====

.Prerequisites

* You have administrative access to the control plane nodes.
* You can connect to the nodes by using SSH.

.Procedure

. Diagnose the current cluster and resource states by running the following command on the surviving node:
+
[source,terminal]
----
$ sudo pcs status --full
----
+
The output shows the failed node as `Offline` and the surviving node as `Online`. Use the output to identify issues with fencing or etcd startup.

. Review Pacemaker activity and etcd resource startup by running the following commands:
+
[source,terminal]
----
$ sudo journalctl -u pacemaker
----
+
[source,terminal]
----
$ sudo journalctl -u pacemaker | grep podman-etcd
----
+
In the output, look for the following:

* Fencing results for the failed node, reported by `stonith-ng` and `fence_redfish` entries. A successful fence reports that the node was powered off. Authentication errors or connection timeouts that point at the BMC indicate a fencing problem; repair the credentials as described in the next step.
* Decisions made by the `podman-etcd` resource agent, such as `shall join as learner`, `is set as standalone`, and revision comparison messages, for example `revision '<N>' is newer than peer revision '<N>'`. An `ADMIN` verdict means that the agent could not determine which node holds the more recent etcd data and stopped instead of guessing.
* Start and stop failures for the `kubelet` resource, if the failure is not related to etcd.

. If fencing is failing with authentication errors, the BMC credentials are wrong or outdated. Repair them as described in xref:../installing_tnf/install-post-tnf.adoc#tnf-updating-fencing-credentials-manually_install-post-tnf[Manually updating fencing credentials] or xref:../installing_tnf/install-post-tnf.adoc#updating-fencing-credentials-script_install-post-tnf[Updating fencing credentials by using the script]. If the cluster recovers after the credentials are repaired, no further action is required.

. If fencing is required but cannot function, and you have verified that the failed node is permanently inaccessible, confirm that the failed node is fenced.
+
[IMPORTANT]
====
Before you confirm fencing, the failed node must meet all of the following conditions:

* The node is powered off and cannot be restarted. Verify this at the BMC, not by attempting to reach the node over the network.
* The node cannot access any shared storage or cluster resources.
* The node is completely isolated from the cluster network.

If the failed node is accessible or can access shared resources, do not confirm fencing. Confirming fencing for a node that is still active can cause data corruption and cluster failure.
====
+
Run the following command:
+
[source,terminal]
----
$ sudo pcs stonith confirm <failed_node_name>
----
+
Replace `<failed_node_name>` with the name of the failed control plane node.

. If etcd does not start on the surviving node although fencing is operational, restore etcd from a backup by running the following commands:
+
[source,terminal]
----
$ sudo cp -r /var/lib/etcd-backup/* /var/lib/etcd/
----
+
[source,terminal]
----
$ sudo chown -R etcd:etcd /var/lib/etcd
----
+
If etcd still does not start, see xref:../installing_tnf/operating-a-degraded-tnf.adoc#resolving-etcd-not-recovering-on-the-surviving-node_operating-a-degraded-tnf[Resolving etcd not recovering on the surviving node].

.Next steps

* If the failed node can be repaired and restarted, allow it to rejoin the cluster, and verify that etcd resynchronizes and is promoted back to a voting member.
* If the failed node cannot be recovered, replace it as described in xref:../installing_tnf/install-post-tnf.adoc#installation-replacing-control-plane-nodes_install-post-tnf[Replacing control plane nodes in a two-node {product-title} cluster with fencing].
