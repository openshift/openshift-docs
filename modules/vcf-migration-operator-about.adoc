= About the VCF Migration Operator

[role="_abstract"]
You can use the VCF Migration Operator to migrate an {product-title} cluster from one {vmw-short} vCenter to another without reinstalling the cluster.
The operator performs an in-place, node-by-node migration that preserves running workloads and cluster state while your infrastructure transitions to VMware Cloud Foundation 9 (VCF9) or VMware vSphere Foundation 9 (VVF9).

Organizations running {product-title} on {vmw-full} might need to modernize their VMware infrastructure as product portfolios migrate to VCF9 or VVF9.
Without operator-driven migration, you must either fully reinstall your cluster, which causes extended downtime and workload disruption, or try a manual migration that carries significant risk of misconfiguration and data loss.
The VCF Migration Operator eliminates these risks by automating the migration workflow.

The VCF Migration Operator works alongside the Machine API Operator, which manages `Machine` and `MachineSet` objects for clusters that use installer-provisioned infrastructure.
During migration, the VCF Migration Operator orchestrates the vCenter migration while the Machine API Operator continues to manage node lifecycle.
You install the VCF Migration Operator from OperatorHub, and the operator runs in the `openshift-vcf-migration` namespace.

The VCF Migration Operator supports two migration engines that control how nodes move to the target vCenter:

Recreate:: The operator creates new virtual machines on the target vCenter by using `MachineSets` and the `ControlPlaneMachineSet`, then scales down and removes the source machines. This is the default migration engine for clusters that use installer-provisioned infrastructure. You must provide a VM template in each target failure domain or configure automatic RHCOS image import.

`VMotion`:: The operator relocates existing virtual machines from the source vCenter to the target vCenter by using cross-vCenter vMotion. You can select live (hot), cold, or automatic mode for each node role. `VMotion` is useful for clusters that use user-provisioned infrastructure and do not have `MachineSets` or a `ControlPlaneMachineSet`.

You configure the migration by creating a `VmwareCloudFoundationMigration` custom resource (CR) that specifies the target vCenter credentials, failure domains, and migration engine settings.
The operator uses a singleton resource pattern: the CR must be named `cluster` in the `openshift-vcf-migration` namespace.

The operator progresses through the following phases in order:

. *Preflight validation*: The Operator verifies that the cluster meets all prerequisites, validates connectivity to the target vCenter, and confirms that the target topology is reachable.
. *Destination initialization*: The Operator creates the required VM folders and topology tags on the target vCenter.
. *Image import*: If configured, the Operator downloads and imports the RHCOS OVA as a VM template on the target vCenter. The Operator skips this phase when you set templates manually.
. *Multisite configuration*: The Operator configures the cluster to recognize both the source and target vCenters by updating secrets, the `Infrastructure` custom resource, and cloud provider configuration.
. *Workload migration*: The Operator migrates worker nodes and control plane nodes to the target vCenter. For the Recreate engine, the Operator creates new `MachineSets` on the target and scales down the source. For `VMotion`, the Operator relocates VMs one by one with configurable rolling limits.
. *Source cleanup*: The Operator removes all references to the source vCenter from the cluster configuration.
. *Ready*: The Operator confirms that all cluster Operators are healthy and that the migration is complete.

You can pause and resume the migration at any point by changing the `spec.state` field on the CR.
The workflow resumes from where it left off.

[IMPORTANT]
====
In this release, automated migration of {vmw-short} CSI persistent volumes is not supported.
You must remove the {vmw-short} CSI driver before starting the migration.
Automated persistent volume migration is planned for a future release.
====
