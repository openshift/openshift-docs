= Understanding {microshift-short} on CIS Level 2 hardened systems

[role="_abstract"]
{microshift-short} can run on {op-system-base} hosts that are hardened to the CIS Level 2 benchmark.
CIS Level 2 hardening applies strict host controls such as firewall lockdown, audit rules, and system configuration policies that can interfere with container orchestration unless you apply documented overrides and postinstall configuration.

[id="microshift-cis-about-supported_{context}"]
== Supported platforms and scope

{microshift-short} CIS Level 2 documentation applies to the following environment:

* {op-system-base} {op-system-version-major} and {op-system-base} {op-system-version-major-10}
* `x86_64` and `aarch64` architectures
* RPM package-mode installations of {microshift-short}

Host compliance is verified with OpenSCAP and the `scap-security-guide` content by using the `xccdf_org.ssgproject.content_profile_cis` profile.
You cannot use the {ocp} Compliance Operator to harden a {microshift-short} host because that operator depends on MachineConfig and related {ocp} APIs that {microshift-short} does not provide.

[id="microshift-cis-about-impact_{context}"]
== How {microshift-short} affects CIS scan results

{microshift-short} introduces host changes that cause a predictable set of CIS rules to fail.
These failures are expected on any system that runs Kubernetes containers and cannot be remediated without disabling core networking or container runtime behavior.

The affected categories are:

* IP forwarding, which OVN-Kubernetes requires for pod networking
* Container image file ownership under `/var/lib/containers/storage/overlay/`
* kubelet volume and termination-log permissions for projected configuration
* Privileged-command audit rules for binaries that {microshift-short} RPMs add after hardening

Plan for these expected failures when you interpret OpenSCAP results after you install and start {microshift-short}.
