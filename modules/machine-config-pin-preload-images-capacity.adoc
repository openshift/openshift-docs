= Planning capacity for pinned images

[role="_abstract"]
Before you pin a large number of images, plan for node disk space, registry reachability, and the time required for the first pull on each machine config pool.

== Image count limits

A single `PinnedImageSet` object can list a maximum of 500 image digests. For workloads that need more than 500 images, split the list across multiple `PinnedImageSet` objects and target them to the appropriate machine config pools. Prefer smaller, purpose-specific sets over one large set so that you can update and troubleshoot pools independently.

== Storage considerations

The Machine Config Operator (MCO) checks whether each affected node has enough free space before it pulls pinned images. If space is insufficient, the MCO does not pull the images and reports an error on the related `MachineConfigNode` object.

Use the following approach to estimate space needs:

. List the digest-referenced images that you plan to pin.
. Inspect each image to determine its compressed size, for example by using `skopeo inspect`.
. Sum the sizes for the images that apply to a given node or pool.
. Reserve additional free space on `/var/lib/containers` for container runtime growth, image updates, and unrelated workloads.

[NOTE]
====
Exact overhead varies by registry, compression, and node workload. Validate capacity on a representative node in a non-production environment before you apply a large `PinnedImageSet` to production pools.
====

== Network and first-pull time

The first time a node processes a `PinnedImageSet`, it must pull every image that is not already present locally. Pull duration depends on image size, registry performance, and available bandwidth. Low-bandwidth or disconnected edge sites can take significantly longer on the first pull.

After the images are cached and pinned, later node boots do not re-pull those images for the pin operation. Image garbage collection does not remove pinned images.

Control plane nodes throttle image pulls more aggressively than worker nodes. Prefer pinning large application image sets to worker or custom pools rather than to the control plane pool unless those images are required on control plane nodes.

== Recommendations for air-gapped and edge clusters

* Mirror images to a registry that every target node can reach, then pin by digest from that mirror.
* Keep edge node sets minimal: pin only the images required for that site's workloads.
* Stage the first application of a large `PinnedImageSet` during a maintenance window.
* Split shared base images and workload-specific images into separate `PinnedImageSet` objects so that edge sites can omit unused application sets.
