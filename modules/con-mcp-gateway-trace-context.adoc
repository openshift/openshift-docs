= Trace context propagation in the {mcpg}

[role="_abstract"]
You can correlate {mcpg} activity with broader {DTShortName} across your infrastructure.

The {mcpg} router propagates W3C trace context on forwarded requests, allowing broker filtering spans to correlate with router work in a single trace. These spans are children of `mcp-broker.handle-request`. However, because outbound header injection is currently a no-operation function, this correlation relies on an incoming client or Envoy `traceparent` header. Without an incoming trace header, the router-generated root context is not forwarded, causing broker spans to start a separate trace.

[id="con-mcp-gateway-w3c-trace-context-header-support_{context}"]
== W3C Trace Context standard header support

The router extracts the `traceparent` header from incoming requests. This header follows the W3C Trace Context standard and has trace ID, parent span ID, and sampling information.

Clients can pass an explicit `traceparent` header for end-to-end observability. When the header is present, the {mcpg} continues the existing trace. When the header is absent, the router creates a new root trace.

[id="con-mcp-gateway-resource-attributes_{context}"]
== Resource attributes

Resource attributes can help you correlate spans and logs across deployments and identify what version of the {mcpg} generated specific telemetry data.

Enabled trace spans and log records can include resource attributes that give the following service metadata:

* `service.name`: Service identifier. Default is `mcp-gateway`.
* `service.version`: Service version from `OTEL_SERVICE_VERSION` or the build version.
* `vcs.revision`: Git commit hash when it you set it at build time.
* `vcs.dirty`: Build dirty-state value when provided.
* `build.go.version`: `Go` runtime version.
