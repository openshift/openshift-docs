= Prerequisites to migrate workloads between {op-system} major versions

[role="_abstract"]
Before you migrate workloads from a {op-system-base} 9 `NodePool` resource to a {op-system-base} 10 `NodePool` resource in {hcp}, verify that your environment meets the requirements. Failing to complete these checks before migration can result in workload failures, blocked drains, or compatibility issues on the new {op-system-base} 10 nodes.

Environment requirements::

* Your `HostedCluster` resource is running {product-title} 5.0 or later.

* The `oc` CLI is installed and configured with access to the `HostedCluster` resource and its `NodePool` resources.

* You have cluster-admin or equivalent permissions on the `HostedCluster` resource.

Container runtime check::

Verify that no `ContainerRuntimeConfig` resources in the cluster set `defaultRuntime: runc` for workloads targeted for {op-system-base} 10 nodes:
+
[source,terminal]
----
$ oc get containerruntimeconfigs -A -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containerRuntimeConfig.defaultRuntime}{"\n"}{end}'
----
+
If any `ContainerRuntimeConfig` specifies `runc`, those workloads must remain on {op-system-base} 9 `NodePool` resources. {op-system-base} 10 does not ship `runc`. For more information, see "Container runtime compatibility for {op-system-base} 10 node pools".

Capacity check::

Confirm that the cluster has sufficient capacity to run both the existing {op-system-base} 9 NodePool and the new {op-system-base} 10 NodePool simultaneously during migration. The side-by-side migration strategy requires both `NodePool` resources to be active at the same time. Plan for the additional resource usage before starting the migration.

PodDisruptionBudget review::

Review `PodDisruptionBudget` (PDB) resources in the namespaces that contain workloads running on the {op-system-base} 9 `NodePool` resource:
+
[source,terminal]
----
$ oc get poddisruptionbudget -A
----
+
PDBs that set `maxUnavailable: 0` or `minAvailable` equal to the total number of pod replicas block the drain operation. Either temporarily adjust the PDB during the migration window, or scale up the workload replica count before draining so that the PDB constraints can be satisfied.

Architecture and platform check::

Confirm that {op-system-base} 10 boot images are available for the target platform and architecture. For more information, see "Supported architectures for {op-system-base} 10 NodePool resources" and "Platform boot image availability for {op-system-base} 10 NodePool resources".

FIPS check::

If FIPS mode is enabled on the `HostedCluster` resource, verify that your architecture supports FIPS on {op-system-base} 10. FIPS is supported on {op-system-base} 10 for x86_64, ppc64le, and s390x architectures only.
+
If your `NodePool` resource uses aarch64, you must keep it on {op-system-base} 9 if FIPS compliance is required.
