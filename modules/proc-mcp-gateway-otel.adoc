= Enable {OTELName} for the {mcpg}

[role="_abstract"]
The {mcpg} uses {OTELName} throughout all components to give you consistent logging, {DTShortName}, and metrics. By using observability, you can achieve the following goals:

* Discover which component generated an error, such as Envoy, an {mcpg} component, or a backend Model Context Protocol (MCP) server.
* Understand how requests flow through the system components.
* See which tools were called and which MCP servers executed those tools.
* Understand where to find relevant logs for each component.
* Examine metrics about tool call patterns, success rates, and error rates.
* Examine {DTShortName} across the request path.

[IMPORTANT]
====
Tracing and log export require a configured OpenTelemetry protocol (OTLP) endpoint. Prometheus metrics function independently from OTLP configuration.
====

.Prerequisites

* You installed {mcpg} using Helm.
* You installed {prodname}.
* You configured a `Gateway` object.
* You are logged into a running {ocp} cluster with an `admin` role.
* You installed {OTELName}.
* You have an OTLP-compatible collector deployed, such as the {OTELName} Collector.
* You configured {TempoName} for traces.
* You installed the OpenShift Logging Operator (Loki).
* You configured an S3-compatible persistent storage volume for Loki to store long-term MCP tool call logs.

.Procedure

. Use the following example YAML to create a collector in your {mcpg} deployment namespace:
+
.Example OpenTelemetryCollector custom resource (CR)
[source,yaml,subs="+quotes"]
----
apiVersion: opentelemetry.io/v1beta1
kind: OpenTelemetryCollector
metadata:
  name: _<mcp_otel_collector>_
  namespace: _<mcp_gateway_system>_
spec:
  mode: deployment
  config:
    receivers:
      otlp:
        protocols:
          grpc:
            endpoint: 0.0.0.0:4317
          http:
            endpoint: 0.0.0.0:4318
    exporters:
      otlp/tempo:
        endpoint: tempo-gateway-http.openshift-tracing.svc.cluster.local:4317
        tls:
          insecure: true
      debug:
        verbosity: basic
    service:
      pipelines:
        traces:
          receivers: [otlp]
          exporters: [otlp/tempo, debug]
        logs:
          receivers: [otlp]
          exporters: [debug]
----
+
* Replace `_<mcp_otel_collector>_` with the name you want to assign to this collector.
* Replace `_<mcp_gateway_system>_` with the namespace of your {mcpg} deployment.
* The `spec.config.exporters:` field value points to {DTShortName}.
* The setting `spec.config.exporters.otlp/tempo.tls.insecure: true` enables unencrypted internal cluster communication.

. Find your release name and namespace by running the following command:
+
[source,terminal]
----
$ helm list -A
----

. Set the OTLP environment variables on your {mcpg} deployment by running the following command:
+
[source,terminal,subs="+quotes"]
----
$ oc set env deployment/_<mcp_gateway_system>_ -n _<namespace>_ \
  OTEL_EXPORTER_OTLP_ENDPOINT="http://_<mcp_otel_collector>_-collector._<mcp_gateway_system>_.svc.cluster.local:4318" \
  OTEL_EXPORTER_OTLP_INSECURE="true"
----
+
* Replace `_<mcp_gateway_system>_` with the deployment name of your {mcpg} instance.
* Replace `_<namespace>_` with the namespace of your {mcpg} deployment.
* Replace `_<mcp_otel_collector>_` with the name used in your `OpenTelemetryCollector` CR. When {OTELName} creates a collector, the default Kubernetes service name generated is `[metadata.name]-collector`.

. Optional. To route traces and logs to separate collector endpoints, set the signal-specific environment variables by running the following command:
+
[source,terminal,subs="+quotes"]
----
$ oc set env deployment/_<mcp_gateway_system>_ -n _<namespace>_ \
  OTEL_EXPORTER_OTLP_TRACES_ENDPOINT="http://trace-collector.tracing-namespace.svc.cluster.local:4317" \
  OTEL_EXPORTER_OTLP_LOGS_ENDPOINT="http://log-collector.logging-namespace.svc.cluster.local:4317"
----
+
* Replace `_<mcp_gateway_system>_` with the deployment name of your {mcpg} instance.
* Replace `_<namespace>_` with the namespace of your {mcpg} deployment.
* Set `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` to override the destination endpoint for distributed traces.
* Set `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` to override the destination endpoint for log export.

. If you are using {TempoName}, navigate to the OpenShift Web Console *Observe > Traces* dashboard and select your stack name as the data source (for example, `tempo-mcp`).

. Filter distributed traces in the *Observe > Traces* dashboard by setting attributes such as `service.name="mcp-gateway"`, `mcp.method`, or `mcp.name` to identify errors or operational bottlenecks.

. For Loki logs, navigate to *Observe > Logs*, select the **Structured** view tab, and filter logs using `trace_id`, `mcp.method`, or `mcp.name`.

. To cross-correlate traces and logs, open a trace span in the *Observe > Traces* timeline view and click the **Log** icon next to a span to jump directly to the correlated execution logs in Loki.

.Verification

* Generate some traffic against the {mcpg} by using an `initialize` or `tools/list` request. Confirm that traces appear in your collector backend. The {mcpg} emits spans under the service name `mcp-gateway` by default.

.Troubleshooting

* If traces or logs do not appear in your backend, verify that the `NetworkPolicy` CR in your namespace permits egress traffic from {mcpg} to the {OTELName} collector service port, `4317` or `4318`.
