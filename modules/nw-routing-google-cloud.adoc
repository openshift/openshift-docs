= Configuring BGP to peer with a Google Cloud Cloud Router

[role="_abstract"]
After you prepare the {gcp-short} environment, configure BGP Cloud Connector so that {product-title} compute nodes establish BGP peering sessions with the {gcp-short} Cloud Router and advertise {VirtProductName} virtual machine (VM) network routes.

When BGP peering establishes, the cluster advertises `_<pod_network_cidr>_` routes to the Cloud Router by using the internal IP addresses of compute nodes.
Each compute node must have a matching `routerNodeSelector` label.
The Cloud Router installs these routes as dynamic routes in the VPC network of the cluster.

If ingress traffic reaches a non-target node, the Cluster User Defined Network (CUDN) transparently forwards the traffic, enabling direct, NAT-free access.
If a next-hop node fails, the BGP session for that node terminates and the Cloud Router routes traffic to an alternate node.

.Prerequisites

* You have prepared the {gcp-short} environment for BGP peering.
* You have installed the BGP Cloud Connector Operator on your cluster.
* You noted the following values while preparing the {gcp-short} environment: the project ID, the region, the name of the Cloud Router, the name of the Network Connectivity Center (NCC) hub, and the autonomous system number (ASN) of the Cloud Router.

.Procedure

. Create a `BGPCloudConfiguration` custom resource (CR) to define the cluster-wide BGP configuration:
+
[source,yaml]
----
apiVersion: networking.openshift.io/v1beta1
kind: BGPCloudConfiguration
metadata:
  name: cluster
spec:
  platform: GCP
  bgp:
    localASN: <local_asn>
    livenessDetection: bgp-keepalive
  routerNodeSelector:
    bgp_router: "true"
  gcp:
    project: <project_id>
    region: <region>
    cloudRouterName: <cloud_router_name>
    ncc:
      hubName: <ncc_hub_name>
      spokePrefix: <spoke_prefix>
----
+
where:
+
--
`spec.bgp.localASN`:: Specifies the ASN for the `FRRouting` (FRR) router of your cluster.
Replace _<local_asn>_ with an ASN that is different from the ASN of the Cloud Router, because BGP sessions between matching ASNs are not eBGP sessions.
The Operator discovers the ASN of the Cloud Router automatically.

`spec.routerNodeSelector.bgp_router`:: Specifies the label key used in the `routerNodeSelector` to identify which compute nodes participate in BGP routing.
Nodes that match this selector have the following characteristics:
+
* Join an NCC router appliance spoke before establishing BGP peering sessions with the Cloud Router.
* Act as the next-hop for BGP-advertised routes for traffic that ingresses from the VPC network to the primary CUDN of the workload.
* Have IP forwarding enabled on their network interfaces by setting the `canIpForward` flag.
+
[IMPORTANT]
====
Traffic always egresses from pods or VMs directly through their own compute node.
Therefore, you must apply this selector to any node where these workloads can be scheduled, not just the nodes intended to receive incoming traffic.
====

`spec.gcp.project`:: Specifies the ID of the {gcp-short} project that hosts the cluster.
Replace _<project_id>_ with the project ID that you noted while preparing the {gcp-short} environment.

`spec.gcp.region`:: Specifies the {gcp-short} region that hosts the Cloud Router.
Replace _<region>_ with the region of the Cloud Router.

`spec.gcp.cloudRouterName`:: Specifies the name of the Cloud Router that the compute nodes peer with.
The interface addresses of the Cloud Router become the BGP neighbors, and the ASN of the Cloud Router becomes the remote ASN.
Replace _<cloud_router_name>_ with the name of the Cloud Router that you noted while preparing the {gcp-short} environment.
+
[IMPORTANT]
====
Do not specify the Cloud Router that the {product-title} installer created for Cloud NAT.
The Operator cannot discover BGP neighbors on that router.
====

`spec.gcp.ncc.hubName`:: Specifies the NCC hub that the compute nodes of the cluster join as router appliance spokes.
Replace _<ncc_hub_name>_ with the name of the hub that you noted while preparing the {gcp-short} environment.
The Operator creates and manages the spokes in this hub automatically.

`spec.gcp.ncc.spokePrefix`:: Specifies the prefix for the names of the router appliance spokes that the Operator manages.
The Operator numbers the spokes `_<spoke_prefix>_-0`, `_<spoke_prefix>_-1`, and so on, and adds up to 8 compute nodes to each spoke.
Replace _<spoke_prefix>_ with a prefix for the spokes, such as the name of your cluster.
--
+
[NOTE]
====
`BGPCloudConfiguration` is a cluster-scoped singleton.
You must provide the name `cluster` to the CR.

The Operator discovers the BGP neighbors and the remote ASN of the Cloud Router automatically.
Do not specify explicit peer groups in the `spec.bgp.peerGroups` field, because the Operator rejects manual peer definitions on the GCP platform.
====

. Apply the updates to the BGP cloud configuration resource on your cluster by entering the following command:
+
[source,terminal]
----
$ oc apply -f bgpcloudconfiguration.yaml
----

. Create a namespace for your workload. Use the labels that the BGP Cloud Connector requires.
+
[source,yaml]
----
apiVersion: v1
kind: Namespace
metadata:
  name: <namespace_name>
  labels:
    k8s.ovn.org/primary-user-defined-network: ""
    cluster-udn: <network_name>
----
+
Replace _<namespace_name>_ with a name for the namespace.
Replace _<network_name>_ with the network name that you plan to use in the following step.
+
[IMPORTANT]
====
You must set the `k8s.ovn.org/primary-user-defined-network` label when you create the namespace.
{product-title} admission policy prevents you from adding this label to an existing namespace.
====

. Create the `Namespace` object by running the following command:
+
[source,terminal]
----
$ oc apply -f namespace.yaml
----

. Create a `BGPRouting` CR to declare the network to advertise over BGP:
+
[source,yaml]
----
apiVersion: networking.openshift.io/v1beta1
kind: BGPRouting
metadata:
  name: <routing_name>
spec:
  network:
    name: <network_name>
    subnets:
      - <pod_network_cidr>
----
+
where:
+
--
`_<routing_name>_`:: Specifies the name for the CR.
`_<network_name>_`:: Specifies the Layer 2 `ClusterUserDefinedNetwork` to create. The value must be the same value that you used for `cluster-udn` in an earlier step.
`_<pod_network_cidr>_`:: The CIDR block that the primary network interfaces of each VM get assigned from. For example `10.100.0.0/16`. The value is set as the `spec.network.layer2.subnets` of the CUDN. The value must not overlap with any of the CIDRs in your VPC network.
+
[NOTE]
====
`BGPRouting` resources create a Layer 2 `ClusterUserDefinedNetwork` based upon the name and subnets you specify. BGP Cloud Connector advertises routes for the subnets to your {gcp-short} Cloud Router.

The `spec.namespaceSelector.matchLabels` label for `ClusterUserDefinedNetwork` is set to `cluster-udn: _<network_name>_` to match the namespace you created in an earlier step. The name of the CUDN is `cluster-udn-_<network_name>_`.

Layer 2 CUDNs only allow a single IPv4 and a single IPv6 CIDR per subnet.
====
--

. Apply the `BGPRouting` CR by running the following command:
+
[source,terminal]
----
$ oc apply -f bgprouting.yaml
----

.Verification

. Confirm that both custom resources report a `Ready` phase by entering the following commands:
+
[source,terminal]
----
$ oc get bgpcloudconfiguration cluster -o jsonpath='{.status.phase}'
----
+
[source,terminal]
----
$ oc get bgprouting <routing_name> -o jsonpath='{.status.phase}'
----
+
Replace _<routing_name>_ with the name of the `BGPRouting` CR.

. Optional: If either resource reports `Degraded`, inspect its conditions for the failure reason by running the following command:
+
[source,terminal]
----
$ oc get bgpcloudconfiguration cluster -o jsonpath='{.status.conditions}' | jq .
----

. Confirm that the Operator generated the supporting resources by entering the following commands:
+
[source,terminal]
----
$ oc get frrconfiguration -n openshift-frr-k8s
----
+
[source,terminal]
----
$ oc get clusteruserdefinednetwork
----
+
[source,terminal]
----
$ oc get routeadvertisements
----

. Deploy a virtual machine into the namespace that you created, and verify that it uses `bridge` binding on its network interface:
+
[source,yaml]
----
spec:
  domain:
    devices:
      interfaces:
        - name: default
          bridge: {}
  networks:
    - name: default
      pod: {}
----
+
[IMPORTANT]
====
Use `bridge` binding, not `masquerade` binding. `masquerade` binding installs nftables rules that drop inbound traffic on the user-defined network (UDN) interface, which blocks the direct connectivity that this feature provides.
====

. From a VM instance within the VPC network, verify that you can reach the VM at its pod network IP address by entering the following command:
+
[source,terminal]
----
$ ping <vm_pod_ip>
----
+
Replace _<vm_pod_ip>_ with the pod network IP address of the VM.

. Optional: To verify connectivity from an external network, such as an on-premises network connected over {gcp-short} Cloud Interconnect or a VPN, first ensure that the external network can route traffic for the VM pod network into the VPC network.
