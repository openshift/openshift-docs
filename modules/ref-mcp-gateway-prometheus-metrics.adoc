= Prometheus metrics for the {mcpg} broker

[role="_abstract"]
You can use Prometheus metrics to monitor discovery attempts, tool counts, connection failures, and response sizes.

The {mcpg} broker component exposes Prometheus metrics on port `9090` without requiring an {OTLPName} (OTLP) endpoint. If telemetry configuration fails, the `/metrics` endpoint returns `503`. If that error is displays, check the startup logs for configuration errors.

The {mcpg} broker component provides the following metrics:

.MCP broker Prometheus metrics
[cols="1,1,2", options="header"]
|===
|Metric |Type |Description

|`mcp_broker_discovery_total`
|Counter
|Total number of discovery attempts by status. Labels: `status`, indicating success or failure. The `mcp_broker_discovery_total` uses `server_name` and `status` labels.

|`mcp_broker_discovery_duration_seconds`
|Histogram
|Latency of `tools/list` calls to backend Model Context Protocol (MCP) servers in seconds. Uses only the `server_name` label.

|`mcp_broker_tools_discovered`
|Gauge
|Cached tool count per upstream MCP server. Cached values survive transient connection or ping failures and reach zero after 3 consecutive connection or ping failures. Uses only the `server_name` label.

|`mcp_broker_upstream_connection_failures_total`
|Counter
|Total number of connection failures to upstream MCP servers. Uses only the `server_name` label.

|`mcp_broker_tools_list_response_bytes`
|Histogram
|Size of serialized tool list responses in bytes. Uses only the `server_name` label.
|===

Label values are formatted as `namespace/name`, matching the namespace and name given in the `MCPServerRegistration` custom resource. For example, `_<mcp_test>/<mcp_server_one>_`. No high-cardinality labels such as `trace_id` or `request_id` are used.
