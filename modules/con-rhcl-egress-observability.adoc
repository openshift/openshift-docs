= Metrics for outbound traffic

[role="_abstract"]
An egress `Gateway` object emits the same metrics, access logs, and traces as a gateway that handles incoming traffic. The values of some metric labels differ, because the destination of an egress request is a service outside the cluster.

include::snippets/egress-gateway-ossm.adoc[]

The egress `Gateway` object terminates the HTTP connection from the workload and originates TLS to the external service, so the full set of application layer metrics is available:

.Metrics that an egress gateway emits
[cols="1,1,2",options="header"]
|===
| Metric | Type | Description

| `istio_requests_total`
| Counter
| Total requests by response code, method, and destination

| `istio_request_duration_milliseconds`
| Histogram
| Distribution of request latency

| `istio_request_bytes`
| Histogram
| Distribution of request body size

| `istio_response_bytes`
| Histogram
| Distribution of response body size
|===

On an egress `Gateway` object, the `source_workload` label identifies the gateway itself rather than the workload that made the outbound call. To attribute egress traffic to individual workloads, use one of the following approaches:

* Resolve workload identity with an `AuthPolicy` custom resource (CR) and correlate requests by using access logs or traces.
* Add custom labels to the {prodname} data plane metrics with a `TelemetryPolicy` CR, which records the calling workload directly on the metrics of a rate limited route.

To isolate egress traffic from incoming traffic in the same monitoring stack, filter queries by the workload name of the egress gateway proxy, which has the form `_<kuadrant_egressgateway>_-istio`. For commands that select pods, use the `gateway.networking.k8s.io/gateway-name` label instead.
