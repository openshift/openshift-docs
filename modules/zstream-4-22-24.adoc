= RHSA-2026:103453 - {product-title} {product-version}.24 bug fix and security update

Issued: 1 December 2026

[role="_abstract"]
{product-title} release {product-version}.24 is now available. The list of fixed bugs that are included in the update is documented in the link:https://access.redhat.com/errata/RHSA-2026:103453[RHSA-2026:103453] advisory. The RPM packages that are included in the update are provided by the link:https://access.redhat.com/errata/RHSA-2026:103451[RHSA-2026:103451] advisory.

Space precluded documenting all of the container images for this release in the advisory.

You can view the container images in this release by running the following command:

[source,terminal]
----
$ oc adm release info 4.22.24 --pullspecs
----

== Enhancements

* Added alert to warn users of OCP 4.22 that EUS-to-EUS upgrade to 5.1 could break their clusters because 5.1 has SELinuxMount enabled. This is only an alert and they need to resolve the conflicts manually. They can use runbook available for them at https://github.com/openshift/runbooks/blob/master/alerts/cluster-storage-operator/SELinuxMountGAReadinessWorkloadsDetected.md. (link:https://issues.redhat.com/browse/OCPBUGS-133478[OCPBUGS-133478])

[id="zstream-4-22-24-fixed-issues_{context}"]
== Fixed issues

The following issues are fixed for this release:

* Before this update, a security fix for a server-side request forgery (SSRF) vulnerability blocked access to Helm chart repositories, chart archives, and Open Container Initiative (OCI) registries on private networks. As a consequence, ProjectHelmChartRepository resources that pointed to internal Helm registries, such as registries on private IPv4 networks (RFC 1918), failed validation in the web console. With this release, the SSRF protection permits requests to private network addresses and in-cluster service names, but still blocks requests to localhost, loopback addresses, unspecified addresses, cloud metadata addresses, and Kubernetes API service names. As a result, you can use Helm chart repositories and registries on private networks. A chart URL must use an OCI scheme, or an HTTP or HTTPS scheme with a path that ends in .tgz or .tar.gz. A repository index URL must have a path that ends in /index.yaml. (link:https://redhat.atlassian.net/browse/OCPBUGS-128587[OCPBUGS-128587])

* Before this update, the `ignore-namespaces` list of the Multus admission controller was never recomputed for namespaces that began qualifying, with the `openshift.io/cluster-monitoring=true` label and the `workload.openshift.io/allowed=management` annotation, after the first reconcile pass of the Cluster Network Operator. As a consequence, refreshing the list required a restart of the Cluster Network Operator pod. With this release, the list is refreshed without requiring a pod restart. (link:https://issues.redhat.com/browse/OCPBUGS-132723[OCPBUGS-132723])

* Before this update, the Control Plane Operator could include AWS Local Zone subnets when creating or modifying VPC endpoints for hosted control planes. As a consequence, AWS rejected the request and endpoint reconciliation failed. With this release, when multiple candidate subnets are configured, subnets known to be outside the configured region's standard Availability Zones are excluded before endpoint subnet selection. As a result, endpoint reconciliation proceeds using eligible standard Availability Zone subnets. (link:https://issues.redhat.com/browse/OCPBUGS-132919[OCPBUGS-132919])

* Before this update, clicking the *Create a virtual machines network using this physical network* row action on the *Physical networks* page did nothing, because the action navigated to a relative URL that matched no route. The action was also offered when the kubevirt console plugin was not installed. With this release, the action navigates to the correct form and is shown only when the kubevirt console plugin is installed. As a result, you can create a virtual machines network from a physical network as expected. (link:https://issues.redhat.com/browse/OCPBUGS-134123[OCPBUGS-134123])

* Before this update, mirror replacements from overlapping ICSP/IDMS definitions could be emitted in different orders. As a consequence, the generated `OPENSHIFT_IMG_OVERRIDES` value could change between reconciliations despite equivalent mirror mappings, causing repeated Control Plane Operator rollouts. With this release, mirror replacement entries are sorted deterministically when generating `OPENSHIFT_IMG_OVERRIDES`. As a result, equivalent mirror configurations produce a stable value, avoiding unnecessary Control Plane Operator rollouts. (link:https://issues.redhat.com/browse/OCPBUGS-138212[OCPBUGS-138212])

* Before this update, when a hardware configuration was restarted, the linuxptp daemon could attempt to stop a process before the process was fully populated, which could cause the linuxptp daemon to deadlock after a node reboot, silently dropping hardware compensation and later configuration updates. With this release, locks were added so that a process cannot be stopped before it has fully started. As a result, processes are closed properly and the linuxptp daemon does not deadlock. (link:https://issues.redhat.com/browse/OCPBUGS-138360[OCPBUGS-138360])

* Before this update, the kubevirt-csi-driver reported `CreateVolume` success before the infrastructure PVC was bound, so infrastructure provisioning errors such as quota failures never reached the guest cluster. As a consequence, tenant clusters could receive volumes that were not actually provisioned and failures went undetected. With this release, the driver detects failures in infrastructure provisioning and propagates them to tenant cluster provisioning. As a result, errors such as quota failures are reported to the guest cluster instead of being silently lost. (link:https://issues.redhat.com/browse/OCPBUGS-140048[OCPBUGS-140048])

* Before this update, the Cluster Autoscaler's Cluster API provider could repeatedly reduce a node group's target size for the same pending Machine, potentially reducing the group to its minimum size. With this update, the provider skips pending Machines already marked for deletion. It also skips stale pending-machine deletion requests for Machines that have since registered as nodes, so that those nodes go through the normal scale-down checks. (link:https://issues.redhat.com/browse/OCPBUGS-140546[OCPBUGS-140546])

* Before this update, the `ovnkube-control-plane` deployment required replicas to be spread across different availability zones. As a consequence, on a single-zone management cluster, replicas could be prevented from being scheduled. With this release, replicas are required to run on different nodes, while zone separation is preferred rather than required. As a result, replicas can be scheduled on distinct nodes within the same zone, retaining a preference for zone separation when available. 

* Before this update, the Vertical Pod Autoscaler Operator could fail to start and enter a CrashLoopBackOff state when its embedded version contained an all-numeric Git commit hash beginning with zero. The version parser rejected the hash as an invalid prerelease identifier. With this update, the hash is recorded as build metadata, which permits leading zeroes, preventing this startup failure. (link:https://issues.redhat.com/browse/OCPBUGS-141622[OCPBUGS-141622])

* Before this update, when a T-BC DPLL exited holdover, the offset qualification was evaluated against the legacy `maxOffsetThreshold` in addition to the holdover free-run bound, so with certain threshold combinations the two checks disagreed. As a consequence, upon holdover exit, a leading T-BC clock that had relocked in-spec reported a spurious FREERUN instead of transitioning directly from HOLDOVER to LOCKED. With this release, the `maxOffsetThreshold` window was removed from the DPLL decision path, and phase offset qualification is now based solely on the holdover free-run bound (`LocalMaxHoldoverOffSet`), consistent with the other holdover qualification checks. As a result, a T-BC clock that relocks within its holdover bound transitions directly from HOLDOVER to LOCKED without reporting a spurious FREERUN. (link:https://issues.redhat.com/browse/OCPBUGS-145532[OCPBUGS-145532])

* Before this update, control-plane metrics forwarding for hosted control planes could generate high cross-availability-zone data transfer costs because metrics scrape responses were transferred uncompressed. With this release, control-plane metrics scrape responses are gzip-compressed when the scraper requests gzip. As a result, the data transferred by metrics forwarding is reduced, and clients that do not request gzip continue to receive uncompressed responses. (link:https://issues.redhat.com/browse/OCPBUGS-145533[OCPBUGS-145533])
