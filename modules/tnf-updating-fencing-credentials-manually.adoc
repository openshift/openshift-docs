= Manually updating fencing credentials

[role="_abstract"]
If the credential update script is unavailable, for example because the cluster API is not reachable, you can update the Baseboard Management Controller (BMC) credentials that Pacemaker uses for fencing directly on a control plane node, and then synchronize the fencing secrets in the cluster.

.Prerequisites

* You have administrative access to the control plane nodes.
* You can connect to the nodes by using SSH.
* You have the new BMC credentials for the fencing devices.

.Procedure

. If the cluster API is unavailable, update the fencing credentials on a control plane node by running the following command:
+
[source,terminal]
----
$ sudo pcs stonith update <node_name>_redfish username=<user_name> password=<password>
----
+
Replace `<node_name>` with the name of the control plane node, and `<user_name>` and `<password>` with the new BMC credentials.

. After the cluster API recovers, or if it is already available, update the fencing secrets in the cluster so that the stored credentials stay in sync. Edit the fencing secrets for the control plane node by running the following commands:
+
[source,terminal]
----
$ oc project openshift-etcd
----
+
[source,terminal]
----
$ oc edit secret fencing-credentials-<node_name>
----
+
The secret contains the following data keys:
+
[cols="1,1,2",options="header"]
.Data keys
|===
| Key | Description | Changes during credential rotation?
| `username` | BMC username | Yes
| `password` | BMC password | Yes
| `address` | Full Redfish URL, for example `redfish+https://192.168.1.10:443/redfish/v1/Systems/1` | Only if the BMC address changed
| `certificateVerification` | `Disabled` or `Enabled` | Only if TLS settings changed
|===
+
[NOTE]
====
The `oc edit secret` command displays base64-encoded values. If you modify any of the values, the new values must also be base64-encoded.
====
+
Alternatively, you can update the secret with literal strings by running the following command:
+
[source,terminal]
----
$ oc create secret generic fencing-credentials-<node_name> \
  --from-literal=address='<redfish_address>' \
  --from-literal=username='<new_username>' \
  --from-literal=password='<new_password>' \
  --from-literal=certificateVerification='<Disabled_or_Enabled>' \
  --dry-run=client -o yaml | oc apply -f -
----
+
All four keys must be present. The cluster etcd Operator rejects secrets with missing keys.

.Verification

. Verify that the new credentials can reach the BMC by running the following command:
+
[source,terminal]
----
$ sudo fence_redfish --action status --ip=<bmc_address> --ipport=<bmc_port> --systems-uri=<systems_uri> --username=<user_name> --password=<password>
----
+
Replace `<bmc_port>` and `<systems_uri>` with the values from the fencing configuration, for example `443` and `/redfish/v1/Systems/1`. If the `certificateVerification` key in the fencing secret is set to `Disabled`, add the `--ssl-insecure` option to the command.
+
This is the same validation that the cluster etcd Operator performs when it applies credentials from the fencing secret.

. Verify that no STONITH resources are blocked by running the following command:
+
[source,terminal]
----
$ sudo pcs status --full
----
