= Gang scheduling configuration

[role="_abstract"]
The `spec.config.gangScheduling` fields in the `Kueue` custom resource (CR) control admission, readiness timeouts, and retry behavior for gang-scheduled workloads.

The following example uses parallel admission and a 10-minute start timeout:

// Example sources:
// Timeout of 600 seconds:
// https://github.com/openshift/kueue-operator/blob/f940304dae5befd94ffdf0a9a7f9a34aa4e9fd6f/pkg/configmap/configmap_test.go#L273-L335
// BatchJob integration with the ByWorkload policy:
// https://github.com/openshift/kueue-operator/blob/f940304dae5befd94ffdf0a9a7f9a34aa4e9fd6f/test/e2e/e2e_gangscheduling_test.go#L264-L430
.Example `Kueue` CR with gang scheduling configured
[source,yaml]
----
apiVersion: kueue.openshift.io/v1
kind: Kueue
metadata:
  name: cluster
  labels:
    app.kubernetes.io/managed-by: kustomize
    app.kubernetes.io/name: kueue-operator
spec:
  config:
    integrations:
      frameworks:
      - BatchJob
    gangScheduling:
      policy: ByWorkload
      byWorkload:
        admission: Parallel
        timeoutSeconds: 600
----

The `policy` field accepts the following values:

.`spec.config.gangScheduling.policy` values
[cols="1,3",options="header"]
|===
|Value
|Behavior

|`ByWorkload`
|Uses the `byWorkload` settings for readiness timeouts and retries. Include the `byWorkload` field.

|`ByWorkloadDefaults`
|Uses the default workload readiness settings. Omit the `byWorkload` field.

|`None`
|Sets a one-year readiness timeout and uses parallel admission. Workloads can still time out. Omit the `byWorkload` field.

|Empty string (`""`)
|Uses the policy selected by the Operator. Omit the `byWorkload` field.
|===

The `admission` field accepts the following values. Set this field when you use the `ByWorkload` policy.

.`spec.config.gangScheduling.byWorkload.admission` values
[cols="1,3",options="header"]
|===
|Value
|Behavior

|`Parallel`
|Admits workloads without waiting for pods in admitted workloads to reach a ready state. Quota and other admission requirements still apply. Workloads can compete for cluster capacity and cause a deadlock.

|`Sequential`
|Waits for pods in admitted workloads to reach a ready state before admitting more workloads across any cluster queue. Sequential admission reduces competition for resources while pods start. It can delay workloads even when the cluster has capacity to run them.

|Empty string (`""`)
|Uses the admission mode selected by the Operator. The current default is `Parallel`.
|===

The `byWorkload` field supports the following timeout fields:

.`spec.config.gangScheduling.byWorkload` timeout fields
[cols="2,3,2,2",options="header"]
|===
|Field
|Description
|Valid values
|If omitted

|`timeoutSeconds`
|Sets the start timeout for an admitted workload to reach the `PodsReady=True` condition. Allow enough time for image pulls, initialization, and resource provisioning.
|`30`–`86400` seconds
|Uses the default readiness timeout.

|`recoveryTimeoutSeconds`
|Sets the recovery timeout for a workload to return to the `PodsReady=True` condition after one or more pods lose readiness. A value of `0` disables recovery timeout checks. The start timeout still applies.
|`0`–`86400` seconds
|Uses the value of `timeoutSeconds`.
|===

The `requeuingStrategy` field supports the following fields. If you include `requeuingStrategy`, specify at least one field. An empty `requeuingStrategy: {}` value is invalid.

.`spec.config.gangScheduling.byWorkload.requeuingStrategy` fields
[cols="2,3,2,2",options="header"]
|===
|Field
|Description
|Valid values
|If omitted

|`timeReference`
|Selects which timestamp {kueue-name} uses to order a workload in the queue after a readiness timeout.
|`Eviction` uses the eviction time. `Creation` uses the workload creation time.
|Uses `Eviction`.

|`retryLimit`
|Limits repeated admission attempts after readiness timeouts. After a workload uses all retries, the next timeout deactivates the workload. The `spec.active` field of the `Workload` object changes to `false`.
|`1`–`200`
|Sets no retry limit.

|`backoffBaseSeconds`
|Sets the base delay before a workload can be admitted again. The delay increases exponentially with the retry count.
|`30`–`3600` seconds
|Uses `60` seconds.

|`backoffMaxSeconds`
|Sets the maximum delay before a workload can be admitted again. If you set both delay fields, `backoffBaseSeconds` must not exceed `backoffMaxSeconds`.
|`30`–`7200` seconds
|Uses `3600` seconds.
|===

After the configured delay, the workload must still meet quota and other admission requirements before {kueue-name} can admit it again.
