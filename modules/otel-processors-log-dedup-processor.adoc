= Log Deduplication Processor

[role="_abstract"]
The Log Deduplication Processor aggregates identical log records over a configurable time interval and emits a single log record that carries the number of aggregated records.

:FeatureName: The Log Deduplication Processor
include::snippets/technology-preview.adoc[]
:!FeatureName:

With this processor, you can reduce repetitive logs before you send them to a storage back end or to a consumer such as a security information and event management (SIEM) system. For example, repetitive logs include health checks, heartbeats, or repeated Kubernetes events.

The processor works only on logs. Two log records are identical when their resource attributes, scope attributes, log attributes, body, and severity are identical. Identical log records that arrive within the `interval` period are emitted as one log record. This log record has the following attributes:

`log_count`::
The number of aggregated log records. You can change the name of this attribute with the `log_count_attribute` setting.

`first_observed_timestamp`::
The time when the processor processed the first matching log during the aggregation interval.

`last_observed_timestamp`::
The time when the processor processed the most recent matching log during the aggregation interval.

[NOTE]
====
The emitted log record has a new `Timestamp` value, which is the time when the aggregated record is emitted, and its `ObservedTimestamp` is set to the start of the aggregation interval. Neither field matches the values in the deduplicated records. For the aggregation window, use the `first_observed_timestamp` and `last_observed_timestamp` attributes.
====

The following `OpenTelemetryCollector` custom resource configures the Log Deduplication Processor:

[source,yaml]
----
# ...
  config:
    receivers:
      otlp:
        protocols:
          http:
            include_metadata: true
    processors:
      log_dedup:
        interval: 30s
        log_count_attribute: log_count
        timezone: UTC
        metadata_keys:
          - x-scope-orgid
        metadata_cardinality_limit: 100
        conditions:
          - 'log.attributes["k8s.resource.name"] == "events"'
    service:
      pipelines:
        logs:
          receivers: [otlp]
          processors: [log_dedup]
# ...
----
where:

`include_metadata`:: Setting of the OTLP Receiver that keeps the client metadata, such as HTTP headers, of the incoming requests. The `metadata_keys` setting of the processor requires it.
`interval`:: Time interval during which identical log records are aggregated into one log record. The value must be greater than `0`. The default is `10s`.
`log_count_attribute`:: Name of the attribute that holds the number of aggregated log records. The default is `log_count`.
`timezone`:: Time zone that is used to format the `first_observed_timestamp` and `last_observed_timestamp` attributes. This setting does not change the timestamps of the log records. The default is `UTC`.
`metadata_keys`:: Optional. List of client metadata keys, such as the `x-scope-orgid` HTTP header or gRPC metadata. Each unique combination of values for these keys gets its own deduplication scope, so that logs of different tenants are never aggregated together. Key matching is case-insensitive. You do not need to list resource attributes in `metadata_keys`. Records with different resource attributes are already deduplicated separately.
`metadata_cardinality_limit`:: Optional. Maximum number of distinct combinations of metadata values. By default, the processor applies no limit. If you set `metadata_keys` without this setting, the processor logs a warning when it starts.
`conditions`:: Optional. List of OTTL conditions that select the log records to deduplicate. Log records that do not match the conditions are forwarded unchanged without deduplication. Start the paths with the context name, for example `log.attributes["k8s.resource.name"]`. The form without the context name is deprecated.

By default, the processor uses all attributes, the body, and the severity of a log record to decide whether two log records are identical. To change this, set either `include_fields` or `exclude_fields` in one configuration. Each field must start with `body` or `attributes` and use a dot to separate the levels, and must identify an individual field; the `body` as a whole cannot be included or excluded. Use `\.` for a dot that is part of a name.

The following `OpenTelemetryCollector` custom resource excludes from the comparison a field that changes with every event:

[source,yaml]
----
# ...
  config:
    processors:
      log_dedup:
        interval: 30s
        exclude_fields:
          - body.object.metadata.resourceVersion
# ...
----
where:

`exclude_fields`:: Optional. List of fields that are not used to decide whether two log records are identical. The processor also removes these fields from the emitted log record.
`include_fields`:: Optional. List of fields that are used to decide whether two log records are identical. All other fields are ignored.

[NOTE]
====
* Fields that change with every log record prevent deduplication. For example, when you collect Kubernetes events with the Kubernetes Objects Receiver, the `resourceVersion` field and the event type differ between the events of one object. Use `exclude_fields` or `include_fields` to leave such fields out of the comparison.
* The processor calculates a hash of the attributes, the body, and the severity of every log record. The time that the hash calculation takes grows faster than linearly with the number of attributes in a single log record. If your logs carry hundreds of attributes, use `include_fields` to limit the fields that are compared.
====
