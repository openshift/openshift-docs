= Rotating the Vault encryption key

[role="_abstract"]
You can rotate your Vault Transit encryption key to generate a new key version while maintaining access to data encrypted with earlier versions. // cite:1
// cite:1 VERIFIED [50]: https://developer.hashicorp.com/vault/docs/secrets/transit#key-rotation - Vault Transit key rotation creates new version, retains old versions for decryption

After you rotate the key in Vault, {product-title} automatically detects the new key version through the KMS plugin health reporter. The platform waits for all control plane nodes to report the new key version consistently for at least 5 minutes, then triggers re-encryption of etcd data. // cite:2
// cite:2 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L500-L504 - External remote-key rotation detected via health reporter, triggers re-encryption via migrationController
// cite:2 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L528 - KEP-3299: >= 5 minutes of cluster-wide converged remote-key-id before keyController may promote target-remote-key-id

.Prerequisites

* You have access to the cluster as a user with the `cluster-admin` role.
* You have access to your Vault instance with permissions to rotate keys.
* KMS encryption is enabled and functioning.

.Procedure

. Rotate the Vault encryption key by entering the following command:
+
[source,terminal]
----
$ vault write -f transit/keys/kms-key/rotate
----
+
Vault creates a new key version while maintaining earlier versions for decryption.

. Verify the new key version by entering the following command:
+
[source,terminal]
----
$ vault read transit/keys/kms-key
----
+
The `latest_version` field shows the current key version number.

.Verification

. Verify that existing secrets remain accessible by entering the following command:
+
[source,terminal]
----
$ oc get secret -A
----
+
All secrets are readable without errors.

. Monitor the automatic re-encryption progress by entering the following command: // cite:3
+
[source,terminal]
----
$ oc get secret -n openshift-config-managed -l encryption.apiserver.operator.openshift.io/component=kube-apiserver -o jsonpath='{range .items[*]}{.metadata.name}: target={.metadata.annotations.encryption\.apiserver\.operator\.openshift\.io/target-remote-key-id} migrated={.metadata.annotations.encryption\.apiserver\.operator\.openshift\.io/migrated-remote-key-id}{"\n"}{end}'
----
+
When `target-remote-key-id` and `migrated-remote-key-id` show the same value, re-encryption is complete. // cite:4
// cite:3 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L544-L549 - Annotation names: target-remote-key-id and migrated-remote-key-id on encryption key Secret
// cite:4 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L525 - "In steady state both are set and equal — etcd data has been fully re-encrypted to that RemoteKeyId"

[NOTE]
====
Automatic re-encryption can take several minutes. The platform waits for at least 5 minutes of consistent key version reporting across all nodes before it starts re-encryption. // cite:5
// cite:5 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L528 - KEP-3299 constraint: >= 5 minutes cluster-wide converged remote-key-id
// cite:5 VERIFIED [90]: https://github.com/openshift/enhancements/blob/66c24fe/enhancements/kube-apiserver/kms-encryption-foundations.md#L563 - "5m convergence clock" described in detail
====
