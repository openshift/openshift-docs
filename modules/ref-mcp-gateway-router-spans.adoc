= {mcpg} router spans for observability

[role="_abstract"]
When you enable tracing, the Model Context Protocol (MCP) router, `ext_proc`, emits protocol-aware trace spans for each external processing request. Logs are exported through {OTELName} when you have configured `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` or the base endpoint.

Spans give you a continuous timeline of traffic events across different pods and services. The {mcpg} supports the following dual-protocol routing:

* The `2025-11-25` protocol, stateful and body-based.
* The `2026-07-28` protocol, stateless and header-based.

The generated spans and their relationships depend on the protocol version negotiated by the client.

.MCP router spans by protocol version
[cols="1,1,2", options="header"]
|===
|Span |Protocol |Description

|`mcp-router.process`
|Both 2025 and 2026
|Root span for one external processing stream. Starts when request headers arrive. Records request and routing attributes as body phases are processed. Records the response status at response headers. Ends after response headers for a non-streamed response or after the final streamed response-body phase.

|`mcp-router.route-decision`
|Both 2025 and 2026
|Records the routing decision for the request.

|`mcp-router.broker-passthrough`
|Both 2025 and 2026
|Handles requests that pass through to the broker.

|`mcp-router.tool-call`
|Both 2025 and 2026
|Handles `tools/call` requests.

|`mcp-router.prompt-get`
|Both 2025 and 2026
|Handles `prompts/get` requests.

|`mcp-router.resource-read`
|2025 stateful only
|Handles `resources/read` requests.

|`mcp-router.elicitation-response`
|2025 stateful only
|Handles elicitation responses.

|`mcp-router.session-init`
|2025 stateful only
|Initializes a backend session when a routed request needs one that is not already available.
|===

* The `2025-11-25` stateful router can create a `mcp-router.session-init` span on a cache miss. Session initialization hairpins an `initialize` request through the gateway and stores the resulting backend session for later requests.

* The `2026-07-28` stateless router does not emit session-initialization or session-cache spans and does not hairpin an initialization request.

* Tool and prompt routing performs routing-table lookups inside the `mcp-router.tool-call` or `mcp-router.prompt-get` span. These lookups do not emit separate spans.

The attributes attached to spans use link:https://opentelemetry.io/docs/specs/semconv/gen-ai/mcp/#server[OpenTelemetry MCP Semantic Conventions]. All router spans include `component=mcp-router`. Header-derived attributes are set even when the corresponding request header is not present. Empty values are recorded as empty strings.

.MCP router span attributes
[cols="1,3", options="header"]
|===
|Span or protocol |Attributes

|`mcp-router.process`
|Request-header attributes `http.method`, `http.path`, `http.request_id`, `mcp.protocol_version`, `mcp.header.method`, and `mcp.header.name`. These attributes have empty-string values when their source headers are not present. Parsed-request attributes include the following spans: `mcp.method.name`, `jsonrpc.protocol.version`, `jsonrpc.request.id`, `gen_ai.operation.name`, and `gen_ai.tool.name` for tool calls, `mcp.session.id` when a stateful session is present, and `client.address` when `x-forwarded-for` is present. The selected router is recorded as `mcp.router` with a value of `202511` or `202607`. Response attributes include `http.status_code` and `mcp.response.protocol_version`. The latter contains the incoming `MCP-Protocol-Version` request-header value and is recorded during response-header processing.

|`mcp-router.route-decision`
|`mcp.method.name`, `protocol.version`, and `mcp.route`. The `2025-11-25` route can be `tool-call`, `prompt-get`, `resource-read`, `elicitation-response`, or `broker`. The `2026-07-28` route can be `tool-call`, `prompt-get`, or `broker`.

|2025-11-25 `mcp-router.tool-call`
|`gen_ai.tool.name`, `mcp.session.id`, `mcp.server`, and `mcp.server.hostname`

|2025-11-25 `mcp-router.prompt-get`
|`mcp.prompt.name`, `mcp.session.id`, `mcp.server`, and `mcp.server.hostname`

|2025-11-25 `mcp-router.resource-read`
|`mcp.resource.uri`, `mcp.session.id`, `mcp.server`, and `mcp.server.hostname`

|2025-11-25 `mcp-router.session-init`
|`mcp.server` and `mcp.session.id`

|2025-11-25 `mcp-router.elicitation-response`
|`mcp.session.id`

|2026-07-28 `mcp-router.tool-call`
|`gen_ai.tool.name`, `mcp.server`, and `mcp.server.hostname`. This stateless span does not set `mcp.session.id`.

|2026-07-28 `mcp-router.prompt-get`
|`mcp.prompt.name`, `mcp.server`, and `mcp.server.hostname`. This stateless span does not set `mcp.session.id`.

|`mcp-router.broker-passthrough`
|`mcp.method.name`
|===

.MCP broker spans
[cols="1,2,2", options="header"]
|===
|Span |When |Attributes

|`mcp-broker.handle-request`
|MCP method requests processed by the broker, such as `initialize`, `ping`, `tools/list`, `tools/call`, `prompts/list`, `prompts/get`, and `resources/list`
|`mcp.method` and `protocol.version`; `mcp.session.id` when the SDK request has a stateful session

|`mcp-broker.tools-list`
|`tools/list` response filtering
|`protocol.version` and `mcp.tools.count`

|`mcp-broker.prompts-list`
|`prompts/list` response filtering
|`protocol.version` and `mcp.prompts.count`

|`mcp-broker.resources-list`
|`resources/list` response filtering
|`mcp.resources.count`

|`mcp-broker.upstream-manage`
|Upstream lifecycle work at startup, on the health check timer, after list-changed notifications, and after reconnect events
|`mcp.server`
|===

The {mcpg} router propagates W3C trace context on forwarded requests, allowing broker filtering spans to correlate with router work in a single trace. These spans are children of `mcp-broker.handle-request`. However, because outbound header injection is currently a no-operation function, this correlation relies on an incoming client or Envoy `traceparent` header. Without an incoming trace header, the router-generated root context is not forwarded, causing broker spans to start a separate trace.

.MCP error attributes
[cols="1,2", options="header"]
|===
|Attribute |Description

|`error.type`
|Error classification.

|`error_source`
|Component that generated the error, such as `ext-proc`, `broker`, or `backend`.

|`http.status_code`
|HTTP status code recorded on the router process span when response headers are processed.
|===

Error recording is component-specific. Errors passed to the router error-recording path include `error.type`, `error_source=ext-proc`, and the associated `http.status_code`.
Broker handler errors record `error.type` and `error_source=broker`.
Backend connection or discovery errors recorded by `mcp-broker.upstream-manage` record `error.type`, `error_source=backend`, and `mcp.server`.
Router route errors can set span status and `error.type`. The resulting HTTP status is recorded on `mcp-router.process` when response headers are processed.
