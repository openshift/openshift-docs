= Preparing API credentials for a nested cluster

[role="_abstract"]
You can create a dedicated service account on the nested cluster and store its `kubeconfig` on the parent cluster. The parent {spiffe-full} Runtime Environment (SPIRE) server uses the `kubeconfig` to attest the nested cluster.

The secret name is `nested-spire-<cluster_name>-kubeconfig`. Set `<cluster_name>` to the `spec.clusterName` value on the nested `ZeroTrustWorkloadIdentityManager` custom resource (CR).

.Prerequisites

* You are logged in to the nested cluster with the `cluster-admin` role.
* You can log in to the parent cluster with the `cluster-admin` role.
* You installed {zero-trust-full} in the same namespace on both clusters.
* You already set the nested `spec.clusterName` field to a DNS subdomain of at most 63 characters.

.Procedure

. On the nested cluster, read the cluster name by running the following command:
+
[source,terminal]
----
$ oc get ZeroTrustWorkloadIdentityManager cluster -o jsonpath='{.spec.clusterName}{"\n"}'
----
+
Use the cluster name as `<cluster_name>` in the secret name on the parent cluster. In the following examples, the cluster name is `cluster01`.

. Create `ServiceAccount`, the RBAC bindings, and a token secret.
+
Grant `ServiceAccount` a `create` permission on `tokenreviews` and a `get` permission on `nodes`. Limit `get` on `pods` to the Operator namespace. Save the following manifest as `nested-spire-attestor.yaml`:
+
[source,yaml]
----
apiVersion: v1
kind: ServiceAccount
metadata:
  name: nested-spire-attestor
  namespace: zero-trust-workload-identity-manager
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: nested-spire-attestor
rules:
  - apiGroups: ["authentication.k8s.io"]
    resources: ["tokenreviews"]
    verbs: ["create"]
  - apiGroups: [""]
    resources: ["nodes"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: nested-spire-attestor
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: ClusterRole
  name: nested-spire-attestor
subjects:
  - kind: ServiceAccount
    name: nested-spire-attestor
    namespace: zero-trust-workload-identity-manager
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: nested-spire-attestor
  namespace: zero-trust-workload-identity-manager
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: nested-spire-attestor
  namespace: zero-trust-workload-identity-manager
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: nested-spire-attestor
subjects:
  - kind: ServiceAccount
    name: nested-spire-attestor
    namespace: zero-trust-workload-identity-manager
---
apiVersion: v1
kind: Secret
metadata:
  name: nested-spire-attestor-token
  namespace: zero-trust-workload-identity-manager
  annotations:
    kubernetes.io/service-account.name: nested-spire-attestor
type: kubernetes.io/service-account-token
----

. Apply the manifest by running the following command:
+
[source,terminal]
----
$ oc apply -f nested-spire-attestor.yaml
----

. Confirm that the token secret contains a token by running the following command:
+
[source,terminal]
----
$ oc get secret nested-spire-attestor-token -n zero-trust-workload-identity-manager -o go-template='{{if index .data "token"}}token present{{end}}{{"\n"}}'
----

. On the nested cluster, set the API server address by running the following command:
+
[source,terminal]
----
$ API_SERVER=$(oc whoami --show-server)
----
+
Run the `oc whoami --show-server` command and the next three commands in the same shell. The command returns the API address of the nested cluster.

. Set the cluster certificate authority (CA) data by running the following command:
+
[source,terminal]
----
$ CA_DATA=$(oc get secret nested-spire-attestor-token -n zero-trust-workload-identity-manager -o jsonpath='{.data.ca\.crt}')
----

. Set the ServiceAccount token by running the following command:
+
[source,terminal]
----
$ TOKEN=$(oc get secret nested-spire-attestor-token -n zero-trust-workload-identity-manager -o jsonpath='{.data.token}' | base64 -d)
----

. Create the `kubeconfig` file by using the following example configuration:
+
[source,yaml]
----
apiVersion: v1
kind: Config
clusters:
- name: cluster01
  cluster:
    certificate-authority-data: ${CA_DATA}
    server: ${API_SERVER}
contexts:
- name: cluster01
  context:
    cluster: cluster01
    user: nested-spire-attestor
current-context: cluster01
users:
- name: nested-spire-attestor
  user:
    token: ${TOKEN}
----

. Log in to the parent cluster.

. Store the `kubeconfig` in the Operator namespace by running the following command:
+
Set the data key to `kubeconfig`.
+
[source,terminal]
----
$ oc create secret generic nested-spire-cluster01-kubeconfig \
  -n zero-trust-workload-identity-manager \
  --from-file=kubeconfig=kubeconfig \
  --dry-run=client -o yaml | oc apply -f -
----

. Delete the local `kubeconfig` file by running the following command:
+
[source,terminal]
----
$ rm -f kubeconfig
----

.Verification

. On the nested cluster, confirm that the ServiceAccount can create token reviews by running the following command:
+
[source,terminal]
----
$ oc auth can-i create tokenreviews.authentication.k8s.io --as=system:serviceaccount:zero-trust-workload-identity-manager:nested-spire-attestor
----

. Confirm that the ServiceAccount can get nodes by running the following command:
+
[source,terminal]
----
$ oc auth can-i get nodes --as=system:serviceaccount:zero-trust-workload-identity-manager:nested-spire-attestor
----

. Confirm that the ServiceAccount can get pods in the operator namespace by running the following command:
+
[source,terminal]
----
$ oc auth can-i get pods -n zero-trust-workload-identity-manager --as=system:serviceaccount:zero-trust-workload-identity-manager:nested-spire-attestor
----

. On the parent cluster, confirm that the secret has a `kubeconfig` key by running the following command:
+
[source,terminal]
----
$ oc get secret nested-spire-cluster01-kubeconfig -n zero-trust-workload-identity-manager -o go-template='{{if index .data "kubeconfig"}}kubeconfig present{{end}}{{"\n"}}'
----
+
[NOTE]
====
You must maintain the `kubeconfig` secret. {zero-trust-full} does not delete the secret when you remove the cluster registration.
====
