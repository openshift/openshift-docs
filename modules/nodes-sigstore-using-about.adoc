= Understanding image signature verification

[role="_abstract"]
Cluster administrators or application developers can use the sigstore project to improve supply chain security by verifying that container images have not been tampered with and come from trusted sources. You can configure signature verification for all platform and operator images, including in disconnected or air-gapped environments. This capability is critical for organizations that require strict supply chain security, such as those in the telecommunications sector, and enables you to use your existing public key infrastructure (PKI) to sign and verify images.

With the sigstore project, signatures can be stored in the same registry as the container images, eliminating the need for a separate signature server. The identity piece of a signature is tied to the OpenID Connect (OIDC) identity through the Fulcio certificate authority, which simplifies the signature process by allowing keyless signing. Additionally, sigstore includes Rekor, which records signature metadata to an immutable, tamper-resistant ledger.

You can use the `ClusterImagePolicy` and `ImagePolicy` custom resource (CR) objects to enable and configure sigstore support at the cluster or namespace scope. These objects specify the images and repositories to be verified and how the signatures must be verified. When enabled, pods that attempt to use unsigned or incorrectly signed images are blocked from starting.

[id="nodes-sigstore-connected-vs-disconnected_{context}"]
== Connected and disconnected environments

Signature verification works differently depending on your environment:

Connected environments:: In connected environments, the cluster can directly access public registries such as `quay.io` and retrieve both images and their associated sigstore signatures. The verification process is transparent and requires minimal configuration beyond creating the appropriate `ClusterImagePolicy` or `ImagePolicy` objects.

Disconnected environments:: In disconnected or air-gapped environments, you must mirror both the container images and their sigstore signatures to your local registry before the cluster can verify them. Use the oc-mirror plugin to mirror images with their signatures. If signatures are not mirrored, signature verification fails and pods cannot start.

[id="nodes-sigstore-upgrade-considerations_{context}"]
== Cluster upgrade considerations

Before upgrading a cluster that has signature verification enabled, ensure that all required signatures are mirrored to your disconnected registry. The Cluster Version Operator (CVO) requires verified images to move pods to new nodes during the upgrade process. If signatures are missing or invalid, the upgrade can fail.

The default `ClusterImagePolicy` object named `openshift` enforces signature verification for {product-title} release images in the `quay.io/openshift-release-dev/ocp-release` and `quay.io/openshift-release-dev/ocp-v4.0-art-dev` repositories. When using a mirror registry, you must mirror the sigstore signatures for these repositories to ensure successful upgrades.

[id="nodes-sigstore-byopki_{context}"]
== Bring Your Own PKI

You can use your existing public key infrastructure (PKI) to sign and verify container images by configuring a Bring Your Own PKI (BYOPKI) policy. This approach is compatible with Cosign and enables you to use X.509 certificates from your organization's certificate authority.

BYOPKI is particularly useful for organizations that:

* Have established PKI infrastructure and want to integrate container signing into existing security workflows
* Require long certificate trust chains with intermediate certificate authorities
* Need to comply with internal security policies that mandate use of organizational certificates

When configuring BYOPKI, you must provide the CA root certificate and any intermediate certificates in the `ClusterImagePolicy` or `ImagePolicy` object. The certificates must be base64-encoded in PEM format.

[id="nodes-sigstore-verification-methods_{context}"]
== Verification methods

{product-title} supports three methods for verifying image signatures:

Public key:: Uses a Cosign public and private key pair. You provide the base64-encoded public key in PEM format. Optionally, you can include Rekor verification to check the signature against the Rekor transparency log.

PKI (BYOPKI):: Uses certificates from your organization's public key infrastructure. You provide the CA root certificate and optionally intermediate certificates. This method is compatible with Cosign's bring-your-own PKI signing workflow.

Fulcio certificate with Rekor:: Uses keyless signing through the Fulcio certificate authority and requires Rekor verification. You provide the Fulcio CA certificate, the OIDC issuer, and the signer's email address. This method ties the signature to an OIDC identity.
