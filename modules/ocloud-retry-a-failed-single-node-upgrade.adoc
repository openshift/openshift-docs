= Retry a failed {sno} cluster upgrade

[role="_abstract"]
When an image-based upgrade fails on a {sno} cluster, the recovery path depends on the failure reason reported in the `UpgradeCompleted` condition. Input errors can be corrected in place, while runtime failures require reverting to the original `ClusterTemplate` version after the automatic rollback completes.

.Prerequisites

* The `UpgradeCompleted` condition on the `ProvisioningRequest` CR shows `reason: PreconditionChecksFailed`, `reason: Failed`, or `reason: TimedOut`.

.Procedure

. Check the `UpgradeCompleted` condition to determine the failure type by running the following command:
+
[source,terminal]
----
$ oc get provisioningrequests.clcm.openshift.io <uuid> \
  -o jsonpath='{.status.conditions[?(@.type=="UpgradeCompleted")]}'
----
+
where:
+
`<uuid>`:: Specifies the UUID of the `ProvisioningRequest` CR for the target cluster.

. If the `reason` is `PreconditionChecksFailed`, fix the input error directly:
+
The upgrade was not started because a precondition was not met, such as a schema validation failure or version mismatch. Patch the `ProvisioningRequest` CR with corrected `upgradeParameters` or fix the referenced `ClusterTemplate` CR. The O-Cloud Manager re-evaluates the upgrade automatically after the change is detected.

. If the `reason` is `TimedOut` or `Failed`, wait for the automatic rollback to complete and then retry:

.. Wait for the automatic rollback to complete. The `ImageBasedGroupUpgrade` plan includes `AbortOnFailure` actions that handle rollback and cleanup automatically.

.. Revert the `ProvisioningRequest` CR to the original `ClusterTemplate` version by running the following command:
+
[source,terminal]
----
$ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateName":"<template_name>","templateVersion":"<original_version>"}}'
----
+
where:
+
--
`<template_name>`:: Specifies the template name, such as `sno-ran-du`.
`<original_version>`:: Specifies the original `ClusterTemplate` version, such as `v4-Y-Z-1`.
--

.. Wait for the `ProvisioningRequest` CR to return to `provisioningPhase: fulfilled`.

.. Investigate and resolve the root cause of the failure based on the `message` field from the `UpgradeCompleted` condition, such as a network timeout or seed image issue.

.. Re-trigger the upgrade by updating the `ProvisioningRequest` CR to the target `ClusterTemplate` version by running the following command:
+
[source,terminal]
----
$ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateName":"<template_name>","templateVersion":"<target_version>"}}'
----
+
where:
+
`<target_version>`:: Specifies the new `ClusterTemplate` version for the target release.

.Verification

* Verify that the upgrade completed successfully by running the following command:
+
[source,terminal]
----
$ oc get provisioningrequests.clcm.openshift.io <uuid>
----
+
.Example output
[source,terminal]
----
NAME                                   DISPLAYNAME   AGE    PROVISIONPHASE   PROVISIONDETAILS
123e4567-e89b-12d3-a456-426614174000                 240m   fulfilled        Upgrade is completed
----
