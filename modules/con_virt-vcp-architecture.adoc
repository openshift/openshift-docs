= Virtualized control plane architecture

[role="_abstract"]
The following diagram shows a multitenant virtualized control plane deployment.
A single hosting cluster runs control plane VMs for multiple target clusters across its nodes.

image::vcp-networking-arch-draft2.png[Virtualized control plane architecture showing multitenant hosting]

The hosting cluster runs each control plane VM as a `VirtualMachine` CR managed by {VirtProductName}.
KubeVirt Redfish exposes these VMs through standard Redfish API endpoints, which the installation workflow uses to manage VM power state and boot order.

Each target cluster's control plane VMs are distributed across hosting cluster nodes by using anti-affinity rules, so that a single node failure affects only one VM for each target cluster.
The VMs run in a dedicated namespace on the hosting cluster, providing resource and access isolation between target clusters.

Each target cluster has its own machine network that provides L2 connectivity between its control plane VMs.
The target cluster's worker nodes run on a separate L2 network segment on bare-metal infrastructure, connected to the control plane through routed L3 connectivity.
The `apiVIPs` must reside on the same L2 segment as the control plane VMs, and the `ingressVIPs` must reside on the same L2 segment as the worker nodes.

[NOTE]
====
Network address translation (NAT) is not supported between the control plane and worker networks.
====

The following diagram shows how network traffic flows inside a single hosting cluster node.
Control plane VM traffic and hosting cluster pod traffic use separate network paths.

image::vcp_network_traffic.png[Network traffic flow inside a hosting cluster node]

Control plane VMs connect to the cluster machine network through a Multus `NetworkAttachmentDefinition` resource and a secondary bridge interface.
Hosting cluster pods use the default OVN-Kubernetes network on a separate bridge and NIC.

The following diagram shows the storage architecture for a virtualized control plane deployment.
Control plane VM disks are backed by {lvms-first} on local NVMe drives, which provides the consistent low latency that `etcd` requires.
