= Release notes for the Red Hat build of OpenTelemetry 3.12.0

// Replace 0.16x.y with the final {OTelOperator} and upstream OpenTelemetry versions of the 3.12.0 release.

The Red Hat build of OpenTelemetry 3.12.0 is available through the link:https://catalog.redhat.com/software/containers/rhosdt/opentelemetry-operator-bundle/615618406feffc5384e84400[Red Hat build of OpenTelemetry Operator 0.16x.y] and is based on the open source link:https://opentelemetry.io/docs/collector/[OpenTelemetry] release 0.16x.y.

[WARNING]

`OpenTelemetryCollector` `v1alpha1` API version is planned for removal::
The deprecated `v1alpha1` API version of the `OpenTelemetryCollector` custom resource, which you use to configure Collector instances, will be removed in a future major release. Migrate to the `v1beta1` API version as soon as possible.

The Red Hat build of OpenTelemetry 3.12.0 release adds these Technology Preview features:

Webhook Event Receiver (Technology Preview)::
The Webhook Event Receiver turns webhook requests into log records. You can use the receiver to collect events from systems that cannot send OpenTelemetry Protocol (OTLP) data, such as source code hosting services and Software-as-a-Service (SaaS) applications. This receiver is a Technology Preview feature.
+
link:https://redhat.atlassian.net/browse/TRACING-6641[TRACING-6641]

Log Deduplication Processor (Technology Preview)::
The Log Deduplication Processor aggregates identical log records over a time interval and emits a single log record with the number of aggregated records. You can use this processor to reduce the volume of repetitive logs, such as health checks, heartbeats, or Kubernetes events, before the Collector sends them to a storage back end or to a security information and event management (SIEM) system. As a result, the Collector stores fewer log records without losing the count of the aggregated events. This processor is a Technology Preview feature.
+
link:https://redhat.atlassian.net/browse/TRACING-6697[TRACING-6697]

Syslog Exporter (Technology Preview)::
The Syslog Exporter sends logs to a syslog server in the RFC 5424 or RFC 3164 format. You can use this exporter to forward logs from the Collector to security information and event management (SIEM) systems and to compliance archives that receive syslog. As a result, you can send logs to syslog-only destinations without deploying an additional log-forwarding agent. This exporter is a Technology Preview feature.
+
link:https://redhat.atlassian.net/browse/TRACING-6788[TRACING-6788]

Remote write export of monitoring stack metrics through the Collector (Technology Preview)::
On OpenShift Container Platform 5.0 or later, you can configure the monitoring stack to send its platform metrics over the Prometheus Remote Write 2.0 protocol to a Collector that runs the Prometheus Remote Write Receiver. If user workload monitoring is enabled, you can configure the user workload monitoring stack the same way. The Collector can export the monitoring stack metrics to an external back end with an OTLP Exporter. The Prometheus Remote Write Receiver remains a Technology Preview feature.
+
[NOTE]
====
On OpenShift Container Platform versions earlier than 5.0, where remote write 2.0 is not available, the Collector can instead scrape a limited, aggregated subset of these metrics from the federation endpoint of the monitoring stack.
====
+
link:https://redhat.atlassian.net/browse/TRACING-6789[TRACING-6789]

The Red Hat build of OpenTelemetry 3.12.0 release deprecates this feature:

Implicit File Log Receiver `ordering_criteria.top_n` default is deprecated::
The implicit default of `1` for `ordering_criteria.top_n` in the File Log Receiver, which applied when `ordering_criteria.sort_by` was configured without `top_n`, is deprecated and might be removed in a future release. Set `ordering_criteria.top_n` explicitly whenever you configure `ordering_criteria.sort_by`; to keep the previous behavior, set it to `1`. To make the Collector reject a configuration that omits `top_n` when `sort_by` is configured, enable the alpha `filelog.requireExplicitTopN` feature gate.
+
[IMPORTANT]
====
With this update, `ordering_criteria.top_n: 0` matches all files that the `include` glob pattern of the File Log Receiver matches. Before this update, `0` behaved like `1` and matched only the first file. As a result, the Collector can read significantly more log data than before. This behavior of `0` is permanent and is not affected by the deprecation.
====

The Red Hat build of OpenTelemetry 3.12.0 release removes these features:

Google Cloud Exporter is removed::
The Google Cloud Exporter, which exported telemetry data to Google Cloud Operations Suite, is removed. The exporter was available as a Technology Preview feature and was deprecated in Red Hat build of OpenTelemetry 3.11.0. You can export telemetry data to Google Cloud Operations Suite by using the OTLP HTTP Exporter with the Google Client Authorization Extension instead.

Kafka Receiver and Kafka Exporter reject configurations that set both `auth.sasl` and `auth.kerberos`::
Before this update, a configuration that set both the `auth.sasl` and the `auth.kerberos` options of the Kafka client was accepted and one of the two authentication methods was used. With this update, the Collector rejects such a configuration and does not start. Set only one of the two authentication methods.

Kafka Exporter `auth.plain_text` and `auth.tls` options are removed::
The `auth.plain_text` and `auth.tls` options of the Kafka Exporter in the Red Hat build of OpenTelemetry, which configured plain text authentication and TLS authentication, are removed and are no longer supported. You can authenticate by using the `auth.sasl` option with the `mechanism`, `username`, and `password` fields, and you can configure TLS in the top-level `tls` section of the exporter instead.

The Red Hat build of OpenTelemetry 3.12.0 release has these known issues:

Prometheus Remote Write Exporter drops data during a backend outage::
By default, the Prometheus Remote Write Exporter stops retrying a failed request after 5 seconds and drops the data. As a consequence, a backend outage longer than 5 seconds causes data loss.
+
To work around this problem, set the `timeout` and `retry_on_failure.max_elapsed_time` fields to at least the duration of the longest outage that you want to tolerate.
+
link:https://redhat.atlassian.net/browse/TRACING-6723[TRACING-6723]

Syslog Exporter does not remove line breaks from log attributes::
When you use `network: tcp` without `enable_octet_counting`, or `protocol: rfc3164`, the receiving server treats a line break as the end of a message. As a consequence, an attacker who controls the content of a log attribute can inject additional syslog messages.
+
To work around this problem, use `protocol: rfc5424` with `enable_octet_counting: true`, or remove the line breaks from the attributes by using the Transform Processor.
+
link:https://redhat.atlassian.net/browse/TRACING-6834[TRACING-6834]

// The Red Hat build of OpenTelemetry 3.12.0 release resolves these Common Vulnerabilities and Exposures (CVEs):

The Red Hat build of OpenTelemetry 3.12.0 release fixes these issues:

Operator generates namespace-scoped RBAC when the Kubernetes Attributes Processor filters on a namespace::
Before this update, the Red Hat build of OpenTelemetry Operator ignored the `filter.namespace` setting of the Kubernetes Attributes Processor and generated a cluster role for it. As a consequence, the admission webhook denied Collectors created by users who hold only namespace-scoped permissions. With this update, the Operator generates a role scoped to the filtered namespace. As a result, you can create Collectors that use the Kubernetes Attributes Processor in your namespace without encountering admission webhook denial errors.
+
link:https://redhat.atlassian.net/browse/TRACING-6719[TRACING-6719]

`NetworkPolicy` automatically reconciles API server IP addresses::
Before this update, the `NetworkPolicy` object generated by the Red Hat build of OpenTelemetry Operator resolved the API server IP addresses once at startup and never updated them. As a consequence, if a control-plane node was replaced, the network policy became stale, and the Operator or target allocator could no longer reach the API server. With this update, the Operator watches the API server `EndpointSlice` objects and automatically reconciles the `NetworkPolicy` object whenever the API server addresses change. As a result, the network policy remains valid when control-plane node IP addresses change.
+
link:https://redhat.atlassian.net/browse/TRACING-6688[TRACING-6688]
