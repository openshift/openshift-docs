= Network planes and port requirements

[role="_abstract"]
A two-node {product-title} cluster with fencing uses three distinct network planes. Each plane serves a specific purpose and has its own port requirements.

.TNF network planes and traffic flows
image::images/tnf-network-planes-and-traffic-flows.png[Diagram showing three color-coded network planes: green for application and API traffic from external clients, blue for cluster communication between nodes, and red dashed lines for BMC fencing via Redfish.]

== BMC and management plane

The BMC and management plane carries fencing traffic. Each node sends Redfish power commands to the BMC of its peer node to fence it during a failure.

.BMC and management plane requirements
[cols="1,3",options="header"]
|===
|Attribute |Value

|Purpose
|Fencing — STONITH power-off of the peer node

|Protocol
|Redfish (HTTPS)

|Port
|443 (default)

|Direction
|Node -> peer node BMC

|Physical path
|Node -> TOR switch -> peer BMC (cross-cabled)
|===

[IMPORTANT]
====
The BMC and management plane must be isolated from the cluster network on a separate VLAN. Fencing devices must not rely on the same network as cluster communication. If both cluster communication and fencing share the same network, a single network failure can cause a split-brain condition that fencing cannot resolve.
====

== Cluster plane

The cluster plane carries internal cluster traffic between the two nodes. This includes Pacemaker cluster membership, HA coordination, and etcd replication.

.Cluster plane requirements
[cols="1,3",options="header"]
|===
|Attribute |Value

|Purpose
|Cluster membership, HA coordination, etcd replication

|Protocols
|Corosync (UDP), PCS (TCP), etcd (TCP)

|Ports
|5405-5407 (Corosync), 2224 (PCS), 2379 (etcd client), 2380 (etcd peer), 9978 (etcd metrics)

|Direction
|Node <-> node (bilateral)

|Physical path
|Through bonded NICs across both TOR switches

|Interface
|`br-ex` (OVN-Kubernetes bridge)
|===

== Application and Kubernetes API plane

The application and Kubernetes API plane carries external traffic into the cluster.

.Application and Kubernetes API plane requirements
[cols="1,3",options="header"]
|===
|Attribute |Value

|Purpose
|Kubernetes API access, application ingress traffic

|Protocols
|HTTPS (API server), HTTP/HTTPS (Ingress)

|Ports
|6443 (API server), 80 (HTTP ingress), 443 (HTTPS ingress)

|Direction
|External clients -> node

|Physical path
|Same bonded NIC path as the cluster plane
|===

For `baremetal` platform deployments, virtual IP addresses (`apiVIP` and `ingressVIP`) handle API and ingress traffic failover between the two nodes. For `none` platform deployments, you must configure an external load balancer.
