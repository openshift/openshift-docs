= After deploying an extension

[role="_abstract"]
After you deploy an extension, it connects and handshakes. On startup the SDK dials the endpoint, reads the current token from the projected file, and calls `Handshake` with the extension's version, the policy kind it intends to claim, and that token.

The Operator verifies the token during `TokenReview` and checks that its `ServiceAccount` is authorized to register the claimed kind during `SubjectAccessReview`. After success, the Operator returns a session token the SDK attaches to every later call automatically. The extension then watches its CRD, resolves topology, and publishes data bindings.

Identity and ownership are both decided by Kubernetes, not asserted by the extension. The token proves who the extension is by its `ServiceAccount`, and the RBAC rule decides what it can claim. So an extension can only take a policy kind that someone with an `admin` role has explicitly granted it.

If the token is missing, expired, or issued for the wrong audience, or the `ServiceAccount` lacks the `register` grant for the kind it claims, the handshake is rejected with a clear reason and the extension does not start managing policies.

Revoking an extension is an RBAC change. Delete the binding and its next handshake fails authorization. Existing sessions are unaffected until they re-handshake. There is no shared secret to rotate. The kubelet rotates the token automatically and the SDK re-reads the file.

Because the extension is now a workload you own, its `ServiceAccount` also needs ordinary controller `RBAC:` permission to watch and reconcile its resource and any other resources it might need to manage. This ships alongside the extension's own manifests.
