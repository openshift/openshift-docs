= About directing outbound workload traffic

[role="_abstract"]
You can direct outbound workload traffic through an egress `Gateway` object to external services by using one of the two primary routing methods. These routing methods apply regardless of how you deployed the egress `Gateway` object.

Before you configure DNS routing for egress traffic, ensure that you have deployed an egress gateway in your cluster. For more information, see "Deploy an egress gateway".

[id="con-rhcl-egress-internal-hostname-routing_{context}"]
== Internal hostname routing

In this approach, the application sends requests directly to the cluster-internal service name of the egress `Gateway` object. The `Gateway` object rewrites the `Host` header and routes the request to the target external service with TLS origination. This approach requires zero DNS modification and works across all {ocp} environments.
+
When a workload sends a request by using the internal service hostname, the following workflow happens:
+
. Name resolution: Cluster DNS resolves the internal service name to the egress `Gateway` virtual IP address (`ClusterIP`).
. Request reception: The egress `Gateway` receives the unencrypted HTTP request.
. Header rewrite: An `HTTPRoute` rule matches the request and applies a `URLRewrite` filter to set the `Host` header to the external domain (for example, `httpbin.org`).
. TLS origination: An egress policy or `DestinationRule` establishes an outbound TLS connection to the external target.
. Response: The external service receives the HTTPS request and returns the response back through the gateway to the pod.
+
When {prodname} provisions the egress `Gateway` object, it automatically creates a corresponding Kubernetes `Service`, such as `kuadrant-egressgateway-istio` in the gateway namespace. Any pod in the cluster can access this service without custom DNS configuration.

[id="con-rhcl-egress-pod-dns-coredns_{context}"]
== Pod DNS with CoreDNS

Use this approach for legacy applications or third-party containers that cannot be reconfigured to use an internal hostname. In this approach, the application continues to use the public external domain transparently. Workload pods are configured with a custom `dnsConfig` pointing to a CoreDNS instance. A `DNSPolicy` custom resource (CR) configures CoreDNS to resolve the external domain to the egress `Gateway` service IP address.
+
When you use custom CoreDNS routing, routing loops are prevented through split-horizon DNS resolution and use the following pattern:
+
* Workload pods query the custom CoreDNS instance, which returns the local `Gateway` service IP address.
* `Gateway` object pods query standard {ocp} cluster DNS, which resolves the external hostname to its actual public IP address on the internet.

[id="con-rhcl-egress-tls-considerations_{context}"]
== TLS and protocol considerations

Both the internal hostname and pod DNS with CoreDNS routing approaches share the following common TLS execution model:

* Pod to `Gateway` object, in-cluster: Unencrypted HTTP. Workloads send plain HTTP requests over the internal cluster network to the egress `Gateway` object service IP address.
* `Gateway` object to external service: TLS origination. The `Gateway` object terminates internal HTTP and initiates an encrypted HTTPS connection with proper Server Name Indication (SNI) to the external destination.

[IMPORTANT]
====
Workload applications must send plain HTTP to the egress `Gateway` object. If an application sends encrypted HTTPS traffic directly, the `Gateway` object cannot inspect HTTP headers. The `Gateway` object also cannot apply {prodname} policies, such as rate limiting or authorization, without possessing the private TLS keys of the external domain.
====
