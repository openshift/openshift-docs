= Upgrade a multi-node cluster

[role="_abstract"]
You can upgrade a multi-node {product-title} cluster by updating the `ProvisioningRequest` custom resource to reference a new `ClusterTemplate` CR version configured for ClusterVersion upgrade. The O-Cloud Manager patches the `ClusterVersion` CR on the spoke cluster, where the Cluster Version Operator (CVO) orchestrates the component-by-component update of the control plane and worker nodes.

.Prerequisites

* The `ManagedServiceAccount` addon is enabled on the hub cluster. To verify, check the `MultiClusterEngine` CR by running the following command:
+
[source,terminal]
----
$ oc get multiclusterengines.multicluster.openshift.io multiclusterengine \
    -o jsonpath='{.spec.overrides.components[?(@.name=="managedserviceaccount")].enabled}'
----
+
If it returns `false` or is not present, enable it by editing the `MultiClusterEngine` CR.

* Administrator pre-upgrade tasks are completed on the spoke cluster before triggering the upgrade, including:
** An etcd backup has been created.
** Deprecated APIs have been reviewed.
** Administrator acknowledgement for minor version upgrades has been configured through an {rhacm} policy.

* The spoke cluster is fully provisioned with `provisioningPhase: fulfilled` on the `ProvisioningRequest` CR.
* A new `ClusterTemplate` CR version is prepared for the target release with `upgradeDefaults.clusterVersion` configured.
* No scaling operation is in progress on the cluster.

.Procedure

. Update the `ProvisioningRequest` CR to reference the new `ClusterTemplate` version by running the following command:
+
[source,terminal]
----
$ oc patch provisioningrequests.clcm.openshift.io <uuid> --type merge \
  -p '{"spec":{"templateName":"<template_name>","templateVersion":"<new_version>"}}'
----
+
where:
+
--
`<uuid>`:: Specifies the UUID of the `ProvisioningRequest` CR for the target cluster.
`<template_name>`:: Specifies the template name, such as `std-ran-du`.
`<new_version>`:: Specifies the new `ClusterTemplate` version for the target release, such as `v4-22-0-v1`.
--
+
The O-Cloud Manager detects the version change and orchestrates the upgrade:
+
* Creates a `ManagedServiceAccount` and RBAC `ManifestWork` for scoped access to the spoke cluster.
* Runs pre-upgrade checks, including verifying the `Upgradeable` condition on the spoke `ClusterVersion`. For standard upgrades, all `MachineConfigPools` must be unpaused. For EUS upgrades, all `MachineConfigPools` must show `Updated=True`.
* Patches the spoke `ClusterVersion` with the configured channel and upstream, then waits for the CVO to retrieve the update graph.
* Verifies the target version is available in `status.availableUpdates`.
* Triggers the upgrade by patching `spec.desiredUpdate` on the spoke `ClusterVersion`.
+
[NOTE]
====
For EUS-to-EUS upgrades, the O-Cloud Manager pauses non-master worker `MachineConfigPools`, triggers the intermediate version upgrade first, then the target version upgrade, and finally unpauses the pools and waits for workers to update. If `intermediateVersion` is not specified in the `upgradeDefaults`, the controller auto-selects the highest valid intermediate version from the update graph.
====

.Verification

* Monitor the upgrade progress by checking the `UpgradeCompleted` condition by running the following command:
+
[source,terminal]
----
$ oc get provisioningrequests.clcm.openshift.io <uuid> \
  -o jsonpath='{.status.conditions[?(@.type=="UpgradeCompleted")]}'
----
+
.Example output on successful completion
[source,terminal]
----
{"lastTransitionTime":"2025-10-08T02:30:00Z","message":"Upgrade to version 4.22.0 completed","reason":"Completed","status":"True","type":"UpgradeCompleted"}
----
+
On successful completion, the `ProvisioningRequest` `provisioningPhase` returns to `fulfilled`.
