= Understanding NUMA image validation

[role="_abstract"]
The NUMA Resources Operator validates scheduler images against a trusted digest list. By default, the operator rejects a custom Resource Topology Exporter (RTE) image so that only the default RTE image runs on worker nodes.

[id="cnf-understanding-scheduler-image-validation_{context}"]
== Scheduler image validation

The NUMA Resources Operator validates scheduler images to ensure that only trusted images run with scheduler privileges.

By default, the operator enforces the following validation rules for images specified in the `NUMAResourcesScheduler` custom resource `spec.imageSpec` field:

Digest-based references required:: The image reference must use a SHA-256 digest format. For example, `registry.redhat.io/openshift4/noderesourcetopology-scheduler-rhel9@sha256:abc123...` is valid, but `registry.redhat.io/openshift4/noderesourcetopology-scheduler-rhel9:v5.0` is rejected.

Trusted digest list:: To be valid, the image digest must meet one of the following conditions:

* Included in the operator's trusted list of production scheduler images for the current release channel.

* The final digest released in the previous release channel.

* Added to the trusted list by setting the `SCHEDULER_IMAGE_DIGESTS` environment variable in the NUMA Resources Operator subscription. For more information, see "Extending the trusted scheduler image list".

If you specify an image that does not meet these requirements, the operator sets the `NUMAResourcesScheduler` resource status to `Degraded` with reason `InvalidSchedulerImage`, and the scheduler pods are not created.

[NOTE]
====
The `spec.imageSpec` field is required. You must specify a scheduler image using a digest-based reference. For standard deployments, use the production scheduler image for your {product-title} release from `registry.redhat.io`. In disconnected environments, mirror this image to your registry and reference it by digest. If the digest changes from the original production digest, add the new digest to the trusted list by setting the `SCHEDULER_IMAGE_DIGESTS` environment variable in the NUMA Resources Operator subscription.
====

* Check the scheduler validation status by running the following command:
+
[source,terminal]
----
$ oc get numaresourcesscheduler numaresourcesscheduler \
  -o jsonpath='{range .status.conditions[?(@.type=="Degraded")]}{.status}{" - "}{.reason}{": "}{.message}{"\n"}{end}'
----
+
The following example illustrates a typical validation failure output:
+
[source,terminal]
----
True - InvalidSchedulerImage: image "registry.example.com/custom-scheduler:v1.0" must be referenced by digest, not by tag
----

[id="cnf-understanding-rte-image-validation_{context}"]
== RTE image validation

By default, the NUMA Resources Operator does not allow a custom Resource Topology Exporter (RTE) image. If you set the exporter image in the `NUMAResourcesOperator` custom resource `spec.imageSpec` field, the operator sets the resource status to `Degraded` with reason `CustomUserImage` and does not reconcile the resource.

Leave `spec.imageSpec` unset so that the operator uses the default RTE image for your {product-title} release. The default RTE image is the same image as the operator container. In a disconnected environment, the image mirroring configuration for the operator container redirects that image to your internal registry.

A cluster administrator can temporarily restore the previous behavior, which allows a custom RTE image, by setting the `EXPORTER_IMAGE_RESTRICTION` environment variable to `false` in the NUMA Resources Operator subscription.

[WARNING]
====
Setting `EXPORTER_IMAGE_RESTRICTION` to `false` allows a custom RTE image to run with RTE privileges on worker nodes. Use this override only when you must run a non-default RTE image.
====

* Check the RTE status by running the following command:
+
[source,terminal]
----
$ oc get numaresourcesoperator numaresourcesoperator \
  -o jsonpath='{range .status.conditions[?(@.type=="Degraded")]}{.status}{" - "}{.reason}{": "}{.message}{"\n"}{end}'
----
+
The following example illustrates the output when a custom exporter image is set:
+
[source,terminal]
----
True - CustomUserImage: custom operand image is not supported: registry.example.com/custom-rte:v1.0
----
