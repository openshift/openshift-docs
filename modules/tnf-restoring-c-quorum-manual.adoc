= Manually restoring corosync quorum after dual node power loss

[role="_abstract"]
When both control plane nodes of a two-node {product-title} cluster with fencing (TNF) lose power and only one node can be restarted, the restartable node cannot form corosync quorum on its own, and Pacemaker keeps etcd and kubelet stopped. You can restore corosync quorum manually on the restartable node. The cluster then operates without high availability on a single node until the peer is replaced.

[IMPORTANT]
====
Perform this procedure only when both of the following conditions are met:

* Both control plane nodes lost power.
* Only one control plane node can be restarted.

This procedure is not a fallback for other failed recovery attempts. Overriding corosync quorum while the peer node is still active can cause data corruption and cluster failure.
====

.Prerequisites

* You have administrative access to the control plane nodes.
* You can connect to the nodes by using SSH.
* The failed node cannot be restarted, for example because it has failed hardware.

.Procedure

. Verify that only one node is online by running the following command on the restartable node:
+
[source,terminal]
----
$ sudo pcs status --full
----
+
The output shows `Current DC: NONE` and both nodes as `UNCLEAN (offline)`, while the PCSD status shows the local node as online. Both nodes appear offline in the node list because neither holds quorum.

. Confirm the loss of quorum by running the following command:
+
[source,terminal]
----
$ sudo pcs quorum status
----
+
When the cluster is not quorate, this command also reports an error and exits with a nonzero status, for example `Error: Unable to get quorum status`. The quorum information printed above the error is the relevant output.
+
The output reports `Quorate: No`, `Expected votes: 2`, `Total votes: 1`, and `Flags: 2Node WaitForAll`. For more information about this state, see xref:../installing_tnf/install-post-tnf.adoc#tnf-understanding-c-quorum_install-post-tnf[Understanding corosync quorum in a two-node cluster with fencing].

. Verify that the failed node is permanently inaccessible before proceeding.
+
[IMPORTANT]
====
Before you restore quorum, the failed node must meet all of the following conditions:

* The node is powered off and cannot be restarted. Verify this at the BMC, not by attempting to reach the node over the network.
* The node cannot access any shared storage or cluster resources.
* The node is completely isolated from the cluster network.

If the failed node is accessible or can access shared resources, do not proceed. Overriding quorum for a cluster whose peer is still active can cause data corruption and cluster failure.
====

. Restore quorum by running the following command:
+
[source,terminal]
----
$ sudo pcs quorum unblock
----

. Verify that quorum is restored by running the following command:
+
[source,terminal]
----
$ sudo pcs quorum status
----
+
The output reports `Quorate: Yes`, for example:
+
[source,terminal]
----
Quorum information
------------------
Date:             Fri Oct  3 14:15:31 2025
Quorum provider:  corosync_votequorum
Nodes:            1
Node ID:          1
Ring ID:          1.16
Quorate:          Yes

Votequorum information
----------------------
Expected votes:   2
Highest expected: 2
Total votes:      1
Quorum:           1
Flags:            2Node Quorate
----

. Wait for Pacemaker to process the quorum change and begin recovery, then verify that etcd is running by running the following command:
+
[source,terminal]
----
$ sudo pcs resource status etcd
----

. If etcd is not running, reset its failure state and instruct Pacemaker to attempt to start it again by running the following command:
+
[source,terminal]
----
$ sudo pcs resource cleanup etcd
----
+
Wait up to 5 minutes for etcd to start, checking the status periodically with `sudo pcs resource status etcd`.
+
If etcd still does not start, inspect the logs by running the following commands:
+
[source,terminal]
----
$ sudo podman logs etcd
----
+
[source,terminal]
----
$ sudo journalctl -u pacemaker | grep podman-etcd
----
+
In the `podman logs etcd` output, look for the following:

* A successful start of etcd as a single-node cluster, for example messages reporting that etcd is serving client traffic.
* Fatal errors that prevent startup, such as a failure to load TLS certificates or a corrupted data directory, for example a WAL metadata mismatch.

In the `journalctl -u pacemaker` output, look for decisions made by the `podman-etcd` resource agent:

* `is set as standalone` indicates that the agent is starting etcd as a cluster-of-one, which is the expected behavior after quorum is restored on a single node.
* `holds force_new_cluster` and `marked to force-new-cluster` indicate that the agent is restarting etcd with the existing state to recover from the loss of its peer.
* `is not in the member list yet` messages that repeat without progress, or an `ADMIN` verdict, mean that the agent cannot determine how to proceed and the start is stalled.

.Verification

* The `pcs quorum status` output reports `Quorate: Yes`.
* The `pcs resource status etcd` output shows the `podman-etcd` resource as started on the surviving node.
* For information about verifying etcd health, see "Verifying etcd health in a two-node {product-title} cluster with fencing".

.Next steps

* The cluster now operates on a single control plane node without high availability. Replace the failed node as soon as its prerequisites are satisfied, as described in xref:../installing_tnf/install-post-tnf.adoc#installation-replacing-control-plane-nodes_install-post-tnf[Replacing control plane nodes in a two-node {product-title} cluster with fencing].
