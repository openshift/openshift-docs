= Multi-cluster meshes

[role="_abstract"]

One Kiali console can show a mesh that spans several {ocp-product-title} clusters. Metrics and traces must already be aggregated to one Prometheus endpoint and one tracing endpoint. How you federate those stores is outside the console configuration.

.Several clusters in one Kiali console
image::ossm-kiali-multi-cluster.png[Kiali console showing more than one cluster]

The Kiali service account needs read access to every remote cluster. That access is separate from the user who signs in. User login for each cluster is described in "Authentication on {ocp-product-title}". On {ocp-product-title}, use the `openshift` authentication strategy for a unified multi-cluster view. Token authentication is not supported for that view.

Use the same `spec.deployment.namespace` and `spec.deployment.instance_name` on every cluster. On a remote cluster that does not run {KialiServer}, install {KialiProduct} and set `spec.deployment.remote_cluster_resources_only` to `true`. The operator creates the service account, role, and binding, and removes them when you delete that custom resource.

Store a client configuration for each remote cluster in a secret in the namespace where {KialiServer} runs. Label the secret so the operator mounts it:

[source,yaml]
----
apiVersion: v1
kind: Secret
metadata:
  name: west
  namespace: istio-system
  labels:
    kiali.io/multiCluster: "true"
stringData:
  west: |
    apiVersion: v1
    kind: Config
    current-context: west
    contexts:
    - name: west
      context:
        cluster: west
        user: west
    users:
    - name: west
      user:
        token: <remote service account token>
    clusters:
    - name: west
      cluster:
        server: <remote cluster API URL>
        certificate-authority-data: <remote cluster CA>
----

The key under `stringData` must be the {istio} cluster name. You can put every cluster in one secret named `kiali-multi-cluster-secret`. Add the label `kiali.io/kiali-multi-cluster-secret: "true"` only on that secret. The operator then restarts {KialiServer} when the secret changes. Do not put that label on any other secret. If several Kiali servers share the namespace, they all use `kiali-multi-cluster-secret` or none of them do.

A secret labeled `kiali.io/multiCluster: "true"` is mounted without further custom resource fields. After the pod restarts, the console is in multi-cluster mode.

To drop a cluster, delete its secret and change an annotation on the `Kiali` custom resource so the operator reconciles. The annotation `kiali.io/reconcile` is the usual choice. If the secret is `kiali-multi-cluster-secret` and it has the matching label, deleting it is enough. The operator redeploys the server.

If each cluster has its own Kiali console and you only want links between them, set `spec.clustering.kiali_urls` with the other console's URL. That does not grant the service account access to the remote cluster.
