= RHSA-2026:83541 - {product-title} {product-version}.19 bug fix and security update

Issued: 20 October 2026

[role="_abstract"]
{product-title} release {product-version}.19 is now available. The list of fixed issues that are included in the update is documented in the link:https://access.redhat.com/errata/RHSA-2026:83541[RHSA-2026:83541] advisory. The RPM packages that are included in the update are provided by the link:https://access.redhat.com/errata/RHBA-2026:83539[RHBA-2026:83539] advisory.

== Fixed issues

* Before this update, when the ingress capability was disabled on a hosted cluster, the console Operator still attempted to reconcile unavailable ingress resources and run route health checks. As a consequence, the console Operator reported degraded or progressing conditions. With this release, the Operator skips route and health check controllers and ingress-dependent reconciliation when ingress is disabled, and resumes normal operation if ingress is later enabled. As a result, the console Operator no longer reports those conditions when ingress is disabled. (link:https://issues.redhat.com/browse/OCPBUGS-113612[OCPBUGS-113612])

* Before this update, the Namespace column was hidden on the *Node Pods* tab when a specific namespace was selected. As a consequence, you could not identify which namespace pods belonged to on the *Node Details* page, even though nodes are cluster-scoped and can display pods from multiple namespaces. With this release, the Namespace column displays on the *Node Pods* tab regardless of project selector state. As a result, you can identify the namespace for each pod on the *Node Details* page. (link:https://issues.redhat.com/browse/OCPBUGS-123201[OCPBUGS-123201])

* Before this update, the `nmstate-metrics` deployment retained an obsolete `kube-rbac-proxy` sidecar with an empty image, causing API validation errors, Operator degradation, and `CrashLoopBackOff` due to port 8443 conflicts during 4.22 upgrades. With this release, the unused sidecar plumbing is removed. As a result, successful Operator reconciliation and normal pod execution is enabled after upgrading to 4.22. (link:https://issues.redhat.com/browse/OCPBUGS-127277[OCPBUGS-127277])

* Before this update, the boot image controller required an exact match between a `MachineSet` `providerSpec` workspace and an `Infrastructure` failure domain on all five fields. As a consequence, `MachineSet` resources on clusters without failure domains or with a datastore not listed in any failure domain were silently skipped for boot image management, and boot image skew could grow over time. With this release, matching logic is improved so that eligible `MachineSet` resources are not skipped in those cases. As a result, boot images stay managed for `MachineSet` resources that had no matching failure domain. (link:https://issues.redhat.com/browse/OCPBUGS-129268[OCPBUGS-129268])

* Before this update, when 4.21 clusters that used the multi-arch payload upgraded to 4.22.15 or later, nodes could fail to update in place because of an `rpm-ostree` defect that omitted Open vSwitch (OVS) binaries from the {op-system-first} image. As a consequence, affected nodes could become unrecoverable during the update. With this release, the Machine Config Daemon works around that `rpm-ostree` defect so that nodes update properly across this transition. As a result, multi-arch payload clusters can complete the update and clusters that use a single-arch payload are not affected. (link:https://issues.redhat.com/browse/OCPBUGS-129375[OCPBUGS-129375])

* Before this update, {vmw-first} machine reconciliation made redundant vCenter API calls and repeated operations. As a consequence, heavy API load, duplicate tasks, and slower provisioning in large clusters occurred. With this release, VM state and tag lookups are cached, queries are batched, and task references are retained. As a result, provisioning is more reliable and vCenter load is reduced. (link:https://issues.redhat.com/browse/OCPBUGS-129423[OCPBUGS-129423])
