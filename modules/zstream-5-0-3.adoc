= RHSA-2026:102899 - {product-title} {product-version}.3 bug fix and security update

Issued: 01 December 2026

[role="_abstract"]
{product-title} release {product-version}.3 is now available. The list of fixed bugs that are included in the update is documented in the link:https://access.redhat.com/errata/RHSA-2026:102899[RHSA-2026:102899] advisory. The RPM packages that are included in the update are provided by the link:https://access.redhat.com/errata/RHSA-2026:102894[RHSA-2026:102894] advisory.

Space precluded documenting all of the container images for this release in the advisory.

You can view the container images in this release by running the following command:

[source,terminal]
----
$ oc adm release info 5.0.3 --pullspecs
----

== Fixed issues

* Before this update, node-ca updated registry CA certificate files in place, so processes reading a certificate during an update could encounter an empty or partially written file. With this update, node-ca writes certificates to a temporary file and atomically replaces the destination. As a result, readers no longer observe incomplete certificate updates. (link:https://redhat.atlassian.net/browse/OCPBUGS-63691[OCPBUGS-63691])

* Before this update, when the cloud-event-proxy emitted logs, reading of process logs was blocked, and if phc2sys selected the clock instance it synchronizes to during that time, the selection was not logged. As a consequence, the HA profile status metrics were not updated. With this release, log output is monitored during the cloud-event-proxy emit-logs operation. As a result, the HA profile status metrics are now updated even if clock selection occurs while the emit-logs operation is underway. (link:https://redhat.atlassian.net/browse/OCPBUGS-104531[OCPBUGS-104531])

* Before this update, a security fix for a server-side request forgery (SSRF) vulnerability blocked access to Helm chart repositories, chart archives, and Open Container Initiative (OCI) registries on private networks. As a consequence, ProjectHelmChartRepository resources that pointed to internal Helm registries, such as registries on private IPv4 networks (RFC 1918), failed validation in the web console. With this release, the SSRF protection permits requests to private network addresses and in-cluster service names, but still blocks requests to localhost, loopback addresses, unspecified addresses, cloud metadata addresses, and Kubernetes API service names. As a result, you can use Helm chart repositories and registries on private networks. A chart URL must use an OCI scheme, or an HTTP or HTTPS scheme with a path that ends in .tgz or .tar.gz. A repository index URL must have a path that ends in /index.yaml. (link:https://redhat.atlassian.net/browse/OCPBUGS-128587[OCPBUGS-128587])

* Before this update, disconnected bare-metal cluster deployments using `ImageDigestMirrorSet` (IDMS) could fail due to malformed multi-document YAML manifests (`Kind is missing` error). With this release, image mirroring for machine-os-images and CoreOS boot artifacts is extracted correctly. As a result, deployments no longer require mirror-rewrite workarounds or encounter registry timeout errors. (link:https://redhat.atlassian.net/browse/OCPBUGS-128901[OCPBUGS-128901])

* Before this update, Hosted Control Plane (HCP) KubeVirt virtual machines that used the bridged pod network could cache a stale gateway MAC address after a live migration, because the virtual machine resolved the default gateway to the migration source node's local router MAC. As a consequence, outbound traffic from the virtual machine could be dropped for up to 60 seconds after the migration completed, and the affected node could briefly report a `NotReady` status. With this release, ovn-kubernetes refreshes the IPv4 gateway neighbor entry on the cluster default network after a live migration by sending gratuitous ARP (GARP) from the target node, advertising the stable proxy-ARP gateway MAC that is consistent across nodes. As a result, virtual machines retain connectivity immediately after a live migration. (link:https://redhat.atlassian.net/browse/OCPBUGS-132210[OCPBUGS-132210])

* Before this release, the Multus admission controller `ignore-namespaces` list was never recomputed for namespaces that began qualifying (label `openshift.io/cluster-monitoring=true` and annotation `workload.openshift.io/allowed=management`) after the network Operator's first reconcile pass, and refreshing the list required a restart of the Cluster Network Operator pod. With this release, the list is refreshed without requiring a restart of the pod. (link:https://redhat.atlassian.net/browse/OCPBUGS-132722[OCPBUGS-132722])

* Before this update, the Control Plane Operator could include AWS Local Zone subnets when creating or modifying VPC endpoints for hosted control planes, causing AWS to reject the request and endpoint reconciliation to fail. With this update, when multiple candidate subnets are configured, subnets known to be outside the configured region's standard availability zones are excluded before endpoint subnet selection. As a result, endpoint reconciliation can proceed using eligible standard availability zone subnets. (link:https://redhat.atlassian.net/browse/OCPBUGS-132917[OCPBUGS-132917])

* Before this update, the *Impersonate* action was missing from `RoleBinding` and `ClusterRoleBinding` details pages when the binding referenced a user or group, even when the action was available in the list view. With this release, the details page uses the first binding subject when no subject index is provided. As a result, authorized users can now access the *Impersonate* action from the details page. (link:https://redhat.atlassian.net/browse/OCPBUGS-135131[OCPBUGS-135131])

* Before this update, on a cluster already running version 5.0 with OLMv0 Operators installed that set `olm.maxOpenShiftVersion="5.0"`, the `Upgradeable=False` message incorrectly claimed that minor version upgrades to 4.23 or major version upgrades to 5.0 were blocked. With this release, the dynamic calculation of the blocked version is restored. As a result, the `Upgradeable=False` message on a 5.0 cluster correctly states that updates from 5.0 to 5.1 are blocked by an Operator that is only compatible through 5.0. (link:https://redhat.atlassian.net/browse/OCPBUGS-135357[OCPBUGS-135357])

* Before this update, after migration to AWS SDK v2, the AWS identity-provider health check used an error-code check that no longer matched credential errors. As a consequence, genuine STS authentication failures were reported as `Unknown`, preventing detection of invalid identity providers. With this release, errors are classified by their underlying AWS error code, distinguishing authentication failures from infrastructure errors, and condition messages are stabilized. As a result, genuine authentication failures report `ValidAWSIdentityProvider=False`, while errors that prevent validation remain `Unknown`. (link:https://redhat.atlassian.net/browse/OCPBUGS-135943[OCPBUGS-135943])

* Before this update, on {hcp} clusters that had no worker nodes, the ingress cluster Operator reported `Available=False` during startup because the router deployment could not schedule any pods. As a consequence, `ClusterVersion` never reached `CompletedUpdate` and minor upgrades were blocked. With this release, the default ingress controller contribution to cluster Operator availability includes a startup exception for zero-worker clusters with external control-plane topology. As a result, installs and upgrades on these clusters now complete as expected. (link:https://redhat.atlassian.net/browse/OCPBUGS-137400[OCPBUGS-137400])

* Before this update, the installation program created an Azure storage account and immediately uploaded a file to it, so when the permission policy was not updated by the time the file was pushed, the upload failed with a `Permission mismatch` error, and by default the Azure SDK did not retry failures of this kind. As a consequence, installation failed while provisioning infrastructure. With this release, the file push operation is retried when a permission mismatch error occurs. As a result, the operation is retried until it succeeds and installations can proceed. (link:https://redhat.atlassian.net/browse/OCPBUGS-137424[OCPBUGS-137424])

* Before this update, mirror replacements from overlapping ICSP/IDMS definitions could be emitted in different orders. As a consequence, the generated `OPENSHIFT_IMG_OVERRIDES` value could change between reconciliations despite equivalent mirror mappings, causing repeated Control Plane Operator rollouts. With this release, mirror replacement entries are sorted deterministically when generating `OPENSHIFT_IMG_OVERRIDES`. As a result, equivalent mirror configurations produce a stable value, avoiding unnecessary Control Plane Operator rollouts. (link:https://redhat.atlassian.net/browse/OCPBUGS-138211[OCPBUGS-138211])

* Before this update, when the hardware configuration restarted a process, `linuxptp-daemon` could attempt to stop the process before the process structure was fully populated. As a consequence, `linuxptp-daemon` could deadlock. With this release, locks were added so that a process cannot be stopped before it has fully started. As a result, processes are closed properly and no longer deadlock `linuxptp-daemon`. (link:https://redhat.atlassian.net/browse/OCPBUGS-138355[OCPBUGS-138355])

* Before this update, switching projects while creating a resource in the web console could redirect you to the resource list or display a 404 error when creating a `VolumeSnapshot`. With this release, switching between projects keeps the resource creation page open and updates the namespace in the YAML editor to match the selected project. (link:https://redhat.atlassian.net/browse/OCPBUGS-138567[OCPBUGS-138567])

* Before this update, Azure VIP route reconciliation could miss a trigger during a systemd reload. As a consequence, the VIP routing rules could remain empty after service recovery. With this release, periodic reconciliation during the boot window and locking to prevent overlapping executions were added. As a result, routing rules are periodically reconciled during that window rather than relying only on file-change triggers. (link:https://redhat.atlassian.net/browse/OCPBUGS-139930[OCPBUGS-139930])

* Before this update, the `kubevirt-csi-driver` reported `CreateVolume` success before the infrastructure PVC was bound, so infrastructure provisioning errors such as quota failures never reached the guest cluster. As a consequence, tenant clusters could receive volumes that were not actually provisioned, and failures went undetected. With this release, the driver detects failures in infrastructure provisioning and propagates them to tenant cluster provisioning. As a result, errors such as quota failures are reported to the guest cluster instead of being silently lost. (link:https://redhat.atlassian.net/browse/OCPBUGS-140045[OCPBUGS-140045])

* Before this update, in a hosted control plane, the Control Plane Operator added the internal OAuth service DNS name to the subject alternative names (SANs) of the OAuth server certificate only when the OAuth server was published with a hostname. When the OAuth server was published with an IP address, the certificate contained only that IP address. As a consequence, requests to the internal OAuth service URL failed TLS verification, so logging in to the web console, logging in with `oc login`, and using the *Copy login command* option failed on hosted clusters whose OAuth server was published with an IP address. With this release, the Control Plane Operator always adds the internal OAuth service DNS name to the SANs of the OAuth server certificate, in addition to the external IP address or hostname. As a result, web console logins, `oc login`, and the *Copy login command* option work on hosted clusters whose OAuth server is published with an IP address. (link:https://redhat.atlassian.net/browse/OCPBUGS-140208[OCPBUGS-140208])

* Before this update, the `ovnkube-control-plane` deployment required replicas to be spread across different availability zones. As a consequence, on a single-zone management cluster, this could prevent replicas from being scheduled. With this release, replicas are required to run on different nodes, while preferring rather than requiring different zones. As a result, replicas can be scheduled on distinct nodes within the same zone, retaining a preference for zone separation when available. (link:https://redhat.atlassian.net/browse/OCPBUGS-140482[OCPBUGS-140482])

* Before this update, the Cluster Autoscaler's Cluster API provider could repeatedly reduce a node group's target size for the same pending machine, potentially reducing the group to its minimum size. With this update, the provider skips pending machines that are already marked for deletion. It also skips stale pending-machine deletion requests for machines that have since registered as nodes, so that those nodes go through the normal scale-down checks. (link:https://redhat.atlassian.net/browse/OCPBUGS-140545[OCPBUGS-140545])

* Before this update, when a T-BC DPLL exited holdover, the offset qualification was evaluated against the legacy `maxOffsetThreshold` in addition to the holdover free-run bound, so with certain threshold combinations the two checks disagreed. As a consequence, upon holdover exit, a leading T-BC clock that had relocked in-spec reported a spurious FREERUN instead of transitioning directly from HOLDOVER to LOCKED. With this release, the `maxOffsetThreshold` window was removed from the DPLL decision path, and phase offset qualification is now based solely on the holdover free-run bound (`LocalMaxHoldoverOffSet`), consistent with the other holdover qualification checks. As a result, a T-BC clock that relocks within its holdover bound transitions directly from HOLDOVER to LOCKED without reporting a spurious FREERUN. (link:https://redhat.atlassian.net/browse/OCPBUGS-140640[OCPBUGS-140640])

* Before this update, the Vertical Pod Autoscaler Operator could fail to start and enter a CrashLoopBackOff state when its embedded version contained an all-numeric Git commit hash beginning with zero. The version parser rejected the hash as an invalid prerelease identifier. With this update, the hash is recorded as build metadata, which permits leading zeroes, preventing this startup failure. (link:https://redhat.atlassian.net/browse/OCPBUGS-141617[OCPBUGS-141617])

* Before this update, selecting the *All* options from a dashboard namespace variable led to no results due to an invalid query. With this release, the *All* option is processed correctly to query all namespaces data. (link:https://redhat.atlassian.net/browse/OCPBUGS-142207[OCPBUGS-142207(link:https://redhat.atlassian.net/browse/OCPBUGS-141617[OCPBUGS-141617])
])

* Before this update, on OKD (SCOS), the installation program generated `Machine` and `MachineSet` host selectors with a `notin` requirement that had an empty list of values for bare metal platforms, because OKD provides only one operating system image stream (`centos-10`). As a consequence, the machine controller rejected the invalid host selector, machines stayed in the `Provisioning` phase, nodes did not receive a provider ID, and the `machine-api` cluster Operator stayed `Degraded` on every OKD bare-metal installation. With this release, when there are no other operating system image streams to exclude, the installation program generates an empty host selector instead of an invalid `notin` requirement. As a result, OKD bare-metal installations complete, and machines are linked to `BareMetalHosts`. This issue affects OKD (SCOS) only; {product-title} is not affected. (link:https://redhat.atlassian.net/browse/OCPBUGS-143034[OCPBUGS-143034])
