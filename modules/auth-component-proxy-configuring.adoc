= Configuring a component-scoped proxy for authentication

[role="_abstract"]
Configure a component-scoped proxy for the authentication stack by setting the `spec.proxy` field on the `Authentication` operator resource. When set, this configuration replaces the cluster-wide proxy for authentication components.

.Prerequisites

* You have cluster administrator privileges.
* You installed the OpenShift CLI (`oc`).
* The `AuthenticationComponentProxy` feature gate is enabled by applying the `TechPreviewNoUpgrade` or `DevPreviewNoUpgrade` feature set.
* You have a working HTTP or HTTPS proxy server accessible from the cluster nodes.

.Procedure

. Optional: If the proxy requires a custom CA certificate, create a config map in the `openshift-config` namespace containing the CA bundle:
.. Create a file called `auth-proxy-ca-bundle.yaml` with the following content:
+
[source,yaml]
----
apiVersion: v1
kind: ConfigMap
metadata:
  name: auth-proxy-ca-bundle
  namespace: openshift-config
data:
  ca-bundle.crt: |
    -----BEGIN CERTIFICATE-----
    <PEM_encoded_CA_certificate>
    -----END CERTIFICATE-----
----
+
`name`:: Specifies the config map name. Reference this name in the `spec.proxy.trustedCA.name` field.
`namespace`:: Specifies the namespace. Must be `openshift-config`.
`ca-bundle.crt`:: Specifies the Privacy-Enhanced Mail (PEM)-encoded CA certificate bundle. The key must be `ca-bundle.crt`.
+
.. Create the config map by running the following command:
+
[source,terminal]
----
$ oc create -f auth-proxy-ca-bundle.yaml
----

. Edit the `Authentication` operator resource to add the proxy configuration:
+
[source,terminal]
----
$ oc edit authentication.operator.openshift.io cluster
----

. Add the `spec.proxy` field with your proxy settings:
+
[source,yaml]
----
apiVersion: operator.openshift.io/v1
kind: Authentication
metadata:
  name: cluster
spec:
  managementState: Managed
  proxy:
    httpProxy: "http://proxy.example.com:3128"
    httpsProxy: "http://proxy.example.com:3128"
    noProxy:
      - ".example.com"
      - "idp.internal.example.com"
    trustedCA:
      name: "auth-proxy-ca-bundle"
----
+
`httpProxy`:: Specifies the proxy URL for HTTP requests. At least one of `httpProxy` or `httpsProxy` is required.
`httpsProxy`:: Specifies the proxy URL for HTTPS requests. At least one of `httpProxy` or `httpsProxy` is required.
`noProxy`:: Specifies hostnames, domains, classless inter-domain routing (CIDR) ranges, or IP addresses that bypass the proxy. Cluster-internal defaults (`.cluster.local`, `.svc`, `127.0.0.1`, the Kubernetes API service IP, and `localhost`) are appended automatically. Maximum 64 entries.
`trustedCA`:: Specifies the config map name in `openshift-config` containing the proxy CA bundle under the key `ca-bundle.crt`. Required only if the proxy uses Transport Layer Security (TLS) interception or a private CA. Omit the `trustedCA` block if you did not create a CA config map in step 1.

. Save the file to apply the changes.

.Verification

* Verify that the configuration was accepted by running the following command:
+
[source,terminal]
----
$ oc get authentication.operator.openshift.io cluster -o jsonpath='{.spec.proxy}' | jq .
----
+
.Example output
[source,json]
----
{
  "httpProxy": "http://proxy.example.com:3128",
  "httpsProxy": "http://proxy.example.com:3128",
  "noProxy": [
    ".example.com",
    "idp.internal.example.com"
  ],
  "trustedCA": {
    "name": "auth-proxy-ca-bundle"
  }
}
----

* Verify that the authentication operator is not reporting errors by running the following command:
+
[source,terminal]
----
$ oc get clusteroperator authentication
----
+
.Example output
[source,terminal]
----
NAME             VERSION   AVAILABLE   PROGRESSING   DEGRADED   SINCE   MESSAGE
authentication   5.0.0     True        False         False      10m
----
+
The `AVAILABLE` column shows `True` and the `DEGRADED` column shows `False`.

* Optional: Test authentication through the proxy by logging in through your configured identity provider:
+
[source,terminal]
----
$ oc login
----

[WARNING]
====
A misconfigured proxy can prevent the OAuth server from reaching the identity provider, locking all users out of the cluster. To recover, use `kubeadmin` credentials or client certificate authentication, both of which bypass OAuth. Correct the proxy configuration after recovering access.
====

[NOTE]
====
Changing the proxy URL triggers an OAuth server redeployment. On single-node {product-title} deployments, this causes a brief authentication outage. Updates to `trustedCA` config map content are hot-reloaded without redeployment.
====
