= Localnet network configuration considerations

[role="_abstract"]
After you configure the cluster node network, you can use the `ClusterUserDefinedNetwork` CR to create a localnet network that defines how VMs attach to the host-level bridge and any VLANs it provides.

By configuring the `ClusterUserDefinedNetwork` CR, you can select the projects that have access to the physical network and assign VLANs to projects.

The following are key attributes to specify when configuring the `ClusterUserDefinedNetwork` CR.

Referencing the physical network::
The `ClusterUserDefinedNetwork` CR must reference the name of the localnet identifier that is configured on the node. This value must match the `spec.desiredState.ovn.bridge-mappings.localnet` field in the `NodeNetworkConfigurationPolicy` manifest that you previously created. This ensures that you are bridging to the intended physical network.
+
[source,yaml]
----
apiVersion: k8s.ovn.org/v1
kind: ClusterUserDefinedNetwork
metadata:
  name: provider-network
spec:
  ...
  network:
    topology: Localnet
    localnet:
      physicalNetworkName: provider-network # <1>
      ...
----
<1> Must match the `spec.desiredState.ovn.bridge-mappings.localnet` field in the `NodeNetworkConfigurationPolicy` manifest.
+
[NOTE]
====
If the physical network is configured only on a subset of the nodes, you must ensure that the VM is scheduled on the correct node. Otherwise, the VM will fail to start.
====

Assigning a VLAN::
To isolate different tenants from each other, you can use unique VLANs for VMs instead of using the native network.
+
[source,yaml]
----
apiVersion: k8s.ovn.org/v1
kind: ClusterUserDefinedNetwork
metadata:
  name: provider-network-100
spec:
  ...
  network:
    ...
    localnet:
      ...
      vlan:
        mode: Access
        access:
          id: 100
----
+
[NOTE]
====
If you have configured a VLAN sub-interface on the host, OVN-Kubernetes automatically handles VLAN tagging.
====
+
[NOTE]
====
OVN-Kubernetes currently does not support VLAN trunking.
====

Selecting namespaces::
You can use one of the following three approaches to select which users or projects have access to the network:
+
--
* All namespaces: To make the network available to all users in the cluster, create a `ClusterUserDefinedNetwork` CR that selects the `default` namespace.
+
[source,yaml]
----
apiVersion: k8s.ovn.org/v1
kind: ClusterUserDefinedNetwork
metadata:
  name: provider-network
spec:
  namespaceSelector:
    matchExpressions:
    - key: kubernetes.io/metadata.name
      operator: In
      values: ["default"]
  network:
    ...
----

* Namespaces by name: You can specify the namespaces that have access to the network directly in the `ClusterUserDefinedNetwork` CR.
+
[source,yaml]
----
apiVersion: k8s.ovn.org/v1
kind: ClusterUserDefinedNetwork
metadata:
  name: provider-network
spec:
  namespaceSelector:
    matchExpressions:
    - key: kubernetes.io/metadata.name
      operator: In
      values: ["tenant-red", "tenant-blue"]
  network:
    ...
----
+
[IMPORTANT]
====
If you select namespaces by name and later need to delete one of those namespaces, it can get stuck in `Terminating` state. The `ClusterUserDefinedNetwork` controller cannot remove the network attachment from a namespace that is still explicitly listed in the selector. To unblock deletion, a cluster administrator must first update the `ClusterUserDefinedNetwork` CR to remove the namespace from the list. To avoid this issue, consider selecting namespaces by label instead.
====

* Namespaces by label (recommended): You can use label selectors to select namespaces that the `ClusterUserDefinedNetwork` CR applies to. This is the recommended approach because namespaces can be granted or revoked access by adding or removing a label, without modifying the `ClusterUserDefinedNetwork` CR.
+
[source,yaml]
----
apiVersion: k8s.ovn.org/v1
kind: ClusterUserDefinedNetwork
metadata:
  name: provider-network
spec:
  namespaceSelector:
    matchLabels:
      provider-network-vlan: "100"
  network:
    ...
----
+
[source,yaml]
----
apiVersion: v1
kind: Namespace
metadata:
  name: red
  labels:
    provider-network-vlan: "100"
----
--

Configuring MTU::
The default MTU for a localnet network is 1500. To change it, set the `spec.network.localnet.mtu` attribute in the `ClusterUserDefinedNetwork` CR.
+
[source,yaml]
----
apiVersion: k8s.ovn.org/v1
kind: ClusterUserDefinedNetwork
metadata:
  name: provider-network-100
spec:
  ...
  network:
    ...
    localnet:
      mtu: 9000
      ...
----
+
[NOTE]
====
The MTU value for the localnet network must match the MTU of the node network and the physical network.
====

VM network requirements::
{VirtProductName} does not support IP address management (IPAM) for VMs that use localnet networks. To make the localnet network work correctly as a VM network, set the `localnet.ipam.mode` attribute to `Disabled` in the `ClusterUserDefinedNetwork` CR.
+
[source,yaml]
----
apiVersion: k8s.ovn.org/v1
kind: ClusterUserDefinedNetwork
metadata:
  name: provider-network-100
spec:
  ...
  network:
    ...
    localnet:
      ...
      ipam:
        mode: Disabled
----
