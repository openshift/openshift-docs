= {SMProductName} version 3.5 fixed issues

[role="_abstract"]

As a distribution based on upstream Istio and the Sail Operator, {SMProduct} inherits bug fixes from these projects.

Upstream fixed issues in {SMProduct} 3.5::
** DestinationRule and backend policy precedence: When both a `DestinationRule` and a Gateway API backend policy (`BackendTLSPolicy` or `XBackendTrafficPolicy`) target the same host, `DestinationRule` fields take precedence. This fix ensures the backend policy only fills in fields that the `DestinationRule` leaves unset, regardless of which resource was created first.
+
** Fixed an issue where `consistentHash` load balancing in `DestinationRule` would not send traffic to new endpoints after scaling, due to an Envoy regression (envoyproxy/envoy#45212) where the RING_HASH ring was not rebuilt on endpoint changes during batched updates.
+
** Fixed an issue where endpoint mTLS mode was not derived from the DestinationRule top-level traffic policy when a targeted subset did not specify a TLS mode for the port. The subset traffic policy now correctly falls back to the DestinationRule-level TLS setting.
+
** Fixed `zoneAwareLbSetting.enabled: false` to explicitly disable Envoy zone-aware routing by emitting `routing_enabled: 0%`. Previously, `enabled: false` was a no-op: Istio emitted no `ZoneAwareLbConfig`, causing Envoy to fall back to its default `routing_enabled: 100%`, which engaged zone-aware routing automatically whenever a self-discovery local cluster was present. This made gradual rollout unsafe, as pods in a mixed state (some with self-discovery, some without) would distribute traffic unevenly.

For complete details, see the upstream Istio release documentation: link:https://istio.io/latest/news/releases/1.31.x/announcing-1.31/change-notes[Istio 1.31 change notes]
