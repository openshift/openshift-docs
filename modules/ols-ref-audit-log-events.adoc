= Audit log event types

[role="_abstract"]
Reference information for the audit events emitted by {ols-long} and agentic {ols-long} when audit logging is enabled.

== Common fields

Every audit log entry contains the following fields, regardless of the event type or component that emits it:

[cols="2,1,4",options="header"]
|===
| Field | Type | Description

| `event`
| string
| Event type identifier. See the event tables in this topic for valid values.

| `trace_id`
| string
| Correlation identifier for the interaction. For {ols-long}: derived from the `conversation_id` with hyphens removed. For agentic {ols-long}: derived from the `AgenticRun` `metadata.uid` with hyphens removed. Doubles as the OTEL trace ID.

| `timestamp`
| string (ISO 8601)
| Time at which the event occurred, in UTC.

| `user_id`
| string
| Identifier of the user who initiated the interaction.

| `component`
| string
| Name of the component that emitted the event, for example `lightspeed-service` or `lightspeed-agentic-operator`.

|===

== {ols-long} events

The `lightspeed-service` component emits a separate trace for each Q&A and troubleshooting request. Each trace contains the following spans:

[cols="2,4",options="header"]
|===
| Span | Description

| `request.lifecycle`
| The overall request lifecycle. This is the root span for the request.

| `request.auth`
| Authentication and authorization of the request.

| `request.rag`
| Retrieval-augmented generation (RAG) context retrieval.

| `request.history`
| Conversation history retrieval.

| `chat <model>`
| Interaction with the large language model (LLM). The span name uses the requested model from the `gen_ai.request.model` attribute. The responding model is recorded separately in the `gen_ai.response.model` attribute.

| `execute_tool <tool-name>`
| A tool call. The tool is named in the span. Model Context Protocol (MCP) semantic convention attributes are added only when the tool is MCP-sourced.

| `request.store`
| Persistence of the request and response.

|===

The following span events are emitted within these spans:

[cols="2,4",options="header"]
|===
| Span event | Description

| `request.started`
| The request was received. Marks the start of an auditable interaction.

| `request.completed`
| The request completed. Marks the end of the interaction.

| `request.failed`
| The request failed.

| `rag.retrieved`
| RAG context was retrieved.

| `history.retrieved`
| Conversation history was retrieved.

| `gen_ai.choice`
| Completion or reasoning content returned by the model. When content capture is disabled, this event can be emitted without the completion or reasoning content attributes.

| `tool.call`
| A tool call was initiated.

| `tool.result`
| A tool call returned a result.

| `approval.requested`
| A human approval was requested.

| `approval.decision`
| An approval decision was recorded.

|===

== Agentic {ols-long} events

Agentic {ols-long} emits audit events in two forms, as described by the dual-emission design: structured audit-log entries and OpenTelemetry (OTEL) span events. The two forms use different names for the same underlying event.

=== Agentic OTEL telemetry

The agentic system emits a separate trace for each phase of an operation. The `lightspeed-agentic-operator` component emits phase span events, and the `lightspeed-agentic-sandbox` component emits telemetry for the model interactions and tool calls that run within a phase. The following table lists the telemetry emitted in each phase:

[cols="1,3,2",options="header"]
|===
| Phase | Operator span events | Sandbox telemetry

| Analysis
a|
* `agenticrun.received`
* `sandbox.sa.created`
* `sandbox.configmap.created`
* `sandbox.rbac.created`
* `sandbox.pod.created`
* `agenticrun.analysis.completed`
a|
* `chat <model>`
* `execute_tool <tool-name>`
* `gen_ai.choice`

| Approval
| `agenticrun.approval.completed`
| None

| Execution
a|
* `sandbox.sa.created`
* `sandbox.configmap.created`
* `sandbox.rbac.created`
* `sandbox.pod.created`
* `agenticrun.execution.completed`
a|
* `chat <model>`
* `execute_tool <tool-name>`
* `gen_ai.choice`

| Verification
a|
* `sandbox.sa.created`
* `sandbox.configmap.created`
* `sandbox.rbac.created`
* `sandbox.pod.created`
* `agenticrun.verification.completed`
a|
* `chat <model>`
* `execute_tool <tool-name>`
* `gen_ai.choice`

| Escalation
a|
* `sandbox.sa.created`
* `sandbox.configmap.created`
* `sandbox.rbac.created`
* `sandbox.pod.created`
* `agenticrun.escalation.completed`
a|
* `chat <model>`
* `execute_tool <tool-name>`
* `gen_ai.choice`

| Terminal
| `agenticrun.terminal`
| None

|===

In the operator column, `+agenticrun.*+` and `+sandbox.*+` are span events attached to the phase span, where the `+sandbox.*+` events record the operator creating the sandbox resources for the phase. In the sandbox column, `chat <model>` and `execute_tool <tool-name>` are spans, and `gen_ai.choice` is a span event that carries the model completion or reasoning content. When content capture is disabled, the `gen_ai.choice` event can be emitted without those content attributes.

=== Structured audit-log events

Structured audit-log entries use a distinct set of `event` names that do not map directly to the span-event names. Examples include `audit.agenticrun.received`, `audit.approval.received`, and `audit.agenticrun.terminal`.

== Additional fields for approval events

Approval events include additional fields that identify the approval. The fields differ between the agentic system and the {ols-long} service.

Agentic approval events, such as the structured `audit.approval.received` event and the `agenticrun.approval.completed` span event, include the following additional fields:

[cols="2,1,4",options="header"]
|===
| Field | Type | Description

| `approver.uid`
| string
| Unique identifier of the user who approved or rejected the proposal, as injected by the mutating webhook on the `agentic-run` `PATCH` request. This field is present regardless of the approval path used: console, `kubectl`, or API.

| `approver.username`
| string
| Username of the user who approved or rejected the proposal, as injected by the mutating webhook on the `agentic-run` `PATCH` request. This field is present regardless of the approval path used: console, `kubectl`, or API.

|===

Approval events emitted by the `lightspeed-service` component include the following additional field:

[cols="2,1,4",options="header"]
|===
| Field | Type | Description

| `approval_id`
| string
| Identifier of the approval associated with the event.

|===
