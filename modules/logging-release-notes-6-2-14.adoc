= Logging 6.2.14 Release Notes

[role="_abstract"]
This release includes link:https://access.redhat.com/errata/RHSA-2026:99635[RHSA-2026:99635].

[id="logging-release-notes-6-2-14-bug-fixes_{context}"]
== Bug fixes

* Before this update, the Loki compactor failed to release disk space after compaction and retention operations. Deleted temporary files remained held open by the Loki process, preventing the operating system from reclaiming disk space and causing persistent high disk usage until the compactor pod was restarted. With this update, the Loki compactor correctly releases open file descriptors after compaction, allowing disk space to be reclaimed as expected.
(https://redhat.atlassian.net/browse/LOG-8700[LOG-8700])

* Before this update, the Loki Operator used an object storage backend that prevented upgrading to Loki 3.7. With this update, the Loki Operator migrates to the `thanos-io/objstorage` backend, enabling the upgrade path to Loki 3.7.
(https://redhat.atlassian.net/browse/LOG-9869[LOG-9869])

* Before this update, when the `detectMultilineException` filter was enabled in the `ClusterLogForwarder`, independent single-line JSON log records that contained exception-related keywords were incorrectly concatenated into a single forwarded log event. With this update, the multi-line exception detection logic correctly identifies record boundaries and forwards independent JSON log records separately.
(https://redhat.atlassian.net/browse/LOG-9998[LOG-9998])

* Before this update, the `PodDisruptionBudget` (PDB) for Logging components did not configure `maxUnavailable`, which could allow more pods than intended to be disrupted simultaneously during voluntary disruptions such as node drains or cluster upgrades. With this update, `maxUnavailable: 1` is set in the PDB for Logging components, ensuring that at most one pod is unavailable at a time during voluntary disruptions.
(https://redhat.atlassian.net/browse/LOG-10315[LOG-10315])

* Before this update, the Loki Operator's Ingester `StatefulSet` did not configure `terminationGracePeriodSeconds`, causing pods to use the Kubernetes default of 30 seconds. This was often too short for a graceful shutdown and could result in abrupt terminations, write-ahead log replay on restart, and log collection or query disruption during rollouts or node drains. With this update, `terminationGracePeriodSeconds` is set to 300 seconds for Loki Ingester pods, providing enough time for graceful shutdown.
(https://redhat.atlassian.net/browse/LOG-10322[LOG-10322])

* Before this update, Vector collector pods could continuously log errors when annotating log events with pod metadata if a matched container name value was null. This triggered the `ClusterLogForwarderRuntimeConfigurationMissingUnmatched` alert and disrupted log collection. With this update, null container name values are handled correctly during annotation, preventing the errors and spurious alerts.
(https://redhat.atlassian.net/browse/LOG-10378[LOG-10378])

* Before this update, the `log_logged_bytes_total` metric in the `log-file-metric-exporter` reported container log bytes at about six times the actual volume. Many symbolic links pointing to the same underlying log file were each counted separately. With this update, the byte counting logic deduplicates log file paths so that `log_logged_bytes_total` accurately reflects the actual volume of container log data.
(https://redhat.atlassian.net/browse/LOG-10398[LOG-10398])

* This update upgrades the Loki component to version 3.7.9.
(https://redhat.atlassian.net/browse/LOG-10402[LOG-10402])

* Before this update, on OpenShift versions 4.21 and earlier, the `log-file-metric-exporter` failed to start with a `permission denied` error when attempting to watch the `/var/log/pods/` directory. The exporter ran as a non-root user by default, but those OpenShift versions restricted the `inotify` watch syscall for non-root processes. With this update, the exporter applies a version-aware security context. On OpenShift versions 4.21 and earlier, the exporter runs as root to allow the `inotify` watch. On OpenShift versions 4.22 and later, the exporter continues to enforce a secure non-root configuration.
(https://redhat.atlassian.net/browse/LOG-10460[LOG-10460])

* Before this update, when using the `thanos-io/objstorage` backend, Loki's S3 client enabled dualstack endpoint resolution by default and rewrote the configured regional endpoint to its dualstack form at request time. This broke deployments with strict firewall rules that allowlisted only the originally configured endpoint. With this update, `dualstack_enabled: false` is explicitly set in the rendered Loki configuration, restoring the pre-migration behavior and ensuring Loki connects to the configured endpoint.
(https://redhat.atlassian.net/browse/LOG-10539[LOG-10539])

* Before this update, deploying cluster-logging 6.2.14 on a FIPS-enabled cluster caused `log-file-metric-exporter` pods to enter a `CrashLoopBackOff` state with the error `FIPS mode is enabled, but the required OpenSSL backend is unavailable`. With this update, the `log-file-metric-exporter` is built with a FIPS-compatible backend and starts successfully on FIPS-enabled clusters.
(https://redhat.atlassian.net/browse/LOG-10545[LOG-10545])
