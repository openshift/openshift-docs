= System constraints, security, and requirements

[role="_abstract"]
Review the system limitations, security constraints, and deployment requirements before you enable autonomous troubleshooting in your environment.

[id="ols-limitations_{context}"]
== Limitations

* *Risk of incorrect diagnoses*: AI agents can produce hallucinated diagnoses or incorrect remediation proposals. Always review details before approving execution.

* *Model-dependent accuracy*: Diagnostic quality depends on the configured large language model (LLM) provider.

* *No guaranteed rollback*: Interrupting an in-progress remediation does not guarantee an automated rollback.

* *No ongoing post-run monitoring*: After a run completes, the agent does not continuously monitor the cluster for regressions. The agent verifies remediation success within the run to confirm the triggering condition is resolved, but you must independently monitor cluster health after the run finishes.

[IMPORTANT]
====
Review all proposed remediation actions before approving execution. You remain responsible for approving and applying changes to your cluster.
====

[id="ols-security-architecture_{context}"]
== Security architecture

* *Policy enforcement*: The `alerts-adapter-config` ConfigMap filters which firing alerts are authorized to trigger investigations, while the approval policy governs whether workflow stages, such as Analysis or Execution, require manual administrator approval.

* *Dynamic RBAC*: Access control is dynamically scoped by the platform to restrict agent execution permissions.

* *Sandboxed execution*: Remediations run in isolated pods managed by the `kubernetes-sigs/agent-sandbox` project using `SandboxClaim`, `Sandbox`, and `SandboxTemplate` resources.

* *Human-in-the-loop governance*: All cluster modifications require explicit administrator approval.
