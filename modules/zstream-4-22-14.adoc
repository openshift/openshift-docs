= RHSA-2026:66358 - {product-title} {product-version}.14 bug fix and security update

Issued: 15 September 2026

[role="_abstract"]
{product-title} release {product-version}.14 is now available. The list of fixed issues that are included in the update is documented in the link:https://access.redhat.com/errata/RHSA-2026:66358[RHSA-2026:66358] advisory. The RPM packages that are included in the update are provided by the link:https://access.redhat.com/errata/RHSA-2026:66356[RHSA-2026:66356] advisory.

== Fixed issues

* Before this update, during `disk-to-mirror` operations, the `oc-mirror` tool reconstructed Helm chart tarball paths by using a fixed format `{name}-{version}.tgz`, for example, `csi-driver-nfs-4.9.0.tgz`, but the Helm downloader could include a "v" prefix in the version, for example, `csi-driver-nfs-v4.9.0.tgz`. As a consequence, `disk-to-mirror` operations failed with the `file not found` errors even though the `mirror-to-disk` download completed successfully. With this update, the `oc-mirror` tool correctly handles both version format variations. As a result, mirror operations complete successfully. link:https://issues.redhat.com/browse/OCPBUGS-90149[OCPBUGS-90149]

* Before this update, on Google Cloud Platform (GCP) clusters, the GCP cloud controller manager could not properly adhere to the `node.kubernetes.io/exclude-from-external-load-balancers` label when selecting load balancer backend nodes. As a consequence, master nodes with the exclusion label were still added as backends to external load balancers. With this release, the cloud controller manager correctly checks for the exclusion label. As a result, master nodes labeled with `node.kubernetes.io/exclude-from-external-load-balancers` are no longer included as load balancer backends. link:https://issues.redhat.com/browse/OCPBUGS-99228[OCPBUGS-99228]

* Before this update, the `baremetal` cluster Operator did not set its `Progressing` status condition to `True` during cluster upgrades. As a consequence, the Cluster Version Operator (CVO) waited for the Operator without receiving proper progress signals, and upgrade monitoring tests failed. With this release, the baremetal Operator correctly reports `Progressing=True` during version changes. As a result, cluster upgrades proceed with accurate Operator status reporting. link:https://issues.redhat.com/browse/OCPBUGS-99390[OCPBUGS-99390]

* Before this update, containers in the `openshift-monitoring` namespace ran with writable root filesystems because `readOnlyRootFilesystem: true` was not enabled in their security contexts. As a consequence, customer compliance scans flagged these containers as security policy violations. With this release, monitoring components enable read-only root filesystems with dedicated `emptyDir` volumes for paths requiring write access. As a result, monitoring containers meet compliance requirements for read-only root filesystems. link:https://issues.redhat.com/browse/OCPBUGS-105469[OCPBUGS-105469]

* Before this update, on Google Cloud Platform (GCP) clusters, values specified in `defaultMachinePlatform` were not applied to individual machine pools during cluster installation. As a consequence, settings such as `osDisk.diskType` were ignored, and control plane nodes used default values instead of the specified configuration. With this release, the installation program correctly applies `defaultMachinePlatform` settings to all machine pools. As a result, GCP machine configurations honor the specified platform defaults. link:https://issues.redhat.com/browse/OCPBUGS-114639[OCPBUGS-114639]

* Before this update, for pods with multiple containers that each requested SR-IOV virtual functions (VFs) from the same shared resource pool via separate network attachments, the Multus container network interface sorted device IDs alphabetically when assigning VFs to network interfaces. As a consequence, the PCI address that the SR-IOV device plugin granted to a container did not always match the PCI address that Multus container network interface wired into that container network namespace, causing pod startup failures with `No such device` errors. With this release, Multus container network interface correctly aligns VF assignments between the device plugin and network attachment operations. As a result, pods with multiple containers sharing SR-IOV resources start successfully without PCI address mismatches. link:https://issues.redhat.com/browse/OCPBUGS-114732[OCPBUGS-114732]

* Before this update, in {hcp} deployments where the management cluster required a proxy for external access, the CSI driver controller deployments did not receive `HTTP_PROXY`, `HTTPS_PROXY`, and `NO_PROXY` environment variables. As a consequence, CSI driver controller containers could not reach cloud provider APIs through the proxy, causing all volume provisioning operations to fail. With this release, the CSI Operator injects proxy environment variables into {hcp} CSI driver controller deployments. As a result, volume provisioning operations complete successfully in proxy-enabled {hcp} environments. link:https://issues.redhat.com/browse/OCPBUGS-119697[OCPBUGS-119697]

* Before this update, upstream GitHub workflow files and issue templates that are not used in {product-title} CI were present in the `cluster-api-provider-aws` release branches. As a consequence, the `golangci-lint` CI job failed on every pull request. With this release, the unused `.github` directory files are removed from the release branches. As a result, CI lint jobs complete successfully. link:https://issues.redhat.com/browse/OCPBUGS-119954[OCPBUGS-119954]
