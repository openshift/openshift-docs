= {product-title} routes and TLSRoutes comparison

[role="_abstract"]
When you migrate passthrough TLS traffic from standard networking to the Gateway API, you can compare {product-title} routes with `TLSRoute` custom resources (CRs). Both send encrypted connections to a backend that terminates TLS by matching the Server Name Indication (SNI) hostname. They differ in how you attach the route, how many hostnames you can set, and which implementation can program the data plane.

The following features are exclusive to `TLSRoute` CRs:

* Multiple SNI hostnames on one route, up to 16
* Attachment to a named gateway listener by using `parentRefs.sectionName`
* Cross-namespace attachment to a parent `Gateway` CR

The following features are exclusive to {product-title} passthrough routes:

* A single `spec.host` hostname
* `insecureEdgeTerminationPolicy` for handling insecure requests
* Mixed passthrough and edge or re-encrypt traffic on port `443` of the default router, by using distinct `Route` CRs
* Support on the default {product-title} router, without a separate `GatewayClass` object

[IMPORTANT]
====
The `openshift-default` `GatewayClass` object does not support `TLSRoute` passthrough or mixed-mode listeners. Same-port passthrough and terminated HTTPS in Gateway API requires a `GatewayClass` object whose implementation supports TLS route passthrough, such as {SMProductName}.
====

The following table outlines the features that are shared between both resources and how their specific implementations differ:

.Shared passthrough features and implementation differences
[cols="1,1,1",options="header"]
|===
|Feature |{product-title} route implementation |`TLSRoute` implementation

|TLS termination
|Supports passthrough with `spec.tls.termination: passthrough`. The destination pod presents the certificate. No key or certificate is set on the route.
|Supports passthrough with a `TLS` listener and `tls.mode: Passthrough`. The backend service presents the certificate. Do not set `certificateRefs` on the listener.

|Hostname matching
|Supports a single hostname in `spec.host`.
|Supports multiple SNI hostnames in `spec.hostnames`. Hostnames must intersect with the listener hostname.

|Backend references
|Supports a service destination with `spec.to` and `spec.port.targetPort`.
|Supports a service destination with `spec.rules.backendRefs`. A `TLSRoute` CR supports a single rule.

|HTTP matching and filters
|Does not support HTTP matching or filters. The router cannot inspect encrypted HTTP.
|Does not support HTTP matching or filters. Routing is by SNI hostname only.

|Attachment
|Supports admission by an Ingress Controller.
|Supports attachment to a `Gateway` CR with `parentRefs`. The listener must allow `TLSRoute` CRs from the route namespace.

|Same-port passthrough and terminated TLS
|Supports distinct `Route` CRs on the same router instance, with different `tls.termination` values.
|Supports distinct listeners on one `Gateway` CR: `protocol: TLS` with `Passthrough` for `TLSRoute` CRs, and `protocol: HTTPS` with `Terminate` for `HTTPRoute` CRs. Not supported on the `openshift-default` `GatewayClass` object.
|===
