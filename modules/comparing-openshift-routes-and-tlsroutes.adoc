= {product-title} routes and TLSRoutes comparison

[role="_abstract"]
When you migrate passthrough TLS traffic from standard networking to the Gateway API, you can compare {product-title} routes with `TLSRoute` custom resources (CRs). Both send encrypted connections to a backend that terminates TLS by matching the Server Name Indication (SNI) hostname. They differ in how you attach the route, how many hostnames you can set, and which implementation can program the data plane.

The following features are exclusive to `TLSRoute` CRs:

* Multiple SNI hostnames on one route, up to 16
* Attachment to a named gateway listener by using `parentRefs.sectionName`
* Cross-namespace attachment to a parent `Gateway` CR

The following features are exclusive to {product-title} passthrough routes:

* A single `spec.host` hostname
* `insecureEdgeTerminationPolicy` for handling insecure requests
* Mixed passthrough and edge or re-encrypt traffic on port `443` of the default router, by using distinct `Route` CRs
* Support on the default {product-title} router, without a separate GatewayClass

[IMPORTANT]
====
The `openshift-default` GatewayClass does not support `TLSRoute` passthrough or mixed-mode listeners. Same-port passthrough and terminated HTTPS in Gateway API requires a GatewayClass whose implementation supports TLSRoute passthrough, such as {SMProductName}. {product-title} routes that mix termination modes on the default router do not imply that `openshift-default` supports Gateway API mixed mode.
====

The following table outlines the features that are shared between both resources and how their specific implementations differ:

.Shared passthrough features and implementation differences
[cols="1,1,1",options="header"]
|===
|Feature |{product-title} route implementation |`TLSRoute` implementation

|TLS termination
|`spec.tls.termination: passthrough`. The destination pod presents the certificate. No key or certificate is set on the route.
|A `TLS` listener with `tls.mode: Passthrough`. The backend service presents the certificate. Do not set `certificateRefs` on the listener.

|Hostname matching
|Matches a single hostname in `spec.host`.
|Matches required `spec.hostnames` against the SNI hostname in the TLS ClientHello. Hostnames must intersect with the listener hostname.

|Backend
|`spec.to` names a Service. `spec.port.targetPort` selects the service port.
|`spec.rules.backendRefs` names a Service and port. A `TLSRoute` CR supports a single rule.

|HTTP matching and filters
|Not available. The router cannot inspect encrypted HTTP.
|Not available. A `TLSRoute` CR has no matches or filters. Routing is by SNI hostname only.

|Attachment
|The route is admitted by an Ingress Controller.
|`parentRefs` attach the route to a `Gateway` CR. The listener must allow `TLSRoute` CRs from the route namespace.

|Same-port passthrough and terminated TLS
|Distinct `Route` CRs on the same router instance, with different `tls.termination` values.
|Distinct listeners on one `Gateway` CR: `protocol: TLS` with `Passthrough` for `TLSRoute` CRs, and `protocol: HTTPS` with `Terminate` for `HTTPRoute` CRs. Not supported on `openshift-default`.
|===
