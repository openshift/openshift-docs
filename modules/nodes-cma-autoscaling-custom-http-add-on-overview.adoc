= Understanding the Kubernetes Event Driven Autoscaling HTTP Add-on

[role="_abstract"]
The Kubernetes Event Driven Autoscaling (KEDA) HTTP Add-on extends the Custom Metrics Autoscaler Operator to automatically scale HTTP-based applications based on incoming request metrics. It enables cost-saving scale-to-zero capabilities, allowing applications to scale from zero replicas during low traffic periods to peak capacity when demand returns.

The HTTP Add-on is a specialized extension that integrates with the Custom Metrics Autoscaler Operator to provide HTTP traffic-based scaling for containerized applications. Unlike traditional horizontal pod autoscaling (HPA) that requires persistent metrics collection, the HTTP Add-on uses an interceptor proxy to observe HTTP traffic in real time and make intelligent scaling decisions.

The KEDA HTTP Add-on uses two main components to track traffic and scale applications:

* **Interceptor proxy**: Routes incoming HTTP traffic through a scaling gateway that collects metrics about request volume, concurrency, and latency. The interceptor forwards traffic to your application while gathering the data the scaler needs to use.

* **Scaler**: Analyzes traffic metrics collected by the interceptor and communicates with the Custom Metrics Autoscaler Operator to calculate how many replicas your application needs. The scaler provides metrics to the horizontal pod autoscaler (HPA), which performs the actual scaling.

When traffic arrives at your application, the interceptor measures request volume and concurrency. Based on configurable thresholds, the scaler determines whether to activate the application (scale from zero to one replica) or allow the HPA to scale to more replica counts. When traffic drops below the activation threshold, the application scales back to zero, reducing infrastructure costs.

[id="nodes-cma-autoscaling-custom-http-add-on-overview-phases_{context}"]
== Activation and scaling phases

The HTTP Add-on supports two distinct scaling phases that give you fine-grained control over your application's behavior:

* **Activation phase**: The initial scaling decision when traffic is very low or zero. If traffic metrics exceed the activation threshold, the scaler brings the application online by scaling from zero to one replica. If traffic falls below the activation threshold, the application scales to zero. This phase prevents unnecessary pod creation during intermittent traffic spikes.

* **Scaling phase**: Once the application has at least one replica, the HPA takes control and scales the application based on your configured metrics (request rate, concurrency, or both). The scaling phase allows the HPA to fine-tune replica counts based on your performance requirements.

You can configure different threshold values for the activation phase and the scaling phase. For example, you might set the activation threshold to 5 requests per second but the scaling threshold to 100 requests per second. This allows your application to remain at zero replicas until traffic is substantial enough to justify running, and then scale up more aggressively when running.

[id="nodes-cma-autoscaling-custom-http-add-on-overview-component_{context}"]
== HTTP Add-on component overview

The HTTP Add-on consists of several Kubernetes resources deployed in the `openshift-keda` namespace:

* **Interceptor deployment**: The proxy that sits between your traffic source and application, collecting HTTP metrics.

* **Scaler deployment**: Analyzes interceptor metrics and provides scaling decisions to the Custom Metrics Autoscaler Operator.

* **Controller**: Manages the lifecycle of interceptor and scaler resources based on your scaling configuration.

* **Custom resources**: You create two custom resources to configure HTTP-based scaling for each application:
  - `InterceptorRoute`: Defines how traffic is routed, which metrics to collect, and scaling thresholds.
  - `ScaledObject`: Specifies which deployment to scale and references the HTTP trigger configuration.
