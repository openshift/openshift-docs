= Router audit log fields

[role="_abstract"]
Each router audit log entry has the following fields. You can use the `audit` field to filter audit entries from other `Info`-level log messages.

.Router audit log fields
[cols="1,3", options="header"]
|===
|Field
|Description

|`audit`
|Always `true`. Filters audit entries from other `Info`-level logs.

|`user`
|JWT `sub` claim from the `Authorization` header. Empty only when no bearer JWT with a `sub` claim is supplied. If you do not have an `AuthPolicy` CR, do not treat this value as an authenticated identity.

|`tool`
|Unprefixed upstream tool name after successful rewriting. If a failure occurs before rewriting, this field can retain the client-supplied name, including its prefix.

|`server`
|`namespace/name` of the `MCPServerRegistration` object. Empty if routing failed.

|`status`
|HTTP status only. Router-generated MCP protocol errors, such as an unknown-tool response, can use HTTP `200`. An upstream tool result can also report failure with `isError: true` and HTTP `200`.

|`request_id`
|Envoy-generated request UUID from the `x-request-id` header.

|`session`
|Log-safe correlation value: `jti:<uuid>` when a JWT contains a JTI claim, otherwise a truncated SHA-256 value such as `sha256:<prefix>`.
|===

[id="con-mcp-gateway-router-audit-user-field_{context}"]
== The user field and authentication

The router extracts the `user` field from the JWT `sub` claim in the `Authorization` header. Do not use `x-mcp-verified-sub` for audit purposes because it is a router-set internal header.

Configure an `AuthPolicy` CR to validate the token before relying on the user field. Without an `AuthPolicy` CR, the user field is not trustworthy. The user field is empty only when no bearer JWT with a `sub` claim is supplied.
