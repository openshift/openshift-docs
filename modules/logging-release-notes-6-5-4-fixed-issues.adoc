= Fixed issues

[role="_abstract"]
The following issues are fixed in this release of {LoggingProductName}. Some linked JIRA tickets are accessible only with Red Hat credentials.

Loki Operator ships Loki 3.7.9::
Before this update, the Loki Operator shipped an earlier version of Loki. As a consequence, users were not receiving the bug fixes, performance improvements, and security patches included in Loki 3.7.9. With this update, the Loki Operator ships Loki 3.7.9. As a result, all Loki components run version 3.7.9, incorporating upstream improvements from that release.
+
https://redhat.atlassian.net/browse/LOG-10300[LOG-10300]

`LokiStack` allows removal of schema entries that have passed their retention period::
Before this update, users could not remove schema entries from the `LokiStack` resource. The Loki Operator blocked this operation to prevent accidental data loss. As a consequence, users could not remove old schema entries associated with `BoltDB`, even after the applicable retention period had elapsed. With this update, the Loki Operator allows schema entries to be removed after the applicable retention period (global and per-tenant, whichever is longer) has elapsed since the effective date of the next schema entry. As a result, users can remove obsolete schema entries, preparing for the removal of `BoltDB` in a future Loki release.
+
https://redhat.atlassian.net/browse/LOG-10312[LOG-10312]

Logging `PodDisruptionBudgets` set `maxUnavailable` to 1::
Before this update, the `PodDisruptionBudget` for Logging components did not configure `maxUnavailable`, which could allow more pods than intended to be disrupted simultaneously during voluntary disruptions such as node drains or cluster upgrades. With this update, `maxUnavailable: 1` is set in the `PodDisruptionBudget` for Logging components. As a result, at most one pod is unavailable at a time during voluntary disruptions.
+
https://redhat.atlassian.net/browse/LOG-10320[LOG-10320]

Loki Ingester pods have an extended termination grace period::
Before this update, the Loki Operator's Ingester `StatefulSet` did not configure `terminationGracePeriodSeconds`, causing pods to use the Kubernetes default of 30 seconds. As a consequence, the grace period was often too short for a graceful shutdown, which could result in abrupt terminations, write-ahead log replay on restart, and log collection or query disruption during rollouts or node drains. With this update, `terminationGracePeriodSeconds` is set to 300 seconds for Loki Ingester pods. As a result, Ingester pods have enough time to flush in-memory data and leave the hash ring cleanly before the process is terminated.
+
https://redhat.atlassian.net/browse/LOG-10327[LOG-10327]

`log-file-metric-exporter` `log_logged_bytes_total` metric reports correct byte counts::
Before this update, the `log_logged_bytes_total` metric in the `log-file-metric-exporter` reported container log bytes at about six times the actual volume. As a consequence, many symbolic links pointing to the same underlying log file were each counted separately, producing inflated byte totals. With this update, the byte counting logic deduplicates log file paths. As a result, `log_logged_bytes_total` correctly reflects the actual volume of container log data.
+
https://redhat.atlassian.net/browse/LOG-10397[LOG-10397]

Loki no longer rewrites S3 endpoints to their dual-stack form when using the `thanos-io/objstorage` backend::
Before this update, when using the `thanos-io/objstorage` backend, Loki's S3 client enabled dual-stack endpoint resolution by default and rewrote the configured regional endpoint to its dual-stack form at request time. As a consequence, deployments with strict firewall rules that allowed only the originally configured endpoint could not reach S3. With this update, `dualstack_enabled: false` is explicitly set in the rendered Loki configuration. As a result, Loki connects to the configured S3 endpoint without rewriting it, restoring the pre-migration behavior.
