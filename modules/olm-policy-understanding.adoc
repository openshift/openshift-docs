= Understanding Operator installation policy

[role="_abstract"]
Operator authors specify the permissions requested by an Operator in the cluster service version (CSV). By default, Operator Lifecycle Manager (OLM) uses `cluster-admin` privileges to grant those permissions.

[id="olm-policy-failed-install-cleanup_{context}"]
== Failed Operator installation cleanup

Failed installations can leave permissions in place, even if the Operator never runs. Inspect the Operator service account for remaining role bindings and cluster role bindings. Delete the bindings created by the failed installation.

OLM can re-create a binding while the resource that owns the binding remains. For example, a failed Operator installation can create a role binding and assign another resource from the same installation as the owner. While that resource remains, OLM can re-create the role binding after you delete it.

After you delete a binding, check whether OLM re-created it. Inspect the `ownerReferences` field of the binding to identify the owning resource. If you no longer need the owning resource, delete it, and then delete the binding again.

Complete the following checks before delegating Operator installation privileges and when auditing existing Operator installations:

* Review the permissions requested by the Operator.
* Identify namespaces with an Operator group that does not specify a service account.
* In each identified namespace, identify non-administrator users or groups that can create subscriptions. Check whether the same users or groups can also create service account tokens or pods.

Check whether the same user or group can create subscriptions and service account tokens or pods in an identified namespace. If both permissions apply, take one of the following actions:

* Configure the Operator group to use a service account with only the permissions approved for installation.
* Restrict the permissions granted to the user or group.

To limit the permissions used during Operator installation and upgrades, associate the Operator group with a service account. Grant that service account only the minimum required role-based access control (RBAC) permissions.

OLM uses the permissions granted to the associated service account during installation and upgrades. OLM creates `APIService` and `CustomResourceDefinition` resources with `cluster-admin` privileges.

Manual install plan approval provides an opportunity to review requested permissions before installation proceeds. Also review the permissions already granted to users and service accounts in the installation namespace. Approval does not restrict those permissions.

include::snippets/olmv0-cluster-scoped-rbac-warning.adoc[]

[NOTE]
====
Users with permission to create `Subscription` objects can start Operator installations in a namespace that has an Operator group, even if those users cannot create `OperatorGroup` objects. Before creating an Operator group, review who can create subscriptions in the namespace and configure the permissions that OLM can use for installation.
====

Keep the following points in mind when associating an Operator group with a service account:

* OLM always creates the `APIService` and `CustomResourceDefinition` resources by using the `cluster-admin` role. Do not grant the service account associated with the Operator group permissions to write these resources.

* If OLM cannot create a required resource with the permissions granted to the specified service account, the installation fails.
