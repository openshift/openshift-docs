= Understanding Operator installation policy

[role="_abstract"]
By default, Operator Lifecycle Manager (OLM) runs with `cluster-admin` privileges and grants any permissions that an Operator author specifies in its cluster service version (CSV).

Operator authors can specify any set of permissions in the cluster service version (CSV), and OLM consequently grants it to the Operator.

Before delegating Operator installation, review the permissions requested by the Operator. Identify namespaces with an Operator group that does not specify a service account. In each namespace, identify non-administrator users or groups that can create subscriptions. Check whether the same users or groups can also create service account tokens or pods. If both sets of permissions are present, configure a scoped service account for the Operator group or restrict the permissions granted to the user or group.

To limit the permissions used during Operator installation and upgrades, associate the Operator group with a service account that has the minimum required role-based access control (RBAC) permissions. OLM uses the permissions granted to the associated service account during installation and upgrades, except when creating `APIService` and `CustomResourceDefinition` resources.

Do not install Operators that require cluster-scoped permissions in namespaces where non-administrator users have the default `edit` cluster role, permission to create service account tokens, or permission to create workloads.

[NOTE]
====
Role-based access control (RBAC) for `Subscription` objects is automatically granted to every user with the `edit` or `admin` role in a namespace. However, RBAC does not exist on `OperatorGroup` objects; this absence is what prevents regular users from installing Operators. Preinstalling Operator groups is effectively what gives installation privileges.
====

Keep the following points in mind when associating an Operator group with a service account:

* The `APIService` and `CustomResourceDefinition` resources are always created by OLM using the `cluster-admin` role. Do not grant the service account associated with the Operator group permissions to write these resources.

* If OLM cannot create a required resource with the permissions granted to the specified service account, the installation fails. A failed installation does not automatically remove permissions already created. Inspect the service account used by the failed Operator for active cluster role bindings. Delete the remaining `ClusterRoleBinding` objects created by the failed installation.
